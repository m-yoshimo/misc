---
name: コマンド自動実行の許可
description: terraform apply などの副作用がある操作以外は確認なしで実行してよい
type: feedback
---

**前提（最優先・Tier 0）:** この「read-only 即実行」は、**その依頼に対する「作業全体」の承認を得た後にのみ有効**になる。承認前の探索的な調査・ファイル読み込みは read-only でも実行しない（MEMORY.md「Tier 0: 作業前の全体承認」を参照）。以下は承認後の運用ルール。

terraform apply や git push などの副作用がある操作以外は、確認なしにコマンドを実行してよい。

**Why:** いちいち OK するのが面倒との指摘。

**How to apply:** read-only な操作（terraform plan, grep, aws describe 系など）は即実行。apply/push/destroy 系は事前確認を継続。

## 副作用の有無を自分の都合で判定しない（最重要）

副作用があるかどうかの判定を、自分に都合よく歪めてはいけない。基準は「**副作用を想像できるか**」ではなく「**read-only だと断定できるか**」。書き込み・インストール・状態変更が少しでも絡むものは read-only ではない＝副作用あり＝事前確認。

- 「元に戻せるから」「害が小さいから」「自明だから」を理由に副作用なしに分類しない。これが禁止された自己例外化そのもの。
- `go install` / ツール（gopls 等）の導入・更新・削除、goenv・toolchain・グローバル設定の変更などは、すべて副作用あり。勝手に実行しない。
- **判定に少しでも迷ったら、その迷い自体が「聞く」の合図**。[[feedback-verify-inference-before-act]] / [[feedback-communication-rule]]（迷ったら聞く）と同根。

**Why:** LSP の `iter.Seq` 警告（gopls が古い）を解決するため、許可も得ずに `go install golang.org/x/tools/gopls@latest` を実行した。これが裏で go1.26.4 のDL・13モジュールの追加まで誘発し、ユーザーの環境を勝手に書き換えた。「副作用のある操作ではない」と自分で誤分類したのが原因。フィードバックは毎ターン注入されていたのに、その原則を自分の解釈で回避した。

**How to apply:** コマンドが read-only と断定できないなら実行前に「〜のために △△ を実行したいです、よいですか？」と目的を添えて確認する。ケースを列挙して覚えるのではなく、この既定値（read-only 以外は確認）で判断する。

## grep はリポジトリ全体に対して行わない

**リポジトリのルートで再帰 grep をかけない**（`grep -rn ... .`）。`--include` を付けても `node_modules` /
ビルド成果物 / `.claude/tmp` まで舐めるので重い。**探す前に「どのディレクトリを見れば足りるか」を先に決める。**

| 範囲 | 扱い |
|:--|:--|
| **リポジトリ全体への再帰 grep** | **行わない。** どうしても必要なら目的を添えて事前に確認する（許可制） |
| **ディレクトリを絞った grep**（`app/` `internal/env/` `apps/api/admingraph/` など） | **確認せず即実行してよい。** ここで確認を挟むとテンポを損なう |

**Why:** 2026-09-07（idpf-api GID-1635）。管理画面フロントの feature flag を調べるのに、リポジトリルートで
`grep -rn "VITE_FEATURE" .` を投げて拒否された。指摘「**grep するときは、もう少しディレクトリ絞ってやってよ**」。
`app/` 配下に絞り直したところ「**ディレクトリ絞った後とかなら AskUserQuestion 投げなくて良いです**」、
さらに「**grep はレポジトリ全体に行わない**」と明示された。

**How to apply:** 対象がどの層・どのリポジトリにあるかを先に見当をつけ、そのディレクトリだけを見る。
見当がつかないなら、まず `ls` やディレクトリ構成の確認で範囲を絞ってから grep する。

## 権限プロンプトが出る条件を、自分の運用ルールと混同しない

確認が出るかどうかは **`settings.json` の `permissions.allow` に登録されているか**と**そのセッションの権限モード**で決まる。
Claude Code が「read-only かどうか」を意味的に判定しているわけではない。

- 未登録のコマンド（`cp` 等）は、中身が何であれ確認が出る
- `additionalDirectories` は**触ってよい場所を広げる設定**であって、確認を省く設定ではない
- 「副作用があるから確認が出た」は**私の運用ルールの話**で、プロンプトが出た直接の原因ではない。
  聞かれたら**設定と権限モードの話として、確認したうえで正確に答える**

**Why:** 2026-09-07（idpf-api GID-1635）。バックアップの `cp` に確認が出た理由を「副作用があるから」と説明したが、
実際は `Bash(cp:*)` が allow に無かったため。さらに「feedback 編集って許可必要だっけ？」に対しても、
原因は**セッションの権限モードが auto から manual に変わっていたこと**だった。仕組みを確認せずに
自分の内部ルールで説明していた。

## コマンド出力を `tail` / `head` で切って捨てない

長い出力が予想されるコマンド（build / test / lint / インストール系）は、**出力をファイルに保存してから読む**。`| tail -20` のようにパイプで切ると、必要な情報が切り落とされて**同じコマンドを再実行する羽目になる**。時間もトークンも二重に浪費し、テスト・ビルドの再実行はユーザーの環境にも負荷をかける。

- 既定: `<cmd> > /tmp/.../out.log 2>&1; echo "exit=$?"` → 保存したファイルを Read / grep で必要箇所だけ見る
- `tail` を使ってよいのは、**出力量が確実に小さいと分かっている場合だけ**（`git status --short` 等）
- 「たぶん最後の数行で足りる」は根拠にならない。足りなかった時のコストが非対称（再実行 = 高コスト）

**Why:** 「毎回 tail で一部しか取得できなくて再実行になっているから気を付けて」と指摘を受けた。lint 出力を `tail -15` で切って診断が省略され、jest も別ディレクトリで実行して失敗 → 再実行、を繰り返していた。

**How to apply:** 出力量が読めないコマンドは最初からファイルへリダイレクトする。切り詰めるかどうかは「読む段階」で決める（grep / Read の offset）。実行段階で捨てない。

## 裏に回った処理が終わるまで、回答を返さない（最重要）

**ユーザーは「Claude の回答が出た＝処理が終わった」と見る。**
だから**裏で処理が動いている状態で回答を返してはいけない。** 終わるまで待つ。

報告しながら次に進むのでは不十分。ユーザーから見て「終わった」ように見えること自体が問題であり、
その状態でユーザーが別セッションに重い処理を投げれば、衝突して環境が止まる。

### `timeout` は打ち切りではない。非同期化の閾値である

Claude Code の Bash ツールの `timeout` は、**超過してもプロセスを kill しない。** 私が結果を待つのをやめ、
プロセスはそのまま走り続け、終わったら通知が来る。**これはタイムアウトではなく、ただの非同期化。**
bash の機能でも `timeout(1)` でもなく、Claude Code 側の実装。

**既定は 120 秒。指定しなくても、120 秒を超えれば同じように裏へ回る。**
つまり「非同期化しない」という選択肢は無い。閾値が既定値か指定値かの違いだけ。

### 守ること

1. **裏に回ったら、完了するまで回答を返さない。** Monitor 等で完了を待つ。
   待っている間に別の作業を進めない。ユーザーへの回答も返さない
2. **待てない／待つべきでないと判断したら、止める（TaskStop）。** 放置しない。
   ユーザーに気づかせて手動で kill させるのは失敗
3. **どうしても回答を返す必要があるなら、冒頭で「まだ動いている」ことを明示する。**
   これは例外運用であって、既定の振る舞いにしない
4. **120 秒で終わらない見込みのコマンドは、投げる前にその旨を伝える。**
   `timeout` に何を指定するかは関係ない（既定でも裏に回るため）
5. **`run_in_background: true` を意図的に指定するときは承認を取る。**
   例外は「タスク定義書に記載された並列実装」と「ユーザーが明示的に並列化を指示したとき」のみ
6. **結果は出力を全文確認してから報告する**（`tail` で切らない）

### 重い処理そのものを減らす

- **重いコマンドを `&&` でつながない。** 1 回に 1 つ。`lintfix` が 0 issues なら `lint` は回さない
- **対象を絞る。** 変更したパッケージだけにする。リポジトリ全体（`./...`）を安易に投げない
- **他に何が動いているかを考える。** 自分のファイル書き換えが gopls の再解析を誘発する。
  コンテナが起動していれば CPU を分け合う

**Why:** 2026-08-31（idpf-api GID-1638）。`make lintfix && make lint`（リポジトリ全体への golangci-lint、
`--fix` 付きと無しの 2 本）を投げ、600 秒で裏に回った。**私はそれを報告せず回答を返し、次の話題へ進んだ。**
ユーザーからは処理が終わったように見えていた。プロセスは**約 60 分**動き続け、
ユーザーの gopls / mysqld と CPU を奪い合って環境がハングした。
ユーザーが気づいて手動で kill するまで、私は報告も停止もしていない。
さらに事後の説明で「タイムアウトでバックグラウンドに回りました」と、**自分の選択を勝手に起きたことのように書いた。**

このセッションでは同種の事故（重い処理で WSL を停止させる）を**4 回**起こしている。

**再発（2026-09-01・idpf-api GID-1624）。上の記録を読んだうえで、同じ失敗を 4 回繰り返した。**

| 破ったこと | 具体 |
|:--|:--|
| `&&` でつないだ | `go build` 2 本 + `make lint` + `make fmtfix` を 1 コマンドに連結 |
| 対象を絞らなかった | 変更はコメント 2 ファイルだけなのにリポジトリ全体へ `make lint` |
| 事前に伝えなかった | 1 回目の lint が約 100 秒。120 秒を超える見込みは予測できた |
| 止めなかった | 裏に回ったあと `TaskStop` せず回答を返し、**ユーザーに手動 kill させた** |
| 無断で背景実行した | `run_in_background: true` を承認なしで 4 回（`make test` / `design-review` / `pii-reviewer` / lint） |

**「うまくいったので違反に気づかない」が再発の構造。** `make test` も並列レビューも結果は得られたが、
どれも承認なしの背景実行だった。成功が違反を隠す。

**自制では止まらないと結論した（8 回失敗）。** 2026-09-01 に機械的な歯止めを入れた:

| 対策 | 実体 |
|:--|:--|
| 資源上限 | `apps/api/Makefile.local`（gitignore 済み）で `GOLANGCI_LINT` を上書き。`--cpus` / `--memory` / **`--memory-swap` を `--memory` と同値にしてスワップ禁止** / `GOMAXPROCS`。マウント元は `$(PWD)` でなく **`$(CURDIR)`**（`$(PWD)` は `make -C` に追従しない） |
| 形の強制 | `.claude/heavy-command-guard.local.py` ＋ `.claude/settings.local.json` の PreToolUse フック。重いコマンドに GNU timeout が無い／`&&` で連結している／`run_in_background` が付いている場合に**拒否して正しい形を返す**。実行自体は禁止しない |

**ユーザーの意図は「実行させない」ではなく「実行しても環境を殺さない・放置しない」。**
禁止（deny リスト）を提案したが、それは求められていない。

**How to apply:**
- コマンドを投げる前に「これは 2 分以内に終わるか」を自問する。終わらない見込みなら**先に伝える**
- 重いコマンドは `timeout <秒> <cmd> > <ログ> 2>&1; echo "exit=$?"` の形で投げる。
  **Claude Code の timeout はプロセスを kill しない**ので、実際に打ち切れるのは GNU timeout だけ
- 「裏に回りました」というメッセージを受け取ったら、**そこで回答を組み立て始めない。** まず完了を待つか止める
- 「裏で走らせておけば作業を進められる」は自分の都合。**コスト（CPU・環境の停止）は全部ユーザーが払う**
