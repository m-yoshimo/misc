## 画面実装は必ず元のデザインファイルを見てから行う

**核心（ユーザーの言葉・2026-08-26 GID-1635）**:
「管理画面だからテキストでも大丈夫かもだけど、**実装した時にちゃんとデザイン通りに実装してもらわないといけないので注意してね**」
「**その時に、僕に指摘させないでね**」

**背景**: Figma の FigJam ボードに MCP からアクセスできず、ユーザーがスクリーンショットを提供してくれた。
それを目視でテキストに書き起こして「これで再開できる」と報告したところ、上記の釘を刺された。

**根本原因**: 書き起こしで「情報は揃った」と判断していた。実際に揃うのは
**項目・文言・状態遷移**だけで、**余白・色・フォントサイズ・角丸・コンポーネント粒度・レスポンシブ挙動**は落ちる。
要件把握の道具と実装の根拠を混同していた。

**How to apply**:
- **スクショの書き起こし・要件表・タスク定義書の表は「要件把握用」**。実装の根拠にしない
- 画面を実装する前に、必ず Figma MCP で該当ノードを取得する
  - `get_design_context`（リファレンスコード＋トークン。**事前に `figma-design-to-code` スキルを読むのが MCP の必須要件**）
  - `get_variable_defs`（色・スペーシングの変数）→ プロジェクト既存のトークン／コンポーネントにマッピング
  - `get_screenshot`（実装後の目視突き合わせ用）
- 書き起こしと Figma が食い違ったら **Figma を正とする**
- **デザインファイルにアクセスできないなら、実装前にアクセス手段を確保する**。
  「スクショはもらったから大丈夫」で進めない。ファイル URL / ノード ID をタスク定義書に控えておく
- 書き起こしファイルを作るときは、**冒頭に「実装の根拠に使うな」と明記する**

**Why:** デザイン崩れは実装後に発覚し、ユーザーが指摘して手戻りになる。
指摘させた時点で失敗。指摘される前に、正しい根拠（デザインファイル）を見て実装する。
