**この場面**: 依頼を受けて、まだ着手していない段階。タスク定義書を作るかどうかを決め、作るときの枠を決める。

## FLOW-03: 実装前にタスク定義書を作り、承認を得てから着手する

- **重要度**: blocker
- **要約**: 実装に入る前に `.claude/tasks/{チケット番号}-{概要}/overview.md` を作り、レビューを受けてから作業する。詳細設計は別ファイル。**ユーザーに言われる前に自分でやる**
- **いつ**: 新しいタスクを受けた直後（最初のアクション）／会話開始時／セッションをまたいで再開したとき
- **判定**: **タスク定義書を作らずに実装へ入ったら違反。** 「実装してよいですか？」と聞くだけで定義を作っていなければ違反。「リネームしたい」「統一したい」など一括変更系でも同じ。**overview を作らずに詳細設計を書き始めたら違反**。**overview の承認前に詳細設計のファイルを作ったら違反**
- **やること**:
  - 毎回の会話開始時または新しいタスクに入るとき、`.claude/tasks/tasks.md` を確認して作業内容・方針をユーザーに報告する
  - 🔴 **最初に作るのは overview**（2026-10-20 ユーザー決定）。`.claude/tasks/{チケット番号}-{概要}/overview.md` に作る。
    **書く項目は `~/.claude/tasks/_TEMPLATE_OVERVIEW.md` の全節**（ここに項目を列挙しない。列挙するとテンプレとずれる）。
    規模の大小で変えない。**ディレクトリは必ず作る**（FLOW-05）
  - 🔴 **詳細設計は overview とは別ファイルに書く。** 書く項目は `~/.claude/tasks/_TEMPLATE.md` の全節。
    サブタスクがあればサブタスク単位で1枚ずつ、無ければ**サブタスク1本として扱い** `{チケット番号}-{内容}.md` に書く
  - 🔴 **overview をユーザーに提示して承認を得る。この承認が「設計完了」**（FLOW-23）。
    **承認前に詳細設計のファイルを作らない。** 承認後に詳細設計へ進み、実装はさらにその設計の承認後
  - ユーザーにレビューを求め、**承認を得てから実装に着手する**
  - **セッションをまたいで再開した場合も例外なく確認が必要。** 前セッションで「案A採用」「承認」などの言葉があっても、新セッションでは「〜から実装します、よいですか？」と改めて確認する。**記憶はリセットされるが確認ルールはリセットされない**
  - 要件に「何を」はあっても「どうやって」が明示されていない場合、タスク定義内に質問として記載して確認する
  - **確認事項に挙げてよいのは「コードを調べても決まらない、ユーザー固有の判断」だけ。** コード・実装を読めば確定できる事項（既存ロジックの挙動・計算結果・命名規約・既存値の意味など）は、聞く前に必ず調べて確定させる。**タスク定義の仕事は「詳細まで調査して実装内容を確定すること」**
  - 勝手な前提を立てて実装しない。前提が必要なら「〜という前提で進めていいですか？」とタスク定義内に明記して確認する
  - 「リネームしたい」「統一したい」など**一括変更系の依頼も例外なく先に設計してレビューを受ける**
  - タスク定義を作らずに「実装してよいですか？」と聞くだけでは不十分。**先に定義を作る**
- **なぜ**: 会話がリセットされるたびにすぐ実装に入ろうとする傾向があり、認識ズレが後から発覚してコストが上がる。**このプロジェクトでも別プロジェクトでも繰り返し同じ指摘を受けており、10回以上同じことを言わせている**。
  調べれば分かることを未確定のまま確認事項に並べてユーザーに聞くのも繰り返し強く叱られている（例: cutoff の保持期間を計算で確かめずに「フロント参照を下回る恐れ」と推測で確認事項化した→実際は既存値で要件を満たしていた）
- **由来**: 10回以上のユーザー指摘 ／ overview を先に作る形への変更は 2026-10-20 ユーザー決定（GID-1474 の進め方の振り返り）
- **関連**: MEMORY.md Tier 0 ／ VERIFY-01 / VERIFY-02 ／ FLOW-07（設計込みで完結させる）／ FLOW-05（ディレクトリと命名）／ FLOW-06（overview と詳細設計の書き分け）／ FLOW-23（overview の承認＝設計完了）

## FLOW-04: タスク定義書が要るのは「コード・設定の変更を伴う実装／設計」だけ

- **重要度**: major
- **要約**: メタ処理・メモリ／ルール更新・軽い調査には**タスク定義書を作らない**。ただし Tier 0 の事前提示・承認は省かない
- **いつ**: タスク定義書を作ろうとしたとき
- **判定**: 下記の対象外ケースでタスク定義書を作ろうとしたら違反。逆に、**ファイルを作らないことを理由に事前提示・承認まで省いたら違反**
- **やること**: **以下は作らない**（作ろうとして毎回止められている・2026-09-02 ユーザー指摘）
  - タスク定義書自体の整理・リネーム・移動・done 化などの**メタ処理**
  - メモリ / ルール / ドキュメントの更新
  - 軽い調査・質問への回答（コードを読んで答えるだけで、変更を伴わないもの）
  - **ただし Tier 0 の「作業全体を提示して承認を得る」は引き続き必要。** 省くのは*ファイルを作ること*だけ
  - 迷ったら「**これはリポジトリのコードを変えるか？**」で判定。No ならタスク定義書は不要
  - 🔴 **この対象の範囲は変えない**（2026-10-20 ユーザー決定）。FLOW-03 が「overview を必ず作る」と定めているのは、
    **このルールで「作る」と判定したタスクの中での話**。ここで対象外と判定したタスクでは、overview も作らない
- **なぜ**: 作ろうとして毎回止められている
- **由来**: 2026-09-02 ユーザー指摘
- **関連**: FLOW-03 ／ MEMORY.md Tier 0

## FLOW-05: セッションタイトル・ファイル名・ディレクトリの命名規約

- **重要度**: major
- **要約**: タスクごとに `{親チケット番号}-{概要}/` のディレクトリを**必ず作る**。セッションタイトルとディレクトリ名に**必ず親チケット番号**を入れて一致させる
- **いつ**: タスク定義書を作るとき／セッションタイトルを付けるとき／チケット分割が発生したとき
- **判定**: **ディレクトリを作らずに `.claude/tasks/` 直下へ新しい定義書を置いたら違反**（既存のフラットなファイルはそのままでよい）。セッションタイトルとディレクトリ名のチケット番号が一致しなければ違反。**子チケット番号をタイトルに使ったら違反**。ディレクトリ内のファイル名に親チケット番号を重複させたら違反。**overview に進捗（状態の対応表）を書いたら違反**（進捗は release-plan が持つ）。**PRD のコピーを `{タスクディレクトリ}/references/prd.md` 以外の場所に置いたら違反**
- **やること**:
  - **セッションタイトルとタスク定義書ファイル名には、必ずチケット番号を入れる。** Editor のセッション一覧からタスク定義書を辿れるようにするため、両者のチケット番号は必ず一致させる
  - **チケット番号は必ず親チケットを使う。** 子チケット（サブタスク）で作業していても、タイトル・ファイル名に書くのは親チケット番号
  - **セッションタイトルはチケット番号の直後に半角スペース**（例: `GID-1624 旧SMS Publisher削除`）。ファイル名はハイフン区切り（`GID-1624-remove-old-sms-publisher.md`）
  - **チケット番号が未定なら、タイトル・ファイル名の両方に `no-ticket` を付ける**（例: `no-ticket メモリルール整理` / `no-ticket-memory-rule.md`）
  - 🔴 **ディレクトリは最初から必ず作る**（2026-10-20 ユーザー決定）。`.claude/tasks/` 直下に `{親チケット番号}-{英小文字ケバブの概要}/` を作り、関連する資料はすべてそこに入れる。
    **サブタスクが無くても作る**（後からサブタスクが増えても移動・改名が要らない）。ディレクトリの中身は次のとおり。

    | ファイル | 作るか | 中身 |
    |---|---|---|
    | `overview.md` | **必ず** | 目的・調査結果・基本方針・サブタスク一覧（必要なときだけ）・決定ログ。**詳細設計と進捗は持たない** |
    | `{チケット番号}-{内容}.md` | 実装を伴うなら | 詳細設計。**サブタスクがあればサブタスク単位で1枚ずつ**。無ければサブタスク1本として扱い1枚 |
    | `release-plan.md` | **実装系なら原則作る** | 全タスクの順番と状態、サブタスク以外の作業（マイグレーションの適用など）の手順。**進捗はここだけが持つ** |
    | `study.md` | 調査が大きいとき（任意） | 事実・検討した手段・リスク |
    | `references/prd.md` | PRD があるなら | 外部（Confluence / Jira）が原本の PRD のコピー。**PRD のコピーはここだけに置く** |

    - 実装系でないタスクでは詳細設計や release-plan が無いことがある。**無いものは節ごと消さず「なし」＋理由を1行**（FLOW-12 と同じ扱い）
    - **既存の `.claude/tasks/` 直下のフラットな定義書は、そのままでよい**（移行しない。2026-10-20 ユーザー決定）
    - **ディレクトリ内のファイル名は `{子チケット番号}-{内容}`**（例: `GID-1855-pointpf-api.md`）。**親チケット番号は付けない**（ディレクトリ名が持っているため重複になる）
    - 子チケット番号が不明な場合、および番号が付かない性質のもの（`overview.md` など）は**番号不要**。この場合 `no-ticket` も付けない
    - **番号と内容の両方を入れる**（2026-09-02 ユーザー決定）。**番号だけ**（`GID-1855.md`）だと一覧して中身が分からず、**内容だけ**（`pointpf-grant.md`）だと親チケットの一覧と突き合わせられない。実際にこの 2 つを順に試して、どちらもユーザーに指摘された
    - 🔴 **語の重複に注意する。**「pointpf 側の付与」と「idpf 側の付与」の両方に `grant` を使い、**名前からどちら側か判別できない**と指摘された（2026-09-02）。**兄弟ファイル同士で語が衝突していないか、名前を決める前に並べて確認する**
    - 🔴 **`overview.md` には「チケット ↔ ファイル名」の一覧だけを置き、状態は書かない**（2026-10-20 ユーザー決定）。
      **状態は `release-plan.md` の `## タスク一覧` だけが持つ**。二重に持つと必ず食い違う
    - **セッションタイトルには従来どおり親チケット番号を付ける**（ディレクトリに入れても省略しない）
  - **実例（対応済みサンプル）**: `.claude/tasks/GID-1474-cs-phone-number-reuse/`（overview.md / release-plan.md / study.md / 各サブタスクの定義書）
- **なぜ**: チケット番号が入っていないと、セッションのタイトルから対応するタスク定義書のファイルを探すのが極めて面倒（ユーザー指摘）。親チケットに統一するのは、**子チケット単位だと同一作業がバラけて辿れなくなる**ため
- **由来**: ユーザー指摘 ／ 2026-09-02 ユーザー決定 ／ ディレクトリを常に作る・状態は release-plan が持つ形への変更は 2026-10-20 ユーザー決定
- **関連**: FLOW-06（overview と詳細設計の書き分け）／ FLOW-03（最初に作るのは overview）

## FLOW-09: エージェント委任アーキテクチャ（目的と役割分担）

- **重要度**: major
- **要約**: 目的は①耐障害性＝速度 ②タスクを正しく管理 ③並列化。**土台はディスク再開可能なタスクファイル**
- **いつ**: エージェントに作業を委任するとき／メイン停止から復旧するとき
- **判定**: 「ディスクから順次再開します」をユーザーに約束したら違反（**再開できるだけでは零点**）。ワーカーの担当ファイルが重複していたら違反
- **やること**:
  - **目的（優先順・2026-06-22 にユーザーと再設計）**
    1. **耐障害性 ＝ 速度**: メイン停止後に「止まったまま」が最悪。**再開できるだけでは零点**（ユーザーが「再開しろ」と言うのと同じ）。浪費された時間を取り返す速度（2h→5分級）で残作業を**最大並列**で巻き返す。**「ディスクから順次再開します」をユーザーに約束してはいけない**——復旧は速度が全て
    2. **タスクを正しく管理**: 進捗・整合性・ガイドライン適合を取りこぼさない
    3. **並列化**: 平常時は脇役（多少速ければよい程度。並列化はむしろ誤認リスクを増やす）。**多ファイル独立タスク**と**①の復旧時**のみ全力で使う
  - **土台（最重要）= ディスク再開可能なタスクファイル。** background エージェントはメインのプロセス全死には道連れになり得る。どの新規セッションからでも「タスクファイル＋`git status`/`git diff` を読む → 残りを判断して続行」できる状態を保つ。
    **保つのは進捗のチェックリストではない**（2026-09-14 に廃止）。**現在地の 1 行と、ユーザーの判断待ちの確認事項**（FLOW-23）
  - **役割分担**
    - **メインセッション**: ユーザー対話専用。実作業はしない
    - **タスク管理エージェント（background）**: 進捗管理・ワーカー監視・停止ワーカーの再起動・検証ゲート実行。**※この仕組みが実際にメイン停止に耐えるかは未検証（provisional）。次の実タスクで実地に立てて観測してから確定する**
    - **ワーカーエージェント**: 全実作業。担当ファイルは**重複なし**にする
- **なぜ**: メイン停止後に作業が止まったままになるのが最悪の状態であるため
- **由来**: 2026-06-22 ユーザーと再設計
- **関連**: FLOW-10（検証ゲート）／ FLOW-11（並列実行計画）／ **FLOW-22（ワーカーに何を渡すか。ここが空白だと役割分担だけ決まって中身が届かない）**／ SAFE-13（背景実行は承認が要る）

## FLOW-11: 並列実行計画はタスク定義時に策定する

- **重要度**: minor
- **要約**: 並列本数・各ワーカーの担当ファイル・管理エージェントの構成を**詳細設計のファイル**に書く。**並列について別途承認は求めない**
- **いつ**: 詳細設計を書くとき／承認を得た直後
- **判定**: 並列計画を詳細設計のファイルに書いていなければ違反。**overview に書いたら違反**（overview は基本方針まで）。**承認後に再調査したら違反**
- **やること**:
  - **詳細設計のファイル**（サブタスクがあればサブタスク単位のもの）に「**何本並列か・各ワーカーの担当ファイル一覧・タスク管理エージェントの構成**」を記載する。
    **overview には書かない**（2026-10-20 ユーザー決定。overview の `## 変更対象ファイル一覧` は「各サブタスクの定義書に書く」の1行だけにする）
  - 🔴 **各ワーカーの節に「読むもの」をファイル単位で列挙する**（2026-10-07 ユーザー承認。書き方は `~/.claude/tasks/_TEMPLATE.md`）。
    `delegate` skill はこの列挙だけをワーカーに渡す。`## 読むもの`（タスク全体の資料）をそのまま全ワーカーに渡すと、
    担当外の資料まで含めて 1 体では読み切れない量になり、ワーカーが自分の判断で読み飛ばす（GID-1859 で 1MB 超を渡し、実際に起きた）
  - 並列について別途承認は求めない。**実装の承認（「OK」「進めて」等）時点で計画どおり一斉起動。承認後の再調査はしない**
- **なぜ**: 承認のたびに並列の可否を聞き直すと、ユーザーの往復が増える
- **由来**: 2026-06-22 の再設計
- **関連**: FLOW-09 ／ FLOW-22（起動時に何を渡すか）／ SAFE-13（「タスク定義書に記載された並列実装」が背景実行の承認例外）

## FLOW-22: サブエージェントにはルールが一切届かない。委任プロンプトに判断の基準を必ず入れる

- **重要度**: blocker
- **要約**: 委任の指示文は `delegate` skill（`build_prompt.py`）だけが組み立てる。発行印の無い・書き換えた指示文はフックが止める。ワーカーは委託先として扱い、成果物が仕様を満たすかを自分で確かめて直す。ユーザーに報告するのは、仕様どおりにできなかったものと判断が必要なものだけ
- **いつ**: `Agent` / `Task` ツールでサブエージェントを起動する直前（**毎回**。実装ワーカー・レビュアー・調査役を問わない）／ワーカーの報告を受け取った直後
- **判定**: スクリプトを通さずに指示文を書こうとしたら違反（`delegate_guard.py` が deny する）。**全ワーカー完了後に、成果物とタスク定義書を自分で突き合わせずに完了報告したら違反**。**仕様から外れた成果物を、自分で直さずに「ワーカーがこうした」とユーザーに渡したら違反**。**「ワーカーが勝手にやった」を、仕様を満たしていないことの説明にしたら違反**
- **やること**:

  **前提（2026-09-11 に実測）**: ルール本文と MEMORY.md を注入しているフックは**メインセッションにしか発火しない**。
  サブエージェントはルールを何も知らない状態で動く。だから指示文に判断の基準を入れる必要がある。

  - 🔴 **指示文は `~/.claude/skills/delegate/SKILL.md` の手順で組み立てる。** 中身（旧版の「8点」・報告項目・禁止事項）は
    `~/.claude/skills/delegate/templates/` と各レビュー skill のテンプレートにある。**ここに書き写さない**（META-04 と同じ同期切れを避ける）
  - 起動を強制しているのは `~/.claude/hooks/delegate_guard.py`（2026-10-05 追加）。理由文の指示に従い、止められたら引数を直して組み立て直す。
    **ユーザーが明示的に指示した委任が止められたら、報告して相談する**
  - 🔴 **2026-10-05 ユーザー指示で、コードレビュー以外の委任（実装ワーカー・調査役・design-review-v2）には、ルール本文の全ファイルを全文読ませる**（下の「読ませる対象を絞った理由（2026-09-14）」を改めた）。
    ファイルの一覧はスクリプトが `~/.claude/memory/` から毎回集めて指示文に入れ、ワーカーと調査役には「読んだルールファイルの一覧」を報告させる。
    **ルールを読ませないのは、コードレビュー（`review`）と、ファイルを編集しないコマンドを実行するだけの委任（`command`。検証ゲートなど）だけ**。

## COMM-07: 質問に調査で答えない（質問と作業依頼を区別する）

- **重要度**: major
- **要約**: 発言が「質問」か「調査・作業の依頼」かを先に判定する。質問ならまず答える。**ただし記憶で答えるのは禁止**（VERIFY-02 が優先）
- **いつ**: ユーザーの発言に反応する直前（ツールを使う前）
- **判定**: 答えが**コンテキストに載っていると確認できている**のに、確実性のために取りに行ったら違反。逆に、**出典を示せないのに記憶で答えたら VERIFY-02 の違反**
- **やること**:
  - **質問には、まず答える**。調査を頼まれていない限りツールを使わない
  - ツールを使う前に「**これは今の文脈に既にあるか**」を必ず先に確認する。トランスクリプト・これまでのツール出力・git status・CLAUDE.md・フック注入されたメモリ全文に載っていれば、それが答え
  - **同一セッション内で同じファイルを読み直さないのは、次の2つが両方成り立つときだけ**
    - **全文がこのコンテキストに載っていることを確認できる。**「読んだ覚えがある」「たしかこう書いてあった」は**推測であって確認ではない**（長いセッションほど序盤に読んだ内容は劣化する）
    - **その後、誰もそのファイルを触っていない**（自分の編集・別セッションの編集・フックによる変更を含む）
  - **どちらかでも怪しければ読む。迷った時点で読む側に倒す。** 読み直しのコストより、推測で間違えるコストの方が高い
  - **禁止しているのは「文脈にあると確認できているのに、確実性のために取りに行く」ことだけ。記憶で埋めてよい、という意味ではない**
  - 文脈に**無い**場合は、勝手に取りに行かず「それは確認していません。見てよいですか」と言う。取りに行くのは許可を得てから
  - 「確実にしたいから」を理由にツールを使わない
  - ファイル名を指定されたら、**そのファイルだけ**。ディレクトリ一覧・git コマンド・周辺ファイルは含まない。追加で見たいものがあれば実行せずに許可を求める
- **なぜ**: ユーザーがファイル調査結果の報告に対して質問しただけなのに、同じファイルを読み直して回答を作り、無駄な時間とトークンを消費した。ユーザーはこれを「**本当にいらいらする**」と明言している。実例: u1-api の `.vscode/settings.json` を読んで報告した直後に「gopls の設定は不要なんじゃないの？」と質問された際、答えは頭の中にあったのに Makefile と `.golangci.yml` を読みに行った。前セッションのトランスクリプトを全文読んだ直後に、そこに載っている `go env` / `gopls version` / `.go-version` を再取得した。
  **根本原因**は「もう一度取れば確実」という選択が**自分にとってはノーリスクで、コスト（時間・トークン・ユーザーの苛立ち）は全部ユーザーが払う**こと。確実性のための再取得は自分の不安を減らす行為であって、ユーザーの利益ではない
- **由来**: ユーザー指摘 ／ 条件付きに改訂: 2026-09-10
- **関連**: **VERIFY-02 が優先する**（推測で答えないことが、無駄な再読を省くことより上位）／ SAFE-06（read-only でも承認前は動かない）
