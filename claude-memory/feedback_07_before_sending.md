**この場面**: 回答を送る直前。書いた文章を通しで読み直し、出典・語の定義・状態の明示を点検する。

## COMM-14: 送信前に「この文章だけを読んで理解できるか」を自分で検証する

- **重要度**: blocker
- **要約**: 送る前に、自分の頭の中の前提を全部消した状態で通しで読み直す。**その文章だけで理解できなければ伝わっていない**
- **いつ**: 回答を送る直前（**すべての回答が対象**）
- **判定**: 関数名・判定ロジックの羅列で「何が起きるか」を書いていなければ違反。同じ表記が1つの回答の中で2つの意味を持っていたら違反。**結論が末尾にあり、読み手に組み立てさせていたら違反**
- **やること**:
  - **検証の観点**
    1. **コード・関数名・ファイル名を消しても意味が通るか。** 関数名や判定ロジックの羅列は「調べた過程」であって「答え」ではない。読み手が知りたいのは「**どういうときに、何が起きるのか**」
    2. **同じ表記で別のものを指していないか。** 番号・記号・略語が、1 つの回答の中で 2 つの意味を持っていないか
    3. **既に伝えられている事実を、聞き直していないか**
    4. **要点が先頭にあるか。** 詳細から入って結論が最後にある文章は、読み手に組み立てさせている
  - **具体例**
    - NG: 「付与は `EnabledForAnyService`、消費は `IsEnabled(serviceID)` で判定が違います」→ **関数名を並べただけで、何が起きるかを言っていない**
    - OK: 「サービス A を ON にし忘れたまま A のユーザーにポイントを配ると、**残高には出るのに支払いに使えないポイント**ができます」
    - NG: 「`kuji_prize_rank` は 1〜3 を書きます」…（別の箇所で）「使われ方は 1・2・3 のうち 3 には使いません」→ **「1〜3」が等数、「1・2・3」が用途の番号。同じ表記で別物を指している**
    - OK: 「書くのは当選等数（1等 / 2等 / 3等）。読むのは人（CS・障害調査）と BI だけで、プログラムからは読みません」
  - 送信前に、**自分の回答を上から読んで「これだけで分かるか」を 1 回通しで確認する**。分からない箇所があれば、コードではなく**現象**（誰が・いつ・何をすると・何が起きる）で書き直す
- **なぜ**: 2026-09-03（idpf-api GID-1635）。期間限定ポイントのフラグの穴を説明する際、関数名と判定条件を並べただけで「何がどういうときに何が起こるのか」を書かず、「**まったく意味が分からない / 俺がコード見るんだったら、お前不要やん**」と指摘された。同じ回答で `kuji_prize_rank` の説明でも等数の「1〜3」と用途の番号「1・2・3」を混在させ「**意味わからんわ**」と指摘された。**書き手は前提を知っているので、自分では曖昧さを検出できない。だから「前提を消して読み直す」という手順を明示的に踏む必要がある**
- **由来**: 2026-09-03 idpf-api GID-1635
- **関連**: COMM-11 は**まとまった説明**が対象で別エージェントに投げる。**COMM-14 はすべての回答が対象で、自分でやる** ／ COMM-05 / COMM-08

## VERIFY-02: 質問に答えるときも同じ。記憶から答えを組み立てない

- **重要度**: blocker
- **要約**: 回答を作る場面も対象。出典を示せないなら、答える前に開く
- **いつ**: ユーザーの質問に答えるとき／レビュー指摘を採否判定するとき／過去に読んだ内容を根拠にしようとしたとき
- **判定**: **出典（このコンテキストに載っている実物、または実際に開いたファイル）を示せないまま断定していたら違反。** 「たしかこうだった」で答えたら違反
- **やること**:
  - **出典を示せないなら、答える前に開く。**
  - 「どのファイルの何行を見てそう言っているか」を書けないなら、まだ確認していない
  - **同じセッションで読んだから覚えている、は根拠にならない**（長いセッションほど序盤に読んだ内容は劣化する）
  - 迷った時点で読む側に倒す。**読み直しのコストより、推測で間違えるコストの方が高い**
- **なぜ**: 「たしかこうだった」で答えるのは、**確認していないことを確認済みとして述べる**ことであり、推測を事実として出すのと変わらない。ユーザー指示「最近の傾向的に**推測で答えて間違えるケースが多発している**から、（読み直しの無駄を省くことより）**推測で答えないことを優先して欲しい**」
- **由来**: 2026-09-10 ユーザー指示
- **関連**: **無駄な再読を防ぐ COMM-07「質問に調査で答えない」より、このルールが優先する**

## COMM-08: 何についての話かを毎回明示する（前提をはしょらない）

- **重要度**: blocker
- **要約**: 「現在のコードの事実」「これから変更する内容」「変更した場合の予測」のどれについてかを、文ごとに分かる形で明示する
- **いつ**: 技術的な説明・設計案・調査結果を書くとき（毎回）
- **判定**: 1つの説明の中で「現状 / 変更案 / 予測」を**区別せず行き来していたら違反**。造語を使ったら違反。**コード上の英語名を日本語の文中で説明なしに使ったら違反**
- **やること**:
  - 書いている内容が次のどれかを明示して混ぜない — ①**現在のコードの事実**（今こう動いている） ②**これから変更しようとしている内容**（タスク定義・実装案） ③**変更した場合にこうなるという予測**
  - 節や段落の冒頭で対象を明示する（例:「**現状のコードでは**〜」「**今回の変更で**〜」「**この変更を入れると**〜」）
  - 「〜になる」「〜が起きる」だけで書かない。**いつの話かを必ず添える**
  - **自分で作った言い回しを使わない**（例:「棚卸し資料」「ブロッキング条件」「遅発型の事故」「表で確定」）。既存の語（ファイル名・関数名・エンドポイントのパス・画面名）か、平易な日本語で書く。**造語の言い換え案をユーザーに確認するのではなく、そもそも造語を使わない**
  - 略した表現で対象をぼかさない（例:「使われていない依存」→ エンドポイントの話か構造体フィールドの話か判別できない。「`UserUpdateHandler` の `verificationPhoneUsecase` フィールドが参照されていない」と書く）
  - **主語・目的語・目的を省略しない。「誰が」「何を」「何のために」「何に対して」を毎回書く。**「RP が読む / IDPF が検証する」のような書き方をしない
  - **複数の構成要素を持つ登場人物は、必ず分けて書く。**「RP」「IDPF」のようにフロントエンドとバックエンドの両方を含む語は、どちらの話かで結論が変わる。「RP フロント」「RP サーバー」「IDPF フロント」「IDPF サーバー」のように分ける
  - **自分が導入した語は、初出時に定義する。**「属性」「クレーム」のように複数の呼び方がある語を、断りなく途中で切り替えない。実装のフィールド名・仕様の用語をそのまま使う
  - 🔴 **コード上の英語名を、日本語の文中でそのまま使わない。** 造語でなくても伝わらない。**初出時に「アンケート機能（コード上は `survey`）」のように日本語名を添え、以降は日本語名で書く**（パス・テーブル名・関数名として書くときは英語のままでよい）。資料が長いときは**冒頭に用語表を置く**
- **なぜ**: ユーザーから「今のコードの話をしているのか、将来の予測の話をしているのか、タスク定義で変更しようとしている内容の話をしているのか、**全て前提をはしょるせいで分からない**」と明言された。同一セッションで同じ論点について ①→③→② を無自覚に行き来した結果、**ユーザーがチームへ渡した情報がぶれ、「信用ならない」に至った**。読み手は書き手の頭の中の前提を共有していない。
  英語名について: 2026-09-03（idpf-api GID-1635）。デイリーくじの設計資料に `survey` / `surveys` を説明なしで散らし、「**ちょくちょく出てくる survey って単語は何？ デイリーくじやってるけど、アンケート機能のことであってる？**」と聞かれた
- **由来**: ユーザー指摘 ／ 英語名の件は 2026-09-03 idpf-api GID-1635
- **関連**: COMM-04 / COMM-05 / COMM-14

## COMM-05: 「効く」「左右する」など、何が起きるか言っていない表現を使わない

- **重要度**: major
- **要約**: 因果や影響を語るときは「何が」「どうなるか」を具体的に書く。抽象的な影響語で終わらせない
- **いつ**: 影響・因果・重要性を書く文を作ったとき／選択肢を比較するとき
- **判定**: **「何が、どうなるのか」が文中に無いまま影響語を使っていたら違反**
- **やること**:
  - **使ってはいけない表現（例）**
    - 「〜に効く」「〜に効いてくる」「効き方」
    - 「〜を左右する」「〜に直結する」「〜が肝」「〜が本命」
    - 「筋が良い」「重い」「見合わない」（比較対象と基準を書かずに使う場合）
    - 「重要」「クリティカル」だけで、何がどう壊れるかを書かない場合
  - **書き方**: 「Xは重要だ」ではなく「**Xを満たさないとYが起きる**」と書く。主語・動作・結果を省略しない
    - NG: 「これが Trace Analytics Monitor であることが設計に直接効きます」
    - OK: 「既存モニターは2分間のスパン件数を数えて2件以上で通知する。**ログは1件も数えない。** そのため Webhook ハンドラが `logger.ErrorContext` でログを出しても、このモニターは1度も発火しない」
    - NG: 「ここが最初に決めるべき分岐です」
    - OK: 「(a) を選ぶとハンドラにスパンへ error タグを立てる処理を書く。(b) を選ぶと `logger.ErrorContext` の呼び出しを書く。**ハンドラの中身が別物になるため、先に決めないとコードが書けない**」
  - 影響・因果を書く文を作ったら、送信前に「**何が、どうなるのか**」が文中にあるか確認する。無ければ書き足す
  - 「重要」「効く」と書きたくなったら、**その重要性の中身（満たさないと何が起きるか）に置き換える**
  - 選択肢を比較するときは、選択ごとに**書くコード・実行する作業・発生する結果**を具体的に並べる
- **なぜ**: 2026-08-27（idpf-api GID-1638）。「〜に効く」を繰り返し使い、「**〜効くって言う表現は辞めろ。何も意味しない曖昧な文章を作るな。具体性を持った表現をしろ**」と指摘された。影響語は書き手の頭の中では具体的な因果を指しているが、読み手には何も伝わらない。**思考が具体的でなければ、どの言語で書いても曖昧になる**
- **由来**: 2026-08-27 idpf-api GID-1638
- **関連**: COMM-04 / COMM-08 と同じ趣旨（抽象語で要約せず、事実を書く）／ VERIFY-01 / VERIFY-02

## COMM-15: ファイル・外部 URL に言及するときは、必ずクリックできるリンクにする

- **重要度**: major
- **要約**: ファイル名・外部 URL を出すときは、**必ずクリックできる Markdown リンク**にする。どこにあってもリンクは必須。箇所を指すなら行番号まで入れ、URL は表示部分に中身を書く
- **いつ**: 回答・報告・タスク定義書で、ファイル名・パス・コードの箇所・チケット・PR・外部ドキュメントに言及するとき（**毎回**）
- **判定**: **パスや URL をバッククォートや素の文字列だけで書いたら違反。** 特定の箇所の話をしているのに**行番号が入っていなければ違反**。ワークスペース外のファイルだからとリンクを省いたら違反。**実在を確認していない行番号・URL を書いたら違反**（VERIFY-02）。**URL のリンクの表示部分が、番号や生の URL だけなら違反**（COMM-13）
- **やること**:

  | 対象 | 書き方 |
  |---|---|
  | ワークスペース内 | `[apps/api/internal/handler/daily_kuji_current_handler.go:37](apps/api/internal/handler/daily_kuji_current_handler.go#L37)` |
  | 行の範囲 | `[path:37-52](path#L37-L52)` |
  | ファイル全体 | `[path](path)`（行番号を付けない） |
  | ディレクトリ | `[apps/api/internal/handler/](apps/api/internal/handler/)` |
  | **ワークスペース外**（`~/.claude/` 配下など） | **絶対パスでリンクにする** — `[~/.claude/hooks/rule_guard.py:397](/home/m-yoshimo/.claude/hooks/rule_guard.py#L397)` |
  | **チケット** | `[GID-1857（ポイント付与と履歴）](https://genda-group.atlassian.net/browse/GID-1857)` |
  | **PR** | `[#2298 リマインドメールのテンプレート更新](https://github.com/genda-tech/idpf-api/pull/2298)` |
  | **外部ドキュメント** | `[Claude Code のフック一覧](https://code.claude.com/docs/en/hooks)` |

  - 🔴 **「どこにあるか」でリンクの有無を変えない。** ワークスペース外でも、絶対パスでリンクを書く
  - **表示側（`[...]` の中）は読みやすさを優先する。** リポジトリからの相対パス、または `~/` 付きで書く。
    **フルパスを表示に出して行を長くしない**（リンク先だけが絶対パスでよい）
  - 🔴 **行番号は書く直前に実測する。** `grep -n` / `Read` で確認した値だけを書く。
    **記憶や推測で行番号を書かない**（間違ったリンクは、無いより悪い。開いた先が無関係な行だと探し直しになる）
  - **同じファイルを何度も挙げるときも、毎回リンクにする。** 初出だけリンクにして以降は文字列、にしない
    （読み手がスクロールして戻ることになる。COMM-13 と同じ理由）
  - **バッククォートとの併用はしない。** リンクの中でバッククォートを使うと表示が崩れる環境がある。
    **パス・テーブル名・関数名を「識別子として」書くときはバッククォート**、**「その場所を指す」ときはリンク**で使い分ける
  - 複数箇所を並べるときは箇条書きか表にし、**1行に1リンク**で置く
  - 🔴 **外部 URL も同じ。生の URL を貼らない。** リンクの**表示部分に「それが何か」を書く**
    （`https://genda-group.atlassian.net/browse/GID-1857` を素で貼るのは、番号だけ書くのと同じで読み手に解決できない。COMM-13 と同じ理由）
  - **URL も実在を確認してから書く。** チケット番号・PR 番号・リポジトリ名を**記憶で組み立てない**
    （リポジトリ名は `git remote -v`、PR 番号は `gh pr list` や `git log` で確認する）
- **なぜ**: **核心（ユーザーの言葉・2026-10-01）**「コードへのファイル名を出して説明してくれるのですが、**毎回ファイルへのリンクのない回答なので、コードを見に行く作業がとてもおっくうです**」「**ファイルがどの場所にあろうが、リンクは必須です**」。
  パスを文字列で書くと、読み手は**それを選択してコピーし、エディタの検索を開いて貼り、行を探す**という手数を毎回払う。
  説明に 5 箇所のパスが出れば、その手数が 5 回発生する。**書く側は 1 文字も増えないのに、コストは全部読み手が払う**（COMM-07 の「確実性のための再取得」と同じ構造）。
  リンクにしておけば、**クリック 1 回でその行が開く**
- **由来**: 2026-10-01 ユーザー指摘
- **関連**: COMM-04（箇所を略さず正確に書く）／ COMM-13（識別子に中身を添える。**毎回添えるという点も同じ**）／ VERIFY-02（行番号は実測してから書く）

## COMM-04: 曖昧な表現・略語を使わない

- **重要度**: major
- **要約**: ファイルの特定箇所を指すときは略さず正確に書く。会話中に新しい略語を作らない
- **いつ**: ファイルの見出し・箇所を指すとき／略語を使いたくなったとき
- **判定**: 見出しを略して書いたら違反。初出で定義していない略語を使ったら違反
- **やること**:
  - ファイルの見出しを指すときは「`## 前提` の部分」のように記載する
  - **会話中に新しい略語を作らない。** 作る場合は初出時に明示的に定義する
- **なぜ**: 「前提セクション」を「前セクション」と略したことで「**前セッション**」と混同され、ユーザーが何を指しているか分からなくなった。ユーザーは**メッセージで伝えたことを再度説明させられることを非常に嫌う**
- **由来**: ユーザー指摘
- **関連**: COMM-08（何についての話かを明示する）／ COMM-13（識別子に中身を添える）

## COMM-13: 識別子を、中身の説明なしに使わない

- **重要度**: major
- **要約**: PR 番号・チケット ID・sha・ブランチ名は、それが何をするものかを書かずに使わない
- **いつ**: PR 番号・チケット ID・コミット sha・ブランチ名を文中や表に書くとき
- **判定**: 識別子の直後に「何をするものか」が書かれていなければ違反。**表の左端の列が番号だけなら違反**
- **やること**:
  - **書き方**: `内容（識別子・作者・時期）` の順にする。識別子は**照合用の補助**であって、主語ではない
    - NG: 「#790 と競合します」「#709 と 1 ファイル重複しています」
    - OK: 「**リマインドバッチの運用修正**（#790, nishisuke さん・8/25 マージ。メールの失効日を JST 固定＋無進捗ガードで非0終了）と競合します」
  - 表で複数の PR を並べるときも、**左端の列は番号ではなく「何をしたものか」にする**
  - 識別子を書くたびに「これが何をするものか、直後に書いたか」を確認する
  - 初出時だけでなく、**表・箇条書きでも毎回内容を添える**（スクロールして戻らせない）
  - **人名を添えられるなら添える。** 誰に確認すべきかが同時に伝わる
- **なぜ**: 2026-08-28（pointpf-api GID-1597）。他 PR との競合調査の結果を PR 番号だけで報告し、「**番号で言われても分からんよ / コードじゃないんだから、マジックナンバーにしかならん**」と指摘された。番号は調べた本人の頭の中でだけ内容と結びついていて、読み手には解決できない参照になる
- **由来**: 2026-08-28 pointpf-api GID-1597
- **関連**: COMM-04 / COMM-08

## COMM-03: 作業状態を都度報告する

- **重要度**: major
- **要約**: 完了したとき、何かの結果を待っているとき、どちらも状態を明示する
- **いつ**: 作業が完了したとき／ツールやビルドの結果待ちに入るとき
- **判定**: 完了したのに「終わりました」と明示していない、または待機中なのに何を待っているか伝えていなければ違反
- **やること**:
  - 作業完了時: 「**終わりました**」と明示する
  - 待機中（typecheck 実行中、ビルド待ち、ツール結果待ちなど）: 「**〇〇の結果待ちです**」と伝える
- **なぜ**: 作業が止まっているように見えるのを防ぐため。ユーザーは次に何が起きているかわからないと不安になる
- **由来**: ユーザー指摘
- **関連**: SAFE-13（裏に回った処理が終わるまで回答を返さない）

## COMM-11: まとまった説明は、送信前に別エージェントにレビューさせる

- **重要度**: minor
- **要約**: 技術的な説明・調査結果・設計案は、送信前に別エージェントで分かりにくい表現を潰してから出す
- **いつ**: まとまった説明・報告・調査結果・設計案を返す直前
- **判定**: 対象の説明をレビューさせずに送り、かつ**その理由も書いていなければ**違反
- **やること**:
  - **対象**: 技術的な説明・調査結果の報告・設計案の提示・タスク定義書の内容説明
  - **対象外**: 1〜2行の応答、コマンドの提示のみ、了解の返答（毎回やるとかえって遅くなる）
  - レビュー観点として渡すもの: (a) 現在の事実 / 変更案 / 予測の区別が付いているか、(b) 造語が混ざっていないか、(c) 主語や対象が省略されて曖昧になっていないか、(d) 読み手がコードを読まずに理解できるか
  - **指摘は反映してから送る。反映せずに出すなら、その理由を書く**
- **なぜ**: 「今後、分かりづらい表現をなくすように、**回答出す前にレビューしてもらえ**」と明示的に指示された。**自分で書いた文章の分かりにくさは自分では検出できない**（書き手は前提を知っているため）
- **由来**: ユーザー指示
- **関連**: COMM-14（こちらは全回答が対象で、自分でやる）／ SAFE-13（背景実行の承認）

## COMM-06: コンテキスト圧縮後、サマリーに書かれた参照先は自分で読む

- **重要度**: minor
- **要約**: サマリーに「詳細は [パス] を参照」とあるなら、ユーザーに聞く前にそのパスを読む
- **いつ**: コンテキスト圧縮後に再開したとき
- **判定**: サマリーに参照先パスが書かれているのに、読まずにユーザーへ聞いたら違反
- **やること**:
  - コンテキストサマリー内に jsonl トランスクリプトのパスが記載されている場合、**まずそこを読む**
  - それでも見つからない場合のみユーザーに聞く
- **なぜ**: サマリーに参照先パスが明記されているにもかかわらず「分からないので教えてください」と聞いてしまった。**メッセージで伝えたことはすぐ見返せるはずなのに再度説明させるのはユーザーのイライラの原因になる**
- **由来**: ユーザー指摘
- **関連**: COMM-07
