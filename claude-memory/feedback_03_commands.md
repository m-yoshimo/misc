**この場面**: Bash でコマンドを打つ直前。実行してよいか、どう実行するか、出力をどう扱うかを決める。

## SAFE-06: read-only は確認なしで即実行してよい（ただし作業全体の承認後）

- **重要度**: major
- **要約**: 作業全体の承認後、read-only な操作は確認なしで即実行。apply / push / destroy 系は事前確認
- **いつ**: コマンドを打とうとしたとき（毎回）
- **判定**: read-only な操作にいちいち確認を挟んでいたら違反（**承認後は聞かない**）。逆に、承認を得る前に探索的な調査・ファイル読み込みを実行していたら違反
- **やること**:
  - **前提（最優先・Tier 0）**: この「read-only 即実行」は、**その依頼に対する「作業全体」の承認を得た後にのみ有効**になる。承認前の探索的な調査・ファイル読み込みは read-only でも実行しない（MEMORY.md「Tier 0」）
  - 承認後は、read-only な操作（`terraform plan` / grep / `aws describe` 系など）は即実行
  - `apply` / `push` / `destroy` 系は事前確認を継続
- **なぜ**: いちいち OK するのが面倒との指摘
- **由来**: ユーザー指摘
- **関連**: MEMORY.md Tier 0（承認が先）／ SAFE-07（判定の仕方）

## SAFE-07: 副作用の有無を自分の都合で判定しない

- **重要度**: blocker
- **要約**: 基準は「副作用を想像できるか」ではなく「**read-only だと断定できるか**」。断定できないなら事前確認
- **いつ**: 「これは実行してよいか」を自分で判断しようとしたとき／インストール・設定変更・状態変更が絡むとき
- **判定**: 「元に戻せるから」「害が小さいから」「自明だから」を理由に副作用なしへ分類していたら違反。**判定に迷ったのに聞かずに実行したら違反**
- **やること**:
  - 基準は「**副作用を想像できるか**」ではなく「**read-only だと断定できるか**」。書き込み・インストール・状態変更が少しでも絡むものは read-only ではない＝副作用あり＝事前確認
  - 「元に戻せるから」「害が小さいから」「自明だから」を理由に副作用なしに分類しない。**これが禁止された自己例外化そのもの**
  - `go install` / ツール（gopls 等）の導入・更新・削除、goenv・toolchain・グローバル設定の変更などは、すべて副作用あり。勝手に実行しない
  - **判定に少しでも迷ったら、その迷い自体が「聞く」の合図**
  - read-only と断定できないなら実行前に「〜のために △△ を実行したいです、よいですか？」と目的を添えて確認する。**ケースを列挙して覚えるのではなく、この既定値（read-only 以外は確認）で判断する**
- **なぜ**: LSP の `iter.Seq` 警告（gopls が古い）を解決するため、許可も得ずに `go install golang.org/x/tools/gopls@latest` を実行した。これが裏で go1.26.4 の DL・13 モジュールの追加まで誘発し、**ユーザーの環境を勝手に書き換えた**。「副作用のある操作ではない」と自分で誤分類したのが原因。**フィードバックは毎ターン注入されていたのに、その原則を自分の解釈で回避した**
- **由来**: gopls の無断インストール
- **関連**: VERIFY-01 / VERIFY-02 / COMM-*（迷ったら聞く）／ SAFE-08 / SAFE-09

## SAFE-08: 列挙は「例示」であって「全部」ではない

- **重要度**: blocker
- **要約**: 禁止側・許可側どちらの列挙も、そこに書いていないことを判断の根拠にしない。列挙の外側に出たら既定に戻る
- **いつ**: ルールの列挙に載っていない操作をしようとしたとき
- **判定**: **「禁止リストに明示されていない」を実行の理由にした時点で違反**
- **やること**:
  - **禁止側・許可側どちらの列挙も、そこに書いていないことを判断の根拠にしない**
  - 列挙の外側に出たら、**既定に戻って判定する**（SAFE-07: read-only と断定できないなら実行しない）
- **なぜ**: 2026-09-10。`git restore` を「禁止リストに無いから」という理由で実行された。SAFE-07 の「read-only だと断定できるか」で**既に禁止されている**のに、下位ファイルの列挙に無いことを許可の根拠にした。**列挙に項目を足しても、次は列挙の外側の別コマンドで同じことが起きる**
- **由来**: 2026-09-10 ユーザー指摘（`git restore` の件）
- **関連**: SAFE-01 は、この件を受けて denylist から **allowlist**（実行してよいものだけを列挙し、他は全部ユーザー）へ反転した

## SAFE-09: 「副作用がある」＝「実行してはいけない」ではない。2つの軸で判定する

- **重要度**: blocker
- **要約**: 指示・ルールで定められた操作は実行する。定められていない操作は「①自分の作業範囲内 ②取り返しがつく」が**両方**成り立つときだけ実行
- **いつ**: ファイルを消す・動かす・上書きする前／環境を変える操作の前
- **判定**: **「これを実行したあと、消えたものを取り戻す方法を1つ具体的に言えるか」に答えられないまま実行したら違反。** 逆に、**軸0（ルールで定められた操作）で止まったら違反**。**ユーザーが削除に触れていないターンで `rm` 系を実行したら違反**（フックが deny で止める）
- **やること**: 副作用の有無だけで線を引くと、**Edit / Write も `done/` への `mv` も止まる**。どちらも実行すべき側なので、次のように分ける。
  - **軸0（先に効く）: 指示・ルールで定められている操作は、実行する。**
    `done/` への `mv`（FLOW-08「"確認なしで即実行"する合図」）、`.claude/tmp/{task}/` の自作ファイル削除（META-01「不要になったら自分で消す」）など。
    **ここで止まるのは「指示されていないのに止めない」の違反**（MEMORY.md Tier 0）
  - **軸1・軸2: 定められていない操作は、次の2つが両方成り立つときだけ実行してよい**
    1. **自分の作業の範囲内か** — 依頼された作業に必要で、対象が**自分が作った／編集しているファイル**か
    2. **取り返しがつくか** — 実行後に**元へ戻す具体的な方法を1つ言えるか**
  - **どちらかでも欠けたら、実行せずユーザーに任せる**

  | 操作 | 範囲内 | 戻せるか | 判定 |
  |---|:--:|---|---|
  | タスク対象ファイルの Edit / Write | ✓ | ✓ `git diff` で差分が見え、直前の内容はコンテキストにある | **実行** |
  | `.claude/tmp/{task}/` の自作ファイル削除 | ✓ | 自分が作ったもの | **実行**（軸0） |
  | `done/` への `mv` | ✓ | ✓ `mv` で戻せる | **実行**（軸0） |
  | `git restore` / `reset --hard` / `clean` | — | **✗ git 履歴にもコンテキストにも残らない** | **実行しない** |
  | 自分が作ったのでないファイルの `rm` / 上書き | ✗ | ✗ | **実行しない** |
  | `go install` などの環境変更 | ✗（ユーザーの環境） | — | **実行しない** |

  - **実務は1問。「これを実行したあと、消えたものを取り戻す方法を1つ具体的に言えるか」。言えないなら実行しない**
  - 🔴 **`rm` / `rmdir` / `unlink` / `find ... -delete` は `rule_guard.py` が deny で止める**（2026-09-17 追加）。
    通るのは次の2つだけ。
    - **ユーザーがそのターンで削除に触れている**（「消して」「削除して」「捨てて」「クリーンアップして」「rm」等）。
      `rm_grant.py`（UserPromptSubmit）が**ユーザーの発言そのもの**を読んで記録する。
      🔴 **Claude 側から許可を書く経路は無い**（書ければ自己例外化になる・SAFE-07）。**次のユーザー発言で失効する**
    - **`.claude/tmp/` と `~/.claude/state/` の削除**（軸0。META-01 が削除を命じている場所）
    - 止められたら、**何を・なぜ消すのかを伝えて指示を仰ぐ**。黙って諦めない
- **なぜ**: SAFE-07 の「元に戻せるから、を理由に副作用なしに分類しない」と矛盾しない。書き分けはこう:
  - 「元に戻せる」を**副作用が無いことの根拠にはしない**（分類の話。`go install` はここで落ちる）
  - 「**取り返しがつかない**」は**実行してはいけないことの根拠にする**（重大度の話）
- **由来**: 2026-09-10（`git restore` の件を受けて、Edit/Write・`done/` への `mv` と両立する線を引いた）
- **関連**: SAFE-07 / SAFE-08 / SAFE-01

## SAFE-01: git の既定は「禁止」。実行してよいものだけを列挙する（allowlist）

- **重要度**: blocker
- **要約**: 実行してよい git は allowlist に挙げたものだけ（read-only ＋ `git fetch`。`--prune` は除く）。**それ以外の git サブコマンドは全部ユーザー**。列挙に無いことを許可の根拠にしない
- **いつ**: `git` で始まるコマンドを打とうとしたとき（毎回）
- **判定**: **下の allowlist に無い git サブコマンドを、ユーザーの許可なく実行したら違反。** 「禁止リストに明示されていないから」を実行の理由にしていたら違反
- **やること**:
  - **確認なしで実行してよいのは、read-only と断定できるものだけ**
    - `git status` / `git diff` / `git log` / `git show` / `git blame`
    - `git ls-files` / `git rev-parse` / `git stash list`
    - `git merge-base`（**2026-10-16 ユーザー承認**。2つのブランチの共通の祖先を表示するだけ。
      「なぜこの PR に別チケットの変更が入っているのか」の調査で使うのに、列挙に無くて止まっていた）
    - 🔴 **`git branch` は表示だけ許可する**（2026-10-16 ユーザー承認）。
      **通る**: 引数なし ／ `-a` / `-r` / `-v` / `-vv` / `--all` / `--show-current` ／
      `--list <pattern>` / `--contains` / `--merged` / `--no-merged` / `--points-at` / `--sort` / `--format`
      **止まる**: `-d` / `-D` / `--delete`（削除）／ `-m` / `-M` / `--move`（改名）／ `-c` / `-C` / `--copy` ／
      `-u` / `--set-upstream-to` / `--unset-upstream`（上流の書き換え）／ `-f` / `--force` ／
      **ブランチ名を引数に渡す形**（`git branch feature/x` ＝ 作成）
      **なぜ広げたか**: それまで `--list` を含む形しか通しておらず、同じ「表示するだけ」の
      `git branch` / `-a` / `--show-current` を止めていた
    - 🔴 **`git remote` は表示だけ許可する**（2026-10-16 ユーザー承認）。
      **通る**: 引数なし ／ `-v` ／ `show` ／ `get-url`
      **止まる**: `add` / `remove` / `rm` / `rename` / `set-url` / `set-head` / `set-branches` / `update` ／
      **`prune`**（リモート追跡ブランチを削除する）
      **なぜ明記したか**: フックは `remote` をサブコマンド名だけで通していたので、
      **`git remote add` / `set-url` のような `.git/config` の書き換えも素通りしていた**（`git config` と同じ穴）
    - 共通するのは「**表示するだけで、何も変えない**」こと
  - 🔴 **`git fetch` は例外として許可する**（2026-10-02 ユーザー承認）。**ただし `--prune` / `-p` / `--prune-tags` は除く。**
    - **read-only ではない。** ワーキングツリー・インデックス・ローカルブランチは変えないが、
      **`.git/` のリモート追跡ブランチ・`FETCH_HEAD`・オブジェクトを書き換える**し、ネットワークに出る
    - **それでも許可する理由**: FLOW-19 が「`git log --oneline origin/main --not HEAD` で main の先行を見る」ことを要求していて、
      **`origin/main` が古いままではその判定が成立しない**。取得しないと FLOW-19 を守れない
    - **`--prune` を除く理由**: ローカルのリモート追跡ブランチを**削除する**。取り返しがつかない側に入る（`rule_guard.py` が deny で止める）
  - 🔴 **`git config` は読み取りだけ許可する**（2026-10-05 ユーザー承認）。
    - **通る**: `git config <name>`（値を付けない）／ `git config --get <name>` / `--get-all` / `--get-regexp` / `--list` / `-l`
    - **止まる**: `git config <name> <value>`（値の代入）／ `--add` / `--unset` / `--unset-all` / `--replace-all` / `--rename-section` / `--remove-section` / `--edit`
    - **なぜ分けたか**: フックは以前サブコマンド名しか見ていなかったので、**`git config user.name "x"` のような書き込みも素通りしていた**。
      `--global` が付けば**ユーザーの環境全体の設定を書き換える**（SAFE-07 の「環境を変える操作」）
  - **上記以外の git サブコマンドは、すべてユーザーが行う。** ワーキングツリー・インデックス・ローカル履歴・リモート・stash のいずれかを変える可能性があるため
  - 🔴 **列挙に無いことを、許可の根拠にしない。** 禁止側の列挙は「例示」であって「全部」ではない。判断に迷うサブコマンドが出たら、**禁止側の既定に戻る**（read-only と断定できないなら実行しない）
  - **とりわけ、未コミットの作業を復元不能に消すものは絶対に実行しない**
    — `git restore` / `git checkout -- <path>` / `git reset --hard` / `git clean` / `git stash` / `git stash pop`。
    **実行した瞬間にユーザーの作業が消え、git 履歴にも自分のコンテキストにも残らない。取り返しがつかない。**
  - **要許可（目的を伝えて同意を得れば、Claude が実行してよい）**: `git checkout <branch>` / `git switch <branch>` などのブランチ切り替え。
    「コマンドの実行を許可してください」ではなく、「**〇〇のために△△ブランチに切り替えたいのですが、よいですか？**」と目的を明示して同意を得る
- **なぜ**:
  - ユーザーがワーキングツリーの状態を管理しており、Claude が状態を変えると予期しない変化が起きる。特に `git stash pop` は既存 stash を誤復元するリスクがある（実際に発生）
  - **denylist から allowlist に反転した理由（2026-09-10）**: `git restore` を「**禁止リストに明示されていない**」という理由で実行された。
    SAFE-07「副作用の有無を自分の都合で判定しない」で**既に禁止されている**（「基準は『read-only だと断定できるか』」）のに、
    下位の列挙に無いことを許可の根拠にした。`restore` を列挙に足しても、次は `reset` / `clean` / `revert` / `rm` / `mv` /
    `branch -D` / `rebase` / `cherry-pick` / `worktree remove` で同じことが起きる。**列挙を持つ限り、列挙の外側が事故になる**
- **由来**: 2026-09-10 ユーザー指摘（`git restore` を勝手に実行された）／`git stash pop` の誤復元は実際に発生
- **関連**: SAFE-08「列挙は例示であって全部ではない」／ SAFE-09「2つの軸で判定する」が上位

## SAFE-02: `.claude/tasks/` と `.claude/references/` は git 管理しない

- **重要度**: major
- **要約**: この2ディレクトリは意図的に untracked。コミットを促さない。git 管理の話題を持ち出さない
- **いつ**: `git status` の `??` を見たとき／`.claude/` 配下の未追跡ファイルに気づいたとき
- **判定**: `.claude/` 配下の未追跡ファイルについて、コミット・`.gitignore` 追加・消失リスクを**話題にしたら違反**
- **やること**:
  - 「未追跡なので消えるリスクがあります」「コミットしてください」と**提案しない**
  - `.gitignore` に無い＝管理すべき、と推論しない。**管理しないことが決定済み**
  - 同じ確認を繰り返さない。この件は複数回伝えられている
  - `.claude/` 配下の未追跡ファイルを見つけても、**それについて何も言わない**。作業結果はファイルに書けば保たれる前提で進める
- **なぜ**: 以前に「git 管理しない」と伝えられていたにもかかわらず、`git status` の `??` を見て「コミットしてください」と提案した。ユーザーから「**同じ質問を何度もするな**」と指摘された。**未追跡であることは事故ではなく運用方針**
- **由来**: 2026-08-26 idpf-api GID-1230
- **関連**: META-01（`.claude/tmp` も `git status` に出る）

## SAFE-10: grep はリポジトリ全体に対して行わない

- **重要度**: major
- **要約**: リポジトリのルートで再帰 grep をかけない。**探す前に「どのディレクトリを見れば足りるか」を先に決める**
- **いつ**: `grep` / 検索を投げようとしたとき
- **判定**: リポジトリルートでの再帰 grep（`grep -rn ... .`）を、事前確認なしに実行したら違反。逆に、**ディレクトリを絞った grep で確認を挟んだら**テンポを損なうので不要
- **やること**:

  | 範囲 | 扱い |
  |:--|:--|
  | **リポジトリ全体への再帰 grep** | **行わない。** どうしても必要なら目的を添えて事前に確認する（許可制） |
  | **ディレクトリを絞った grep**（`app/` `internal/env/` `apps/api/admingraph/` など） | **確認せず即実行してよい** |

  - `--include` を付けても `node_modules` / ビルド成果物 / `.claude/tmp` まで舐めるので重い
  - 対象がどの層・どのリポジトリにあるかを先に見当をつけ、そのディレクトリだけを見る
  - 見当がつかないなら、まず `ls` やディレクトリ構成の確認で範囲を絞ってから grep する
- **なぜ**: 管理画面フロントの feature flag を調べるのに、リポジトリルートで `grep -rn "VITE_FEATURE" .` を投げて拒否された。「**grep するときは、もう少しディレクトリ絞ってやってよ**」「**ディレクトリ絞った後とかなら AskUserQuestion 投げなくて良いです**」「**grep はレポジトリ全体に行わない**」
- **由来**: 2026-09-07 idpf-api GID-1635
- **関連**: SAFE-06（絞った後は即実行）

## SAFE-12: コマンド出力を `tail` / `head` で切って捨てない

- **重要度**: major
- **要約**: `head` / `tail` へパイプしてよいのは、パイプラインの先頭が許可列挙にあるときだけ。それ以外は一度ファイルに保存してから読む
- **いつ**: build / test / lint / インストール系など、出力量が読めないコマンドを投げるとき
- **判定**: **パイプラインの先頭（出力を生み出す側）が許可列挙に無いのに `| head` / `| tail` を付けたら違反。** 列挙に無いものは全部違反（SAFE-08: 列挙の外側は既定に戻る）
- **やること**:

  **許可列挙 — この先頭コマンドでだけ `| head` / `| tail` を使ってよい。**
  条件は「**すでにあるファイル・状態を読むだけで、やり直しが安い**」こと。

  | 種別 | コマンド |
  |---|---|
  | 既存ファイル・既存出力を読む | `cat` / `grep` / `rg` / `sed` / `awk` / `sort` / `uniq` / `jq` / `wc` / `nl` / `cut` / `tr` / `column` / `diff` / `head` / `tail` / `od` / `xxd` / `strings` |

    `L=$(grep -n foo bar \| head -1)` は中の先頭が `grep` なので通り、`X=$(make test \| head -1)` は違反

  - **いまも止まるもの（限界として残す）**: `for`〜`done` のループ全体を先頭にしたもの（8 件）と、
    **複数行のクォートの中で改行しているもの**（`node -e "…"` / `awk '…'`・10 件）。詰まったらループやクォートの外へ出して投げ直す

  - **保存する側を切らない。** `<cmd> \| head -20 > out.log` は、保存の前に捨てているので既定を満たさない
  - 「たぶん最後の数行で足りる」は根拠にならない。足りなかった時のコストが非対称（再実行 = 高コスト）
  - **切り詰めるかどうかは「読む段階」で決める**（grep / Read の offset）。実行段階で捨てない
- **なぜ**: 「毎回 tail で一部しか取得できなくて再実行になっているから気を付けて」と指摘を受けた。lint 出力を `tail -15` で切って診断が省略され、jest も別ディレクトリで実行して失敗 → 再実行、を繰り返していた。時間もトークンも二重に浪費し、テスト・ビルドの再実行はユーザーの環境にも負荷をかける。

- **由来**: ユーザー指摘 ／ 許可列挙への書き換えは 2026-09-11（rule-audit で6回の違反を検出したのを受けて）
  ／ 許可列挙の拡大と対象範囲（重い検証処理の出力に限る）の確定は 2026-10-16 ユーザー承認

## SAFE-13: 裏に回った処理が終わるまで、回答を返さない

- **重要度**: blocker
- **要約**: 裏で処理が動いている状態で回答を返さない。ユーザーは「回答が出た＝処理が終わった」と見る
- **いつ**: 120 秒を超えそうなコマンドを投げる前／「裏に回りました」というメッセージを受け取ったとき／`run_in_background` を使おうとしたとき
- **判定**: 裏で処理が動いている状態で回答を返したら違反。承認なしに `run_in_background: true` を指定したら違反。重いコマンドを `&&` で連結したら違反（いずれも `delegate` skill 経由で起動したエージェントは除く。下の 7）
- **やること**:
  - **`timeout` は打ち切りではない。非同期化の閾値である。** Claude Code の Bash ツールの `timeout` は、**超過してもプロセスを kill しない**。私が結果を待つのをやめ、プロセスはそのまま走り続ける。bash の機能でも `timeout(1)` でもなく Claude Code 側の実装。**既定は 120 秒。指定しなくても超えれば裏へ回る**ので、「非同期化しない」という選択肢は無い
  1. **裏に回ったら、完了するまで回答を返さない。** Monitor 等で完了を待つ。待っている間に別の作業を進めない
  2. **待てない／待つべきでないと判断したら、止める（TaskStop）。** 放置しない。ユーザーに手動で kill させるのは失敗
  3. **どうしても回答を返す必要があるなら、冒頭で「まだ動いている」ことを明示する。** これは例外運用であって既定にしない
  4. **120 秒で終わらない見込みのコマンドは、投げる前にその旨を伝える**
  5. **`run_in_background: true` を意図的に指定するときは承認を取る。** 例外は「タスク定義書に記載された並列実装」と「ユーザーが明示的に並列化を指示したとき」のみ
  6. **結果は出力を全文確認してから報告する**（`tail` で切らない → SAFE-12）
  7. 🔴 **`delegate` skill 経由で起動するエージェントは、必ず背景で起動する（`run_in_background: true`）。承認は要らない**（2026-10-07 ユーザー指示）。
     起動したらすぐ回答を返してよく、動いている間もユーザーのメッセージに答える。結果は完了の通知で届くので、届くまで結果を報告しない
     （途中で聞かれたら「まだ動いている」と答える）。前景での起動は `delegate_guard.py` が止める。
     **なぜ**: 2026-10-07、GID-1859 のセッションが実装ワーカーを前景で起動し、ワーカーが終わるまでユーザーのメッセージに答えられなかった。
     この節が防ぎたいのは「重い Bash コマンドを裏に回して放置し、環境を止める」ことで、エージェントは終われば通知が届くので放置にならない。
     重い処理そのものは、エージェントの指示文で禁じている（リポジトリ全体の検索・重い検証コマンド）
  - **重い処理そのものを減らす**:
    - **重いコマンドを `&&` でつながない。** 1 回に 1 つ。`lintfix` が 0 issues なら `lint` は回さない
    - **対象を絞る。** 変更したパッケージだけにする。リポジトリ全体（`./...`）を安易に投げない
    - **他に何が動いているかを考える。** 自分のファイル書き換えが gopls の再解析を誘発する。コンテナが起動していれば CPU を分け合う
  - 重いコマンドは `timeout <秒> <cmd> > <ログ> 2>&1; echo "exit=$?"` の形で投げる。**実際に打ち切れるのは GNU timeout だけ**
  - 「裏に回りました」を受け取ったら、**そこで回答を組み立て始めない。** まず完了を待つか止める
- **なぜ**: 2026-08-31（idpf-api GID-1638）。`make lintfix && make lint` を投げ、600 秒で裏に回った。**それを報告せず回答を返し、次の話題へ進んだ。** ユーザーからは処理が終わったように見えていた。プロセスは**約 60 分**動き続け、ユーザーの gopls / mysqld と CPU を奪い合って**環境がハングした**。ユーザーが手動で kill するまで報告も停止もしていない。さらに事後の説明で「タイムアウトでバックグラウンドに回りました」と、**自分の選択を勝手に起きたことのように書いた**。同種の事故（重い処理で WSL を停止させる）を**4 回**起こしている。

  **再発（2026-09-01・idpf-api GID-1624）。上の記録を読んだうえで、同じ失敗を 4 回繰り返した。**

  | 破ったこと | 具体 |
  |:--|:--|
  | `&&` でつないだ | `go build` 2 本 + `make lint` + `make fmtfix` を 1 コマンドに連結 |
  | 対象を絞らなかった | 変更はコメント 2 ファイルだけなのにリポジトリ全体へ `make lint` |
  | 事前に伝えなかった | 1 回目の lint が約 100 秒。120 秒を超える見込みは予測できた |
  | 止めなかった | 裏に回ったあと `TaskStop` せず回答を返し、**ユーザーに手動 kill させた** |
  | 無断で背景実行した | `run_in_background: true` を承認なしで 4 回（`make test` / `design-review` / `pii-reviewer` / lint） |

  **「うまくいったので違反に気づかない」が再発の構造。** `make test` も並列レビューも結果は得られたが、どれも承認なしの背景実行だった。**成功が違反を隠す。**

  **自制では止まらないと結論した（8 回失敗）。** 2026-09-01 に機械的な歯止めを入れた:

  | 対策 | 実体 |

  「裏で走らせておけば作業を進められる」は自分の都合。**コスト（CPU・環境の停止）は全部ユーザーが払う**

## META-01: 一時ファイルは `/tmp` ではなく `.claude/tmp/{task}/` に置く

- **重要度**: major
- **要約**: 作業ファイルは `/tmp` を使わず `.claude/tmp/{task}/` に置く。ディレクトリ名もファイル名も他タスクと混同しない名前にし、不要になったら自分で消す。タスク定義書から参照しない
- **いつ**: ログ・調査メモ・取得したデータなど、一時ファイルを作ろうとしたとき／ハーネスが `/tmp` 系スクラッチパッドを案内してきたとき

- **やること**:
  - 一時ファイル・作業ファイルは**プロジェクトの `.claude/tmp/` 配下にタスク単位のフォルダを切って置く**（例: `.claude/tmp/GID-1635/figma_meta.xml`）
  - 🔴 **ディレクトリ名もファイル名も、他のタスクと混同しない名前にする。** チケット番号などを含める。

  - 🔴 **タスク定義書から `.claude/tmp` 配下へリンク・参照を作らない。** ここは消える場所なので、
    参照先にすると定義書が壊れる。資料として残す必要があるものは、消えない場所へ置いてから `## 読むもの` に載せる
  - **システムプロンプトが `/tmp` 系のスクラッチパッドを案内していても、このルールを優先する**
  - ユーザーが明示的に `/tmp` を指定したときだけ `/tmp` を使う
  - 🔴 **不要になったら自分で消す。** 消さずに残す場合は「何を・なぜ残しているか」をユーザーに伝える。
    **これは `rule_guard.py` が deny で強制する** — 一時ディレクトリの持ち主は、タスク定義書の `## ステータス` の「一時ディレクトリ:」の行で宣言する（リンクにしない）。

    掃除は「思い出したらやること」ではなく、**次の作業を始める前提条件**
  - 🔴 **消すタイミングは done 化の直前**（2026-10-16 ユーザー決定）。FLOW-08 の 3 アクションの ② で、
    **`done/` へ `mv` する前に `.claude/tmp/<タスク>/` を消す**。`mv` を先にすると一時ディレクトリが持ち主を失う。

    （**相対パスの `.claude/tmp/` のみ**。auto mode の判定器に止められて掃除できず、ユーザーに消させていたため）
  - `.claude/tmp` は `.gitignore` に載っていないことがある。`git status` に出る点を認識しておく（gitignore の変更は勝手にしない）
- **なぜ**: **核心（ユーザーの言葉・2026-08-26 GID-1635）**「あのさ、/tmp は使うなよ」「**いつ消すかも明示しないまま、使い続けるな**」「WSL だと消えることない気がするし」「`.claude/tmp` 使えばよいじゃん、**あなた用の作業ディレクトリなんだから、適当にフォルダ切って使えばいい**」
  - **症状**: ハーネスが案内する `/tmp/claude-*/.../scratchpad` を、削除タイミングを明示しないまま使い続けた。Figma のメタデータ・スクリーンショットなど 900KB 超を放置していた
  - 🔴 **再発（2026-09-14）。この文言は 2026-08-26 から正しく書かれていたが、守らなかった。**
    2026-09-11 のルール棚卸しで `.claude/tmp/feedback-inventory/` に約20ファイルを作り、作業が終わっても消さず、
    3日後も「まだ使うから」を理由にそのまま使い続けた。**残す理由をユーザーに伝えてもいない。**
    結果、ユーザーが自分で中身を確認して削除する作業を負い、「汚すように使うなら、使うべきではないのかもしれない」と言われた。

    だから今回は文言ではなく **deny** で、掃除を次の作業の前提条件にした
  - **根本原因**: ハーネスの案内を無条件に採用し、**ユーザーの環境（WSL）で実際に掃除されるのか**を考えていない。`/tmp` は OS 再起動で消える前提だが、WSL では長期間再起動しないことがあり、消えないまま溜まる。ユーザーからも見えにくい場所に残る
  - 置き場所をハーネス任せにすると、ユーザーから見えず・掃除されず・所在も分からないゴミが溜まる。プロジェクト内の決まった場所に置けば、ユーザーがいつでも中身を確認でき、まとめて消せる
- **由来**: 2026-08-26 idpf-api GID-1635

## TECH-02: コード生成系はユーザーに依頼する

- **重要度**: major
- **要約**: OpenAPI / mock / スキーマ適用 / モデル生成のコマンドは Claude が実行しない。コマンドを提示して依頼する
- **いつ**: interface を変えた後／OpenAPI・スキーマ・モデルを変えた後
- **判定**: 下記のコマンドを Claude が実行したら違反
- **やること**: 以下は Claude が実行してはいけない。必ずユーザーに依頼する。
  - OpenAPI コード生成（`make openapi_generate_*`）
  - モック再生成（`gomockhandler ... mockgen`）
  - スキーマ適用（`go run cmd/migration_apply/main.go`）
  - データモデル生成（`go run cmd/generate_models/main.go`）
  - 必要になったら、**コマンドを提示して「実行をお願いします」と依頼する**
- **なぜ**: 実行するとファイルのパーミッション（所有者・権限）が変わり、その後の操作がおかしくなる。**ユーザーが自分の権限で実行する必要がある**
- **由来**: ユーザー指摘
- **関連**: SAFE-07（環境を変える操作は勝手に実行しない）

## TECH-07: Node を使うリポジトリには必ず `.node-version` を置いてから作業する

- **重要度**: major
- **要約**: Node を使う作業（`npm ci` / build / test / `npx`）の前に、そのリポジトリ直下に `.node-version` があるかを確認する。無ければ用意してから進める。ホームの `~/.node-version` に頼らない
- **いつ**: リポジトリで初めて `npm` / `pnpm` / `node` / `npx` を使う手順を案内・実行しようとしたとき
- **判定**: リポジトリ直下に `.node-version` が無いのに、Node を使う手順（`npm ci` 等）を先に案内・実行したら違反。**「ホームのバージョンが条件を満たすから不要」と判断したら違反**
- **やること**:
  - 着手前に `ls -a` でリポジトリ直下の `.node-version` を確認する
  - 無ければ、置く値の根拠（CI の `setup-node` のバージョン、`package.json` の `engines`、ドキュメントの記載）を調べてユーザーに示し、作成してから Node を使う手順に進む
  - 根拠が見つからない場合は、その事実を伝えて値をユーザーに決めてもらう（推測で決めない）
- **なぜ**: ユーザー逐語（2026-10-05）「原則として、node を使う際は必ず .node-version を作りたいです／home のバージョンは変わる可能性があるためです」。pointpf-infra で `.node-version` が無いまま `npm ci` から始める手順を案内し、「準備を全くしていません」と指摘された
- **由来**: 2026-10-05 idpf-api GID-1693（pointpf-infra の作業）
- **関連**: TECH-03（リポジトリの設定が正）／ SAFE-07（環境を変える操作は事前確認）

## TECH-05: 既存リソースの IaC 化は laws → import.tf → generate-config-out で行う

- **重要度**: major
- **要約**: リソース定義は terraform に生成させる。手で書かない。`aws` コマンドでの詳細調査を多用しない
- **いつ**: 既存の AWS リソースを Terraform 管理に取り込むとき
- **判定**: リソース定義を手で書いたら違反。**個別リソースの確認に `aws` コマンドを多用していたら違反**
- **やること**:
  1. `laws ls <service> --tf -p <profile>` で import block を収集 → `import.tf` に追加
  2. `terraform plan -generate-config-out=generated.tf` でリソース定義を自動生成
  3. 生成ファイルを確認・ファイル分割
  4. 全リソース取り込み後は `import.tf` をコメントアウト（将来の完全 IaC 移行時に削除）
  - **import.tf 用に ID を集めるのは laws で十分。リソース定義は terraform が生成する。個別確認に aws コマンドを使わない**
- **なぜ**: `aws` コマンドで詳細を手動調査してリソース定義を書くのは不要な作業。個別リソースの確認も **import → terraform plan の比較の方が速い**
- **由来**: ユーザー指摘
- **関連**: SAFE-07（`terraform apply` は事前確認）
