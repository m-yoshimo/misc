**この場面**: 設計・タスク定義書を書き始めるとき。何を読んでから書くか、何を裏取りしてから書くかを決める。

## FLOW-20: 詳細設計を書く前に、必ず PRD（要件の一次資料）を全文読む

- **重要度**: blocker
- **要約**: **設計を書く前に読むものの筆頭は PRD。** 親のタスク定義書・既存コード・設計規約より先に読む。**設計レビューに投げるときも PRD を必ず渡す**
- **いつ**: 詳細設計を書き始める前／設計レビューを外部エージェントに投げるとき
- **判定**: PRD を読まずに設計を書いたら違反。**設計レビューの資料に PRD が入っていなければ違反**。「PRD の想定」と書く前に PRD を grep していなければ違反
- **やること**:
  - **タスク定義書の「再開手順」に、PRD を必読の 1 番目として明記する。** 次のセッションが同じ順序で始められるようにする
  - **設計レビューを投げるときの資料に PRD を必ず含める。**「規約と既存コードとの照合」だけのレビューは、要件の落ち・誤読を**構造的に検出できない**
  - **設計に数字・条件を書くときは、出典が PRD か別資料かを毎回確認する。**「PRD の想定」と書く前に PRD を grep する
  - **要件を PRD 原文で引用してから設計を書く。** 記憶や要約から書かない
- **なぜ**: **PRD を読まずに設計すると、次の 2 つが必ず起きる。**

  | | 内容 |
  |---|---|
  | **要件の落ち** | PRD に書いてある要件が設計に存在しない。**コードと規約だけを見ていると気づけない**（コードには「まだ無いもの」が写らないため） |
  | **要件の誤読** | PRD に書いていない数字・条件を「PRD の想定」として根拠に使う。**別の資料由来の数字が、いつの間にか PRD 由来として設計の根拠になる** |

  **親のタスク定義書は PRD の要約ではない。** 親に書いていない要件が PRD にある。**「親を読んだから PRD は要らない」は成立しない。**
  2026-09-03（idpf-api GID-1635 / GID-1855）。pointpf の設計規約と `spec.md` との照合だけで**設計レビューを 3 回**回し、いずれも「規約に合っているか」しか見ていなかった。4 回目で初めて PRD をレビュアーに渡したところ、**要件の落ち 3 件**（0pt のときの契約が無い／「1人1日1回」を誰が担保するかが未記述／既存関数の改修規模を過小評価）と **PRD の誤読 3 件**（PRD に存在しない数字を「PRD の想定」として値域の根拠にしていた／日数の計算が両端とも誤り／親が却下済みの案を子から親へ差し戻していた）が一度に出た。「**ってか、デザインレビューに PRD 渡してないの？**」と指摘された。**3 回分のレビューと、それに費やした時間がほぼ無駄になった**
- **由来**: 2026-09-03 idpf-api GID-1635 / GID-1855
- **関連**: VERIFY-01 / VERIFY-02（推測は検証してから）／ COMM-08 ／ FLOW-21

## FLOW-19: 着手前に「今の main に何が入っているか」「誰が今どこを触っているか」を調べる

- **重要度**: blocker
- **要約**: base が最新か／触る領域に既マージの変更が無いか／open PR が同じファイルを触っていないか。**調査コストは数分、怠ったときの手戻りは数日**
- **いつ**: 実装に入る前（タスク定義書の `## 前提（確認済み）` を書くとき）
- **判定**: `## 前提（確認済み）` に下記3点の**実測結果が書かれていなければ違反**。衝突する相手の修正を、作者に確認せず消したら違反
- **やること**:
  1. **作業ブランチの base が最新か** — `git log --oneline origin/main --not HEAD` で、main 側が先行しているコミットを見る
  2. **これから触る領域に、既にマージされた変更が無いか** — 特に同じ機能・同じバッチ・同じファイル
  3. **open PR が同じファイルを触っていないか** — `gh pr list` + 各 PR の `--json files`
  - タスク定義書の `## 前提（確認済み）` に、**上記 3 点の実測結果を必ず書く**
  - 「既に main に入っている他人の修正」は表にして、**自分の変更との関係（重複 / 衝突 / 無関係）**を明記する
  - 衝突する場合、**相手の修正を消してよいかは自分で判断せず、作者に確認する**
  - 同じ機能を並行して触っている人がいると分かったら、**実装を始める前に**知らせる
- **なぜ**: 2026-08-28（pointpf-api GID-1597）。失効リマインドバッチの改修に着手する際、main の状態を確認しなかった。その結果:
  - **3 日前にマージ済みだった同じバッチの修正**（メールの失効日を JST 固定するバグ修正）に気づかず、**同じバグを見つけ直して「実害のあるバグを発見した」と報告した**
  - 古い base の上に作業を積み、相手が追加した型（`RemindCursor.Equal`）を削除する形になり、正面衝突を抱えたまま **16 ラウンドのレビュー**を回した
  - 最終的に「main から作り直す」判断になり、**それまでの作業の大半が捨てられた**
- **由来**: 2026-08-28 pointpf-api GID-1597
- **関連**: VERIFY-01 / VERIFY-02（推測せず確認してから動く）／ COMM-13（他 PR は内容を添えて書く）

## FLOW-12: タスク定義はテンプレートから起こす（毎回抜ける最重要ミス）

- **重要度**: blocker
- **要約**: ゼロから書き始めない。**場面ごとのテンプレを使い、全節を残して原則として全部埋める**。該当しない節は「なし」「不要」＋理由
- **いつ**: 新規タスク定義を書き始めるとき／承認を求める直前
- **判定**: テンプレをコピーせずゼロから書いたら違反。**場面と違うテンプレを使ったら違反**。**節を空欄にしたり削除したりしたら違反**。承認前チェックで「テンプレの全節が埋まっているか」を確認していなければ違反
- **やること**:
  - 🔴 **場面ごとに使うテンプレが違う**（2026-10-20 ユーザー決定）

    | 作るもの | 使うテンプレ |
    |---|---|
    | `overview.md`（**最初に作る**） | `~/.claude/tasks/_TEMPLATE_OVERVIEW.md` |
    | 詳細設計（`{チケット番号}-{内容}.md`） | `~/.claude/tasks/_TEMPLATE.md` |
    | `release-plan.md` | `~/.claude/tasks/_TEMPLATE_RELEASE_PLAN.md` |

  - **テンプレの全節を残す。原則として全部埋める。** どの節があるかは**テンプレの実物が唯一の正**で、ここにもタスク定義書にも節の一覧を書き写さない（写した瞬間にテンプレとずれる。実際に2箇所の列挙が両方とも古くなっていた）
  - **overview では、詳細設計に属する節を消さずに「各サブタスクの定義書に書く」の1行だけを入れる**（節を消すと、書き忘れたのか委譲したのかが区別できない）
  - **該当しない節は「なし」「不要」＋理由を書く。空欄にも削除にもしない。**「書き忘れたのか、該当しなかったのか」を読み手が区別できなくなるため。**「該当なし」も記載内容の一つとして扱う**
    - 例: 懸念点が無ければ「なし」／画面を伴わないなら「Figma の取得は不要」／並列不要なら「ワーカー1本・順次・理由」
  - 🔴 **実装の進捗を刻むチェックリストは作らない**（2026-09-14 ユーザー確認で `## 実装ステップ` の要求を撤回し、テンプレからも外した）。
    **定義書どおりに実装している限り、途中経過に書く中身が無い**ため。
    再開に要るのは「現在地の 1 行」と「ユーザーの判断待ち」だけ（**FLOW-23**）で、どこまで書けたかは `git status` / `git diff` を見る
  - **承認前チェックに「テンプレの全節が埋まっているか」を1項目として自分で確認する**
- **なぜ**: **症状（繰り返し発生・「何で毎回抜けるんですかね」と叱られた・GN-5811）**: タスク定義を自分の関心事（技術設計）だけで書き、`## 変更対象ファイル一覧（並列実行計画）` / `## 再開手順` を丸ごと落とす（当時は `## 実装ステップ（チェックポイント）` も対象だったが、2026-09-14 に廃止した）。5784 では書けていたのに次タスクで消える。
  **根本原因**: 「技術設計＝成果物」と捉え、実行体制・耐障害の足場を"付随的な定型"として省略する。設計裏取り漏れ（VERIFY-01）と同じ「**テンプレを機械的に埋めず自分の書きたい所だけ書く**」構造
- **由来**: GN-5811 ／ 列挙の廃止は 2026-09-10 ／ テンプレを3種に分けたのは 2026-10-20 ユーザー決定
- **関連**: META-04（同じ「一覧を書き写すとずれる」構造）／ FLOW-03（最初に作るのは overview）

## FLOW-21: タスク定義書の「読むもの」は、そのファイルだけで辿れる具体度で書く

- **重要度**: blocker
- **要約**: パス・URL・ノード ID・スキル名まで書く。**この一覧は `design-review-v2` のレビュアーも読む**ので、載せなかった資料は判定者に渡らない
- **いつ**: タスク定義書の枠を作ったとき／設計中に新しい資料が必要になったとき
- **判定**: 「〜一式」「関連する〜」「必要に応じて」と書いていたら違反。**この定義書だけを渡されて設計できない状態なら違反**。画面を伴わないのに「Figma の取得は不要」と明示していなければ違反
- **やること**:
  - ユーザーからの指示が「**そのタスク定義書を読んで詳細設計して**」の一言だけでも、**定義書に書いてあるものを順に読めば設計に必要な材料が全部揃う**状態にしておく
  - **この一覧は `design-review-v2` のレビュアーも読む**（skill の Step 0b が本節からパスを抽出して全レビュアーに渡す）。つまりこの節は「次のセッションのため」だけでなく「**判定者に判定材料を渡すため**」のもの。**上流が委譲した論点・前回のレビュー結果・セッション固有の調査メモも必ず載せる**（載せ忘れ自体が R4-12 の違反として指摘される）
  - 節は `~/.claude/tasks/_TEMPLATE.md` と `~/.claude/tasks/_TEMPLATE_OVERVIEW.md` の `## 読むもの（実装者・レビュアー共通）` にある
  - 🔴 **overview と詳細設計の両方に置く**（2026-10-20 ユーザー決定）。**overview にはタスク全体で共通の資料**（PRD・設計規約・調査記録）、
    **詳細設計のファイルにはそのサブタスク固有の資料**（参考にする既存コード・画面のノード ID・上流の成果物）を書く。
    同じものを両方に書き写さない（overview 側を指すリンクで済ませる）

  **必ず書くもの**

  | 種別 | 具体度 |
  |---|---|
  | **要件（PRD）** | **ファイルパス**。「PRD を読む」では足りない |
  | **親のタスク定義書** | **どの節か**（`§5.1` / `§3.3` など） |
  | **画面デザイン（Figma）** | **ファイル URL ＋ ページ名 ＋ section ＋ 画面ごとのノード ID の表**。<br>**MCP を使う前に読む必要があるスキル名**（`figma-design-to-code` 等）。<br>**取得できないもの**（FigJam は編集者権限が要る等）と**その場合どうするか** |
  | **参考にする既存コード** | **1 ファイルずつのパス**。「survey 一式」「関連コード」のような塊で書かない |
  | **設計規約** | **ディレクトリではなくファイル単位**（`.claude/rules/api/` なら「配下の全ファイル」と明記） |
  | **資料の優先順位** | 同じ対象について複数の資料があるとき、**どれが正か**（例: 画面 = デザインファイル / 仕様 = PRD / 検討ボード = 旧案で根拠にしない） |
  | **既知の誤り・制約** | デザイン側の誤記や、取得できない資料。**「そのまま写すと間違える」箇所を先に潰す** |

  - **画面を伴わないチケットには「Figma の取得は不要」と明示する。** 書いていないと、次のセッションが「取るべきか」を判断できず、取りに行って無駄になるか、取らずに要件を落とすかのどちらかになる
  - 枠を作った時点で「**この定義書だけを渡されたら設計できるか**」を自分で読み返して検証する
  - 「〜一式」「関連する〜」「必要に応じて」と書きたくなったら、**具体名に置き換える**
  - 設計中に新しく必要になった資料が出たら、**その場で定義書の必読リストに追記する**（次の人が同じ探索をしないで済む）
- **なぜ**: 2026-09-03（idpf-api GID-1635）。サブチケットの枠に「PRD を読む」「親の §5.1 を読む」しか書いておらず、「**新セッションに『タスク定義書を読んで詳細設計して更新して』しか僕からは伝えないけど、それで必要なものすべて読んで詳細設計できますか？**」と問われた。実際には ①Figma のノード ID が枠に無い ②Figma MCP の事前スキルが書いていない ③どの資料が正かが辿れない ④参考コードが「survey 一式」のような塊 の 4 つが欠けており、**できなかった**。
  **定義書は「自分が覚えているものを思い出すためのメモ」ではなく、「何も知らない次のセッションが動けるための指示書」**
- **由来**: 2026-09-03 idpf-api GID-1635
- **関連**: COMM-14 ／ FLOW-16（`## 読むもの` に無いものをレビューに渡さない）／ FLOW-20

## FLOW-07: タスク定義は「設計込み」で完結させる（実装中に新事実が判明する状態を許さない）

- **重要度**: blocker
- **要約**: **詳細設計のファイル**に書く設計は、**すべて実コードで裏取り済み**でなければならない。先送り表現を残さない
- **いつ**: 詳細設計を書くとき／承認を求める直前
- **判定**: 「実装時に既存コードと照合して確定」「詳細は実装で決める」といった**先送り表現が詳細設計に残っていたら違反**（＝調査未了のサイン）。設計項目ごとに「どのファイルの何行がどうなっているから、この設計で通る」と実証していなければ違反
- **やること**:
  - 設計項目ごとに「**どのファイルの何行がどうなっているから、この設計で通る**」と実証してから書く
  - **承認前に自分で詳細設計の全設計項目を逐一コードで再確認する**
  - 🔴 **対象は詳細設計のファイル**（2026-10-20 ユーザー決定）。**overview は基本方針まで**なので、
    DDL・API スキーマ・関数の形までの裏取りは求めない（overview に書くのは方式の選択で、その選択の根拠は裏取りする）
  - 影響を受ける読み書き箇所は「その関数内で必要データ（例: booth）が既に取得済みか」を実際に開いて確認し、新規取得の要否を確定させる
  - 既存コードの慣習（例: このリポジトリは DB JOIN を一切使わずアプリ側 map 突合）も grep で裏取りし、設計をそれに合わせる
- **なぜ**: 「**設計含めたタスク定義なのに、実装中に新しいことが分かった、が最近頻発している**」とユーザーに指摘された（GN-5811）。新規 Find が要ると書いたが、実際は全 usecase が既に `prize_booths` を取得済みで不要だった等、調査不足のまま設計を書いていた
- **由来**: GN-5811
- **関連**: VERIFY-01 / VERIFY-02 と同根

## FLOW-01: 設計段階は多角的な視点で考える（根＝考え方、を直す）

- **重要度**: major
- **要約**: 最初の案・既存手法を唯一の前提に固定しない。別方式を**自分から複数考え**、比較材料を**促される前に**出す
- **いつ**: 設計を始めるとき／「既存がこうだから」と言おうとしたとき／レビューで別案を指摘されたとき
- **判定**: **促されてから初めて選択肢を並べたら違反**（自分から出せていない＝多角的に考えていない証拠）。既存実装を擁護する形で議論を閉じたら違反
- **やること**:
  - 設計・実装の**設計段階**では、最初に思いついた案や既存の実装手法にとらわれず、**多角的な視点で手法・構造そのものを複数の角度から検討する**。これが目的そのもの
  - **downstream と混同しない**: 「選択肢として並べる」「トレードオフ（影響範囲×品質）で評価する」「既存踏襲か新方式か」「迷ったら聞く」は、すべて**多角的に考えた"結果に対してどうするか"**でしかない。副次的で、これらを主役に置かない
  - **症状でなく根を直す**: 「選択肢を並べる」を最適化するのではなく「多角的に考える」を直す。真に多角的に考えていれば、選択肢は**促される前に**自然に出る。「促されてから比較する」で止まるのは、根が直っていない証拠
  - **既存も新方式もそれ自体は正義でない**: 既存パターンの踏襲も新方式の採用も正義にしない。既存が正解とは限らない。最終目的は**高品質・一貫性のあるコードの維持**で、影響範囲（方式混在による一貫性の毀損）と品質改善を天秤にかけて判断する。決めきれなければ聞く
  - 着手前に、最初に浮かんだ案・既存の実装手法を「唯一の前提」に固定しない。別の構造・別方式（既存の枠にない代替を含む）を**自分から複数考え**、比較材料を**促される前に**提示する
  - ただし提示はゴールでなく、多角的に考えた結果。評価して決めきれなければ COMM-02 に従い聞く
- **なぜ**: GN-5832 / `useFloorMapSearch` で、`P` ジェネリクス指摘時に**既存実装を擁護（現状肯定にアンカー）**し、畳めることに自力で気づけなかった。`scopes`（u1-api のパーツ方式）も自力で出せず、ユーザー提案で初めて選択肢が揃った。＝設計段階で多角的に考えられておらず、促されてからしか比較できていなかった。**ここが崩れると設計・実装の質が根本から損なわれる**
- **由来**: GN-5832 / `useFloorMapSearch`
- **関連**: この規範は「実装者としての私」が設計段階で守る**層1**。タスク定義書を作った後、本当に出来ているかは**外部 design-review が `~/.claude/notes/design-review-v2/` で事後評価する層2**（実装者は自分の盲点＝既存手法へのアンカーに気づけないため判定を分離）。該当ルールは **R6-01（多角的検討）／ R6-02（判定条件から始める）／ R3-01（既存追随の両方向）**、制約優先の設計原則は **R2-04**。／ META-07 ／ COMM-*

## VERIFY-01: 推測を検証してから結論を出す。確認前に動かない

- **重要度**: blocker
- **要約**: 推測をコードで確認してから結論を出す。確認前に動いてはいけない
- **いつ**: 「〜だから問題ない」「〜だから修正が必要」と言おうとしたとき／ユーザーが前提を口にしたとき／設計や実装に着手する直前
- **判定**: **「どのファイルの何行を見て、そう言っているか」を書けない状態で結論を出していたら違反。** 「〜のはず」「〜と思われる」を根拠に動いていたら違反
- **やること**:
  - ユーザーが「〜であれば問題ない」と言ったら、**まずその前提が成立しているかコードを読んで確認する**
  - 確認が終わってから「〜であることを確認しました。したがって〜」と報告する
  - 確認前に「〜のはずだから実装します」と動かない
  - 確信が持てないなら、判断をユーザーに委ねる（「〜という前提で進めてよいですか？」）
- **なぜ**: 「〜だから問題ない」「〜だから修正が必要」という推測が不正確なまま実装に入り、手戻りや余計な変更が生まれた。ユーザーから「**前提事項と本質がすぐにブレる**」と指摘されている
- **由来**: ユーザー指摘
- **関連**: COMM-*（迷ったら聞く）／ [[feedback-04-editing]]（修正の意図が達成されたことを確認する）
