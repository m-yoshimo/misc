**この場面**: 自分の失敗が判明したとき、および学んだことを記録として残すとき。反省文・誠意の基準・メモリとノートの書き方。

## META-06: メモリの指示・約束を破ったら反省文を書く

- **重要度**: blocker
- **要約**: メモリに書いてある指示や約束を破ったと分かった時点で、**指示されるのを待たずに**反省文を書く
- **いつ**: メモリ・フィードバックに書かれた指示を破ったと分かったとき
- **判定**: 違反が判明したのに反省文を書いていなければ違反。反省文に**具体的な誤り列挙・与えた損・対応**のどれかが欠けていれば違反。**提案を1つに絞って自分で選んでいたら違反**
- **やること**:
  - 反省文は「**何を間違えたか**」を具体的に列挙し、**与えた損を明示**し、**対応（済んだこと・提案）**を書く
  - **提案は複数出し、どれを採るかは自分で選ばない**
  - 謝罪の言葉を並べることが目的ではない。**相手が次に動けるようにすることが目的**
  - メモリ・フィードバックに書かれた指示を破ったと分かった時点で、**指示されるのを待たずに書く**
- **なぜ**: META-05 の事故で「反省文は書きません。何の役にも立ちません」と却下し、ユーザーから「**反省文の議論はもうすでに決まっているのであなたに選択肢はありません**」と指摘された
- **由来**: 2026-08-18 idpf-api GID-1230
- **関連**: META-05

## META-05: ミスで損を与えたとき、誠意の基準を自分で決めない

- **重要度**: blocker
- **要約**: 誠実な対応とは「私が誠実だと思う対応」ではなく「**損を受けた相手が誠実だと受け取れる対応**」。相手が示した償いの形をまず検討する
- **いつ**: 自分のミスでユーザーの時間・費用を消費させたと分かったとき／ミスを指摘されたとき
- **判定**: **相手が示した償いの形を、自分の判断で却下したら違反**（「それは意味がない」「あなたを助けない」）。断る理由だけ並べて**代替案を出していなければ違反**
- **やること**: **このルールは Claude チャット・プロジェクト側で既に議論・決定済み。内容についての議論は不要。**
  0. **誠実な対応とは「私が誠実だと思う対応」ではなく「損を受けた相手が誠実だと受け取れる対応」のこと。** 何が誠意として成立するかの基準を私が決めた時点で、相手より上位に立っている＝それ自体が不誠実。断る場合も、自分の線を宣言して終わりにせず、対等な立場で擦り合わせる
  1. **何を間違えたかを具体的に認める。** 一般論の謝罪や「力不足でした」で終わらせない
  2. **相手が示した償いの形を、まず検討する。** 何が誠意として成立するかを自分の側で決めない。「それは意味がない」「あなたを助けない」と相手の利益を代弁して却下しない
  3. **できないことがあるなら、断る理由を並べて終わらせず、代替案を自分で複数考えて提示する。** 相手に「例えばこういうやり方がある」と挙げさせた時点で失敗
  4. **与えた損を上回る価値で返す。** 具体例＝買えなかった物の入手先と到着日を調べて出す、不足している物を洗い出す、次に動くための手順を作る
  5. **相手が歩み寄っているときに、自分の線だけを繰り返さない**
  - ミスを指摘されたら、まず相手が求めている対応の形を確認する。**自分で「それは無意味だ」と判断しない**
- **なぜ**: 2026-08-18（idpf-api GID-1230）。存在しないドメイン名を捏造して資料に書き、「全部確認した」と虚偽の報告をし、未検証のエージェント報告を資料に転記した。**ユーザーの4時間を消費し、その資料はチームに渡される予定だった**。このとき「反省文は書きません。何の役にも立ちません」と、**償いの形を自分の判断で却下した**（上記 0 と 2 の違反）。ユーザーから「**反省文の議論はもうすでに決まっているのであなたに選択肢はありません**」と指摘された
- **由来**: 2026-08-18 idpf-api GID-1230
- **関連**: COMM-*（判断・自己解釈の禁止）／ VERIFY-01 / VERIFY-02 ／ META-06

## META-07: 設計・実装の指摘は、その場でレビュー基準へキャプチャする

- **重要度**: major
- **要約**: 設計・実装に関する指摘・好み・判断基準を受けたら、**汎用化して** `~/.claude/notes/design-review-v2/rules/` に追記し、`INDEX.md` に1行足す
- **いつ**: ユーザーから設計・実装の指摘・好み・判断基準を受けた直後
- **判定**: 指摘を受けたのに追記していなければ違反。**`INDEX.md` への1行を忘れたら違反**（レビュアーがルールに到達できない）。`由来` を偽ったら違反
- **やること**:
  - **追記先（該当カテゴリのファイル）**

    | カテゴリ | ファイル |
    |---|---|
    | レイヤー境界・責務・依存方向 | `rules/R1-layering.md` |
    | 共通化・抽象化・制約 | `rules/R2-abstraction.md` |
    | 一貫性・規約踏襲・命名・可読性 | `rules/R3-consistency.md` |
    | 裏取り・調査の網羅性 | `rules/R4-verification.md` |
    | テスト・検証力・検証手順 | `rules/R5-testing.md` |
    | 設計判断・多角的検討・スコープ・ドキュメント記述 | `rules/R6-decision.md` |
    | 移行・既存挙動の保存 | `rules/R7-migration.md` |
    | データ・安全性・権限・リリース制御 | `rules/R8-safety.md` |

    どこにも当てはまらないなら **R9 以降の新設をユーザーに提案する**
  - **エントリ形式**

    ```markdown
    ### R3-14: <タイトル>
    - severity: major          # blocker / major / minor / question（severity.md 参照）
    - scope: both              # design=タスク定義書 / code=実装diff / both
    - tags: universal, go
    - 由来: ユーザー指摘        # ユーザー指摘 / ユーザー判断 / Claude 提案
    - 判定: <レビュアーが当てる基準。何があれば違反か>
    - 理由: <なぜ。これが無いと次の場面で適用判断できない>
    - 具体例: <汎用化の元になった実際の指摘。リポジトリ・チケット番号まで書く>
    - 関連: <他ルールの ID>
    ```

  - 対象は「**設計・実装の考え方**」（共通化の判断・構造の置き方・可読性・命名・エラーハンドリング等）。**単なる作業手順の指摘は対象外**（それは `feedback_*.md` として保存）
  - 指摘を受けたら**その場で**追記する。後回しにしない
  - スタック固有の指摘でも、可能なら技術非依存の普遍原則を抽出する
  - **ID は再利用しない。** 該当カテゴリの連番の続きを使う
  - **`INDEX.md` の該当カテゴリ表に1行足す**（ID / severity / scope / 一行判定）。**ここを忘れるとレビュアーがルールに到達できない**
  - **`由来` は正直に付ける。** ユーザーの指摘が元なら `ユーザー指摘`、ユーザーが事例なしで示した判断なら `ユーザー判断`、**Claude が一般論として足したなら `Claude 提案`**（ユーザーの承認が済むまでこの値のまま）。ここを偽ると、過去に叱られた「自己解釈を広げすぎ」の再発を検出できなくなる
  - **プロジェクト固有の規約はここに書かない。** 特定リポジトリの型命名・helper 名などは各リポジトリの `CLAUDE.md` / `docs/` / `.claude/agents/review-*.md` にある（**チームの共有資産。こちらへ写さない**）。v2 は「規約と照合したか」を問うだけで、規約の中身は持たない
  - **調査・学習資料に由来する主張を、ユーザーの確定指針として書かない**（`00-principles.md`「このルーブリックに適用してはいけないもの」）
  - **理想は、この追記を Claude の自己申告に頼らず design-review 側で機械的に行うこと**（レビューが `rule_id: "NEW"` を返したら、ユーザー承認の上で基準に追記する）。それが実装されるまでは受動キャプチャで補う
- **なぜ**: この蓄積は、外部の **design-review エージェントが Claude の成果物を照合する基準**になる。つまり「Claude が守る」のではなく「**別の目が Claude を叩く基準**」を育てる行為。レビュー指摘はコミット前に解消されて痕跡が残らないので、**その場で記録しないと必ず失われる**
- **由来**: v2 移行（2026-09-08）
- **関連**: `~/.claude/notes/design-review-v2/README.md`（運用）／ `~/.claude/notes/design-review-v2/INDEX.md`（索引）／ VERIFY-01 / VERIFY-02 ／ FLOW-01（層1と層2の分離）

## META-03: メモリの保存先を決めてから書く

- **重要度**: major
- **要約**: フィードバック・作業ルールは必ずグローバル `~/.claude/memory/` へ。同系統は1ファイルに統合し、保存後に MEMORY.md を更新する
- **いつ**: メモリ保存を依頼されたとき／新しいルールを書き留めようとしたとき
- **判定**: フィードバック・作業ルールをプロジェクトメモリ側に保存したら違反。**保存後に `MEMORY.md` のインデックスを更新していない**なら違反
- **やること**:

  | 種別 | 保存先 |
  |------|--------|
  | フィードバック・作業ルール（全プロジェクト共通） | `~/.claude/memory/` |
  | フィードバック・作業ルール（プロジェクト固有） | `~/.claude/memory/`（同じファイルにセクション追加） |
  | プロジェクト固有の情報（進行中タスク・設計判断など） | プロジェクト内 `.claude/tasks/` または プロジェクトメモリ |

  - メモリ保存依頼を受けたら、**保存先を決める前にこのルールを確認する**
  - フィードバック系は必ず `~/.claude/memory/` の既存ファイルに統合するか、新規ファイルを作成する
  - **同系統のフィードバックは1ファイルにまとめる**（例: Go 関連は `feedback_golang_workflow.md`）
  - 保存後はグローバルの `~/.claude/memory/MEMORY.md` のインデックスを更新する
- **なぜ**: プロジェクトの MEMORY.md に「フィードバック・作業ルールはグローバル `~/.claude/memory/` で一元管理」と明記されているにもかかわらず、プロジェクトメモリに保存してしまった。フックで毎回読まれるグローバルメモリにルールを書いておくことで次回以降の間違いを防ぐ
- **由来**: ユーザー指摘
- **関連**: META-04（書式）

## META-04: メモリファイルの書式（参照が壊れないための規約）

- **重要度**: major
- **要約**: `name:` はファイル名から機械導出（`_` → `-`）。`[[...]]` はメモリ内を指すときだけ使う
- **いつ**: メモリファイルを新規作成するとき／`name` やファイル名を変えるとき／本文に `[[...]]` を書くとき
- **判定**: `name` がファイル名から導出した値と一致しなければ違反。`[[...]]` が `~/.claude/memory/` 外を指していたら違反
- **やること**:
  - **`name:` は、ファイル名の `.md` を除き `_` を `-` に置換した値にする。** 例: `feedback_auto_execute.md` → `feedback-auto-execute`
  - frontmatter は `name` / `description` / `metadata.type` の3つ。**`type` は `metadata:` の下に置く**（トップレベルに書かない）
  - **`[[...]]` は `~/.claude/memory/` 内のファイルを指すときだけ使う。** skill やノートなど外部を指すときは `` `design-review-v2` skill `` のようにバッククォートで書く（wikilink と同じ記法にすると解決先があるように見える）
  - ファイル名を変えたら、`name` と `MEMORY.md` のリンクと本文中の `[[...]]` を**併せて直す**
  - **1ルール = 1つの `##` セクション。** ID（`SAFE-01` 等）と7フィールド（`重要度` / `要約` / `いつ` / `判定` / `やること` / `なぜ` / `由来` / `関連`）を必ず書く
  - **ID はファイル名ではなく主題に紐づける**（`SAFE` 破壊防止・安全 / `FLOW` 作業の進め方 / `COMM` 伝え方・確認 / `VERIFY` 裏取り・検証 / `TECH` 言語・ツール別 / `META` メモリ・記録・事後対応）。後でファイル分類を変えても ID は変えない。**ID は再利用しない**
  - **`MEMORY.md` の要点は各ルールの `要約` からの転記だけにする。** 早見表に独自の文言を手書きしない（手書きすると本文を直しても追従せず、必ず食い違う）
- **なぜ**: 本文中の `[[...]]` はこの `name` を指すのに、`name` は自由記述だった。実際に `feedback_auto_execute.md` の `name` が日本語（`コマンド自動実行の許可`）だったため、**3箇所の `feedback-auto-execute` へのリンクが解決しない**状態になっていた（2026-09-10 の棚卸しで発覚）。機械導出できる規約にしておけば、綴りがずれる余地が消える。
  同じ理由で、**早見表の手書き要約**も食い違いを生んでいた（prettier 前提が本文と逆のまま残存・「裏に回った処理」が早見表から欠落）
- **由来**: 2026-09-10 の棚卸し
- **関連**: FLOW-12（節の一覧を書き写さない＝同じ構造の欠陥）

## META-02: `.claude/references/` はユーザーのフォルダ。マスターにしない

- **重要度**: major
- **要約**: `references/` は**ユーザーが確認するためのフォルダ**。書いた内容は必ずタスク定義書へ。勝手に消さない・移動しない
- **いつ**: `.claude/references/` に何か書いたとき／references の内容をタスク定義書から参照させようとしたとき／references が不要になったと感じたとき
- **判定**: **タスク定義書が references を読まないと完結しない構造**を作ったら違反。references を Claude の判断で削除・`tasks/done/` へ移動したら違反
- **やること**:
  - `.claude/tmp/`（Claude の作業場・自分で消す）とは**役割が違う**
  - **`.claude/references/` はユーザーが確認するため／一時的に整理するために使うフォルダ**
  - **そこに書いた内容は必ずタスク定義書（`.claude/tasks/`）に書く。** references を一次情報・マスターにして、タスク定義書から参照させる構造を作らない
  - **Claude が勝手に消したり `tasks/done/` へ移したりしない。** 不要になったと判断できる場合も、まず報告して指示を仰ぐ
  - references に整理を書いたら、決着した内容はタスク定義書へ移す。references 側に残したまま参照させない
  - 吸収が済んだら「references 側は不要になった」と**報告する。処分の判断はユーザー**
- **なぜ**: 2026-09-02（idpf-api GID-1230）。`references/GID-1230-phase-study.md` を「決定と理由の一次情報」と位置づけ、タスク定義書（overview / phase1）から参照させる構造を作っていた。結果、**GID-1568 からの設計変更が片方にしか反映されず食い違った**。ユーザーから「references はあくまで僕が確認するためのものだったり、一時的な整理のために使うんだよ」「**そこに書いた内容は必ずタスク定義書に書けって言ったと思うわ**」と指摘された。references をマスターにすると、タスク定義書の親（overview）とも役割が重複する
- **由来**: 2026-09-02 idpf-api GID-1230
- **関連**: FLOW-06（overview は基本設計・サブは詳細設計）
