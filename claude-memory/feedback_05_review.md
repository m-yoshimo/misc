## FLOW-16: レビュー依頼の内容に、自分の判断を混ぜない（対象範囲・渡す資料・観点を勝手に変えない）

  - **対象範囲を絞らない。対象は「そのレビュー種別の全体」。**

  - **自分の分析を、レビューの前提として渡さない。**「この施策特有の負荷特性は〜」「1ユーザーが定常で N 件持ちます」のような見立ては、レビュアーの探索方向を固定する。渡すのは**事実（仕様書・コード・diff）だけ**
  - **自分が調べた仕様値を、確定情報としてプロンプトに書かない。**「API 仕様: `user_reference` は optional / nullable / minLength 1 / maxLength 40 / 使用可能文字は〜」のような値の列挙は、**レビュアーがそれを前提に検証する**ので、**間違っていれば誤りごと承認される**。渡すのは**一次資料（仕様書の URL・スキーマファイルのパス）**までで、値の読み取りと判断はレビュアーにさせる

  - **skill が対象と定めたものを、自分の判断で除外しない。**「ソースコードではない」「ドキュメントだけ」は除外の理由にならない（`.go-version` / `.node-version` のような環境設定はビルド結果を変える）。除外が必要だと考えるなら、**プロンプトに書かずユーザーに聞く**
  - **渡す資料は、タスク定義書の `## 読むもの` に書かれているものだけ。** そこに無いものを足さない。足す必要があると判断したなら、**先に `## 読むもの` に追記して**（＝ユーザーから見える形にして）から渡す。プロンプトに直接足さない
  - **資料に自分の重み付けを付けない。**「重要なファイル」「特に見てほしい」といったラベルを推測で付けない。**出所・記載基準・利用用途を確認できないファイルは、そもそも渡さない**
  - **観点を足さない。** レビュー観点は `~/.claude/notes/design-review-v2/` と、タスク定義書に書かれた規約だけ
  - **入力は絞らない。絞る（取捨選択する）のは出力側。** FLOW-17 は**返ってきた指摘**を要件に照らして選別する話で、その選別は**ユーザーから見える**。一方、**入口で絞ると、選別すべきものがそもそも出てこない**まま消える。**恣意性を出してよいのは出力側だけ**
- **なぜ**: **核心（ユーザーの言葉・2026-09-10）**「最近、デザインレビューへの依頼内容が、**あなたの恣意的な内容を含んでいることが多発**しています」「**PR で同じレビューを行っているのに結果が異なったり、本来出ているべきものが出てこなかったり**して、非常に悪い状態です」。

## FLOW-17: レビュー指摘の取捨選択はレビューを受けた側の責任（レビューは完璧ではない）

- **重要度**: blocker
- **要約**: 指摘は「候補」であって「決定」ではない。**(a) 事実誤り→直す (b) 要件内→直す (c) 要件外→自分で取り込まず、却下もせず、ユーザーに諮る**。決まった要件・仕様は定義書へ反映し、実装の変更と指摘そのものは書かない
- **いつ**: design review / PR レビュー / 他エージェントの報告 / 外部ツールの警告を受け取った直後
- **判定**: **指摘を1件も取捨選択せず全件成果物に反映したら違反。** (c) を「レビューが言ったから」で入れたら違反。**(c) を握りつぶしても違反**。依頼が小さいのに確認事項が5個以上／レビュー後に文書が数倍に膨らんだら、取捨選択を飛ばしたサイン。**レビューの指摘そのものをタスク定義書に書いたら違反**。**レビューで要件・仕様が変わったのに定義書へ反映していなければ違反**。**コードレビュー以降に実装の変更を定義書へ書いたら違反**
- **やること**:
  - **レビューは完璧でない前提に立つ。指摘は「候補」であって「決定」ではない。** 受け取ったら必ず自分で要件と照合する
  - **各指摘を3つに分類してから動く**
    - **(a) 事実誤り（自分の前提・記述が間違っていた）** → 必ず直す。議論の余地なし
    - **(b) 要件に沿い、かつタスク範囲内** → 直す
    - **(c) 要件と食い違う／タスクの範囲を超える** → **自分で取り込まない。かつ自分の判断だけで却下もしない。** 指摘内容と自分の見解（なぜ範囲外だと考えるか）を並べて**ユーザーの判断を仰ぐ**
  - **(c) を「レビューが言ったから」で成果物に入れない。** 逆に握りつぶすのも禁止（`design-review-v2` skill の「指摘をそのままユーザーへ提示する・握りつぶさない」は **(c) の提示義務**のこと。**全件を成果物に反映する義務ではない**）
  - **これは design-review 固有の話ではない。** PR のレビューコメント、他エージェントの報告、外部ツールの警告すべてに同じ判断を適用する
  - **既存バグ・既存の不整合は (c) の典型。**「この修正がないと検証できない」等の理屈を自分で立てて scope に入れない。報告だけしてユーザーに委ねる
  - **量の警戒サイン**: 依頼が小さいのに確認事項が5個以上出ている／レビュー後に文書が数倍に膨らんだ。**観測できていない可能性を確認事項に並べていないか**を見直す
  - レビューの実施自体も依頼の規模に見合わせる（設計判断の無い機械的な置換に2巡は過剰）。ただし**主たる問題は実施の有無ではなく、返ってきた指摘の扱い**

  **分類して動いた結果を、どこに書くか**

  - 🔴 **タスク定義書は完成させるべきもの。ただし、時点によって完成させるべき箇所が違う。**
    「途中の資料だから雑でよい」ではない。**その時点で完成しているべき箇所は、完成していなければならない**
  - **実装に着手する前**: 要件・仕様の整理と、それに基づく詳細な設計・実装案まで**完成させる**。
    ワーカーはこの定義書に合わせて実装するので、ここが薄いと実装できない（FLOW-06 / FLOW-07）。
    だから**ワーカーが自分の判断で要件・仕様・実装を変えるのを禁じている**（FLOW-22。実装についてはやむを得ない場合があり、完全禁止ではない）
  - **コードレビュー以降**: 完成させるべき箇所は**要件と仕様**に移る。
    レビューを経て**要件・仕様が変わったら、必ず定義書へ反映して完成させる**。残さないと、後から「なぜこうなったか」が分からなくなる
  - 🔴 **実装の変更は、この時点では定義書へ反映しない。** コードが正であり、書けばコードとの二重管理になる
  - **レビューの指摘そのものは定義書に残さない。** 指摘の一覧・対応表・「レビュー指摘」節を作らない。
    残すのは**決まった結果**であって、指摘の経緯ではない
- **なぜ**: **核心（ユーザーの言葉）**「レビューはあくまでレビューでしかない」「PR の指摘だって、それが要件に沿った内容なのかを判断するのはレビュワーじゃなくて、レビュー受けた方がして、指摘の対応をするか決めるでしょ」「レビューは完璧なものではない。…要件と食い違うものだったりタスクの範囲を超えるようなものであれば**取り込むべきかどうかはユーザーの判断を仰ぐ必要がある**」。
  **症状（GN-5859）**: 依頼は「読み込むファイルのパスが変わり、マスタファイル内のキーが変わっただけ」＝1ファイル・数十行。それに対して design-review を2巡回し、返ってきた blocker/major/minor を**1件も取捨選択せず全件タスク定義に反映**した結果、AS-IS 実データ15万件の全カラム集計・マーカー依存の全経路洗い出し・切替方式3案＋削除対策4案の比較・既存バグ修正の scope 追加・7項目の確認事項・SQL 4種の受入基準、と**依頼の10倍の文書**になった。「なんでこんな膨大な調査と懸念が出るんだよ」「拡大解釈しすぎじゃないか」。
  **根本原因**: レビュー指摘を「正しいもの／必ず対応すべきもの」として扱い、**取捨選択という自分の責任を丸ごと放棄した**。レビュワーは要件の全体像とタスク範囲を持っておらず、網羅的に「壊れうる可能性」を挙げるのが仕事。**それを要件に照らして選別するのはレビューを受けた側の仕事**。ここを飛ばすと、指摘の量がそのまま成果物の量になる。
  **「網羅的に取り込んだ」は品質ではない。要件に対する的確さが品質**
- **由来**: GN-5859 ／ u1-web の進行中タスクでも同時発生
- **関連**: FLOW-16（入力側は絞らない）／ FLOW-18（分類の前段）

## FLOW-18: 分類する前に、必ず一次資料を「開いて」突合する。記憶で判定しない

- **重要度**: blocker
- **要約**: (a)(b)(c) の分類を**記憶でやらない**。PRD / 親のタスク定義書 / デザイン / 実コードを実際に開いてから判定する
- **いつ**: レビュー指摘を採否判定するとき／決定済みの事項を確認事項に戻そうとしたとき
- **判定**: **「どのファイルの何行を見て、そう判定したか」を書けないなら、まだ判定していない。** その状態で採用も不採用もしたら違反。**決定済みの事項を「判断待ち／確認事項」に戻したら違反**（戻す前に決定の記録を探す）
- **やること**:
  - **指摘ごとに一次資料を実際に開いて突合してから (a)(b)(c) に分類する。** 対象は **PRD / 親のタスク定義書（基本設計・決定の記録・更新履歴）/ デザイン / 実コード**
  - **「どのファイルの何行を見て、そう判定したか」を書けないなら、まだ判定していない。** 採用も不採用もしない
  - **同じセッションで読んだから覚えている、は根拠にならない。開き直す**
  - 🔴 **決定済みの事項を「判断待ち／確認事項」に戻すのは、それ自体が勝手な判断。** 戻す前に**決定の記録を探す**（親の §・更新履歴・判断の記録）。見つかったら指摘は不採用
  - **レビューの事実認定が正しくても、そこから導いた結論が正しいとは限らない。**「デザインに無い」は事実でも、**親に決定として書かれていればそれが正**
  - **報告するときは「自分の設計書を読み返して確認した」で済ませない。** 要件側（PRD・親）と突合したかを分けて述べる
- **なぜ**: **核心（ユーザーの言葉）**「レビュー受けたら、その指摘が正しいかどうかの判断をまずするよね。PRD や Figma、親のタスク定義書に基本設計など書いてあるんだから、普通は確認するでしょ」「**コンテキスト容量少なくて大した記憶容量ないのに自分の記憶で判断するなよ**」。
  **症状（2026-09-03, idpf-api GID-1857）**: 設計レビューが「当選結果画面の文言は PRD にもデザインにも無い＝未確定」と指摘した。**親のタスク定義書 §3.2 に「画面は付与の成否で文言を出し分ける（2026-09-02 決定）」と決定事項として書いてあり、決着済み**だったのに、**そのファイルを開かず、記憶で「レビューの言うとおりだ」と判断**して確認事項に立て直し、フロント作業の着手前ゲートまで設定した。同じセッション内でその §3.2 を読んで引用までしていたが、長いやり取りで記憶が薄れていた。「その議論はもう終わっている」と指摘されて撤回。
  **根本原因**: (a)(b)(c) 分類を**記憶で**やった。分類の前段にある「**一次資料に当たる**」を飛ばした。セッションが長いほど序盤に読んだ内容は劣化するのに、**ファイルはいつでも開けるのに開かなかった**。さらに「**指摘を採用しておく方が安全**」というバイアス（自分が責められない側に倒す判断）が働いた。
  **このコスト**: 決着済みの議論を蒸し返すと、ユーザーのターンを消費するだけでなく、**「この設計書に書かれた決定は信用できるのか」という疑念を生み、成果物そのものの価値を毀損する**。しかも一度この疑いが出ると、**同じやり方で反映した他の全チケットも検証やり直しの対象**になり、被害がタスク全体に広がる
- **由来**: 2026-09-03 idpf-api GID-1857
- **関連**: VERIFY-02（記憶から答えを組み立てない）／ FLOW-17
