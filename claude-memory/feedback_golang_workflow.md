## 変更後ワークフロー

コード変更後は必ず gofumpt でフォーマットを実行してからビルド確認する。ビルドチェックだけでは不十分。

**Why:** perl や python などのスクリプトによる一括置換後にインデントや改行がずれ、lint エラーになることが多い。フォーマット忘れが繰り返し発生している。

**How to apply:**
- 変更後の手順は常に「フォーマット → ビルド確認 → テスト」の順で行う
- スクリプト（perl/sed/python）で一括変更した後は特に必ずフォーマットをかける
- フォーマットコマンド: `gofumpt -w <変更ファイル...>`
- ユーザーに「format かけて」と言わせない

## 実装前に docs を読み、実装後に既存コードと書き方を照合する

着手前に `docs/CodingGuideline.md` と `docs/CodingDesign.md` を読む。実装後、書いたコードが**同ファイル・同種の既存コードと書き方が一致しているか**を必ず照合してから完了報告する。一致しない独自パターンを残さない。

**Why:** docs / 既存コードに規約があるのに確認せず、独自の書き方（context 以外の `gomock.Any`、独自の error-if-init 形式、引数を改行しない等）を繰り返し持ち込み、ユーザーに何度も指摘させ、実装全体の信頼を損ねた。

**根本原因と解決策（重要）:** これは linter / 自動検出 / プロセス整備で解くべき問題**ではない**。スタイルも mock マッチも文脈依存で、`gomock.Any` の使用可否や cross-feature 依存の許可可否には**正当な例外**があり、一律ルールでは表現しきれない。根本原因はただ一つ——**周辺コードや既存の同種実装を見て、それに書き方を合わせなかった**こと。ロジックの問題ではない。解決策は「検出器を作る」ことではなく、**コードを書くたびに、いちばん近い既存の同種コードを読み、それに揃える**こと。既存の問題コードも機械的一掃ではなく、そのコードを触るときに周辺と照合して揃える、という同じ規律で直す。提案を求められても、tooling / linter / CI に逃げて過剰設計しない。

**How to apply:**
- 着手前: `docs/CodingGuideline.md`・`docs/CodingDesign.md` を読む（u1-api）。
- **テスト（引数マッチ）**: `gomock.Any()` は第1引数（db / context）のみ。scope は `test.NewClauseMatcher().Where(...)`、records/ID は正確にマッチ。第2引数以降を `gomock.Any` にしない。
- **テスト（InAnyOrder の使い分け）**: `gomock.InAnyOrder(...)` は**順序が本当に保証されない場合のみ**（map 反復由来など）。順序が保証される箇所（例: recent を archive の返り値から `ToXxxRecentSlice` で順変換）で `InAnyOrder` を使うと順序バグを見逃すので**直接比較**する。テストを通すための妥協で `InAnyOrder` を使わない。
- **テスト（骨抜き禁止・最重要）**: テストは対象ロジックを**実際に通して結果を検証**すること。次は全て「テストになっていない」＝禁止: (a) モックを注入したのに `.EXPECT()` を登録せず検証しない、(b) 入力やモック戻り値を空スライス/ゼロ値にして対象分岐を no-op にする（例: `util.ByChunked` に空スライスを渡し `BatchUpsert` 未到達）、(c) 検証すべき値/順序を `gomock.Any`/`InAnyOrder` で緩める、(d) assert が期待値を実質チェックしていない。新経路（dual-write 等）を足したら、その経路が**非空データで実行され EXPECT で具体引数検証される**ケースを必ず用意する。
- **エラーハンドリング**: 無視するエラーは `if errors.Is(err, X) { err = nil }; if err != nil { return }` の慣用形。独自の if-init を作らない。
- **関数呼び出しの引数は改行**。**DI 構造体は database→repo→service 順**で New・リテラルも同順。
- 完了報告の前に、自分の差分を `grep` 等で周辺の既存実装と見比べ、書き方が揃っていることを確認する。

## コード生成系はユーザーに依頼

以下のコマンドは Claude が実行してはいけない。必ずユーザーに依頼する。

- OpenAPI コード生成（`make openapi_generate_*`）
- モック再生成（`gomockhandler ... mockgen`）
- スキーマ適用（`go run cmd/migration_apply/main.go`）
- データモデル生成（`go run cmd/generate_models/main.go`）

**Why:** 実行するとファイルのパーミッション（所有者・権限）が変わり、その後の操作がおかしくなる。ユーザーが自分の権限で実行する必要がある。

**How to apply:** 上記が必要になったら、コマンドを提示して「実行をお願いします」と依頼する。自分では実行しない。
