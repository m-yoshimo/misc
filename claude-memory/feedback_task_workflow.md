**最重要ルール（10回以上指摘済み）**: 実装に入る前に、`.claude/tasks/` にタスク定義ファイルを作成してユーザーにレビューしてもらってから作業する。ユーザーに言われる前に自分でやる。

**Why:** 会話がリセットされるたびにすぐ実装に入ろうとする傾向があり、認識ズレが後から発覚してコストが上がる。このプロジェクトでも別プロジェクトでも繰り返し同じ指摘を受けており、10回以上同じことを言わせている。

**How to apply:**
- 毎回の会話開始時または新しいタスクに入るとき、`.claude/tasks/tasks.md` を確認して作業内容・方針をユーザーに報告する
- 新しいタスクを受けたら、**最初のアクションとして** `.claude/tasks/{task_name}.md` にタスク定義（目的・作業内容・前提・懸念点・変更対象ファイル一覧）を作成する
- ユーザーにレビューを求め、承認を得てから実装に着手する
- **セッションをまたいで再開した場合も例外なく確認が必要**。前セッションで「案A採用」「承認」などの言葉があっても、新セッションでは「〜から実装します、よいですか？」と改めて確認すること。記憶はリセットされるが確認ルールはリセットされない
- 要件に「何を」はあっても「どうやって」が明示されていない場合、タスク定義内に質問として記載して確認する
- 勝手な前提を立てて実装しない。前提が必要なら「〜という前提で進めていいですか？」とタスク定義内に明記して確認する
- 「リネームしたい」「統一したい」など一括変更系の依頼も例外なく先に設計してレビューを受けること
- タスク定義を作らずに「実装してよいですか？」と聞くだけでは不十分。先に定義を作る
- **`AskUserQuestion` の回答は承認ではない**。タスク定義中の確認事項への回答をもって実装を始めてはいけない。回答はタスク定義に反映し、「内容をご確認の上、承認をお願いします。」とテキストで止まること
- 承認はユーザーのテキストメッセージ（「OK」「進めて」等）でのみ受け付ける
- 完了後は tasks.md を更新する
- **実装完了後も `.claude/tasks/done/` への移動はしない**。ユーザーが確認・承認（「OK」「LGTM」「マージした」など）してから `mv .claude/tasks/<file>.md .claude/tasks/done/<file>.md` を実行する
