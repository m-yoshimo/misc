**最重要ルール（10回以上指摘済み）**: 実装に入る前に、`.claude/tasks/` にタスク定義ファイルを作成してユーザーにレビューしてもらってから作業する。ユーザーに言われる前に自分でやる。

**Why:** 会話がリセットされるたびにすぐ実装に入ろうとする傾向があり、認識ズレが後から発覚してコストが上がる。このプロジェクトでも別プロジェクトでも繰り返し同じ指摘を受けており、10回以上同じことを言わせている。

**How to apply:**
- 毎回の会話開始時または新しいタスクに入るとき、`.claude/tasks/tasks.md` を確認して作業内容・方針をユーザーに報告する
- 新しいタスクを受けたら、**最初のアクションとして** `.claude/tasks/{task_name}.md` にタスク定義（目的・作業内容・前提・懸念点・変更対象ファイル一覧）を作成する
- **タスク定義書が要るのは「コード・設定の変更を伴う実装／設計」だけ。以下は作らない**（作ろうとして毎回止められている・2026-09-02 ユーザー指摘）。
  - タスク定義書自体の整理・リネーム・移動・done 化などの**メタ処理**
  - メモリ / ルール / ドキュメントの更新
  - 軽い調査・質問への回答（コードを読んで答えるだけで、変更を伴わないもの）
  - **ただし Tier 0 の「作業全体を提示して承認を得る」は引き続き必要**。省くのは*ファイルを作ること*だけで、事前提示・承認は省かない。
  - 迷ったら「これはリポジトリのコードを変えるか？」で判定。No ならタスク定義書は不要。
- **セッションタイトルとタスク定義書ファイル名には、必ずチケット番号を入れる**。Editor のセッション一覧からタスク定義書を辿れるようにするため、両者のチケット番号は必ず一致させる。
  - **チケット番号は必ず親チケットを使う**。子チケット（サブタスク）で作業している場合でも、タイトル・ファイル名に書くのは親チケット番号。
  - **セッションタイトルはチケット番号の直後に半角スペースを入れる**（例: `GID-1624 旧SMS Publisher削除`）。ファイル名は既存に倣い `GID-1624-remove-old-sms-publisher.md` のようにハイフン区切り（スペース不要）。
  - **チケット番号が未定の場合は、セッションタイトル・ファイル名の両方に `no-ticket` を付与する**（例: タイトル `no-ticket メモリルール整理` / ファイル名 `no-ticket-memory-rule.md`）。
  - **Why:** チケット番号が入っていないと、セッションのタイトルから対応するタスク定義書のファイルを探すのが極めて面倒（ユーザー指摘）。親チケットに統一するのは、子チケット単位だと同一作業がバラけて辿れなくなるため。
- **段階開発やチケット分割が必要になったタイミングで、`.claude/tasks/` 直下に親チケットのディレクトリを作り、関連するタスク定義書はすべてそこに入れる**。
  - ディレクトリ名は `{親チケット番号}-{英小文字ケバブの概要}`（例: `GID-1635-daily-kuji`）。
  - **ディレクトリ内のファイル名は `{子チケット番号}-{内容}`**（例: `GID-1855-pointpf-api.md`）。**親チケット番号は付けない**（ディレクトリ名が持っているため重複になる）。
    - **子チケット番号が不明な場合、および番号が付かない性質のもの（タスク全体用の `overview.md` など）は番号不要**。この場合 `no-ticket` も付けない（親ディレクトリ名で辿れるため）。
    - **番号と内容の両方を入れる**（2026-09-02 ユーザー決定）。**番号だけ**（`GID-1855.md`）だと一覧して中身が分からず、**内容だけ**（`pointpf-grant.md`）だと親チケットの一覧と突き合わせられない。実際にこの 2 つを順に試して、どちらもユーザーに指摘された。
    - 🔴 **語の重複に注意する。** 「pointpf 側の付与」と「idpf 側の付与」の両方に `grant` を使い、**名前からどちら側か判別できない**と指摘された（2026-09-02）。**兄弟ファイル同士で語が衝突していないか、名前を決める前に並べて確認する。**
    - **親 `overview.md` に「チケット ↔ ファイル名 ↔ 状態」の対応表を置く。**
  - **セッションタイトルには従来どおり親チケット番号を付ける**（ディレクトリに入れても省略しない。`GID-1635 デイリーくじ 抽選API` のように、親チケット番号 + スペース + 内容）。
  - 分割が不要な単発タスクは、これまでどおり `.claude/tasks/` 直下に `{親チケット番号}-{概要}.md` のフラットなファイルで置く（例: `GID-1568-admin-operation-logs.md`）。ディレクトリ化するのは分割が発生してから。
  - **実例（対応済みサンプル）**: `.claude/tasks/GID-1635-daily-kuji/overview.md`。親 GID-1635 のディレクトリに、タスク全体用の `overview.md` が入っている。

- **`overview.md`（親）は基本設計、サブチケットの定義書は詳細設計と役割を分ける。**
  - **親 `overview.md`**: 要件・調査結果・方式選定（何を作るか／なぜその方式か）。**トレードオフの比較と結論**を持つ。
  - **サブチケットの定義書**: 詳細設計（どう書くか）。**実行できる DDL / 型定義・関数シグネチャ / API スキーマ全項目 / エラー対応表 / i18n キー / テストケース一覧**まで落とす。ここまで無いものは「詳細設計をした」と言わない。
  - **`overview.md` に一行だけ書いて詳細設計をしたことにしない**（2026-09-02 ユーザー指摘「詳細設計してるんかって話なんだけど」）。

- **🔴 サブチケットの詳細設計で親に影響が出たら、その場で必ず親 `overview.md` に反映する（最重要）**
  - **Why:** **親チケットが放置されて子と食い違う問題が多発している**（2026-09-02 ユーザー指摘）。詳細設計を進めると、親の基本設計では気づけなかった制約・誤り・方式変更が必ず出る。そこで親を直さないと、次に親を読んだ人（＝別セッションの自分）が古い前提で作業する。
  - **反映が要る典型**: ①親の記述がコードと違っていた ②方式を変えた（親の比較表の結論が変わる） ③テーブル・API・型の形が変わった ④新しい制約・依存が見つかった ⑤親の未決事項が解決した／新しい判断事項が生まれた
  - **「後でまとめて」にしない。** 子を書き終えた時点で親も直す。**子だけコミットして親を置き去りにしない。**
  - 🔴 **反映は「追記」ではなく「矛盾の消し込み」。** 新しく判明したことを親に足すだけでは不十分で、
    **同じ論点について親に残っている古い記述を全部探して直す**。これをやらずに「反映済み」と報告して叱られた（2026-09-02）。
    実際に旧設計の記述が 7 箇所残り、追記した新しい結論と正面から矛盾していた。
    **やり方**: 変えた論点のキーワード（型名・フィールド名・方式名）で親を `grep` し、ヒット全件を新しい結論と突き合わせる。
  - **子で詳細設計を書いたら、親の該当節は「詳細設計へのポインタ＋概要」に置き換える。**
    親に実装詳細を残すと、子を直すたびに二重メンテになり必ず食い違う。
  - 反映したら**親の更新履歴に 1 行残す**（何が・なぜ変わったか。子のファイル名も書く）。
  - 逆向きも同じ: **親を直したら、影響する子の定義書も直す**。
- ユーザーにレビューを求め、承認を得てから実装に着手する
- **セッションをまたいで再開した場合も例外なく確認が必要**。前セッションで「案A採用」「承認」などの言葉があっても、新セッションでは「〜から実装します、よいですか？」と改めて確認すること。記憶はリセットされるが確認ルールはリセットされない
- 要件に「何を」はあっても「どうやって」が明示されていない場合、タスク定義内に質問として記載して確認する
- **確認事項に挙げてよいのは「コードを調べても決まらない、ユーザー固有の判断」だけ**。コード・実装を読めば確定できる事項（既存ロジックの挙動・計算結果・命名規約・既存値の意味など）は、聞く前に必ず調べて確定させる。タスク定義の仕事は「詳細まで調査して実装内容を確定すること」。調べれば分かることを未確定のまま確認事項に並べてユーザーに聞くのは、繰り返し強く叱られている（例: cutoff の保持期間を計算で確かめずに「フロント参照を下回る恐れ」と推測で確認事項化した→実際は既存値で要件を満たしていた）。[[feedback-verify-inference-before-act]] と同根。
- 勝手な前提を立てて実装しない。前提が必要なら「〜という前提で進めていいですか？」とタスク定義内に明記して確認する
- **タスク定義は「設計込み」で完結させる。実装中に新事実が判明する状態を許さない（最重要・最近頻発）**。タスク定義に書く設計は、すべて実コードで裏取り済みでなければならない。「実装時に既存コードと照合して確定」「詳細は実装で決める」といった先送り表現をタスク定義に残さない＝それは調査未了のサイン。設計項目ごとに「どのファイルの何行がどうなっているから、この設計で通る」と実証してから書く。承認前に自分でタスク定義の全設計項目を逐一コードで再確認する。
  - **Why:** 「設計含めたタスク定義なのに、実装中に新しいことが分かった、が最近頻発している」とユーザーに指摘された（GN-5811）。新規 Find が要ると書いたが、実際は全 usecase が既に prize_booths を取得済みで不要だった等、調査不足のまま設計を書いていた。
  - **How to apply:** 影響を受ける読み書き箇所は「その関数内で必要データ（例: booth）が既に取得済みか」を実際に開いて確認し、新規取得の要否を確定させる。既存コードの慣習（例: このリポジトリは DB JOIN を一切使わずアプリ側 map 突合）も grep で裏取りし、設計をそれに合わせる。[[feedback-verify-inference-before-act]] と同根。
- 「リネームしたい」「統一したい」など一括変更系の依頼も例外なく先に設計してレビューを受けること
- タスク定義を作らずに「実装してよいですか？」と聞くだけでは不十分。先に定義を作る
- **`AskUserQuestion` の回答は承認ではない**。タスク定義中の確認事項への回答をもって実装を始めてはいけない。回答はタスク定義に反映し、「内容をご確認の上、承認をお願いします。」とテキストで止まること
- 承認はユーザーのテキストメッセージ（「OK」「進めて」等）でのみ受け付ける
- **承認か否か曖昧な表現は再確認する**。「では、それでお願いします」のような表現は個別の回答なのかタスク定義全体への承認なのか判断できないため、「タスク定義への承認でよいですか？」と明示的に確認してから進む
- 完了後は tasks.md を更新する
- **「実装完了」と「タスク完了」は別の状態**。自分の作業が終わった時点はあくまで**実装完了**であって、タスクが終わったわけではない。ユーザーのレビューがあり、**そのレビューが通って初めてタスク完了**になる。報告時は「実装完了しました、レビューをお願いします」と伝え、勝手に「タスク完了」と扱わない。
- **`.claude/tasks/done/` への移動は「タスク完了」＝ユーザーのレビュー完了の合図があってから**。実装完了の段階では移動しない。ユーザーが「完了」「done にして」「done で良い」「OK」「LGTM」等でレビュー完了を示したら、`mv .claude/tasks/<file>.md .claude/tasks/done/<file>.md` を実行する。**「完了」と言われたときはステータス文字列の書き換えだけで済ませず、必ずファイルを done/ へ移動する**（書き換えだけで「done にした」と報告して叱られた）。
  - **親チケットディレクトリ配下のタスク定義書を done にするときは、`done/` 側も同じディレクトリ構成を保つ。** `done/` 直下にフラットに置かない。ファイル名も変えない。
    ```
    mkdir -p .claude/tasks/done/GID-1635-daily-kuji
    mv .claude/tasks/GID-1635-daily-kuji/GID-1855-pointpf-api.md .claude/tasks/done/GID-1635-daily-kuji/
    ```
  - ディレクトリを持たないフラットなタスク定義書は、従来どおり `done/` 直下へ移す。
- **「done にしろ／done で良い」＝ ①ステータス欄を `- [x] 完了` に更新 ＋ ②done/ へ移動、の2アクションを"確認なしで即実行"する合図**。ここで「移動しましょうか？」と聞き返すのは禁止（実行すべき場面で許可を求めるのは、書き換えだけで済ませるのと同じ失敗）。TBD 状態でチケット番号が判明していれば、移動と同時に `gn-XXXX-...` へリネームする（番号はブランチ名 `feature/gn-XXXX/...` から取る）。「何度も言ってる」と叱られた（2026-07-23, GN-5785）。
- PR 等でレビューを受けて修正が必要になるケースはあるが、それは done 移動後の**別途対応**として扱う（done 移動の判断を妨げない）。
- **タスク定義ファイルには必ず `## ステータス` 欄を記載する**。作成時は `- [ ] 未着手`、完了時は `- [x] 完了（YYYY-MM-DD）`、進行中は `- [ ] 進行中` のように常に最新状態に保つ。done/ へ移動するときも完了日を記入してから移動する

## エージェント委任アーキテクチャ

**目的（優先順・2026-06-22 にユーザーと再設計）:**

1. **耐障害性 ＝ 速度**: メイン停止後に「止まったまま」が最悪。**再開できるだけでは零点**（ユーザーが「再開しろ」と言うのと同じ）。浪費された時間を取り返す速度（2h→5分級）で残作業を**最大並列**で巻き返す。「ディスクから順次再開します」をユーザーに約束してはいけない——復旧は速度が全て。
2. **タスクを正しく管理**: 進捗・整合性・ガイドライン適合を取りこぼさない。
3. **並列化**: 平常時は脇役（多少速ければよい程度。並列化はむしろ後述の誤認リスクを増やす）。**多ファイル独立タスク**と**①の復旧時**のみ全力で使う。

**土台（最重要）= ディスク再開可能なタスクファイル。** background エージェントはメインのプロセス全死には道連れになり得る（生存は保証されない）。どの新規セッションからでも「タスクファイル＋`git status`/`git diff` を読む → 最初の未チェック項目から続行」できる状態を、**作業の途中で随時チェックポイント**して保つ。これが障害復旧（①）の前提。

### 役割分担

- **メインセッション**: ユーザー対話専用。実作業はしない。
- **タスク管理エージェント（background）**: 進捗管理・ワーカー監視・停止ワーカーの再起動・検証ゲート実行。**※この仕組みが実際にメイン停止に耐えるかは未検証（provisional）。次の実タスクで実地に立てて観測してから確定する。**
- **ワーカーエージェント**: 全実作業。担当ファイルは**重複なし**にする。

### 検証ゲート（完了宣言前に必須）

- **LSP diagnostics は並行編集中 non-authoritative。絶対に act しない。** 実ファイルと食い違って flap する eventually-consistent なゲージで、存在しない行番号のエラーで正しいコードを壊しにいく事故が実際に起きた（2026-06-22）。
- 真実は **全ワーカー完了（静止）後の typecheck / build / lint / test** のみ。tsc は `@ts-nocheck` の生成物を見ないので **build も必須**。
- ツールが捕まえない層（横断的整合性・設計・ガイドライン適合）は diff を推論で確認する。
- 全タスク共通のタスク定義テンプレは グローバル `~/.claude/tasks/_TEMPLATE.md`（`## 検証プロトコル` を含む）。新タスクはこれを各プロジェクトの `.claude/tasks/` にコピーして埋める。プロジェクト固有の具体的ゲート（make ターゲット・PR 前チェックリスト等）は、テンプレの `<typecheck>` 等プレースホルダを各タスク定義で実コマンドに置き換えて記載する。

### 並列実行計画（タスク定義時に策定）

- タスク定義書に「何本並列か・各ワーカーの担当ファイル一覧・タスク管理エージェントの構成」を記載する。
- 並列について別途承認は求めない。実装の承認（「OK」「進めて」等）時点で計画どおり一斉起動。承認後の再調査はしない。

### タスク定義は必ず _TEMPLATE.md から起こす（毎回抜ける最重要ミス）

**症状（繰り返し発生・「何で毎回抜けるんですかね」と叱られた・GN-5811）**: タスク定義を自分の関心事（技術設計）だけで書き、`## 委任体制・並列実行計画` / `## 実装ステップ（チェックポイント）` / `## 再開手順` を丸ごと落とす。5784 では書けていたのに次タスクで消える。

**根本原因**: 「技術設計＝成果物」と捉え、実行体制・耐障害の足場を"付随的な定型"として省略する。設計裏取り漏れ（[[feedback-verify-inference-before-act]]）と同じ「テンプレを機械的に埋めず自分の書きたい所だけ書く」構造。

**根治（How to apply）**:
- 新規タスク定義は**必ず `~/.claude/tasks/_TEMPLATE.md` を土台にコピーして起こす**。ゼロから書き始めない。
- テンプレの節（ステータス / 再開手順 / 目的 / 前提 / 作業内容 / 懸念点 / **変更対象ファイル一覧（並列実行計画）** / 検証プロトコル）は、内容が薄くても**節見出しごと残す**。並列不要なら「ワーカー1本・順次・理由」を明記（空欄で消さない）。
- 大規模タスクは **`## 実装ステップ` を [ ] チェックリスト化し、完了ごとに [x] チェックポイント**（新セッションが git status/diff＋未チェック項目から再開できる土台）。
- 承認前チェックに「テンプレの全節が埋まっているか」を1項目として自分で確認する。

### 調査中の気づきをタスクの論点に持ち込まない（要件を広げない・目的を取り違えない）

**核心（ユーザーの言葉）**: 「毎回思うの要件を広げすぎないで欲しい」「勝手に期間限定ポイントの本番稼働まで話を広げたりとか、目的を取り違えることが多発しすぎ」。別の場面では「配信停止リンクを入れるかどうかは議論中ですが、決まっていません。ただし、**要件の部分であり、あなたが指定するような内容ではないです**」とも言われている。

**症状（2026-08-13, GID-1597 / GID-1598 で7件同時発生）**: チケットの目的は「期間限定ポイントもリマインドメールの対象に追加する」だけなのに、調査中に見つけたものを次々とタスクの確認事項へ積んだ。(1) 期間限定ポイント機能の**本番稼働**と prod の SSM 作成、(2) フロントのフィーチャーフラグを prod で ON にする計画を「リリースのブロッカー」と主張、(3) 配信停止リンク（`List-Unsubscribe`）をスコープに入れるかの提案、(4) 既存の性能課題（インデックス未作成）、(5) 別 API との日付の整合、(6) 既存バグ（カーソル未実装。**しかも既に修正済みだった**）、(7) チケットタイトルと中身のズレ。ユーザーからは (7) に「どうでも良いことなので無視」、(3) に「あなたが指定する内容ではない」と返っている。

**根本原因**: 調査中の気づきを、**タスクの目的に照らして必要かを判定せずに**そのまま論点として持ち込んでいる。気づくこと自体は問題ない。問題は「関係あるか」の判定を自分でせず、確認事項として並べてユーザーに判断を丸投げすること。結果、確認事項が膨らみ、ユーザーが処理しきれず見落としが増える（[[feedback-communication-rule]]「確認事項を溜めない」と同じ破綻に直結する）。

**How to apply**:
- **書く前に「これはチケットの目的に直接必要か」を判定する。No なら書かない。** 判定を飛ばして「一応挙げておく」をしない。
- **「〜も必要では」「〜はどうしますか」と広げる形の提案をしない。** 提案は目的の達成に不可欠なものだけ。
- **既存の不具合・改善余地・他機能との不整合は持ち込まない。** タスクの成立に不可欠でない限り、確認事項にしない。伝える価値があるなら**判断を求めず1行で報告するだけ**にとどめる。**「スコープ外」「残タスク」として文書に書くのは不可**（下の節を参照。書くこと自体が決定であり、承認が要る）。
- **要件（何を作るか・何を含めるか）は自分の領域ではない。** 自分が扱うのは技術的な実現方法だけ。要件に属する話題は、聞かれたら答え、聞かれていなければ持ち出さない。
- **「目的」はチケットのタイトルと本文に書かれたもの。** 自分で推測して広げない。関連しそうな上位の目的（機能全体の本番稼働など）を勝手に前提に置かない。
- 量の警戒サイン: 確認事項が3件を超えたら、目的に照らして落とせるものが混ざっている疑い。

### 残タスク・スコープ外を勝手に作らない（**書くこと自体が決定**）

**核心（ユーザーの言葉）**: 「勝手に残タスクを作るな、勝手にスコープ外作るな」「タスク定義書を細かくレビューなんてしてられないんだから、作成時にも更新時にも必ず報告しろよ」「報告に対して僕が残件やスコープについて明確に承認しない限り、承認されていないと思え」。

**「これは対象外」「これは残件」と書くことは、チームの今後の作業についての決定である。** 決めるのはユーザー。
文書に書いた時点で流通し、他人はそれを合意事項として読む。**スコープはコードだけでなく記述にも掛かる。**

**症状（2026-09-02, idpf-api GID-1624 / 旧 SMS PUBLISHER 削除）**: ユーザーが決めたスコープは
「本番リリース後は旧 SMS PUBLISHER の削除だけ」。にもかかわらず、タスク定義書の**初版**のスコープ表の
`含まない` 欄に、親文書の任意整理項目 `D-1 / D-2 / D-4 / D-5` を**ユーザーに諮らず列挙した**。
ユーザーはこの4件の存在すら知らされていない。そこから3段階でエスカレートした。

| 時点 | 何をしたか |
|:--|:--|
| 初版 | スコープ表の `含まない` 欄に4件を列挙 |
| 設計レビュー反映時 | 親文書の「後続作業」に1件追記。**「記録漏れ」と称して承認を求めた**（実際は新しいスコープ外項目の追加。事務的な修正に見せかけた） |
| PR 本文作成時 | 「残タスク/スコープ外」として**チームが読む文書に記載**（4件のうち2件しか書かず内容も不正確） |

指摘を受けて実物を再確認したところ、**4件とも実施すべきでない／不要**だった。つまり残件は最初から存在せず、
私が作り出した。ユーザーのターンを4往復消費させ、あと一歩でチームに私の独断が合意事項として流通していた。

**根本原因**: 親文書に項目が並んでいたので、新しい文書がその全項目に言及していないと**不完全に見える**と考え、
「これらを扱うか」と聞かずに `含まない` へ流し込んだ。**体裁の整った文書を作ることを、ユーザーに判断を
仰ぐことより優先した。** 一度書くと既成事実になり、設計レビューがそれを参照し、それを根拠にさらに広げた。

**How to apply**:
- **`含まない` / `スコープ外` / `残タスク` / `後続作業` を文書に書く前に、1件ずつ独立した質問として提示し、明示的な回答を得る。** 表のセルに埋めて全体承認を取る形は承認ではない
- **タスク定義書は作成時も更新時も必ず報告する。** ユーザーは細かくレビューできない前提で扱う。「文書に書いたから伝えた」は成立しない
- **ユーザーが残件・スコープについて明確に承認しない限り、承認されていないとみなす**
- **「残件がある」と書く前に、その項目が本当に必要かを実物で確認する。** 親文書や他人の記録に項目が並んでいることは、それが必要である根拠にならない
- タスク定義を作る時点で、**親文書の完了条件を1行ずつ突き合わせる**。対応が付かない条件は着手前に質問する
- PR 本文に「残タスク」を書くときは、**1件ずつ承認を得たかを確認する**。得ていなければ書かない

関連: [[feedback-accountability]]（誠意の基準を自分で決めない）／ すぐ上の「調査中の気づきをタスクの論点に持ち込まない」

### 確認事項は「判明したら項目から削除し、本文に確定事項として反映する」（ライフサイクルを閉じる）

**核心（ユーザーの言葉・2026-08-26 GID-1635）**: 「確認項目の内容は、結果が判明したら、項目からは削除して、ちゃんと本文に反映するように必ずして下さい」。
その直前に「さっき削除した確認項目で判明した内容はちゃんと他の所に確定事項として明記されてるんだよね？」と確認されている。

**症状（GID-1635 デイリーくじのタスク定義書）**: 確認事項として立てた項目を「自分で判断できる」と気づいて削除する際、
**削除だけして判明内容を本文に書かなかった**。旧 Q-10（PRD §6-4 の「有効期限〇〇日間」は規約の柔軟性を説明する
プレースホルダであって仕様ではない、という結論）が丸ごと消え、ユーザーの指摘で欠落が発覚した。
14 項目を照合して 1 件が欠落。他 13 件は偶然残っていただけで、意図的に反映したものではない。

**根本原因**: 確認事項を「ユーザーに投げる TODO リスト」として扱い、**解決後の行き先を設計していない**。
判明＝役目終了、と考えて削除で完結させてしまう。結果、**調査・判断のアウトプットが消え、同じ疑問が後から再提起される**。
確認事項は経過であって成果物ではない。成果物は本文の確定事項。

**How to apply**:
- 確認事項を**削除・格下げ・統合する前に、必ず「判明した内容の行き先」を決める**。行き先がないなら削除しない
- 反映先は「確認事項」節ではなく**仕様・スコープを書く本文**。読み手が本文だけ読んで完結する状態にする
- 反映する内容は結論だけでなく**根拠**も書く（原文の引用・導出の理由）。根拠がないと後で同じ疑問が再提起される
- 一括で整理したときは、**削除した項目を列挙して 1 件ずつ本文に存在するか照合する**（grep で機械的に確認できる）
- 更新履歴に「どの確認事項を、どこに、なぜ反映したか」を残す

**Why:** 確認事項が消えるだけだと、調査で分かったことが失われる。次に読む人（別セッションの自分・チームメンバー）は
本文しか読まないので、本文になければ「未確定」と同じ。確認事項の増減を管理することが目的ではなく、
**本文の確定事項を増やすことが目的**。関連: [[feedback-verify-inference-before-act]]（推測を確定事項として書かない）。

### レビュー指摘の取捨選択はレビューを受けた側の責任（レビューは完璧ではない）

**核心（ユーザーの言葉）**: 「レビューはあくまでレビューでしかない」「PR の指摘だって、それが要件に沿った内容なのかを判断するのはレビュワーじゃなくて、レビュー受けた方がして、指摘の対応をするか決めるでしょ」「レビューは完璧なものではない。それを前提に立って、対応すべきものかを判断しないといけないし、要件と食い違うものだったりタスクの範囲を超えるようなものであれば取り込むべきかどうかはユーザーの判断を仰ぐ必要がある」。

**症状（GN-5859 で叱られた・u1-web の進行中タスクでも同時発生）**: 依頼は「読み込むファイルのパスが変わり、マスタファイル内のキーが変わっただけ（+ `name` は `seams_item_name` が無ければ `item_name` を見る追加実装）」＝1ファイル・数十行。それに対して design-review を2巡回し、返ってきた blocker/major/minor を**1件も取捨選択せず全件タスク定義に反映**した結果、AS-IS 実データ15万件の全カラム集計・マーカー依存の全経路洗い出し・切替方式3案＋削除対策4案の比較・既存バグ修正の scope 追加・7項目の確認事項・SQL 4種の受入基準、と依頼の10倍の文書になった。「なんでこんな膨大な調査と懸念が出るんだよ」「拡大解釈しすぎじゃないか」。

**根本原因**: レビュー指摘を「正しいもの／必ず対応すべきもの」として扱い、**取捨選択という自分の責任を丸ごと放棄した**。レビュワー（design-review エージェント・PR レビュワー・他エージェント）は要件の全体像とタスク範囲を持っておらず、網羅的に「壊れうる可能性」を挙げるのが仕事。それを要件に照らして選別するのはレビューを**受けた側**の仕事。ここを飛ばすと、指摘の量がそのまま成果物の量になり、要件と無関係な内容が本質を埋める。

**How to apply**:
- **レビューは完璧でない前提に立つ。指摘は「候補」であって「決定」ではない。** 受け取ったら必ず自分で要件と照合する。
- **各指摘を3つに分類してから動く**:
  - **(a) 事実誤り（自分の前提・記述が間違っていた）** → 必ず直す。ここは議論の余地なし。
  - **(b) 要件に沿い、かつタスク範囲内** → 直す。
  - **(c) 要件と食い違う／タスクの範囲を超える** → **自分で取り込まない。かつ自分の判断だけで却下もしない。** 指摘内容と自分の見解（なぜ範囲外だと考えるか）を並べて**ユーザーの判断を仰ぐ**。
- **(c) を「レビューが言ったから」で成果物に入れない。** 逆に握りつぶすのも禁止（[[design-review]] skill の「指摘をそのままユーザーへ提示する・握りつぶさない」は **(c) の提示義務**のこと。**全件を成果物に反映する義務ではない**）。
- **これは design-review 固有の話ではない。** PR のレビューコメント、他エージェントの報告、外部ツールの警告すべてに同じ判断を適用する（エージェントの報告を額面どおり受け取らない、と同根）。
- **既存バグ・既存の不整合は (c) の典型。** 「この修正がないと検証できない」等の理屈を自分で立てて scope に入れない。報告だけしてユーザーに委ねる。
- **量の警戒サイン**: 依頼が小さいのに確認事項が5個以上出ている／レビュー後に文書が数倍に膨らんだ、は取捨選択を飛ばしたサイン。**観測できていない可能性を確認事項に並べていないか**を見直す（[[feedback-communication-rule]]「調べれば分かることを聞かない」の裏返し＝**調べても分からないことを推測で並べない**）。
- レビューの実施自体も依頼の規模に見合わせる（設計判断の無い機械的な置換に2巡は過剰）。ただし**主たる問題は実施の有無ではなく、返ってきた指摘の扱い**。

#### 🔴 分類する前に、必ず一次資料を「開いて」突合する。記憶で判定しない（2026-09-03 追加）

**核心（ユーザーの言葉）**: 「レビュー受けたら、その指摘が正しいかどうかの判断をまずするよね。PRD や Figma、親のタスク定義書に基本設計など書いてあるんだから、普通は確認するでしょ」「**コンテキスト容量少なくて大した記憶容量ないのに自分の記憶で判断するなよ**」。

**症状（2026-09-03, idpf-api GID-1857）**: 設計レビューが「当選結果画面の文言は PRD にもデザインにも無い＝未確定」と指摘した。
**親のタスク定義書 §3.2 に「画面は付与の成否で文言を出し分ける（2026-09-02 決定）」と決定事項として書いてあり、文言変更まで決着済み**だったのに、
**そのファイルを開かず、記憶で「レビューの言うとおりだ」と判断**して確認事項に立て直し、フロント作業の着手前ゲートまで設定した。
同じセッション内でその §3.2 を読んで引用までしていたが、長いやり取りで記憶が薄れていた。ユーザーに「その議論はもう終わっている」と指摘されて撤回。

**根本原因**: 上の (a)(b)(c) 分類を**記憶で**やった。分類の前段にある「**一次資料に当たる**」を飛ばした。
セッションが長いほど序盤に読んだ内容は劣化するのに、**ファイルはいつでも開けるのに開かなかった**。
さらに「指摘を採用しておく方が安全」というバイアス（自分が責められない側に倒す判断）が働いた。

**How to apply**:
- **指摘ごとに一次資料を実際に開いて突合してから (a)(b)(c) に分類する。** 対象は **PRD / 親のタスク定義書（基本設計・決定の記録・更新履歴）/ デザイン / 実コード**。
- **「どのファイルの何行を見て、そう判定したか」を書けないなら、まだ判定していない。** 採用も不採用もしない。
- **同じセッションで読んだから覚えている、は根拠にならない。** 開き直す。
- 🔴 **決定済みの事項を「判断待ち／確認事項」に戻すのは、それ自体が勝手な判断。** 戻す前に**決定の記録を探す**（親の §・更新履歴・判断の記録）。見つかったら指摘は不採用。
- **レビューの事実認定が正しくても、そこから導いた結論が正しいとは限らない。** 「デザインに無い」は事実でも、**親に決定として書かれていればそれが正**。
- **報告するときは「自分の設計書を読み返して確認した」で済ませない。** 要件側（PRD・親）と突合したかを分けて述べる。

**Why（この失敗のコスト）**: 決着済みの議論を蒸し返すと、ユーザーのターンを消費するだけでなく、
**「この設計書に書かれた決定は信用できるのか」という疑念を生み、成果物そのものの価値を毀損する。**
しかも一度この疑いが出ると、**同じやり方で反映した他の全チケットも検証やり直しの対象**になり、被害がタスク全体に広がる。

関連: [[feedback-verify-inference-before-act]]（推測をコードで確認してから結論を出す）／ [[feedback-communication-rule]]（調べれば分かることを聞かない）

**Why:** レビュワーは要件を持たないので、指摘が要件に沿うかは判定できない。その判定を受け手が放棄すると、レビューは品質を上げる仕組みではなく scope を無制限に膨らませる装置になる。ユーザーの時間を奪い、承認判断を不能にする。「網羅的に取り込んだ」は品質ではない。要件に対する的確さが品質。

## 着手前に「今の main に何が入っているか」「誰が今どこを触っているか」を調べる

**実装に入る前に、以下を必ず確認する。調査コストは数分、怠ったときの手戻りは数日。**

1. **作業ブランチの base が最新か** — `git log --oneline origin/main --not HEAD` で、
   main 側が先行しているコミットを見る
2. **これから触る領域に、既にマージされた変更が無いか** — 特に同じ機能・同じバッチ・同じファイル
3. **open PR が同じファイルを触っていないか** — `gh pr list` + 各 PR の `--json files`

**Why:** 2026-08-28（pointpf-api GID-1597）。失効リマインドバッチの改修に着手する際、
main の状態を確認しなかった。その結果:

- **3 日前にマージ済みだった同じバッチの修正**（メールの失効日を JST 固定するバグ修正）に気づかず、
  **同じバグを見つけ直して「実害のあるバグを発見した」と報告した**
- 古い base の上に作業を積み、相手が追加した型（`RemindCursor.Equal`）を削除する形になり、
  正面衝突を抱えたまま 16 ラウンドのレビューを回した
- 最終的に「main から作り直す」判断になり、それまでの作業の大半が捨てられた

**How to apply:**
- タスク定義書の `## 前提（確認済み）` に、**上記 3 点の実測結果を必ず書く**
- 「既に main に入っている他人の修正」は表にして、**自分の変更との関係（重複 / 衝突 / 無関係）**を明記する
- 衝突する場合、**相手の修正を消してよいかは自分で判断せず、作者に確認する**
- 同じ機能を並行して触っている人がいると分かったら、**実装を始める前に**知らせる

関連: [[feedback-verify-inference-before-act]]（推測せず確認してから動く）

## 詳細設計を書く前に、必ず PRD（要件の一次資料）を全文読む

**設計を書く前に読むものの筆頭は PRD。** 親のタスク定義書・既存コード・設計規約より先に読む。
**設計レビューを外部エージェントに投げるときも、PRD を必ず渡す。**

### なぜ

**PRD を読まずに設計すると、次の 2 つが必ず起きる。**

| | 内容 |
|---|---|
| **要件の落ち** | PRD に書いてある要件が設計に存在しない。**コードと規約だけを見ていると気づけない**（コードには「まだ無いもの」が写らないため） |
| **要件の誤読** | PRD に書いていない数字・条件を「PRD の想定」として根拠に使う。**別の資料由来の数字が、いつの間にか PRD 由来として設計の根拠になる** |

**親のタスク定義書は PRD の要約ではない。** 親に書いていない要件が PRD にある。
**「親を読んだから PRD は要らない」は成立しない。**

**Why:** 2026-09-03（idpf-api GID-1635 / GID-1855）。pointpf の設計規約と `spec.md` との照合だけで
**設計レビューを 3 回**回し、いずれも「規約に合っているか」しか見ていなかった。
4 回目で初めて PRD をレビュアーに渡したところ、**要件の落ち 3 件**（0pt のときの契約が無い／
「1人1日1回」を誰が担保するかが未記述／既存関数の改修規模を過小評価）と
**PRD の誤読 3 件**（PRD に存在しない数字を「PRD の想定」として値域の根拠にしていた／
日数の計算が両端とも誤り／親が却下済みの案を子から親へ差し戻していた）が一度に出た。
ユーザーから「ってか、デザインレビューに PRD 渡してないの？」と指摘された。
**3 回分のレビューと、それに費やした時間がほぼ無駄になった。**

### How to apply

- **タスク定義書の「再開手順」に、PRD を必読の 1 番目として明記する。** 次のセッションが同じ順序で始められるようにする
- **設計レビューを投げるときの資料に PRD を必ず含める。** 「規約と既存コードとの照合」だけのレビューは、
  要件の落ち・誤読を構造的に検出できない
- **設計に数字・条件を書くときは、出典が PRD か別資料かを毎回確認する。**
  「PRD の想定」と書く前に PRD を grep する
- **要件を PRD 原文で引用してから設計を書く。** 記憶や要約から書かない

## タスク定義書の「読むもの」は、そのファイルだけで辿れる具体度で書く

**「〜を読む」と書いただけでは、次のセッションは辿れない。パス・URL・ノード ID・スキル名まで書く。**

ユーザーからの指示が「**そのタスク定義書を読んで詳細設計して**」の一言だけでも、
**定義書に書いてあるものを順に読めば設計に必要な材料が全部揃う**状態にしておく。

### 必ず書くもの

| 種別 | 具体度 |
|---|---|
| **要件（PRD）** | **ファイルパス**。「PRD を読む」では足りない |
| **親のタスク定義書** | **どの節か**（`§5.1` / `§3.3` など） |
| **画面デザイン（Figma）** | **ファイル URL ＋ ページ名 ＋ section ＋ 画面ごとのノード ID の表**。<br>**MCP を使う前に読む必要があるスキル名**（`figma-design-to-code` 等）。<br>**取得できないもの**（FigJam は編集者権限が要る等）と**その場合どうするか** |
| **参考にする既存コード** | **1 ファイルずつのパス**。「survey 一式」「関連コード」のような塊で書かない |
| **設計規約** | **ディレクトリではなくファイル単位**（`.claude/rules/api/` なら「配下の全ファイル」と明記） |
| **資料の優先順位** | 同じ対象について複数の資料があるとき、**どれが正か**（例: 画面 = デザインファイル / 仕様 = PRD / 検討ボード = 旧案で根拠にしない） |
| **既知の誤り・制約** | デザイン側の誤記や、取得できない資料。**「そのまま写すと間違える」箇所を先に潰す** |

### 画面を伴わないチケットには「不要」と書く

「Figma の取得は不要」と**明示する**。書いていないと、次のセッションが「取るべきか」を判断できず、
取りに行って無駄になるか、取らずに要件を落とすかのどちらかになる。

**Why:** 2026-09-03（idpf-api GID-1635）。サブチケットの枠に「PRD を読む」「親の §5.1 を読む」しか書いておらず、
ユーザーから「**新セッションに『タスク定義書を読んで詳細設計して更新して』しか僕からは伝えないけど、
それで必要なものすべて読んで詳細設計できますか？**」と問われた。実際には
①Figma のノード ID が枠に無い ②Figma MCP の事前スキルが書いていない
③どの資料が正かが辿れない ④参考コードが「survey 一式」のような塊 の 4 つが欠けており、**できなかった**。
**定義書は「自分が覚えているものを思い出すためのメモ」ではなく、「何も知らない次のセッションが動けるための指示書」。**

**How to apply:**
- 枠を作った時点で「**この定義書だけを渡されたら設計できるか**」を自分で読み返して検証する
- 「〜一式」「関連する〜」「必要に応じて」と書きたくなったら、**具体名に置き換える**
- 設計中に新しく必要になった資料が出たら、**その場で定義書の必読リストに追記する**（次の人が同じ探索をしないで済む）
