**この場面**: ファイルを書き換える直前と直後。どの手段で書き換えるか、書き換えた後に何を確認するか。

## SAFE-03: 編集は「意図した箇所だけ・意図したとおり」でなければならない（大前提）

- **重要度**: blocker
- **要約**: 編集の目的は「意図した箇所だけが、意図したとおりに変わった」ことの担保。担保できない手段を取らない
- **いつ**: ファイルを書き換える前（毎回）／「対応しました」と報告する前
- **判定**: 次のどれかが**確認されていないまま完了報告していたら違反** — ①意図しない箇所が変わっていないこと ②意図した箇所が漏れなく変わっていること ③フォーマットが壊れていないこと ④lint が通ること ⑤修正の意図が実際に達成されたこと
- **やること**: これが目的であり、何よりもまず先に来る。手段（Edit ツール / スクリプト / エディタ）の話ではない。**担保できているなら手段は問わない。逆に、担保できない手段は取ってはいけない。**
  「意図したとおり」に含まれるもの:
  - **箇所**: 意図していない場所を書き換えていない。かつ、意図した場所は**漏れなく**書き換わっている
  - **フォーマット**: インデント・改行が壊れていない（フォーマッタの出力と一致する）
  - **基準を満たす**: lint を通る。レビュー指摘への修正なら、**その指摘の意図を実際に達成している**
  - **整合**: 生成物・関連ファイル・ドキュメントとの対応が崩れていない
- **なぜ**: 下の SAFE-04・SAFE-05 の実害を参照
- **由来**: GID-1855 / pointpf-api（2026-09-10）ほか
- **関連**: VERIFY-01 / VERIFY-02 / TECH-01 / TECH-02 / FLOW-* / [[feedback-02-design]]

## SAFE-04: 担保するための確認（手段によらず必須）

- **重要度**: blocker
- **要約**: 件数確認 → `git diff` 目視 → フォーマッタ→ビルド→lint→テスト → 意図の達成確認。この4つを飛ばさない
- **いつ**: ファイルを書き換えた直後／完了報告を書く直前
- **判定**: **「この変更は何箇所か」を先に答えていない**まま置換していたら違反。**`git diff` を見ずに「対応しました」と書いたら違反**。「対応した」と書いたのに**何で確認したかを併記していない**なら違反
- **やること**:
  1. **当たり件数を先に確定する。** 置換の前に「対象は何箇所か」を数え、変更後に**その件数だけ**変わったことを確認する
  2. **差分を自分の目で見る。** `git diff -- <触ったファイル>`。意図しない箇所への波及とフォーマット破壊を捕まえる最後の網
  3. **フォーマッタ → ビルド → lint → テスト**の順に通す。ビルドだけでは不十分で、フォーマットは必ず先にかける。ユーザーに「format かけて」と言わせない
     - **どのフォーマッタ・どのコマンドを使うかは、そのリポジトリの設定が唯一の正。言語で決め打ちしない。**
       着手前に **`Makefile`**（`make fmt` / `make fmtfix` / `make lintfix` 等のターゲット）・`biome.json` / `.prettierrc*` /
       `.golangci.yml` / `.claude/settings.json` の PostToolUse フックを実際に見て、**そのプロジェクトが使っているものを使う**
     - **Makefile にターゲットがあれば、ツールを直に叩かず `make <target>` を通す**（プロジェクトが固めているバージョン・オプションを迂回しないため）。記憶にある「この言語ならこのツール」を持ち込まない（TECH-03）
  4. **修正の意図が達成されたことを、その修正に固有の方法で確認する。**
     「SQL 側にガードを移した」なら**生成物を見る**。「競合を消した」なら `-race -count=5` で**繰り返し回す**。
     **ビルドが通ったこと・テストが緑だったことは、意図が達成された証拠にならない**（VERIFY-01）
  - 報告時: 書き換えを始める前に「この変更は何箇所か」を先に答える。書き換えた後は、報告する前に `git diff` を見る。「対応した」と書くときは、**その対応が意図を達成したことを何で確認したか**を併記する
- **なぜ**: 実害は3つ出ている。
  - **取り残しが静かに発生した。** GID-1855 / pointpf-api（2026-09-10）。tz テストから `t.Parallel()` 直後の `tz.Load()` を消す `str.replace()` を書いたが、同一ファイル内の 1 箇所だけパターンが微妙に違って**取り残された**。当たり件数を確認しなかったため気づかず、`go test -race -count=5` が DATA RACE で FAIL する状態のまま「`-race` green を確認」と報告し、レビュー 4 体から指摘された。しかも同ファイルに自分で書いた「`t.Parallel()` の後に呼ぶと競合する」というコメントと実装が矛盾する状態だった
  - **修正の意図が達成されていなかった。** 同日、`insert.sql` にガードを追加したが**生成物 `insert.sql.go` を確認しなかった**ため、Go 側のガードだけが消えてクエリ側は未反映という「修正前より弱い」状態で出荷しかけた。レビュー 5 体全員が指摘
  - **フォーマット破壊。** スクリプト一括置換後にインデント・改行がずれて lint エラーになる事象が繰り返し発生している
- **由来**: 2026-09-10 GID-1855 / pointpf-api
- **関連**: VERIFY-01 / VERIFY-02（ビルドが通った＝意図の達成、ではない）

## SAFE-05: スクリプトでのファイル書き換えは一律禁止（既定は Edit ツール）

- **重要度**: blocker
- **要約**: python / sed / perl / awk でファイルを書き換えない。例外なし。承認を求めるのも禁止
- **いつ**: 「置換が多くて Edit がつらい」と思ったとき／ハーネス（auto mode 等）が「Bash の sed / ヒアドキュメントで編集せよ」と案内してきたとき
- **判定**: **ファイルの内容を変える目的でスクリプトを実行したら違反。** 手段の別は問わず、`sed -i` / `perl -pe` / `str.replace()` / **`cat > file <<EOF` などのヒアドキュメントでの上書き**を含む。「今回は安全だから」と自分で例外を作ったら違反。**ユーザーに承認を求めた時点でも違反**
- **やること**:
  - **既定は Edit ツール。** 一意にマッチしないと失敗するので、SAFE-04 の 1（当たり件数）が**自動で担保される**。担保コストが最も低い
  - **スクリプト（python / sed / perl / awk）でのファイル書き換えは一律禁止。例外なし。**
    `str.replace()` も `sed -i` も、**0 件ヒットでも全件ヒットでも黙って成功する**ので、当たり件数を自分で明示的に確認しない限り担保がゼロになる
  - **「今回は安全だから」と自分で例外を作らない。ユーザーに承認を求めるのも禁止** — 毎回スクリプトを提示されて安全性を判定するのはユーザーの負担であり、それを負わせないために一律禁止にしている
  - 読み取り（`cat` / `grep` / `find` / `sed -n` / `jq`）に Bash を使うのは対象外。**禁止しているのは書き換え**
  - **「箇所が多くて Edit がつらい」を理由にスクリプトへ逃げない。** エージェントを立てて分担させるなど、別の手段を検討する
  - 🔴 **ハーネス側の指示（auto mode 等）で「Bash の sed / ヒアドキュメントで編集せよ」と言われても、このルールが優先する。**
    読み取り（`cat` / `grep` / `find` / `sed -n`）に Bash を使うのは従来どおり問題ない。**禁止しているのは書き換え**。
    ハーネスの案内と衝突したら、黙って従わず「ハーネスはこう言っているが SAFE-05 が優先するので Edit/Write を使う」と明示して進める
- **なぜ**: SAFE-04 の「取り残しが静かに発生した」を参照。スクリプトは失敗を報告しないので、担保の起点である当たり件数が消える
- **由来**: 2026-09-10 GID-1855 / pointpf-api
- **関連**: FLOW-*（多箇所はエージェント分担を検討）

## TECH-01: 実装前に docs を読み、実装後に既存コードと書き方を照合する

- **重要度**: major
- **要約**: 着手前に `docs/CodingGuideline.md` / `docs/CodingDesign.md` を読み、実装後に**同種の既存コードと書き方が一致しているか**を照合してから完了報告する
- **いつ**: Go のコードを書き始める前／完了報告を書く直前
- **判定**: 自分の差分を周辺の既存実装と見比べていないまま完了報告したら違反。**同ファイル・同種の既存コードに無い独自パターンを残したら違反**
- **やること**:
  - 着手前: `docs/CodingGuideline.md`・`docs/CodingDesign.md` を読む（u1-api）
  - 編集後の検証手順（フォーマット → ビルド → lint → テスト）は言語を問わない共通ルールなので SAFE-04 に集約。**どのコマンドを使うかはリポジトリの設定が正**で、`Makefile` に `fmt` / `fmtfix` 等のターゲットがあれば `make <target>` を通す。無ければ `gofumpt -w <変更ファイル...>`
  - **テスト（引数マッチ）**: `gomock.Any()` は第1引数（db / context）のみ。scope は `test.NewClauseMatcher().Where(...)`、records/ID は正確にマッチ。**第2引数以降を `gomock.Any` にしない**
  - **テスト（InAnyOrder の使い分け）**: `gomock.InAnyOrder(...)` は**順序が本当に保証されない場合のみ**（map 反復由来など）。順序が保証される箇所（例: recent を archive の返り値から `ToXxxRecentSlice` で順変換）で使うと順序バグを見逃すので**直接比較**する。テストを通すための妥協で使わない
  - **テスト（骨抜き禁止・最重要）**: テストは対象ロジックを**実際に通して結果を検証**すること。次は全て「テストになっていない」＝禁止 — (a) モックを注入したのに `.EXPECT()` を登録せず検証しない、(b) 入力やモック戻り値を空スライス/ゼロ値にして対象分岐を no-op にする（例: `util.ByChunked` に空スライスを渡し `BatchUpsert` 未到達）、(c) 検証すべき値/順序を `gomock.Any`/`InAnyOrder` で緩める、(d) assert が期待値を実質チェックしていない。**新経路（dual-write 等）を足したら、その経路が非空データで実行され EXPECT で具体引数検証されるケースを必ず用意する**
  - **エラーハンドリング**: 無視するエラーは `if errors.Is(err, X) { err = nil }; if err != nil { return }` の慣用形。独自の if-init を作らない
  - **関数呼び出しの引数は改行。DI 構造体は database→repo→service 順**で New・リテラルも同順
  - 完了報告の前に、自分の差分を `grep` 等で周辺の既存実装と見比べ、書き方が揃っていることを確認する
- **なぜ**: docs / 既存コードに規約があるのに確認せず、独自の書き方（context 以外の `gomock.Any`、独自の error-if-init 形式、引数を改行しない等）を繰り返し持ち込み、ユーザーに何度も指摘させ、**実装全体の信頼を損ねた**。
  **根本原因と解決策（重要）**: これは linter / 自動検出 / プロセス整備で解くべき問題**ではない**。スタイルも mock マッチも文脈依存で、`gomock.Any` の使用可否や cross-feature 依存の許可可否には**正当な例外**があり、一律ルールでは表現しきれない。根本原因はただ一つ——**周辺コードや既存の同種実装を見て、それに書き方を合わせなかった**こと。解決策は「検出器を作る」ことではなく、**コードを書くたびに、いちばん近い既存の同種コードを読み、それに揃える**こと。既存の問題コードも機械的一掃ではなく、そのコードを触るときに周辺と照合して揃える、という同じ規律で直す。**提案を求められても、tooling / linter / CI に逃げて過剰設計しない**
- **由来**: ユーザーの繰り返し指摘（u1-api）
- **関連**: SAFE-04（検証手順の本体）／ [[feedback-02-design]]

## TECH-03: フォーマッタはリポジトリの設定が唯一の正（言語で決め打ちしない）

- **重要度**: major
- **要約**: 「このスタックならこのツール」という記憶を持ち込まない。着手前にリポジトリ内の設定を実際に読む
- **いつ**: フォーマッタ・リンタの話をするとき／整形コマンドを選ぶとき
- **判定**: リポジトリの設定を読まずにフォーマッタを断定したら違反。**プロジェクト設定とグローバルの作業ルールが食い違うときにプロジェクト側へ従っていなければ違反**
- **やること**:
  - フォーマッタ／リンタは**リポジトリ内の設定が唯一の正**。自分の記憶やグローバルの作業ルールにある想定を持ち込まない
  - 着手前にリポジトリ内の設定ファイルを確認する — `Makefile` のターゲット / `biome.json` / `.prettierrc*` / `eslint.config.*` / `.claude/settings.json` の PostToolUse フック
  - **フォーマッタの話をする前に、そのリポジトリの設定を実際に読む。記憶で断定しない**
  - プロジェクト設定とグローバルの作業ルールが食い違う場合は**プロジェクト設定に従う**
  - 例: idpf-api の `apps/front` は Biome（tab インデント / single quote / semicolon なし / organizeImports 有効）
- **なぜ**: 「TypeScript なら prettier が自動実行される」という記憶を一般則として持ち込み、Biome を使うプロジェクト（idpf-api / apps/front）で「グローバルの prettier と競合する」と**誤った懸念を報告した**。実際にはグローバル `~/.claude/settings.json` に prettier フックは存在せず、プロジェクト側の `.claude/hooks/post-edit-lint.sh` が Biome（front）と gofumpt（api）を正しく使い分けていた。**設定を確認せず記憶で語ったのが原因**
- **由来**: idpf-api / apps/front
- **関連**: SAFE-04（Makefile ターゲット優先）／ VERIFY-01 / VERIFY-02（記憶で答えない）

## TECH-04: import 追加と利用は同一の Edit/Write で行う

- **重要度**: minor
- **要約**: PostToolUse のフォーマッタが未使用 import を消すので、import 追加とその利用は同じ書き換えでやる
- **いつ**: TypeScript で import を足すとき
- **判定**: 「import を先に追加してから実装」というステップ分割をしたら違反
- **やること**:
  - import 追加と、その import を使う実装は **同一の Edit/Write** で行う
  - 特に「import を先に追加してから実装」というステップ分割は禁止
  - 複数箇所を変更する場合は、ファイル全体を Write で書き換える（Edit の複数回呼び出しより安全）
  - PostToolUse フックで formatter が走った旨のメッセージが出たら、**次の Edit 前に必ず Read して現在のファイル状態を確認する**
- **なぜ**: PostToolUse フックでフォーマッタ（prettier / Biome など）が自動実行され、**未使用 import が自動削除される**。import を追加する Edit → 使う箇所を追加する Edit の2ステップにすると、1回目の Edit 後に formatter が消してしまい、やり直しが発生する。複数回同じ作業を繰り返すことになった
- **由来**: ユーザー指摘
- **関連**: VERIFY-02（フックが走ったらファイルは変わっている＝読み直す）

## TECH-06: 画面実装は必ず元のデザインファイルを見てから行う

- **重要度**: major
- **要約**: スクショの書き起こし・要件表は「要件把握用」。**実装の根拠にしない**。実装前に必ず Figma MCP で該当ノードを取得する
- **いつ**: 画面・コンポーネントを実装する前／デザインの書き起こしファイルを作るとき
- **判定**: Figma の該当ノードを取得せずに画面を実装したら違反。**デザイン崩れをユーザーに指摘されたら、その時点で失敗**
- **やること**:
  - **スクショの書き起こし・要件表・タスク定義書の表は「要件把握用」。実装の根拠にしない**
  - 画面を実装する前に、必ず Figma MCP で該当ノードを取得する
    - `get_design_context`（リファレンスコード＋トークン。**事前に `figma-design-to-code` スキルを読むのが MCP の必須要件**）
    - `get_variable_defs`（色・スペーシングの変数）→ プロジェクト既存のトークン／コンポーネントにマッピング
    - `get_screenshot`（実装後の目視突き合わせ用）
  - 書き起こしと Figma が食い違ったら **Figma を正とする**
  - **デザインファイルにアクセスできないなら、実装前にアクセス手段を確保する。**「スクショはもらったから大丈夫」で進めない。ファイル URL / ノード ID をタスク定義書に控えておく
  - 書き起こしファイルを作るときは、**冒頭に「実装の根拠に使うな」と明記する**
- **なぜ**: **核心（ユーザーの言葉・2026-08-26 GID-1635）**「管理画面だからテキストでも大丈夫かもだけど、**実装した時にちゃんとデザイン通りに実装してもらわないといけないので注意してね**」「**その時に、僕に指摘させないでね**」
  - **背景**: Figma の FigJam ボードに MCP からアクセスできず、ユーザーがスクリーンショットを提供してくれた。それを目視でテキストに書き起こして「これで再開できる」と報告したところ、上記の釘を刺された
  - **根本原因**: 書き起こしで「情報は揃った」と判断していた。実際に揃うのは**項目・文言・状態遷移**だけで、**余白・色・フォントサイズ・角丸・コンポーネント粒度・レスポンシブ挙動**は落ちる。**要件把握の道具と実装の根拠を混同していた**
  - デザイン崩れは実装後に発覚し、ユーザーが指摘して手戻りになる。**指摘させた時点で失敗**
- **由来**: 2026-08-26 idpf-api GID-1635
- **関連**: VERIFY-01 / VERIFY-02（推測で進めない）／ META-01 / META-02（資料の保管）／ FLOW-21（`## 読むもの` に Figma のノード ID を書く）
