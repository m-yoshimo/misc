## FLOW-06: `overview.md` は基本設計、詳細設計は別ファイル。詳細設計で overview に影響が出たらその場で直す

- **重要度**: blocker
- **要約**: overview は要件・方式選定、詳細設計は実行できる粒度で別ファイル。進捗は release-plan が持つ。**詳細設計で overview に影響が出たら、その場で「矛盾の消し込み」で直す**
- **いつ**: 詳細設計を書き終えたとき／overview を直したとき
- **判定**: **詳細設計だけ更新して overview を置き去りにしたら違反。** overview への反映が「追記」だけで、**同じ論点の古い記述が残っていたら違反**。`overview.md` に一行だけ書いて「詳細設計をした」と言ったら違反。**overview に詳細設計（DDL・API スキーマ・関数の形・テストケース）を書いたら違反**。**overview や詳細設計に進捗を書いたら違反**（release-plan が持つ）
- **やること**:
  - 🔴 **4つのファイルの書き分け**（2026-10-20 ユーザー決定。サブタスクが無いタスクでも同じ）。詳しい表は `~/.claude/tasks/_TEMPLATE_OVERVIEW.md` の `## overview と詳細設計の書き分け` にあり、**ここに書き写さない**

    | ファイル | 持つもの |
    |---|---|
    | `overview.md` | 要件・調査結果・方式選定（何を作るか／なぜその方式か）・**トレードオフの比較と結論**・サブタスク一覧・サブタスク間で共有する決め事・決定ログ |
    | 詳細設計（`{チケット番号}-{内容}.md`） | 詳細設計（どう書くか）。**実行できる DDL / 型定義・関数シグネチャ / API スキーマ全項目 / エラー対応表 / i18n キー / テストケース一覧**まで落とす。**ここまで無いものは「詳細設計をした」と言わない** |
    | `release-plan.md` | **全タスクの順番と進捗**、サブタスク以外の作業の手順 |
    | `study.md`（任意） | 事実・検討した手段・リスク |

  - **`overview.md` に一行だけ書いて詳細設計をしたことにしない**（2026-09-02 ユーザー指摘「詳細設計してるんかって話なんだけど」）
  - 🔴 **詳細設計で overview に影響が出たら、その場で必ず `overview.md` に反映する（最重要）**
    - **反映が要る典型**: ①親の記述がコードと違っていた ②方式を変えた（親の比較表の結論が変わる） ③テーブル・API・型の形が変わった ④新しい制約・依存が見つかった ⑤親の未決事項が解決した／新しい判断事項が生まれた
    - **「後でまとめて」にしない。** 子を書き終えた時点で親も直す。**子だけコミットして親を置き去りにしない**
    - 🔴 **反映は「追記」ではなく「矛盾の消し込み」。** 新しく判明したことを親に足すだけでは不十分で、**同じ論点について親に残っている古い記述を全部探して直す**。これをやらずに「反映済み」と報告して叱られた（2026-09-02）。実際に旧設計の記述が **7 箇所**残り、追記した新しい結論と正面から矛盾していた
    - **やり方**: 変えた論点のキーワード（型名・フィールド名・方式名）で親を `grep` し、**ヒット全件**を新しい結論と突き合わせる
    - **詳細設計を書いたら、overview の該当節は「詳細設計へのポインタ＋概要」に置き換える。** overview に実装詳細を残すと、詳細設計を直すたびに二重メンテになり必ず食い違う
    - 反映したら**overview の決定ログに 1 行残す**（何が・なぜ変わったか。詳細設計のファイル名も書く）
    - **逆向きも同じ: overview を直したら、影響する詳細設計のファイルも直す**
  - 🔴 **分割は暫定として扱う**（2026-10-20 ユーザー決定）。詳細設計で前提が崩れてサブタスクの分け方・依存・順番を変える必要が出たら、
    **その場で overview を直してユーザーの承認を取る**。黙って進めない／自分の判断で分け直さない（FLOW-14 と同じ）
- **なぜ**: **overview が放置されて詳細設計と食い違う問題が多発している**（2026-09-02 ユーザー指摘）。詳細設計を進めると、基本設計では気づけなかった制約・誤り・方式変更が必ず出る。そこで overview を直さないと、**次にそれを読んだ人（＝別セッションの自分）が古い前提で作業する**。
  **GID-1474 でも実際に起きた**: S-3 の詳細設計の段階で、S-2 が置いた前提（どの DB から読むか）が揺らいだ。**分割は一度で確定しない**ので、作り直しを事故ではなく手順として扱う（2026-10-20）
- **由来**: 2026-09-02 ユーザー指摘 ／ ファイル構成の変更と「分割は暫定」の明記は 2026-10-20 ユーザー決定
- **関連**: FLOW-15（決定の反映も同じ「矛盾の消し込み」手順）／ FLOW-05（ファイル構成）／ FLOW-12（テンプレの使い分け）

## FLOW-23: タスク定義書のステータスは 6 状態。状態が変わった瞬間に書き換える

- **重要度**: blocker
- **要約**: ステータスは6状態（未着手／設計中／設計完了／実装中／実装完了／完了）。状態が変わった瞬間に書き換え、実装完了以降は単線を増やさず検証ゲートとレビューの表で表す
- **いつ**: タスク定義書を作ったとき／設計を書き始めたとき／ユーザーが設計完了を判断したとき／**実装の最初の編集・最初のワーカー起動の前**／仕様どおりにできなかったもの・判断が必要なものが出たとき／実装が全部終わったとき／ユーザーが done を指示したとき／**コードを触ったまま回答を返そうとしたとき**
- **判定**: 現在地の 1 行に**6 つ以外の状態名**を書いたら違反。**「設計完了」のまま実装に入ったら違反**。**仕様どおりにできなかったもの・判断が必要なものを、`## 確認事項` に起こさず会話に置いたまま次へ進んだら違反**。**実装完了より後に単線の状態を増やしたら違反**（そこから先は表で表す）。**自分の判断で「設計完了」にしたら違反**（これはユーザーの判断）。**自分の判断で「完了」にしたら違反**（これもユーザーの判断。マージは完了ではない）。**各タスクの進捗を定義書に書いたら違反**（`release-plan.md` が持つ）。コードを触ったのに、そのあと定義書を一度も触らずに回答を返したら違反
- **やること**:

  **現在地は 1 行だけ。** ステータス節の最初のチェックボックス行がそれで、状態はこの 6 つしかない。

  - 🔴 **仕様どおりにできなかったもの・判断が必要なものが出たら、会話に置かず、その場で `## 確認事項` に 1 件ずつ起こす**（COMM-10）。
    **会話にしか無い状態で compaction が起きると、何が未判断かが丸ごと消え、ユーザーは判断できなくなる**

    **ファイルに書かない**（書いても次の瞬間には古くなる）
  - **状態名の一覧を他のファイルに書き写さない。** 正は本ルールの上表と `~/.claude/hooks/taskdef_status.py` の `PHASES`（META-04 と同じ理由）

    **同じ状態を両方に書かない** — release-plan には 6 状態を書かず、定義書には他タスクの進捗を書かない
  - 🔴 **PR を出した・マージされた・環境に出たと分かった時点で、その場で `release-plan.md` の該当行を書き換える**（2026-10-20 ユーザー決定）。

## FLOW-08: 承認の受け取り方と、「実装完了」「タスク完了」「done 移動」の区別

- **重要度**: blocker
- **要約**: 承認はテキストメッセージだけ。**実装完了 ≠ タスク完了。マージも完了ではない**。「done で良い」は**ステータス更新＋`.claude/tmp/` の削除＋done/ 移動を確認なしで即実行する合図**
- **いつ**: 確認事項に回答をもらったとき／実装が終わったとき／「完了」「done にして」と言われたとき
- **判定**: **`AskUserQuestion` の回答をもって実装を始めたら違反。** 実装が終わっただけで「タスク完了」と扱ったら違反。**マージされただけで完了として扱ったら違反**。「done で良い」に対して**ステータス書き換えだけで済ませたら違反**。**タスク全体の完了でないのに `overview.md` / `release-plan.md` を `done/` へ移したら違反**。**タスク全体の完了でないのに `.claude/tmp/<タスク>/` を消したら違反**（タスク全体の完了では消さなければ違反）。「移動しましょうか？」と聞き返したら違反
- **やること**:
  - **`AskUserQuestion` の回答は承認ではない。** タスク定義中の確認事項への回答をもって実装を始めてはいけない。回答はタスク定義に反映し、「**内容をご確認の上、承認をお願いします。**」とテキストで止まる
  - 承認は**ユーザーのテキストメッセージ**（「OK」「進めて」等）でのみ受け付ける
  - **承認か否か曖昧な表現は再確認する。**「では、それでお願いします」は個別の回答なのか全体への承認なのか判断できないため、「タスク定義への承認でよいですか？」と明示的に確認してから進む
  - 完了後は `tasks.md` を更新する
  - **「実装完了」と「タスク完了」は別の状態。** 自分の作業が終わった時点はあくまで**実装完了**。ユーザーのレビューが通って初めて**タスク完了**になる。報告は「**実装完了しました、レビューをお願いします**」と伝え、勝手に「タスク完了」と扱わない
  - **`.claude/tasks/done/` への移動は「タスク完了」＝ユーザーのレビュー完了の合図があってから。** 実装完了の段階では移動しない。ユーザーが「完了」「done にして」「done で良い」「OK」「LGTM」等で示したら `mv` を実行する
  - 🔴 **マージは完了ではない**（2026-10-20 ユーザー決定）。サブタスクは **test 環境などでの動作確認を経て、ユーザーが「完了」と言った時点**が完了。
    PR のマージ・デプロイはリリースでも完了でもない（リリースはフラグを ON にすること）
  - **「完了」と言われたときはステータス文字列の書き換えだけで済ませず、必ずファイルを done/ へ移動する**（書き換えだけで「done にした」と報告して叱られた）
  - **親チケットディレクトリ配下を done にするときは、`done/` 側も同じディレクトリ構成を保つ。** `done/` 直下にフラットに置かない。ファイル名も変えない
    ```
    mkdir -p .claude/tasks/done/GID-1635-daily-kuji
    mv .claude/tasks/GID-1635-daily-kuji/GID-1855-pointpf-api.md .claude/tasks/done/GID-1635-daily-kuji/
    ```
  - ディレクトリを持たないフラットな定義書は、従来どおり `done/` 直下へ移す
  - **「done にしろ／done で良い」＝ ①ステータス欄を `- [x] 完了` に更新 ＋ ②`.claude/tmp/<タスク>/` を削除 ＋ ③done/ へ移動、の3アクションを"確認なしで即実行"する合図。** ここで「移動しましょうか？」と聞き返すのは禁止。
    - 🔴 **②は③より先にやる**（2026-10-16 ユーザー決定）。`mv` を先にすると一時ディレクトリは**持ち主を失う**し、
      `rule_guard.py` の警告（`check_done_leftover_tmp`）は PreToolUse で走るので、
      移動元の宣言がまだ有効に見えて**その `mv` が孤児にするディレクトリを検出できない**。
      実際に 2026-10-16 12:15 の GID-1858 の done 化で、`.claude/tmp/GID-1858/`（12ファイル/160KB）が無警告で残った
    - ②で残す必要があるものは、**何を・なぜ残すかを報告する**（META-01）。
      削除は `permissions.allow` の `Bash(rm -rf .claude/tmp/*)` で許可済み（2026-10-16）
    - TBD 状態でチケット番号が判明していれば、移動と同時に `gn-XXXX-...` へリネームする（番号はブランチ名 `feature/gn-XXXX/...` から取る）。「**何度も言ってる**」と叱られた（2026-07-23, GN-5785）
  - 🔴 **移す単位**（2026-10-20 ユーザー決定）

    | 何に「完了」と言われたか | 移すもの | 残すもの |
    |---|---|---|
    | **サブタスク1つ** | そのサブタスクの詳細設計のファイルだけを `done/{チケット番号}-{概要}/` へ | **`overview.md` と `release-plan.md` は元の場所に残す**（残りのサブタスクと `R-n` が参照する） |
    | **タスク全体** | ディレクトリの残り全部（`overview.md` / `release-plan.md` / `study.md` / 残りの定義書） | なし。`.claude/tmp/<タスク>/` の削除もこの時点 |

    - **サブタスク単位の完了では `.claude/tmp/` を消さない**（他のサブタスクが使っているため）。消すのはタスク全体の完了時
    - **完了と言われていないものを勝手に移さない。** マージ済み・STG 済みでも、ユーザーが「完了」と言うまでは `done/` へ移さない（FLOW-23）
  - PR 等でレビューを受けて修正が必要になるケースはあるが、それは done 移動後の**別途対応**として扱う（done 移動の判断を妨げない）
  - **タスク定義ファイルには必ず `## ステータス` 欄を記載する。** **状態名と書き換える瞬間は FLOW-23 が正**（ここに書き写さない）。done/ へ移動するときも完了日を記入してから移動する
- **なぜ**: 実行すべき場面で許可を求めるのは、書き換えだけで済ませるのと同じ失敗
- **由来**: 2026-07-23 GN-5785 ほか ／ 「マージは完了ではない」と移す単位の明文化は 2026-10-20 ユーザー決定
- **関連**: SAFE-09 軸0（ルールで定められた操作は実行する）／ COMM-12 ／ FLOW-05（ファイル構成）／ FLOW-23（完了はユーザーの判断）

## FLOW-02: トークン残量が少なくなったら、途中結果を保存してセッションを終える

- **重要度**: major
- **要約**: 残量が減ってきたら作業を続けず、途中結果を `.claude/tasks/` のタスクファイルに保存して終える
- **いつ**: 長い調査・作業の途中で、トークン残量が少なくなってきたとき
- **判定**: 残量が少ないと分かった状態で、**保存せずに作業を続けていたら違反**
- **やること**:
  - 作業を続けようとせず、その時点での調査結果や作業状況を `.claude/tasks/` のタスクファイルに保存して終了する
  - 保存する内容は「**次のセッションがこれだけ読んで再開できる**」粒度にする（FLOW-12「再開手順」／ FLOW-23「現在地と判断待ち」）
  - 🔴 **書く先を間違えない**（2026-10-20 ユーザー決定）。**作業中の詳細設計のファイル**に現在地と判断待ちを書き、
    **各タスクの進捗は `release-plan.md`** に書く。方針が変わったなら `overview.md` も直す（FLOW-06）
- **なぜ**: セッションをまたいで作業を続けるため。**ユーザーはトークン回復後に別セッションで作業を再開できるようにしたい**
- **由来**: ユーザー指摘
- **関連**: FLOW-09（ディスク再開可能なタスクファイルが土台）
