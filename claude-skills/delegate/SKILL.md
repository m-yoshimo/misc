# delegate — エージェントへの委任

エージェントに渡す指示文は、**`build_prompt.py` だけが組み立てる。** Claude は出力をそのまま Agent ツールの `prompt` に渡す。
指示文の末尾には発行印 `[delegate:<12桁>]` が付き、`~/.claude/hooks/delegate_guard.py` が起動のたびに検査する。
**発行印が無い指示文・発行後に書き換えた指示文・指定と違うエージェントの種類では、エージェントは起動できない。**

背景（なぜ Claude に指示文を書かせないか）は `~/.claude/hooks/delegate_guard.py` の冒頭にある。

## 手順

1. 委任の種類と引数を決め、スクリプトを実行する

   ```
   python3 ~/.claude/skills/delegate/build_prompt.py <種類> --repo <修正対象のリポジトリ> <引数>
   ```

2. 出力の `■` の行（対象リポジトリとブランチ・使うレビュー skill・差分の取り方・作業ディレクトリ）を、ユーザーへの報告にそのまま載せる。
   取り違えがあれば、ユーザーがエージェントの完了前に気づける
3. 🔴 **指示文はファイルで渡す**（2026-10-22 ユーザー決定）。スクリプトは体ごとに次の 3 行を出すので、**その 3 行をそのまま `prompt` に渡す**。
   ファイルを開いて貼り直さない（開く必要も無い）。

   ```
   次のファイルを全文読み、そこに書かれた指示に従って作業してください。**この prompt には指示の本文は含まれていません。**
   <指示文のファイルのパス>

   [delegate:<発行印>]
   ```

   `subagent_type` は出力に書かれたものを使う。**`run_in_background: true` を必ず付けて背景で起動する**（前景は `delegate_guard.py` が止める。SAFE-13 の 7。承認は要らない）。
   起動したらすぐ回答を返してよい。結果は完了の通知で届くので、届くまで結果を報告しない
   - **複数体のときは 1 つのメッセージで全員ぶんの Agent を呼ぶ**（`cat` は不要）。**全員を起動する。** 一部だけ起動して回答を終えようとすると Stop フックが止める
   - 背景のエージェントは `AskUserQuestion` を使えない。許可の要るツールを呼ぶと、許可の確認がメインのセッションに出る
   - 1 つのセッションで同時に動かせるのは既定で 20 体まで
   - エージェントが動ける時間の上限と、メインのセッションを閉じたときの動きは、公式ドキュメントに記述が無い（2026-10-07 確認）

   **なぜファイル渡しか**: 指示文は 1 体あたり約 10,000 文字で、`prompt` に書くとその全文がメインのセッションの出力になる。
   実測（2026-10-20〜21 の GID-1474）で **9 体の起動に 1 体 30〜45 秒・合計 4〜5 分**かかり、出力は 9 体で約 94,000 文字だった。

   **指示文のファイルは `build_prompt.py` だけが書く。** 読むのは可（`Read` / `cat`）。
   書き換え・移動・`chmod` は `rule_guard.py` が止める。内容を変えたいならスクリプトを引数を変えて実行し直す（新しいファイルとして発行される）。
4. **何を指示したかは、エージェントの結果の冒頭に全文が転記される**（スクリプトが全種類の指示文に転記を義務づけている）。
   受け入れ検査（FLOW-22）は、転記された指示文と成果物を突き合わせて行う
5. エラーが出たら、エラー文のとおりに引数を直す。**スクリプトを通さずに指示文を書かない**

## `--repo`（対象リポジトリ）

- **修正対象の実装があるリポジトリ（worktree）を指定する。既定値は無く、セッションの作業ディレクトリは使わない。**
  セッションやタスク定義書が別のリポジトリ（例: idpf-api）にあっても、修正対象（例: pointpf-api）を指定する
- どれか分からなければ、推測せずにユーザーに聞く
- タスク定義書の `- 作業ブランチ:` と `--repo` の今のブランチを照合し、違えばエラーになる（`review-design-v2 --design` を除く）

## 種類

| 種類 | 用途 | 必須の引数 |
|---|---|---|
| `review` | コードレビュー。`--repo` にあるリポジトリ専用の skill をスクリプトが選ぶ | `--repo`・`--taskdef`・差分の取り方 |
| `review-design-v2` | `design-review-v2` skill の判定者（9体） | `--repo`・`--taskdef` と、`--design` または差分の取り方 |
| `worker` | 実装ワーカー | `--repo`・`--taskdef`・`--assign`・`--fixed-sections` |
| `research` | 調査・検証（読み取りのみ） | `--question`（`--taskdef` を付けると結果をファイルに書かせる） |
| `command` | ファイルを編集しないコマンドを実行するだけ（検証ゲートのテスト・lint など） | `--repo`・`--taskdef`・`--command`（複数可） |

### 作業ルールを読ませるか

| 種類 | ルール |
|---|---|
| `worker`・`research`・`review-design-v2` | **ルール本文の全ファイル（`~/.claude/memory/` の `MEMORY.md` と `feedback_*.md`）を全文読ませる。** 一覧はスクリプトが毎回集める。`worker` と `research` は読んだファイルの一覧を報告する |
| `review`・`command` | 読ませない |

2026-10-05 のユーザー指示「コードレビュー以外は、ルールを必ず順守させたい」「単純にスクリプトやコマンドを実行する系のものは除外。ただし、ファイル編集などを含むスクリプトやコマンドは対象」による。
委任1回ごとに、ルールの読み込みで**実測 274,261 バイト**（2026-10-22 計測）を使う。

🔴 **`research --no-rules` で、調査役のルール読み込みを省ける**（2026-10-22 ユーザー指示
「research に省くオプションを付けろ、ただしこのオプションが僕が明示的にルール不要といった時だけ使えるようにしろ」）。

- 使えるのは **ユーザーが「ルールは不要」と明示したターンだけ**。許可は `rm_grant.py`（UserPromptSubmit）が
  **ユーザーの発言から**記録する。**Claude 側から許可を書く経路は無い**（自己例外化の禁止・SAFE-07）
- 記録が無いときは `build_prompt.py` がエラーにする。**自分の判断で付けない**
- 省いたときは、指示文に「ルールの読み込みを省いている」と明記され、守るのは指示文の「制約」と「報告」だけになる

### 差分の取り方（レビューの種類。省略すると既定）

| 引数 | 内容 |
|---|---|
| `--cached` | `git diff --cached` |
| `--worktree` | `git diff` |
| `--head` | `git diff HEAD` |
| `--range A..B` | `git diff A..B` |
| `--untracked` | 上のどれかに足して使う。未追跡ファイルを新規追加の差分として同じ差分ファイルにつなげる |

- **指定が無ければ既定の取り方「PR に載る変更の全部」になる**（2026-10-07 ユーザー指示「既定値は作って」。それまでは毎回聞き返していた）。聞き返さない。
  実行されるのは次のとおり（`<base>` は `git merge-base <ベースブランチ> HEAD` の結果。ベースブランチは、タスク定義書の
  `- ベースブランチ: \`...\`` の行があればそれ、無ければ `origin/HEAD` が指すブランチ。別の作業ブランチから切ったとき・マージ先が main 以外のときは、
  行を書かないと元のブランチの変更まで入る）:
  - `git diff <base>` — 既定のブランチから分かれた後の、コミット済み・ステージ済み・未ステージの変更をまとめて取る
  - `git ls-files --others --exclude-standard` で未追跡ファイルを集め、`.claude/` 以下を除いて、1 つずつ `git diff --no-index /dev/null <ファイル>` でつなげる
  - origin の既定ブランチが分からないときはエラーになるので、そのときだけ取り方を聞く
  - `■` の行に、起点・ベースブランチ・起点から積まれたコミットの数が出る。想定より多ければ、起動前にベースブランチを確かめる
  - fetch で `origin/main` が進んでも、`git rebase origin/main` で積み直しても、main 側の変更は入らない（起点は分かれた地点で、rebase に合わせて進む。テストで確認済み）
- 「ステージしたものだけ」のように**ユーザーが取り方を指示したときだけ**、下の引数で指定する
- 未追跡ファイルのうち `.claude/` 以下は、スクリプトが常に除外する。追跡済みの差分は `.claude/` 以下も対象に入る
- 各リポジトリの `.git/info/exclude` に書いたファイルも、未追跡の収集から外れる

### `review` が選ぶ skill

`--repo` の中身を見て、次の順に決める（2026-10-07 ユーザー決定）。**リポジトリの名前でも skill の名前でも判定しない**（中身の形で見分ける。worktree でも同じに動く）。

1. **リポジトリのコードレビューの skill**（`.claude/skills/` の全 skill を見て、スクリプトが組み立てられる形のもの）
   | 形 | 見分け方 | 組み立て方 | 今の該当 |
   |---|---|---|---|
   | テンプレート型 | コードブロックの中に差分の差し込み口 `{diff}` がある | テンプレートをそのまま使う（チーム共用なので書き換えない）。差分は作業ディレクトリの `target.diff` に保存し、`{diff}` にはそのパスを入れる。汎用エージェント 1 体 | idpf-api の `local-review` |
   | 専門レビュアー型 | `- review-xxx` の一覧があり、`.claude/agents/` に全員の定義ファイルがあり、「各サブエージェントには「…」と指示」の 1 文がある | 差分は skill の決まりどおりリポジトリ直下の `pr-diff.txt` に保存する。各定義ファイルの本文と skill の 1 文を指示文に入れ、汎用エージェントで起動する。`pr-diff.txt` などのファイル名は対象リポジトリの絶対パスに置き換える | pointpf-api の `code-review-local` |
2. **GitHub Actions の Claude コードレビューの定義**（`.github/workflows/` で `anthropics/claude-code-action` に `prompt:` を渡していて、ファイル名・ワークフロー名・ジョブ名のどれかに「review」「レビュー」を含むもの）。
   `prompt:` をそのまま使い、前に固定の前置き（ローカルの差分であること・`gh pr diff` の代わりに差分のファイルを読むこと・PR にコメントせず最後のメッセージで返すこと）を付ける。汎用エージェント 1 体。今の該当は idpf-admin-frontend の `claude-code-review.yml`
3. **どちらも無ければ design-review-v2**（`review-design-v2` の差分モードと同じ 9 体）

**止めてユーザーに聞くとき**（エラーになる）:
- 形の合う skill が 2 つ以上ある
- 形の合う skill は無いのに、名前・説明・ファイル名に「レビュー」「review」を含む skill がある（チームのレビューの skill をスクリプトが読めないだけかもしれないので、黙って 2・3 に切り替えない）
- 2 の定義が 2 つ以上ある（例: pointpf-api には `claude-code-review.yml` と `claude-opus-review.yml` がある。今は 1 で決まるので影響しない）

出力の `■ レビュー:` の行に、何を使ったか（skill のファイル・ワークフローのファイル・design-review-v2）が出る。

pointpf-api の 5 体を定義ファイルの名前（`subagent_type: review-security` など）で起動しないのは、セッションが pointpf-api に無いと起動できないため。
汎用エージェントで起動するので、定義ファイルの `restrictedTools` は効かない（2026-10-05 ユーザー了承）。

### 種類ごとの補足

- `review-design-v2`: 判定者のテンプレートは `~/.claude/skills/design-review-v2/reviewer_prompt.md`。補助資料はタスク定義書の `## 読むもの` から機械的に抜き出し、規約は `--repo` の `CLAUDE.md`・`docs/*.md`・`.claude/rules/`・`.claude/agents/review-*.md` から機械的に集める。**資料を足したいときは、プロンプトではなくタスク定義書の `## 読むもの` に書く**
- `worker`: `--assign` はタスク定義書の `## 変更対象ファイル一覧` にある担当の節の名前（`### Worker A（…）` なら `Worker A`）、`--fixed-sections` は改変禁止にする節の名前（複数可）。
  ワーカーに渡す資料は、その節の「- 読むもの:」の列挙だけ（`## 読むもの` 全体は渡さない。2026-10-07 ユーザー承認）。書き方は `~/.claude/tasks/_TEMPLATE.md` の同じ節。
  節や「読むもの」が無い、リポジトリ丸ごとのディレクトリがある、定義書と合わせた合計が 500KB（画像は数えない。ルール本文は別枠）を超える、のどれかでエラーになる。
  エラーになったら、定義書の側（担当の分け方・「読むもの」の絞り方）を直す。**ワーカーに読み飛ばしを判断させない**ため
- `command`: 受け付けるのは、実行する場所（`--cwd`。`--repo` からの相対パス、既定はリポジトリ直下）の `Makefile` に定義されたターゲット（`include` したファイルも含む）と、`go test` / `go build` / `go vet` / `golangci-lint run` / `pnpm run test|lint|typecheck` だけ。
  それ以外・`>` `|` `;` `&&` などを含むもの・`-o` で書き出すもの・`make -C` / `-f` は拒否する。
  エージェントは渡したコマンドを順にそのまま実行し、出力を作業ディレクトリの `command-<番号>.log` に全文保存し、失敗したらそこで止めて報告する。ファイルは編集せず、失敗しても直さない。
  **Makefile のターゲットはすべて通る**（`make mock` のようなコード生成や `make sam.deploy` も含む）。どれを渡すかは私が決めるので、TECH-02（コード生成はユーザーに依頼する）と SAFE-07（read-only と断定できないものは事前に確認する）は、組み立てる前に私が守る
- `research`: `--taskdef` を付けると、調べた結果はスクリプトが決めた `result.md` 1 つにだけ書き出させる（2026-10-06 ユーザー決定。設計時の調査は結果が大きく、メッセージで返すとコンテキストを圧迫し、要約で細部が失われるため）。エージェントの最後のメッセージは「書き終えた」とパスだけ。
  `--question` に「削除」「消す」「git push」など読み取り以外の操作を指す語や、「レビュー」「観点」「指摘」が入っていると、スクリプトが組み立てを拒否する（調査役でレビューの代わりをさせない）

## 作業ファイルの置き場所と片付け

要件（2026-10-06 ユーザー）: tmp 以下は作業（セッション）ごとに持つ。どのチケットのファイルか分かること。遅くともチケットの完了時には必ず消えていること。

- **置き場所**: タスク定義書の `## ステータス` で宣言した一時ディレクトリ（META-01。名前にチケット番号が入る）の中の
  `delegate/<日時>-<種類>-<ランダムな6文字>/`。例: `idpf-api/.claude/tmp/GID-1857-point-history/delegate/20261006-110500-research-3f9a1c/`
  - そのため `review`・`review-design-v2`・`command` は `--taskdef` が必須で、定義書に「一時ディレクトリ: `.claude/tmp/<名前>/`」の行が無いとエラーになる（先に宣言する）
  - `research` は `--taskdef` を付ければ結果を `result.md` に書かせ、付けなければメッセージで返させる（タスク定義書が無い作業では一時ディレクトリを作らない。META-01）
  - `worker` は、宣言があれば同じ場所にワーカー用のディレクトリを作って渡す（出力の保存先）。無ければ一時ファイルを作らないよう指示する
  - 名前の末尾のランダムな文字列で、複数のセッションが同じ秒に組み立てても重ならない
  - 共用の `.claude/tmp/delegate/` は作らない
- **調査役の結果は、必要な事実をタスク定義書の本文に書き写してから使う。`result.md` をタスク定義書から参照しない**（META-01。消える場所なので、参照すると定義書が壊れる）
- **消すタイミング**
  - 結果をユーザーに報告し終えたら、私が消してよい
  - 遅くとも、タスク定義書を `done/` に移した（完了した）ターンの終わりに、Stop フック（`delegate_guard.py --stop`）が `delegate/` を丸ごと消す。セッションの開始時（`--sweep`）にも同じ確認をする
  - 持ち主の対応は、スクリプトが `~/.claude/state/delegate/workdirs.jsonl` に記録する
- pointpf-api のコードレビューの `pr-diff.txt` と `findings-*.json` は、skill の決まりどおりリポジトリ直下に置かれ、レビューの最後に skill の手順で削除する。
  - 消し忘れた場合は、完了時の削除で、`pr-diff.txt` の中身が書いたときのままなら `findings-*.json` と一緒に消える（中身が違えば別のセッションのものなので消さない）
  - 固定の名前でリポジトリに 1 組しか置けないので、残っているとスクリプトはエラーにする（別のセッションのレビューが進行中かもしれないため、上書きしない）

## エージェントがフックに止められないように

エージェントの中でもフック（`rule_guard.py`、idpf-api の重いコマンドの検査など）は動く。途中で止められて中断し、委任をやり直すことにならないようにする（2026-10-06 ユーザー要件）。

- `command`: 実行する行（`cd <場所> && timeout 590 <コマンド> > <ログ> 2>&1; echo "exit=$?"`）をスクリプトが組み立て、エージェントはそのまま実行する。テストで実物のフックを通ることを確かめている。
  `timeout 590` は Bash ツールの上限（600 秒）に収めるため。590 秒を超えるコマンドは打ち切られ、終了コード 124 として報告される
- `research`（ファイルに書かせるとき）は汎用エージェントに固定する（書き込みのツールを持たない種類だと結果を書けない）
- `worker`・`research`・`command` の指示文には、出力の保存先と「フックに止められても中断せず、理由文の直し方に従って続ける。直せないものは飛ばして最後に報告する」を固定の文で入れている

## このスキルで止まらないもの

- 起動後のエージェントへの追加指示（SendMessage）。止めるよう言われたエージェントは、止める
- Workflow ツールのスクリプトから起動されるエージェント
- `research` の `--question` に書く「調べる内容」そのものの取り違え。レビューを言い換えた依頼も通る
- 組の指示文を 1 体も起動しないこと（Stop フックが見るのは、一部だけ起動した組）
