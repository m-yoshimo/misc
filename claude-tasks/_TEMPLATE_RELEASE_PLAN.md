# release-plan テンプレート（全プロジェクト共通）

> **サブタスク以外の作業（マイグレーションの実行・フラグの ON・デプロイ・他チームへの依頼など）があるときに作る。**
> 置き場所は overview と同じディレクトリの `release-plan.md`。**overview とは必ず別ファイル**にする。
> 作らない場合は、overview の `## リリース計画・タスク管理` に「なし（サブタスク以外の作業は無い）」と書く。

**親**: [overview.md](overview.md)（基本方針・サブタスクの中身・フラグ一覧・決定ログ）

## この資料で扱うもの

- **このチケットの全タスク（サブタスク＋サブタスク以外の作業）の順番と進捗**は、この資料の `## タスク一覧` だけで管理する（overview には書かない。二重に持つと食い違うため）
- サブタスクの定義書は自動テストまでを扱う。**サブタスクにしていない作業（R-n）とその手順**は、この資料で管理する
- 決定の記録は overview の `## 決定ログ` に書く
- **ID の種類**（**番号は足した順に振る**。実行順は `順` 列が持つ。欠番は埋めず、**ID は再利用しない**）

  | ID | 何か | 定義書 | 実行するのは |
  |---|---|---|---|
  | `S-n` | **サブタスク**（1チケット＝1 PR） | そのサブタスクの定義書 | Claude |
  | `M-n` | **チケットを増やさずに PR だけ分けて出すもの**（レビュー経路が違う／独立して出したい）。**内容はマイグレーションに限らない**（CI 設定・生成物なども同じ） | 切り出し元のサブタスクの定義書（新しく作らない） | Claude |
  | `R-n` | **サブタスク以外の作業**（マイグレーションの適用・フラグの ON・デプロイ・他チームへの依頼など） | 無し。手順は下の `## R-n …` に書く | **ユーザー** |

- **タスクを足すとき**: 一覧に ID を振って1行足し、手順があれば `## R-n …` の節を分けて書く
- **状態は「未着手／作業中／完了」の3つ。** 変わったその場で書き換える
  - **サブタスク（S-n・M-n）はこの3つだけ**を書く。詳細な状態（設計中・設計完了・実装中など）は各定義書の `## ステータス` を正とし、ここには書かない
  - **サブタスク以外の作業（R-n）は、3つに加えてサブステータスを自由に添えてよい**（定義書が無く、ここが唯一の記録になるため）。例: `作業中（test・stg は ON 済み。本番は R-4 待ち）`
- リリースの考え方（フラグの ON がリリースで、PR のマージ・デプロイはリリースではない、など）は、このチケットの前提をここに1行書く

## タスク一覧

**順**: 小さい順に進める。同じ順のタスクは並行してよい。
**R-n の時期はユーザーが決める**ので、順は付けず（`―`）、前提だけを書く。

| 順 | ID | 種類 | タスク | 前提 | 担当 | 状態 |
|---|---|---|---|---|---|---|
| 1 | S-1 | 実装（{リポジトリ}） | {チケット番号} {内容}（[定義書]({ファイル名})）。PR・マージ日・環境の状況もここに書く | なし | Claude | 未着手 |
| 2 | M-1 | 実装（{リポジトリ}） | {何を切り出した PR か}。**定義書は切り出し元**（S-n）。レビュー経路が違う理由も1行書く | {前提} | Claude | 未着手 |
| ― | R-1 | 実装以外 | {内容} | {前提} | ユーザー（時期もユーザーが決める） | 未着手 |

（作らないと決めたタスクがあれば、表の下に1行で残す。例: `- S-5 は作らない（overview 決定ログ {日付} {議題}）`）

## R-{n} {作業の名前}

（手順。**実ファイル・実ワークフロー・行番号へのリンク付き**で書く。確認した日付も入れる。
ユーザーが実行するので、何をどの順に・どこで確かめるかが分かる粒度にする。）
