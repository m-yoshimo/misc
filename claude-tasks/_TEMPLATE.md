# タスク定義書テンプレート（全プロジェクト共通）

> 新しいタスクはこのテンプレートを各プロジェクトの `.claude/tasks/{task_name}.md` にコピーして埋める。
> 末尾の `## 検証プロトコル` は**全タスク共通の標準セクション**。削らない。
> 検証プロトコルの具体コマンド（`<typecheck>` 等のプレースホルダ）は、着手するプロジェクトの実コマンドに置き換える。

## ステータス

- [ ] 未着手（**承認待ち**）
- 作業ブランチ: `feature/gn-XXXX/...`

## 再開手順（新セッション・再起動後はここから）

このファイルだけで再開できるようにまとめる。会話履歴が無くても以下の順で進める。

1. 作業ブランチを確認する。
2. ベースラインの状態（typecheck / build エラー数など）を確認し、何が解消対象かを把握する。
3. **承認確認**: 再開時も「このタスク定義どおり実装してよいか」をユーザーに確認してから着手する。
4. 承認後、`## 変更対象ファイル一覧（並列実行計画）` のとおりワーカー＋タスク管理エージェント（background）を起動する。承認後の再調査は不要。
5. 全ワーカー完了後、`## 検証プロトコル` を実行する。
6. 完了したら `## ステータス` を更新する。

## 目的

（このタスクで達成したいこと。仕様変更の背景など。）

## 前提（確認済み）

（着手前に確定している事実。関連チケットの対応状況、ベースラインのエラー内容など。）

## 作業内容

（A. 削除 / B. 修正 / C. 後処理 のように分類して列挙。）

## 懸念点・確認事項

（着手前にユーザーへ確認すべき点。回答は `【回答済み】` を付けて反映する。）

## 変更対象ファイル一覧（並列実行計画）

ワーカーを N 本に分割。担当ファイルは**重複なし**にする（並行編集の競合を避ける）。

- **Worker A（担当範囲）**: ファイル一覧
- **Worker B（担当範囲）**: ファイル一覧
- **タスク管理エージェント（background）**: 各ワーカーの進捗を git diff で監視し、停止時は再起動。全ワーカー完了後に `## 検証プロトコル` を実行。

> **並列化は必須ではない。** 小規模・ファイル間に依存順があるタスクは「ワーカー1本・並列化不要」と明記してよい（並列化はむしろ競合・誤認リスクを増やすため、多ファイル独立タスクと障害復旧時のみ全力で使う）。

## 検証プロトコル（全タスク共通・標準セクション）

> このセクションは**管理エージェントが完了を宣言する前に必ず通す自己ゲート**。
> ユーザー起動の `/code-review` skill（より深いレビュー）とは役割が別物。混同しない。
> `<...>` のコマンドは着手プロジェクトの実コマンドに置き換える。プロジェクト固有の具体ゲート・PR 前チェックリストは各タスク定義に記載する。

### 0. 大原則

真実は「**静止後の authoritative gate**」だけ。実行中の **LSP diagnostics は non-authoritative、絶対に act しない**（並行編集中は実ファイルと食い違って flap する eventually-consistent なゲージ。存在しない行番号のエラーで正しいコードを壊しにいく事故が実際に起きた）。

### 1. Quiescence（静止判定）

**全ワーカーが done を報告 = 静止**。ここで初めてゲートを実行する。途中の部分チェック・LSP 反応では動かない。

### 2. Authoritative gate ―「動くか」（機械チェック・全て green が条件）

順に実行する（`<...>` はプロジェクトの実コマンドに置換）:

1. `<typecheck>`（増分キャッシュで素通りが疑わしければフルビルドを強制する）
2. **`<build>`** ← typecheck の盲点（生成物・`@ts-nocheck` 等、型チェック対象外のファイル）は build でしか検出できないため**必須**
3. `<lint>`
4. `<check-format>`
5. `<test>`
6. 削除主体タスクなら `grep -rin "<除去対象シンボル>" <src>`（生成物除く）で残存ゼロを確認

**記入例（参考・着手プロジェクトの値に置き換える）**
- u1-web: `make typecheck`（疑わしければ `pnpm exec tsc --build --force`） / `make build-development` / `make lint` / `make check-format` / `make test`。盲点は `routeTree.gen.ts` 等の `@ts-nocheck` 生成物。
- u1-api: `docker compose exec api go build ./...` / `docker compose exec api go test ./...` / `golangci-lint run` / `gofumpt -l .`（フォーマット差分ゼロ確認）。

### 3. 整合性・設計レビュー ―「ツールが捕まえない層」（管理エージェントが全 diff を推論で確認）

- 親子・呼び出し側/呼ばれ側間の **型契約・引数契約**（削除した項目の受け渡しが両側で揃っているか）
- 削除フィールド/関数の **残存参照**（型上通っても意味的に壊れていないか）
- **タスク定義書の前提自体の誤り**（前提が事実かの再確認。例: 「生成物が型エラーを出す」前提が実は `@ts-nocheck` で誤りだった、のような取り違え）
- 盲点ファイル（生成物 / 型チェック対象外）が絡む変更は build とランタイム経路で裏取り

### 4. ガイドライン適合レビュー ―「ユーザーがコードを見て判断する層」

着手プロジェクトの開発ガイドライン（PR 前チェックリスト）を実行する。特にツールで検出できない推論項目を確認:

- **設計・可読性**: 責務分離 / ロジックのベタ書きをしていない / ドメイン指向の命名 / ロジック重複なし / 不要なキャストの新規導入なし
- **ガイドライン適合**: 編集禁止ファイル（生成物等）を手編集していない / 禁止パターンの新規導入なし / テスト要求のある変更にテストがある / 命名・配置規約への適合

**ゲートが green でも、設計・ガイドラインに逸脱があれば未完了として差し戻す。**

> **プロジェクト固有のガイドライン参照先（記入例）**
> - u1-web: `docs/dev-guidelines.md` の §17 PR 前チェックリスト
> - u1-api: `CLAUDE.md` の「コードスタイル」「テスト要件」、`docs/CodingDesign.md`
