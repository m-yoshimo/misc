# 設計レビュー・ルーブリック（design-review agent 用の照合基準）

このファイルは **外部の design-review エージェントが「Claude の成果物」を照合するためのチェック基準**である。
Claude 自身が守るルール（注入 feedback）ではなく、**別の目（レビュー担当）が使う採点表**。判定者を実装者から分離するのが目的。

## 適用タイミング（2箇所）
- **A. タスク定義書作成時**: 実装前の設計・計画を、この基準で照合する（コードを書く前に設計欠陥を捕捉）。
- **B. 実装時**: 実 diff を、この基準で照合する（Convert 再発明・DI 混在・未使用変数 等を捕捉）。

---

## 0. 設計原則（全観点の"土台"・判断の視点）

個別チェック項目より上位の「常に持つべき視点」。機械的に ○× できない判断も含むが、レビュー時は必ずこの視点で問い直す。**個別ルールが衝突した時の最終裁定もここに帰る。**

1. **常に高い品質と一貫性のあるアーキテクチャ・コードを保つ。** 一貫性・可読性・堅牢性・拡張性が最終目的。
2. **仕様を忠実に守るだけでなく、仕様の矛盾・問題があれば回避策・代替案の提案を検討する。** 言われたまま実装して破綻を放置しない。
3. **変更量の最小化を目的化しない。** 「差分が小さい」を理由に品質・一貫性を犠牲にしない。最優先は最終成果物の品質。
4. **破壊的変更は最小限にする（特にデータが絡む変更）。ただし一切やらないわけではない。** 必要なら破壊的変更も選ぶが、影響を見極めた上で。
5. **⭐ あらゆる変更は、そのリスク・影響とメリットを天秤にかけて判断する。** ← **これが判断の核。** センス・経験を要し、機械化もチェックリスト化もできない領域だが、レビューでは必ず「この変更のリスク／影響（誰に・データに・将来に）とメリットは何か、その天秤は取れているか」を問うこと。ここが最も難しく、最も重要。

## 1. レビュー観点（違反があれば file:line 付きで指摘）

### 品質・一貫性・判断（原則の適用）
- 変更量の最小化を目的化していないか。最小差分のために一貫性・可読性を崩していないか（原則3）。
- 破壊的変更・データが絡む変更で、影響を見極めた上での判断になっているか（原則4）。リスク／影響とメリットの天秤が取れているか（原則5）。
- 仕様の矛盾・問題を見つけたのに、代替案・回避案を検討せず言われたまま実装していないか（原則2）。
- **可読性を常に意識しているか。** 命名・関数分割・整形・コメント・制御フローが、読み手の認知負荷を下げているか。「動く」だけでなく「読みやすい」を後回しにしない。

### DRY・共通化・既存資産の活用
- 重複ロジックを **usecase 間で共有していないか**（＝usecase/モジュール間の依存を作っていないか）。共有ヘルパーを片方の usecase に定義して別 usecase から呼ぶのは NG。
- 共通変換は **model / entity 層**に置き、**既存の変換関数（例: `Convert()`）を再発明していないか**。必要なら既存関数に引数を足して使う。
- **新しい関数・引数を足す前に、既存関数の合成で表現できないか**確認したか。プリミティブ（正規化系）に高レベル関数（offset 計算等）を内部依存させない（依存方向は下から上へ積む）。

### レイヤー境界・責務・依存方向
- domain/app が上位レイヤーを import していないか（依存は下向き）。
- **横断的・統一的処理は Service 層に置く**（レイヤの責務境界を守る）。
- **common（共通基盤）は原則 repository にのみ依存**する。
- 相互依存しやすいフィーチャ間は、**cross-import より「各フィーチャに同等実装を持たせる」**。
- **usecase は service を app/services の具象で参照しない。domain/services の interface 経由**にする。
- **query/取得サービスに、別リポジトリの取得責務（責務外）を混ぜない**。他エンティティが要る整形は、それを持つ呼び出し側で行うか、返り値を型を保って分割して返す。
- **抽象/レイヤは責務が実在する箇所にのみ置く。対称性のための空ラッパを作らない。**
- **副作用（API 呼び出し・DB 書き込み・mutation）の共通化が、経路の追いやすさ・責務の分離を崩していないか（原則。共通化自体は否定しない）。** 単一目的で複数副作用・複数利用箇所なら共通化してよいが、(1)どの経路（ページ・ルート／API）起点で副作用が走るか追いやすい (2)共通化先が責務的に正しい（異ドメイン・無関係文脈に紛れ込まない）、の2条件を満たすか見る。フロント: 原則、再利用可能な共通 UI コンポーネント(view)内で副作用を呼ばない（mutation はルート隣接 usecase.ts 所有＋ `onXxx` コールバック注入）。バックエンド: 目的別 service への集約は可、ただし異なるドメインに紛れ込ませない。※フロント・サーバ双方で特殊ケースはあり得るため絶対禁止としては扱わない。詳細は design_philosophy.md「副作用の共通化は禁じない。原則、呼び出し経路が追え・責務が混ざらない形にする」。

### 責務分離・返り値設計
- 各関数/型が単一の責務か。
- 異種のデータを1スライスに無理やり concat/変換して**情報を落としていないか**（型を保って分割して返し、変換・紐付けは呼び出し側に委ねる）。

### DI・記法の一貫性
- コンストラクタへの依存の渡し方で、**変数宣言と inline `NewXxx()` を混ぜていないか**。周囲の同種コードの流儀に合わせる。
- **DI 構造体のフィールド順は database → repo → service。** New 関数・構造体リテラルも同順。

### エラーハンドリング
- **既存コードの慣用形に合わせる。独自の if-init パターンを新規に持ち込まない。** 同一ファイル内に慣用形があれば必ずそれに合わせる。

### 既存パターンへの追随（＝書く前に読む・裏取りする）
- 新規 usecase/factory/repo/変換を書く前に、**同 feature の既存同種ファイルを読み、その流儀を真似ているか**。多くの設計ミスは「既存を見る前に書き始めた」ことに起因する。
- **着手前に現状の仕様・既存実装をコードで裏取りし、依頼の前提が正しいか**を確認したか（前提が崩れていれば対応の要否から問い直す）。

### 多角的な設計・実装視点（＝最初の案・既存手法に固定されていないか）
- **タスク定義書／設計が多角的な視点で検討されているか。** 最初の案・既存手法だけに固定せず、別の構造・別方式（既存の枠にない代替を含む）を俎上に載せて比較したか。**1案しか出ていない設計は比較材料が欠けている疑い**として問い、代替の視点・手法を提示する。
- 直前の『既存パターンへの追随』の**対の歯止め**。既存踏襲も新方式もそれ自体は正義ではなく、両者は**原則5（リスク/影響とメリットの天秤）**に帰る（影響範囲＝方式混在による一貫性の毀損 × 品質改善）。
- 実装者は自分の盲点（既存手法・最初の案へのアンカー）に気づきにくいので、この観点は分離した評価者が**事後に必ずチェック**する。詳細・具体例は design_philosophy.md「設計・実装は多角的な視点で考える」。

### 「少数派パターン」の扱い
- **少数派＝不整合ではない。** 用途で分類（重複排除／処理済み／無効化 等）して判断し、多数派に短絡的に揃えない。

### テストの骨抜き禁止
- `gomock.Any()` は db/context 等の**第1引数のみ**。scope・ID・モデル・件数は**正確な matcher で検証**しているか。
- 各 mock の EXPECT は**単体で成立（standalone）**しているか（他 mock の返り値/引数を流用していないか）。
- 共有テストヘルパの不具合は per-test の回避策でなく**本体を直す**。matcher の `Matches` は冪等に。

### 前提が明確な処理（バッチ等）／dual-write
- 仕様上の前提（span・対象集合）が確定している処理に、**汎用 API 由来の再導出・突合・防御分岐を持ち込んでいないか**。
- dual-write の同期は、span が確定しているなら「**対象期間のスナップショットを上書き**」で足りる。新規/既存の判定や ID 個別追跡をしない。
- 逆に、**前提を持たない汎用 API でこれらが必要になるのは正常**。前提の違う両者を無理に共通化していないか（形の違いは前提の違いのシグナル）。
- この観点は「DRY・共通化」観点と正面から衝突しうる。**衝突時は §0 原則5（リスク・影響とメリットの天秤）で裁定する。** 天秤にかけずどちらかを機械適用した設計が指摘対象であり、天秤にかけた上での結論はどちらでも可（判断が記述されているか、を見る）。

### 命名・可読性
- map/set 等の命名規則（`map[K]V`→`vByKey`／`map[K][]V`→`vsByKey`／set は `{Key}Set` 等）に従っているか。複数形/単数形の違い・返り値型違いで紛らわしい命名を新設していないか。
