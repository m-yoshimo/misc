## 共有テストヘルパの不具合は、per-test の回避策でなく本体を直す。matcher の Matches は冪等に
- タグ: go, universal, 関心: テスト, 関心: 共通化
- 対象/場面: 共有のテストヘルパ（カスタム matcher 等）が原因で個別テストに回避コードを書きたくなったとき。
- 判断: 回避策を各テストに撒くのではなく、**共有ヘルパ本体の不具合を直す**。特にカスタム matcher の `Matches` は**冪等**にする（呼び出しごとに新しい状態に対して評価し、matcher 自身のフィールドを変異させない）。gomock は1つの実呼び出しを複数の期待値の matcher に対して試行するため、`Matches` が状態を蓄積すると後続のマッチが壊れる。影響範囲が広い共有コードでも、修正が「より正しくする」性質なら full test suite を通して安全性を裏取りすれば本体修正してよい。
- 理由: 回避策（per-test ラッパー等）は同じ不具合に当たるたびにコピーされ、周辺と不整合な独自コードを増やす。根本を直せば全テストが恩恵を受け、周辺と同じ標準パターンに揃う。
- 具体例: u1-api。`test.ClauseMatcher.Matches` が永続フィールド `m.db` へ WHERE 句を適用して蓄積し、同一メソッドに複数 EXPECT があると汚染された。バッチテスト側で「呼び出しごとに matcher を作り直す `freshClauseMatcher`」で回避していたが、ユーザー指摘で本体の `Matches` を fresh db 適用に直し（冪等化）、full suite green を確認して workaround を撤去・標準の `test.NewClauseMatcher()` に統一した。

## 「少数派パターン」は3種類に分類する。少数派＝不整合ではない
- タグ: universal, 関心: コード分析, 関心: レビュー, 関心: 規約
- 対象/場面: 全コード横断で「規約から外れたコード」を検出するとき。多数派＝事実上の規約、少数派＝容疑、とまず置くが、少数派をそのまま欠陥扱いしない。
- 判断: 少数派を必ず次の3つに分類する。
  - **(a) ユースケース限定型**: その実装パターンを必要とする文脈がそもそも限られている（例: mutationService / queryService は特定の限られた文脈でしか使われない）。数が少ないのは当然で正しい。→ Guideline に「この文脈でだけ使う」と明記する対象。
  - **(b) 意図的な例外**: 例外として意図して対応しているケース（例: 正当な cross-feature 依存）。→ Guideline に「これは例外」と明記する対象。
  - **(c) 単純な不整合**: 周辺・他コードと書き方が揃っていないだけ。→ **修正対象はこれだけ。**
- 理由: (a)(b) を機械的に「少数派だから直す」とすると正しい設計を壊す。修正対象は (c) のみ。(a)(b) は消すのではなく Guideline に記録して「なぜ少数なのか」を明文化する。
- 補足: 規約の棚卸し（CodingGuideline 整理）はサンプルでなく**全コードを列挙して**行う。サンプルだと見落とす。各構文を全件列挙→バリアントにクラスタ→各バリアントを (a)(b)(c) に分類、の順で進める。

## 横断的・統一的処理は Service 層に置く（レイヤの責務境界を守る）
- タグ: go, universal, 関心: 構造, 関心: 共通化
- 対象/場面: 「複数のデータストア（テーブル/repo）へ同時に書き込む」「複数の下位コンポーネントを束ねて1つの統一操作にする」ような処理を、どのレイヤに置くか
- 判断: そういう**統一的・横断的な処理は Service 層に置く**。下位レイヤ（repository）に同種コンポーネントをラップした合成オブジェクトを作って解決しない。各レイヤが守っている**構成の不変条件（invariant）**を、利便性のために壊さない。
- 理由: repository は「model（テーブル）につき1つ」という構成を取っている。複数 repo を束ねる合成 repo を repository 層に置くと、その「1 model = 1 repo」という全体設計が崩れる。横断処理を束ねる責務はもともと Service 層が担っており、そこに置けば既存の責務分担と整合する。利便性（既存インターフェースに drop-in できる等）のために層の不変条件を破ると、設計の一貫性が失われ、後から読む人がレイヤの規則を信頼できなくなる。
- 具体例: u1-api GN-5760。archive と recent の2テーブルへ dual-write する処理を、`IPrizeMeterReadRepo` を実装する `PrizeMeterReadDualWriteRepo`（archive repo + recent repo を内包）として repository 層に置こうとしたが却下。「repository は model 1対1の構成。DualWriteRepo は全体設計を崩す。統一的処理は Service 層が担うので Service で行うべき」と指摘された。

## 変更量の最小化を目的化しない。最優先は最終成果物の品質（一貫性・可読性・堅牢性・拡張性）
- タグ: universal, 関心: 品質基準
- 対象/場面: 設計・実装の案を選ぶとき。「この案の方が変更が小さい / 差分が少ない / 既存を触らずに済む」を選定理由にしようとする場面
- 判断: **変更量の少なさを意思決定の根拠にしない**（言語・システムに依存しない普遍原則）。大きな変更になっても、最終的に実装された**全体コードが一貫性・可読性・堅牢性を持ち、将来の変更・拡張に耐えるか**で選ぶ。常にコード全体が高品質であることを最優先する。
- 理由: 変更量最小化を優先すると、既存の歪みに合わせた継ぎ足しが積み上がり、全体品質が劣化する。短期の差分の小ささより、長期に読みやすく・壊れにくく・拡張しやすい状態の価値が高い。
- 具体例: u1-api GN-5760。「読みのみの4消費者は変更ゼロ」「委譲が1枚増えるだけ」という変更量ベースの論拠を提示したところ、「変更量を減らすことは重視しない。それ以上に、最終的に実装された結果が一貫性・可読性・堅牢性かつ柔軟な変更・拡張に耐えるかを最重要視する」と明確に指摘された。

## 抽象/レイヤは責務が実在する箇所にのみ置く。対称性のための空ラッパを作らない
- タグ: go, universal, 関心: 構造
- 対象/場面: 似たモデル間で、片方にだけ query / mutation 等のサービスを置くと構成が非対称になる、という場面
- 判断: 責務が実在する所にだけ抽象（query service 等）を置く。**対称性をそろえる目的で、ロジックの無い委譲レイヤを足さない**。結果が非対称でも、その非対称が「責務の有無」を明示するなら、むしろ可読性上のメリット（どこに何の責務があるか一目で分かる）になる。
- 理由: 空の委譲レイヤは読み手に「ここに固有責務がある」と誤認させ追跡コストを増やす。非対称は欠陥ではなく、責務分布を表すシグナルになり得る。
- 具体例: u1-api。prize_meter_read は usecase に archive 参照（query）責務が無いため query service を作らない。一方 prize_booth_sales は usecase で archive 参照が必要になるため query service を持つ。両者を対称化（両方に query service を持たせる）より、必要な側だけが持つ非対称の方が責務が明示的で分かりやすい、と判断された。

## common（共通基盤）パッケージは原則 repository にのみ依存する
- タグ: go, 関心: 構造, 関心: 依存方向
- 対象/場面: common から他フィーチャ（prizes 等）の実装を使いたくなる場面
- 判断: common は他フィーチャの **domain/repos のみに依存**する。他フィーチャの app/services・usecase・domain/services には依存しない（原則）。横断的処理が必要なら、その実装を **common 側にも持たせて repos から組み立てる**。
- 理由: common は最も多くから参照される土台。ここが特定フィーチャのサービス層に依存すると依存グラフが汚れ、循環・結合が広がる。依存先を repos（データアクセス境界）だけに限定すれば common の独立性が保たれる。
- 具体例: u1-api GN-5760。prizes の mutation service を common の `am_machine_setting_prize_service` に注入しようとしたが、「common → 各レイヤ依存は許容するが**原則 repository のみ**」という方針で却下。common 側に同等の mutation service を新設し、prizes/domain/repos から組み立てる方針にした。

## 相互依存しやすいフィーチャ間は、cross-import より「各フィーチャに同等実装を持たせる」
- タグ: go, universal, 関心: 構造, 関心: 依存方向
- 対象/場面: 複数フィーチャ（prize と report、common と prize 等）が同種の処理を必要とし、相互依存が発生しやすい場面
- 判断: 共有実装を一方に置いて他方から cross-import するのではなく、**各フィーチャ（共通基盤含む）に同等の実装をそれぞれ持たせる**。多少の重複を許容してでも、フィーチャ間の依存エッジを増やさない。共有してよいのは下位の安定層（domain/repos・domain/models 等）のみ。
- 理由: 相互依存しやすい関係で cross-import を許すと双方向依存・循環に陥りやすい。実装を各自に持たせれば依存方向が一方向（下位共有層のみ）に保たれ、各フィーチャを独立して読める・変更できる。**DRY より依存の清潔さを優先**する判断。
- 具体例: u1-api。report と prize は相互依存が発生しやすいため、それぞれに実装を持たせている。GN-5760 でも prizes と common の双方に meter read の mutation service を置き、共有層は domain/repos と domain/models（変換関数）に限定する。

## usecase は service を app/services の具象で参照しない。domain/services の interface 経由にする
- タグ: go, 関心: 構造, 関心: 依存方向
- 対象/場面: usecase が service に依存するとき（u1-api のレイヤ構成）
- 判断: usecase は service を `app/services` の**具象型で import しない**。**`domain/services` に interface を定義し、それ経由で依存**する（既存 `IPrizeBoothSaleService` 等と同じ）。factory が具象を生成して interface 引数に渡す。service 同士の**同一パッケージ内**利用は具象でよい（docs の「services を除いたアクセスは interface 経由」の範囲）。
- 理由: app→app の具象結合を避け、依存を domain interface に集約。テストも interface mock で差し替え可能になり、既存パターン・docs/CodingDesign.md のレイヤ規約と一貫する。**プロジェクトの設計ドキュメントに明記された基礎規約は、実装前に読んで従う**（ユーザーに毎回指摘させない）。
- 具体例: u1-api GN-5760。prize_meter_reads_usecase が mutation サービスを `prize_services "internal/prizes/app/services"` の具象で参照していたのを指摘され、`domain/services` に `IPrizeMeterReadMutationService` を定義して経由する形に修正した。

## DI 構造体のフィールド順は database → repo → service。New 関数・構造体リテラルも同順
- タグ: go, 関心: 構造, 関心: 可読性
- 対象/場面: Usecase など DI で生成する構造体にフィールド（特に service）を追加するとき
- 判断: フィールド順は **`database` → repo 群 → service 群**。`New` 関数の引数順と構造体リテラル（`return Xxx{...}`）の順は、**必ず構造体フィールドと同一**にする。既存に service を足すときは repo 群の中ではなく **service 群（末尾側）** に置く。service 構造体（`*Service`）でも同じく repo→service で揃える。
- 理由: 種別ごとに並ぶと依存の構成が一目で読める。位置引数の構造体リテラルでは並びがズレると別フィールドに代入され事故になる（型が合えばコンパイルも通ってしまう）。struct 定義・`New` 引数・リテラルの3箇所を同順に保つのが安全。
- 具体例: u1-api GN-5760。Worker が mutation サービスを repo 群の中（recent repo の直後）に挿入していたのを「repo → service の順、New も構造体と同順」と指摘され、service を末尾の service 群へ移動した。`PrizeMeterReadsUsecase`・`AmMachineSettingPrizeService` 双方で修正。

## テストの mock 引数は context（第1引数）以外を gomock.Any で省略しない
- タグ: go, 関心: テスト, 関心: 品質基準
- 対象/場面: gomock で repository / service のモック呼び出しを EXPECT するとき
- 判断: `gomock.Any()` を使ってよいのは **repository 等の第1引数（context / db）だけ**。それ以外の引数（scopes・ID・モデル・件数等）は **必ず正確な matcher で検証**する。Any で省略するとテストが「呼ばれたこと」しか見ず、引数の正しさを検証できないため**テストの意味が失われる**。
- 理由: 引数を Any にすると、誤った scope/ID/データで呼んでもテストが通り、回帰検出能力が消える。既存テストも context 以外は正確にマッチしているので、Any 省略は既存規約からの逸脱でもある。
- 具体例: u1-api GN-5760。re-read Find や recent BatchUpsert・Delete の期待値を全引数 `gomock.Any()` で省略していたのを「context 以外で Any を使うな、テストになっていない。同じファイルの他箇所はやっていないのに、なぜ省略したのか」と強く指摘された。

## エラーハンドリングは既存コードの慣用形に合わせる。独自の if-init パターンを作らない
- タグ: go, 関心: 可読性, 関心: 一貫性
- 対象/場面: repository の Delete 等でエラーを判定し、特定エラー（ErrNoRecordToDelete 等）を無視するとき
- 判断: プロジェクトの慣用形に従う。例（u1-api）: `err = repo.Delete(...)` の後に `if errors.Is(err, apperror.ErrNoRecordToDelete) { err = nil }` ＋ `if err != nil { return }`。`if localErr := call(); localErr != nil && !errors.Is(...) { err = localErr; return }` のような**独自の長い if-init 形式を新規に持ち込まない**。
- 理由: 同種処理を同じ書き方に揃えると読み手の負担が減り一貫性が保たれる。独自パターンは「なぜここだけ違うのか」を考えさせ、レビューで必ず引っかかる。**同一ファイル内に既に慣用形があるなら必ずそれに合わせる**（書く前に周辺の同種処理を確認する）。
- 具体例: u1-api GN-5760。recent/archive の Delete で `if recentErr := ...; recentErr != nil && !errors.Is(...) { err = recentErr; return }` と独自に書き「こんな書き方をしているコードがあるか？」と指摘された。同ファイル内の他の Delete は全て `if errors.Is(err, X) { err = nil }; if err != nil { return }` の慣用形だった。

## テストの mock 期待値は1つずつ独立（standalone）にする。他 mock の返り値・引数を流用しない
- タグ: go, 関心: テスト, 関心: 構造
- 対象/場面: gomock で複数の repository/service 呼び出しを EXPECT するとき
- 判断: 各 mock の EXPECT は**単体で成立**させる。期待する引数・records・返り値は**そのモック専用のテストケースフィールドから明示的に**与える。**他の mock の `ret` や `args` を流用して別 mock の期待値を組み立てない**（変換流用も禁止。例: archive BatchUpsert の `ret` を変換して recent BatchUpsert の期待 records にする、archive の `args[2:]` を recent の scope に使い回す、は厳禁）。mock 同士が依存し合う構造を作らない。
- 理由: mock が依存し合うと、テストケース側で各 mock の状況を独立に制御・検証できず、片方を直すと連鎖で壊れる。1つずつ独立なら、テストケースを読めばその mock に何を期待しているか自明になる。
- 具体例: u1-api GN-5760。recent BatchUpsert の期待値を `gomock.InAnyOrder(test.ToRecentSliceForReturn(archiveMock.ret))` ＋ `archiveMock.args[2:]` と archive mock から導出していたところ、「他にこんな書き方はない。各 mock は単体で動くようにし、テストケース側で状況判断できるようにすべき。mock 同士の依存・返り値/引数の使い回しは厳禁」と指摘された。

## 前提条件が明確な処理に、汎用的・防御的な処理を持ち込まない
- タグ: universal, go, 関心: 構造, 関心: 過剰設計
- 対象/場面: バッチのように、仕様上の前提（対象期間 span・対象集合・全行が新規か等）が確定している処理を書くとき
- 判断: その前提に特化した最小の処理を書く。汎用 API が必要とする「入力からの再導出」「1 件ずつの突合」「前提が崩れた場合の防御分岐」を持ち込まない。dual-write の同期なら、span が確定しているのだから span の正データを取得してもう一方をそのまま上書き（upsert）すれば足りる。新規/既存の判定も ID 個別追跡も要らない。
- 理由: 前提が保証されている場所に汎用処理を置くと、読む人は「この分岐はどの前提が崩れたときのためか」を追わされ、前提の明確さがコードから消える。逆に、前提を持たない汎用 API ではこれらの処理が正常に必要になる。形の違いは前提の違いのシグナルなので、無理に共通化しない。
- 位置づけ: このエントリは**基本原則そのものではなく、基本原則（`design_review_rubric.md` §0 の 5 項目）を評価するための視点の一つ**。「DRY・共通化」の視点と正面から衝突しうる。**衝突時は原則5（リスク・影響とメリットの天秤）で裁定する。** 天秤にかけずどちらかを機械適用するのが誤りであって、天秤にかけた上での結論はどちらでもよい。
- 具体例1: u1-api GN-5760 preparePrizeMeterReads。dual-write の同期で、書き込んだ records から from/to を計算し boothId 単位で再取得していたのを「span が決まっているのだから span の期間を archive から取得して recent に上書きすればよい。新規判定もしていないし dual-write なら上書きで問題ない」と指摘された。**過剰なのは「スナップショットでないこと」ではなく「前提が明確なのに汎用的な追跡をしたこと」。**
- 具体例2: u1-api GN-5846 `DualBatchUpsertForInitialize`。呼び出し元から前提が見えない汎用の書き込み API では、一意キーで archive を読み直して入力行に対応する行だけを recent へ書く（gorm の `INSERT ... ON DUPLICATE KEY UPDATE` の返り ID が信用できないため）。これは前提を持たない側では正常な処理。具体例1 と両立する。
- 注意（教訓）: このエントリは当初「dual-write の同期は期間スナップショットを上書きでよい」という**結論だけ**を書いていた。そのため後日、原則（前提が明確なら過剰な処理をするな）ではなく手段（スナップショット）が規範として読まれ、汎用 API にまで機械的に適用しようとする誤りを招いた。**教訓は結論ではなく原則の形で書く。**

## 着手前に「現状の仕様・既存実装」を確認する。依頼の前提が正しいかをコードで裏取りしてから対応する
- タグ: universal, 関心: 進め方, 関心: 要件確認
- 対象/場面: 「Xという仕様になったのでYを変えたい」という依頼を受けたとき。特に前提（＝現状はこうなっている）が、依頼者の記憶・認識ベースで語られているとき。タスク定義の作成段階を含む。
- 判断: 実装（やタスク定義作成）に入る前に、関連する**現状の仕様・既存実装を必ずコードで確認**し、依頼の前提が事実かを裏取りする。前提が崩れていればその時点で指摘し、対応の要否そのものから問い直す。前提確認を「自明」と思って飛ばさない。
- 理由: 前提が誤っていると、作ったタスク定義・実装ごと丸ごと無駄になる（最悪、意図と逆方向の変更をしてしまう）。着手前のひと手間（現状の該当箇所を読む）で防げる。
- 具体例: u1-web GN-5779。「prize_meter_reads は当月含む過去3ヶ月しか保持しないので日付選択を限定する」という依頼で、タスク定義〜実装まで進めた。しかし既存 UI は元々「編集可能期限＝過去31日」で選択下限を制限済みで、保持期間(3ヶ月)より**厳しかった**。つまり変更は不要（むしろ選択範囲を広げる逆方向の変更だった）。最初に「現状の選択下限がどうなっているか」をコードで確認していれば着手前に判明した。実装・タスク定義は全て revert した。

## 新しい関数・引数を足す前に、既存関数の合成で表現できないか確認する
- タグ: universal, react, 関心: 共通化, 関心: 構造
- 対象/場面: ユーティリティに新関数を追加したり、既存関数へ引数を足したくなったとき。
- 判断: 追加の前に、まず**既存プリミティブの合成**で要件を表現できないか探す。(1) 合成で足りるなら新規追加しない。(2) プリミティブ（正規化系の関数）に高レベル関数（offset 計算等）を**内部依存させない**＝依存方向は「プリミティブを土台にして上へ積む」。(3) 既存関数と紛らわしい命名（複数形/単数形の違い・返り値型違い）での新設は避ける。
- 理由: 関数・引数の数は保守コスト。合成で済むなら最小で済む。依存方向を揃えると既存の合成パターンに馴染み、似た命名の乱立は誤用を招く。
- 具体例: u1-web。「当月含む過去3ヶ月の月初」を得るのに `getMonthAgo` 新設や `getMonthStart` への offset 引数追加を検討したが、既存の `getMonthStart(getMonthsAgo(2))` の合成だけで足りた。既存に `getNextMonthStart = getMonthStart(base).add(1,'month')` という「プリミティブの上に積む」前例があり、`getMonthStart` が offset 関数を内部利用するのは逆方向。また既存 `getMonthsAgo`(複数形/string) の隣に `getMonthAgo`(単数形/Dayjs) を作るのは紛らわしい、と整理した。

## 共通ロジックを usecase 層に置いて usecase/モジュール間の依存を作らない。共有変換は既存の変換関数(Convert 等)を活かし、必要なら引数を受けられるよう拡張する
- タグ: universal, go, 関心: 共通化, 関心: 構造
- 対象/場面: 複数 usecase が同じ変換・突合ロジックを必要とするとき
- 判断: 共有ヘルパーを片方の usecase ファイルに定義して別 usecase から呼ぶ(=usecase 間依存)ことはしない。変換ロジックは対象モデル/エンティティ側に置く。既に `Convert()` のような変換関数があるなら再発明せず、必要な文脈(booth 等)を引数で受けられるよう拡張して使う。
- 理由: usecase 間依存・重複定義は保守性を壊す。既存関数の再利用が最小で一貫する。
- 具体例: u1-api GN-5811。tone→PrizeBoothSale 変換を各 usecase の共有ヘルパー convertToneBoothSales で行っていたが、「usecase 間依存は NG、既存の TonePrizeBoothSale.Convert() を booth を受けられるようにして解決しろ」と指摘された。

## query/取得サービスに別リポジトリの取得(責務外)を混ぜない。他エンティティが要る整形は呼び出し側で
- タグ: universal, 関心: レイヤー分離, 関心: 責務
- 対象/場面: sales を返す query service 内で、ソートや突合のために booth 等の別データが必要になったとき
- 判断: query service は自分の責務(sales 取得)に徹する。ソート/突合に別エンティティが要るなら、それを既に持っている呼び出し側(usecase)で行う。返り値は型を保ったまま分割して返し、変換・紐付けは呼び出し側に委ねる(情報を落とさない)。
- 理由: 責務混在は「何のためのサービスか」を壊す。呼び出し側は既に必要データ(booths 等)を持っていることが多い。
- 具体例: u1-api GN-5811。FindByDateRange(sales 取得)内で booth_name ソートのため boothRepo.Find していたのを撤去。tone も Convert して単一スライスに concat せず、boothSales と tone を別々の返り値にして usecase 側で booth に突合、と指摘された。

## DI・呼び出しの書き方はコードベースの流儀に一貫させる(変数宣言 vs inline を混ぜない)
- タグ: universal, go, 関心: 一貫性, 関心: 可読性
- 対象/場面: factory 等で依存(repo)をコンストラクタに渡すとき
- 判断: 周囲が repo を変数で宣言して渡しているなら全て変数に揃える。一部だけ inline `NewXxx()` を混ぜない(逆も同様)。周辺の同種コードを見てから書く。
- 理由: 混在は読みにくく、レビューで必ず引っかかる。過去の自分の追加がこの混在を生んでいた。
- 具体例: u1-api GN-5811。factory で一部 repo を inline `prize_repos.NewXxx()` で渡し、他は変数、と混在させて「書き方がやばすぎ」と指摘された。

## ユーザー可視文字列（ラベル/ボタン/メッセージ）を造語しない。必ずコードベースの実在慣習に照合する
- タグ: universal, react, 関心: 規約, 関心: 可読性
- 対象/場面: 新規UIにラベル・ボタン文言・ダイアログ見出し・トースト文などのユーザー可視文字列を置くとき。
- 判断: **文字列を発明しない。** 実装前に同種UIの文言をコードベース全体で grep し、(1) 圧倒的多数の定型があるか、(2) 同一画面・同一機能ファミリの兄弟が何を使っているか、(3) 意味的に最も近い先行実装が何を使っているか、を照合する。複数系統が競合する（例: 汎用「絞り込み」多数派 vs 特定機能だけ別文言）場合は、どれに揃えるべきかを**ユーザーに確認**する。既存文言のどれも意味が合わない場合も、勝手に新語を作らずユーザーの指定に従う。
- 理由: UI文言は製品の一貫性そのもの。造語や近くの1例からのコピペは、同一画面・同一系統の他所と食い違い、ユーザーに「他のコードを一切見ていない」と映る（＝信頼を最も損なう）。行番号や型と違いツールで自動検証されないぶん、明示的に grep 照合しないと必ず捏造が紛れる。
- 具体例: u1-web GN-5831/5832。SPアシストフロアマップの絞り込みラベルを実績フロアマップから借りて `"ブース・景品検索"` としたが、同系統の兄弟 `sp-assist-booth-filter` も同一画面の list タブも `"絞り込み"`（コードベースの約35ファイルが "絞り込み"、"ブース・景品検索" はフロアマップ2画面のみ）で、どちらに揃えるべきか照合していなかった。続く GN-5832 では `"プライズ機種名検索"` という**コードベースに存在しない造語**をタスク定義に書き、ユーザーに「勝手に定義」「他のコードを一切見ていない」と指摘された。

## 共有フックを「module-import 参照」から「引数注入」に変えると exhaustive-deps と安定参照が新たな制約になる
- タグ: react, universal, 関心: 共通化, 関心: リファクタ, 関心: 正しさ
- 対象/場面: 既存の共有フックを汎用化するため、これまで module スコープの import を直接参照していた関数（matcher/比較関数等）を、フックの引数（パラメータ）に切り出して注入可能にするとき。
- 判断: 「本体ロジックは不変・参照だけ差し替え」と安易に書かない。(1) 引数化した関数を使う `useMemo`/`useCallback` の deps に**その関数を追加**する（module import 時は非リアクティブで deps 不要だったが、引数化した瞬間 `react-hooks/exhaustive-deps` が要求する＝lint が落ちる）。(2) 呼び出し側は注入する関数を**モジュールスコープの安定参照**にする（inline 関数だと毎レンダー identity が変わり、memo 無効化・派生 useCallback の連鎖再生成・effect 暴発を招く）。この2点を設計時に明記し、「挙動不変」の前提条件として言語化する。
- 理由: module import は参照が固定で deps に現れないが、引数はレンダーごとに変わりうる値なので lint も再計算も挙動が変わる。ここを「参照の差し替えだけ」と誤認すると、lint 落ち・パフォーマンス劣化・フォーカス/ズームの暴発など、汎用化前には無かった不具合を持ち込む。
- 具体例: u1-web GN-5832。共有 `useFloorMapSearch` を `<T,P>` にジェネリック化し `matchesPoint`/`isSearchEmpty` を引数注入する設計で、タスク定義に「本体の useMemo/useCallback は現行維持・参照だけ差し替え」と書いたが、design-review で「引数化すると exhaustive-deps が deps 追加を要求し make lint が落ちる。かつ注入関数が安定参照でないと再ズームが暴発する」と指摘された（SPアシストが同フックで eslint-disable している事実が lint 有効の証左）。

## 実装とは「制約を付けること」。汎用性より制約・可読性を優先し、型で不能を表す
- タグ: universal, go, typescript, 関心: 構造, 関心: 可読性, 関心: 型設計
- 対象/場面: 共通化・抽象化の設計。ジェネリクスやパラメータ注入で「何でも扱える」形にするか、扱える対象を型で絞るかを選ぶ場面。
- 判断: **汎用性を上げるほど可読性は落ち、抜け漏れによる不具合・実装漏れのリスクが増える**という前提を常に置く。可能な限り**制約を付ける**方向に倒す。具体的には (1) 不要なジェネリクス型パラメータは足さない・剥がす、(2) 扱える入力を単一の型に固定し「この型にあるものでしか処理できない」を型で明示する、(3) 派生が必要な場合は `Pick<Base, 'field'>` 等で基底型から絞って単一の出所を保つ。「実態が複数あるから汎用化」ではなく「本当に別物の軸だけをジェネリクスに残す」（例: 点の型 T は本当に構造が違うので残す／検索条件 P は実質同一なので固定に畳む）。
- 理由: 汎用化は表面上のDRYと引き換えに、呼び出し側の意図が型から読み取れなくなり、想定外の入力を通してしまう余地を生む。制約が強いほど「できないことは書けない」状態になり、コンパイル時に誤用が弾かれ、新規メンバーも短時間で意図を掴める。これは言語非依存の普遍原則。
- 補足（ユーザーの好み・背景／現状は能動ルール化しない）: ユーザーは「TS は実行時に型情報が失われる（API 経由データは特に注意）」という理由で Go など型制約の強い言語を好み、TS を全面的には好まない、と述べた（07:46）。ただし後に「**これは私の好みの例であり、現状意識する必要はない**」と明言（08:40）。よってこれは背景の好みであって、能動的な実装ルールとして課すものではない。
- 具体例: u1-web GN-5832。`useFloorMapSearch` を `<T, P>` の2ジェネリクスにしていたが、検索条件 P は meter-reads の `MeterReadFloorMapSearchParams`（`prizeBoothName`）も実質 `FloorMapSearchParams.boothName` と等価だった。P を剥がして `searchParams: FloorMapSearchParams` に固定し（`isSearchEmpty` 注入も不要化）、meter-reads 側は `Pick<FloorMapSearchParams, 'boothName'>` で派生。点の型 T は `PrizePlanFloorMapPoint` と `PrizeMeterReadFloorMapPoint` で本当に構造が違うので残した。「このフックは FloorMapSearchParams にあるものでしか検索できない」という制約を型で強めるのが狙い、とユーザーが明言。
- 参考（勉強材料・確定指針ではない）: ユーザーは「この『制約>汎用性』の一般化・基準は自分でも言葉にするのが難しい」として理論的裏付けの調査を依頼した（08:40, 08:42「僕も理論的な話や裏付けを勉強したい」）。調査結果は notes/[[research-constraint-first-design]] にある。**これは学習用の探索であって、ユーザーの確定した設計指針ではない**ため、その中の個別主張（Metz/Dodds/Parse-don't-validate 等）を規範やレビュー基準として引用しない。

## 設計・実装は多角的な視点で考える（既存手法・最初の案にとらわれない）
- タグ: universal, 関心: 設計プロセス, 関心: 構造, 関心: レビュー
- 対象/場面: 設計・実装の設計段階で、手法・構造そのものを決めるとき。共通化・抽象化・データ構造・フックAPI 等、複数の実現手段があり得る場面。
- 判断: 最初に思いついた案や既存の実装手法に固定せず、**多角的な視点で複数の手法・構造を検討する**。これ自体が目的。「選択肢として並べる／トレードオフ（影響範囲×品質）で評価する／既存踏襲か新方式か／迷ったら聞く」は、多角的に考えた"結果への対処"＝downstream にすぎず、主役にしない。症状（選択肢を並べる）を最適化するのでなく、根（多角的に考える）を直す＝真に多角的なら選択肢は**促される前に**出る。既存の踏襲も新方式もそれ自体は正義でない（既存が正解とは限らない）。目的は高品質・一貫性のあるコードの維持で、影響範囲（方式混在による一貫性毀損）× 品質改善の天秤で判断する。
- 理由: 実装者は自分の盲点（既存手法・最初の案へのアンカー）に気づきにくい。1案しか出さないと、最も制約が強く保守的な案に到達できない（比較して初めて辿り着く）。この盲点は自己申告で埋まらないので、**設計段階では実装者が多角的に考え、タスク定義書作成後は分離した評価者（design-review）が「多角的に検討されているか」を事後評価する**二層で担保する。
- 具体例: u1-web GN-5832。`useFloorMapSearch` の `P` ジェネリクス指摘時、私は既存実装を擁護（現状肯定にアンカー）し畳めることに自力で気づけなかった。`scopes`（u1-api のパーツ方式）もユーザー提案で初めて俎上に載った。促されてからしか比較できていなかった＝多角的に考えられていなかった典型。
- 関連: この観点の要約（レビュー観点）は design_review_rubric.md「多角的な設計・実装視点」。実装者としての規範は feedback `feedback-multi-angle-design`。制約優先の原則（本ファイル「実装とは制約を付けること」）と対で使う。

## 同種の関数（matcher 等）の置き場所は分散させず一箇所に統一する（一貫性）
- タグ: universal, 関心: 一貫性, 関心: 構造
- 対象/場面: ジェネリックな共通フック等に注入する同種の関数（matcher・比較関数など）を、usecase 側に個別定義するか共通側にまとめるかを選ぶ場面。
- 判断: 同種の関数の置き場所を **usecase 側と共通側に散らばらせない。どちらか一方に統一する**。一貫性を優先する。
- 理由: ジェネリクスだと同種の関数が usecase 側にあったり共通側にあったりして混乱する。置き場所が揃っていれば、どこに同種の判定があるか一目で分かる。
- 具体例: u1-web GN-5832。`matchesPlanPoint` が共通の `useFloorMapSearch.ts` にある一方 `matchesMeterReadPoint` は meter-reads の usecase 側にあった。ユーザー指示（08:26「matchesMeterReadPoint も matchesPoint と同様の場所に書いて export。一貫性大事、usecase にもあったり共通化もあったりは混乱するのでどちらかに統一、今回は後者＝共通側」）で両方を共通側に統一した。

## 「制約 vs 共通化」の一般化・基準は未確定。調査結果は勉強材料であり確定指針・レビュー基準にしない
- タグ: universal, 関心: メタ, 関心: 設計プロセス
- 対象/場面: 「制約を付けるべきか／共通化すべきか」の一般的基準を、設計指針やレビュー基準として記録・適用しようとする場面。
- 判断: この領域の一般化・基準は**ユーザー自身も言葉にするのが難しい未確定領域**。理論的裏付けの調査（notes/[[research-constraint-first-design]]）は**勉強材料**であって、ユーザーの確定した設計指針ではない。**調査由来の主張（重複を許す／間違った抽象／DRY 原義／YAGNI 等）を、ユーザーの指針・レビュー採点表として記載・適用しない。**
- 理由: ユーザーは「1・2の一般化・基準は私も言葉にするのが難しい、一般的な設計・実装に関して一度調査した方がよい」（08:40）、「僕も理論的な話や裏付けを勉強したい」（08:42）と、調査を**勉強目的**で依頼した。確定指針への昇格は指示していない。
- 具体例: 本セッションで実装者が Metz/Dodds「重複を選ぶ」「知識か形か（DRY 原義）」を philosophy/rubric に指針として書き込み、ユーザーに「僕が言った内容と全く違う、自己解釈を広げすぎ」と指摘され撤去した（＝この drift の再発防止のためのガードレール）。

## 検索結果を head / limit で打ち切ったまま「全件確認した」と結論づけない
- タグ: universal, 関心: コード分析, 関心: 設計プロセス, 関心: レビュー
- 対象/場面: grep / find の結果を根拠に「該当は N 箇所のみ」「他には存在しない」と設計上の前提を立てるとき。
- 判断: **網羅性を主張する検索は、出力を打ち切ってはいけない。** `| head -N` を付けたコマンドの結果から「これで全部」と結論づけない。網羅を確かめたいときは打ち切らない形（`grep -rl`／`grep -c`／`sort | uniq -c`）で件数・ファイル一覧そのものを取る。「探索のための grep（打ち切ってよい）」と「網羅を主張するための grep（打ち切ってはいけない）」を意識的に区別する。
- 理由: 「裏取りした」という記述だけが残り、実際には出力の先頭 N 行しか見ていない状態が生まれる。裏取り済みと明記された前提は後続の設計判断がそれに乗るため、誤りが下流の判断（スコープ・リネームの是非・影響範囲）をまるごと歪める。しかも「確認済み」と書かれているせいで誰も再確認しない。既存の「着手前に依頼の前提をコードで裏取りする」原則の**証拠の質**に関する系。
- 具体例: u1-api GN-5839。`grep -rn "SnowFlake\|sfPrize" cmd/batch/batches/databricks/ | head -30` の出力が `importDatabricksPrizes/exec.go` の行だけで 30 行埋まっていたため、「Snowflake 命名は 1 ファイルにのみ残存」とタスク定義書の「前提（確認済み・すべて実コードで裏取り済み）」に断言した。実際は 8 ファイルに残存しており、design-review エージェントが blocker として検出。`grep -rlo` で再実測して訂正した。この誤りは「prizes だけリネームすれば一貫する」という設計判断そのものを誤らせていた。

## コメントは非自明な WHY だけを書く。コード再説明・出所付記は書かない。WHY の重複は定義側へ集約する
- タグ: universal, react, 関心: 可読性, 関心: コメント
- 対象/場面: 実装にコメントを付けるとき／既存コメントを整理するとき。特に既存実装をパターン踏襲して書くと、参照元由来のコメントをそのまま増殖させがちな場面。
- 判断: コメントは**コードから読めない「なぜ」だけ**を書く。次は書かない/消す: (a) 型名・変数名・処理をそのまま言い換えただけの説明（`Pick<...,'boothName'>` の隣に「boothName に限定する」等）、(b) 出所・由来の付記（「実績に倣う」「〜と同じ重ね方」）、(c) アクションの実況（「検索条件が変わったら先頭ヒットへフォーカスする」＝直後のコードが言っている）。**同じ WHY を複数の呼び出し側に重複させない** — 共有関数の使用理由は、その関数の定義側コメントに1回だけ書き、呼び出し側は関数名で参照到達させる。周辺コードのコメント密度に合わせる。
- 理由: 冗長コメントは可読性を下げ、コードとズレて陳腐化する。「3分で理解できるコード」の観点で、再説明・出所・実況はノイズ。ただし**過剰削除も禁物**: 型や近接コードから読めない**ドメイン知識**（例: メーターリードのフロアマップ検索語＝プライズ機種名で、それが `boothName` に対応する／なぜ 4 項目でなく boothName だけか）は、たとえ 1 行でも WHY として残す。「再説明か WHY か」の線引きが判断の核。
- 具体例: u1-web GN-5833。フロアマップ検索の実装で、型を言い換えたコメント・「実績と同じ重ね方」の付記・各フィルタに重複した searched バッジの WHY を削除し、WHY は共有 `isFloorMapSearchEmpty` の定義側へ集約した。一方で `MeterReadFloorMapSearchParams` の「プライズ機種名（＝ブース名）で絞るため boothName のみ」は非自明なドメイン理由なので、design-review の minor 指摘を受けて 1 行に圧縮して復活させた。

## 共有ヘルパの名前は用途スコープを名前に込める（汎用に見える名前を避ける）
- タグ: universal, 関心: 命名, 関心: 可読性
- 対象/場面: 複数箇所から使う共有の関数・フック・定数に名前を付けるとき。
- 判断: その関数が**特定の文脈専用**なら、名前にその文脈を含める。汎用的に見える一般名（`isSearchEmpty`, `format`, `validate` 等）は、本来無関係な場面（別種のリスト絞り込み等）でも使える/使うべきものに見えてしまい、誤用と責務の越境を誘う。名前で「これはフロアマップ検索専用」と分かるようにする（`isFloorMapSearchEmpty`）。
- 理由: 名前は最初のドキュメント。スコープを名前に込めると、無関係な文脈での流用を名前の時点で抑止でき、読み手も適用範囲を即座に理解できる。
- 具体例: u1-web GN-5833。フロアマップ検索専用の空判定 `isSearchEmpty` を、ユーザー指摘（「このままだと他のリスト形式などの絞込みでも使うものに見える」）で `isFloorMapSearchEmpty` にリネームした。

## 副作用の共通化は禁じない。原則、呼び出し経路が追え・責務が混ざらない形にする
- タグ: universal, backend, react, tanstack-query, 関心: 構造, 関心: 可読性, 関心: 副作用
- 対象/場面: 副作用のある操作（外部 API 呼び出し・DB 書き込み・mutation 等）を、どのレイヤ/部品に所有させるか決める場面。特に複数箇所から使う共有部品（フロントの共有 UI コンポーネント/modal/organism、バックエンドの共有 service 等）を経由させたくなるとき。「共有部品の中に副作用を持たせれば呼び出し側は無改修」という誘惑が生じる。
- 判断（原則。絶対禁止ではない）:
  - **共通化そのものは否定しない。** 単一の目的に対して複数の副作用が必要で、かつその利用箇所が複数あるなら、副作用を共通化してよい。論点は「共通化の可否」ではなく、次の2条件を満たすか。
    1. その副作用が**どの経路（どのページ・ルート／どの API）を起点に走るかが追いやすい**こと
    2. 共通化先が**責務的に正しい**（無関係な文脈・異なるドメインに紛れ込まない）こと
  - **フロント（React/TanStack Query）**: 原則、**再利用可能な共通 UI コンポーネント（view）の中で副作用（mutation 等）を呼ばない**。どの経路から呼ばれたか辿るのが大変になり、かつ副作用が貼り付くことで UI コンポーネントの使い回しがしにくくなるため。→ 副作用は経路が特定できる `usecase.ts` が所有し、UI へは `onXxx?: (req) => Promise<void>` コールバックで注入（presentational 化）。ローディングは UI 内 RHF `formState.isSubmitting` / フォーム外は usecase の `mutation.isPending`。ガイドライン §7.1・§10.2 もこの原則の一表現。
  - **バックエンド（u1-api 等）**: 目的に応じて **service 等に副作用を集約するのは問題ない**。ただし原則、**異なるドメインの処理に紛れ込ませない**（本ファイル「common は原則 repository のみに依存」と同じ動機）。
  - **いずれも原則であり、フロント・サーバサイドとも特殊なケースはある。** 逸脱するなら、経路の追いやすさ・責務の妥当性を別手段で担保できるかを吟味した上で判断する。
- 理由: 副作用は「いつ・どこ起点で状態が変わるか」が可読性・デバッグ性の要。共通化の可否が本質ではなく、**経路が追えるか／責務が混ざっていないか**が本質。ここが崩れると副作用が散って追跡不能になりスパゲッティ化する。「呼び出し側無改修」という短期の省コストより、副作用の経路が構造から追える保守性を優先する。**この判断は再発する**（過去の別 TanStack Query 対応でも共通部品の mutation について同じ結論＝usecase 所有・共有 UI は presentational を採用済み）。
- 具体例: u1-web GN-5703（差分ページ TanStack Query 対応）。共有 modal（`InventoryPrizeApplyDifferenceModal` 等、複数ルートで使用）の `useSubmitting`+API直呼びを、当初「organism 内に Orval mutation を保持（呼び出し元無改修）」で提案したが、ユーザーに「共有 UI に副作用を埋めると経路が追えず使い回しもしにくい」と却下された。organism 内 mutation の既存例は 2 件（`ArcadeBookmarkButton` 等）のみ・いずれもガイドライン(2026-04-24)より前(2〜3月)の初期移行コードで事後追認ではないことを確認。最終的に modal を presentational 化し mutation は各ルート usecase が所有する案に確定。material.details 側の再改修（onFinish→コールバック注入）はそのコストとして許容。
- 実装ディテール（u1-web の usecase mutation ラッパ）: Orval `useXxxMutation` を usecase に包んで `onXxx` を返すとき、`useCallback` 内で `mutate`/`mutateAsync` を使うなら **`const { mutate } = useXxxMutation(...)` と分割代入して deps に `mutate`/`mutateAsync` を入れる**。`mutation` オブジェクト全体を deps に入れると v5 では identity が毎レンダー変わり `useCallback` が毎レンダー再生成されてメモ化が無効になる（`mutation.mutate` を deps に書くと `react-hooks/exhaustive-deps` が「`mutation` 全体が必要」と警告してこの罠に誘導する）。分割代入した `mutate`/`mutateAsync` は v5 で安定参照なので両立する。**他 PR でも頻出の指摘**。既存ファイルに `mutation` 全体を deps に入れた例が残るが影響は軽微（機能はするがメモ化が効かないだけ）。新規・改修時は必ず分割代入形にする。
- 関連: 「多角的な設計・実装視点」（1案＝比較材料欠如。実装者が「無改修で済む案」に安易にアンカーした失敗例）。バックエンド側の同型は本ファイル「common は他フィーチャの domain/repos のみに依存」系。上の実装ディテールは本ファイル「引数化した関数の deps と安定参照」（L172）と同根。

## 参照実装をテンプレとして踏襲するとき、対象固有のロジック/分岐/ガードの脱落を差分で洗い出す
- タグ: universal, react, 関心: 構造, 関心: 仕様忠実
- 対象/場面: 既存の移行済み「兄弟」実装（別ページ・別リソースの同種画面）をテンプレにして、対象ページを移行・再構成する場面。「material が済んでいるから prize も同型に」のように、参照実装のatom/hook/mutation構造をそのままなぞるとき。
- 判断: 参照実装を**逐語コピーせず、対象ページ固有の要素との差分を明示的に洗い出す**。特に (1) 対象だけが持つ**フィルタ/除外条件**、(2) 対象だけの**分岐・ガード**、(3) 参照側と**データ型の意味論が違う点**（例: 常に配列 vs 未取得 undefined）。参照実装との**非対称は「固有責務のシグナル」**であり、揃えて消すのでなく意図として残す。定義書には「参照と非対称になる箇所」を固有理由付きで列挙する。
- 理由: 参照実装は「型」であって「仕様」ではない。テンプレ化は速いが、対象固有の業務ロジックは参照側に無いため**沈黙して落ちる**（コンパイルは通るので気づきにくく、退行として本番で出る）。落ちるのは往々にして「その画面だけの例外扱い」＝業務上重要な分岐。差分を先に洗い出すコストは、退行の発見コストより桁違いに小さい。
- 具体例: u1-web GN-5704（棚卸確定 prize の TanStack Query 化）。参照実装 material の導出 atom をそのまま真似る設計を書いたが、design-review が「prize の `notExecutedPlacements` は現行コードで `.filter(p => p.placementName !== '荷捌き')` と**荷捌きを明示除外**（material には無い prize 固有ロジック。UI「荷捌きは棚卸未完了でも確定可能」を支える）」の脱落を指摘。逐語コピーしていたら荷捌き未実査で確定不可の退行になっていた。併せて「参照 atom は未取得 undefined を返すのに、現行判定は常に配列前提」の型意味論差（逐語移設で `undefined.length` クラッシュ/誤判定）も指摘された。
- 関連: 「ユーザー可視文字列を造語しない・兄弟実装に照合」（L162。兄弟からの借用時に全文脈を照合せず取り違える同根）。「コメントは参照元由来をそのまま増殖させない」（L214。参照踏襲時に不要物を"増やす"逆方向の失敗）。本エントリは参照踏襲時に固有物を"落とす"失敗。

## 前提が変わったら、その前提の上に得た許可・結論も失効させる。持ち越して正当化を後付けしない
- タグ: universal, 関心: 構造, 関心: スコープ, 関心: 判断の誠実さ
- 対象/場面: 設計中に論点を提起 → ユーザーから条件付きの許可（「〜なら、そうして良い」）を得た → **その後に設計方針が変わり、元の論点自体が消滅した**、という場面。とくに「A案なら X の変更が要る」と説明して X の許可を得た後、B案（X 不要）に決めたとき。
- 判断:
  - 許可は**それを引き出した前提とセットで失効する**。前提が消えたら、許可も自動的には残らない。「許可はもらってある」を根拠に変更を実行しない。
  - 方針を変えた瞬間に、**その方針変更で不要になった作業を洗い出して落とす**。設計を確定させる前に「この変更は、確定した設計にとって本当に必要か？」を一項目ずつ問い直す。
  - **後から見つけた別の利点（バグ修正など）を、その変更の理由に横滑りさせない**。時系列を偽らない。「やると決めた後に見つけた利点」は理由ではなく副産物であり、**単独で改めてスコープ判断にかける**（別チケットが筋なことが多い）。
  - 判定法: 「この変更を戻したら、要件は満たせなくなるか？」に **No** なら、それは要件由来ではない。スコープ外の可能性を疑い、ユーザーに諮る。
- 理由: 条件付き許可は「その条件が成立している世界」への許可であって、白紙委任ではない。前提が変わったのに結論だけ残すと、**誰も必要としていない変更が「承認済み」の顔をして混入する**。さらに後から見つけた利点を理由として語ると、本人にもレビュアーにも「要件由来の変更」に見えてしまい、スコープ逸脱が検出されなくなる（レビュアーもその正当化を受け入れてしまう）。ユーザーが本当に見たいのは「要件に必要な最小の差分」であり、ついでの改善は別途判断したい。
- 具体例: u1-web GN-5857（SPアシストCSVの推奨金額自動反映）。「推奨値フォールバックをスキーマ内に入れるか変換段階に入れるかで個別編集画面への影響が変わる」と論点提起し、**スキーマに入れる前提**で「共有スキーマは可読性が落ちるなら usecase 毎に分けて良い」という条件付き許可を得た。その後フォールバックを `csvToFormData` 側に置く設計に決めた時点で**懸念は消滅していた**が、許可だけ持ち越して共通スキーマの分割を実行。さらに分割**後**に知った `z.union` のエラーメッセージ不備（`Invalid input` が出る既存バグ）を分割の理由として説明した。ユーザーの「今回 form の内容は変更されない気がするが、変更理由はバグ修正か？要件か？」で発覚。元スキーマを復元したプローブで**要件は3ケースとも変更なしで通る**ことを実証し、スキーマ関連を全 revert（9 files→7 files、個別編集画面は差分から完全に消えた）。既存バグは別チケットへ。
- 関連: 「着手前に現状の仕様・既存実装をコードで裏取りする」（L127。前提の正しさを問う点で同根）。「設計・実装は多角的な視点で考える」（L185。方針転換時に結論を再検討しない＝アンカー）。「実装とは制約を付けること」（L176）。

## データ層の定数を UI の装飾文言に流用しない。表示専用の文字列は UI 側にベタ書きする
- タグ: universal, react, 関心: 命名, 関心: 可読性, 関心: レイヤ境界
- 対象/場面: 画面に補助文言・注記・バッジ等の**表示専用の文字列**を出すとき、たまたま同じ語のデータ層の定数（CSVの列名・API のフィールドラベル・DB のカラム名等）が既にある場面。「定数を参照すれば定義元が変わっても追従して乖離しない」という DRY の誘惑が生じる。
- 判断:
  - **表示専用の文字列は、その UI の場所にベタ書きする。** データ層の定数を流用しない。
  - 判定法: その文字列は**データとして保存・送信・出力されるか？** されないなら UI 専用であり、データ層の定数とは**別物**。字面が同じでも同一概念ではない。
  - DRY の適用単位は「字面」ではなく「概念」。同じ語でも、片方が「CSVの列名」・片方が「画面の注記」なら、**独立に変わってよい**（むしろ独立に変われるべき）。追従してしまう方が害。
  - 例外は、その文字列が**本当に同一概念の単一の出所**である場合（例: 同じフォームのラベルとバリデーションメッセージが同じ項目名を指す）。
- 理由: データ層の定数を UI の装飾に流用すると、読み手にとって **「これはデータに入る値なのか、画面だけの飾りなのか」の境界が消える**。コードを読んだ人が「CSVの列名を使っている＝CSVに出力されるのでは」と誤読する。実害は誤読だけに留まらず、レビュー時に「この文言はデータに混入しないか」を毎回追跡させるコストを生む。定数参照が防ぐ「乖離」は、そもそも独立に変わってよい2つの文字列の間には存在しない問題であり、**存在しないリスクを回避するために可読性を売っている**。
- 具体例: u1-web GN-5857。CSVプレビューで推奨金額が自動反映されたセルに `500（推奨金額）` と注記を出す実装で、注記の文言を `SP_ASSIST_CSV_COLUMNS.recommendedAssistPrice`（CSVの列名定数）で組み立てた。「列名を変えれば注記も追従し二度と乖離しない」という理由だったが、ユーザーから **「僕は列名とは認識できず、CSVの値と勘違いした」「普通に定数参照するのではなく、そのまま『推奨金額』とハードコードして良い。UI 部分だし」** と指摘され、ベタ書きに修正。実際にはこの注記は JSX の1箇所だけで作られており CSV にも API リクエストにも混入しないが、**コードからその事実が読み取れなくなっていた**（ユーザーが「CSVにも文言が入るのか？」と確認する必要が生じた時点で失敗）。
- 関連: 「ユーザー可視文字列を造語しない・実在慣習に照合する」（L162。可視文字列の"内容"の話。本エントリは可視文字列の"出所"の話）。「実装とは制約を付けること」（L176。表示専用と明示するのも制約）。「共有ヘルパの名前は用途スコープを名前に込める」（L221。名前で適用範囲を伝える点で同根）。

## データ取得の移行では「取得の実現方式」ごとに変わる挙動（ローディング／エラーの見え方・状態の保持スコープ）をコードで裏取りする
- タグ: universal, react, tanstack-query, 関心: 挙動保存, 関心: 移行, 関心: 裏取り
- 対象/場面: 旧データ取得（`useResource` 等）を Orval/TanStack Query の `useQuery` に移す移行。同種の先行タスクを参照実装として踏襲する場面。
- 判断:
  - **「現状こう見えているはず」を憶測で書かない。実現方式をコードで確認してから設計に落とす。** 特に次の2軸は移行で暗黙に変わりやすい:
    - **ローディング/エラーの見え方**: `useResource` は未取得時に Promise/例外を throw する Suspense 方式で、上位の `<Suspense fallback>` がスピナーを出す。非 Suspense の `useQuery` は throw せず `data=undefined` を返すため、**何もしないと空表示のちらつき**になる。`isPending` を明示的にローディング UI へ接続して初めて現行の見え方が保てる。
    - **状態の保持スコープ**: module-scope の Jotai `atom` はアプリ生存中値が残り、**画面離脱→再訪で保持**される。`useState` はアンマウントで**リセット**。「単一コンポーネントに集約されたから useState でよい」と機械的に倒すと、cross-navigation 保持という既存挙動を黙って壊す。
  - 参照実装踏襲時は、対象固有の「保持要否」「Suspense か否か」を差分で洗い出す。字面が似ていても挙動が同じとは限らない。
- 理由: データ取得の移行はロジックだけでなく**見え方と状態寿命**を静かに変える。テストや typecheck は通っても、スピナーが消える・フィルタが再訪で飛ぶといった退行は動かして初めて分かる。裏取りせず「現行維持」と書くと、その一文が誤った実装ガイドになり退行を承認済みの顔で通す。
- 具体例: u1-web GN-5883（operation-logs の TanStack Query 対応）。タスク定義書に「現行は取得中に空テーブルが一瞬見える／現行挙動を維持」と憶測で書いたが、design-review の裏取りで **現行は `useResource` の throw → `MainContentLayout` の `<Suspense fallback={<LoadingBox/>}>` でスピナー表示**と判明（前提が事実と逆）。`isPending` を `MainContentLayout isLoading` へ接続する方針に是正。さらに日付範囲を `useState` に倒しかけたが、元は **module-scope atom で画面再訪時も保持**される挙動と分かり、atom 温存へ（正当化文も「content が読むから」→「cross-navigation 保持のため」に訂正）。
- 関連: 「着手前に現状の仕様・既存実装をコードで裏取りする」（同根）。「前提が変わったら結論も失効させる」（L250。構造変更後に正当化文が失効した点）。「参照実装踏襲時に対象固有のガード脱落を差分で洗い出す」。

## submit 移行では「成功トーストの発火点」と「mutation 後の命令的後処理」の分離を意識する（成功トースト先行＋沈黙失敗の罠）
- タグ: universal, react, tanstack-query, 関心: 挙動保存, 関心: 移行, 関心: エラーハンドリング
- 対象/場面: 旧送信（`useSubmitting` の `submitPromises([{ promise }])` 等）を Orval/TanStack Query の `useXxxMutation` + `MutationCache`（`meta.subject` でトースト集約）へ移す移行。特に mutation 成功後に「別 API の再取得で共有 atom/state を更新する」といった**後処理**が付随する場面。
- 判断:
  - **成功トーストの発火点が移行で前にずれる**ことを把握する。`useSubmitting` は `promise` 全体（patch + 後処理）が resolve して初めて成功トーストを出す＝**patch と後処理が1つの成功単位**。一方 `MutationCache.onSuccess` は **patch（mutation）成功時点で即発火**し、`mutateAsync` の外に置いた後処理とは切り離される。
  - この分離により、**patch 成功→後処理（再取得等）失敗**の経路で挙動が反転しうる: ①成功トースト表示済み ②後処理の例外が `await submit()` まで unhandled で伝播（view に try/catch なし）③mutation 自体は成功のため error トーストは出ない ④後処理が担う状態更新（atom 等）は未達。つまり **「成功通知＋沈黙の失敗」**。
  - 対処の選択肢を明示的に俎上に載せる: (a) 後処理を mutation の成功単位に載せ直せるか検証、(b) 後処理をやめて mutation の入力値で楽観更新（第2の呼び出し自体を消す）、(c) 稀ケースとして**既知の許容差分**と文書化し "behavior-preserving" の文言を成功経路に限定する。いずれにせよ**失敗経路を設計に書く**（黙って参照実装を踏襲しない）。
  - 参照実装の後処理が `router.history.back()` のような fallible でない処理だと、この罠は顕在化しない。**後処理が失敗しうる I/O（再取得 GET 等）かどうか**を差分で見る。
- 理由: 送信移行はトーストをロジックから `MutationCache` へ剥がすため、**「いつ成功と告げるか」の時点がロジックの完了時点から mutation 完了時点へ移動する**。この時間差に後処理を挟むと、成功を告げた後に静かに失敗する窓が生まれる。テスト・typecheck は通り、成功パスの手動確認でも見えない。設計文書が「behavior-preserving」と書いていると、この反転がレビューをすり抜ける。
- 具体例: u1-web sales-reports.settings の TanStack Query 対応。3 mutation が現行 `useSubmitting` で `patch → getArcade 再取得 → setArcade(currentArcadeState) → onClose` を1成功単位で実行。`usePatchArcade` + `MutationCache` へ移すと成功トーストが patch 直後に発火し、後続 `getArcade`（mutateAsync 外）が失敗すると「成功トースト＋error トースト無し＋atom 未更新」に反転。design-review が major として指摘。発生条件（patch 直後の GET のみ失敗）が稀かつ本移行群に共通する構造差分のため、選択肢(c)＝既知の許容差分として文書化し "behavior-preserving" を成功経路に限定する方針を採用。
- 関連: 「データ取得の移行では実現方式ごとに変わる挙動を裏取りする」（L263。GET 側の対。本エントリは mutation/トースト側）。「実装とは制約を付けること」（L176。失敗経路を書くのも制約）。「前提が変わったら結論も失効させる」（L250）。

## テストは「検出したい性質を実際に検出できるか」を実測で裏取りする（比較器のセマンティクスで検証力がゼロになる）
- タグ: universal, go, 関心: テスト, 関心: 裏取り
- 対象/場面: 期待値と実測値を汎用比較器（`cmp.Diff` / `assert.Equal` / `reflect.DeepEqual` / `toEqual`）で突き合わせるテストを設計するとき。とくに**タイムゾーン・数値精度・内部表現**など「型としては等価だが表現が違う」性質を検証したいとき。
- 判断:
  - 「期待値をこう書く」で終わらせない。**実装から当該変換を一時的に外し、そのテストが FAIL することを実測する**。落ちないなら、そのテストは何も検証していない。
  - 落ちない場合は比較器を変える。**シリアライズ結果（`Format(time.RFC3339)` / JSON 文字列）で比較する**、あるいは `cmpopts` で比較器を明示する。
  - `Equal` メソッドを持つ型（`time.Time`、`decimal.Decimal` 等）は、go-cmp / testify がその型の等価規則へ委譲する。`time.Time.Equal` は**絶対時刻のみを見て `Location` を無視する**ため、tz 変換の正しさは値比較では原理的に検証できない。
  - **期待値を実装と同じ関数で組み立ててよいのは、その関数が検証対象でないときだけ**。検証対象そのものを期待値側でも呼ぶと、実装が変われば期待値も一緒に動くのでトートロジーになる。検証対象でないなら既存流儀に従って再利用してよい（一律禁止ではない）。
  - 値比較のテストを残す場合は、**「ここでは値の伝播のみを見る。表現の正しさは○○のテストで担保する」とコメントで役割を明示**する。役割不明のまま置くと「検証している」という誤ったシグナルになる。
- 理由: 既存の「テストの骨抜き禁止」は `gomock.Any()` のような**書き方**の問題を扱うが、本件は書き方が正しくても**比較器の意味論により検出力がゼロ**になるという別の失敗様式。設計文書に「テストで担保する」と書かれると、レビューでも実装でもそれ以上検証されず、退行が承認済みの顔で通る。
- 具体例: u1-api GN-5899。`updatedAt` に `t.In(JST)` 相当の変換を入れる設計で、usecase テストの期待値を同じ変換関数で包んだ。しかしこの変換は絶対時刻を保つため `cmp.Diff` では無変換実装と区別できず、**実装から変換を外しても PASS した**（実測確認済み）。皮肉にも「不採用にした誤った案（`ToTokyoTime` 単体＝絶対時刻が9時間ずれる）」だけが検出可能だった。`entities` 側に `Format(time.RFC3339)` の文字列で比較するテストを追加して初めて 3 ケースとも FAIL するようになった。
- 関連: 「テストの骨抜き禁止」（書き方の問題。本エントリは比較器の意味論の問題）。

## 「全数調査」の判定基準は、アプリコード外の書き込み経路も対象に含める
- タグ: universal, 関心: 裏取り, 関心: コード分析
- 対象/場面: 「この列に時刻が入るか」「この値はどこで書かれるか」といった**書き込み経路の全数調査**を行い、その結果を根拠に修正範囲を確定するとき。
- 判断:
  - 判定基準をアプリコードの代入だけに置かない。**スキーマのデフォルト値・`ON UPDATE` 句・トリガ・外部システムからの直接投入**も書き込み経路である。
  - 調査結果を書くときは「**どの経路を見たか**」を明記する。見ていない経路があるなら「見ていない」と書く。網羅したように書いて実は片側しか見ていない、が最も危険。
- 理由: 「`clock.GetCurrentDateTime()` で保存＝時刻あり／`GetToday()` で保存＝00:00:00」のような基準はアプリコード上は完全に見えるが、`DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` はコード上に代入が現れないまま**時刻付きの値**を生む。基準の穴は「調査済み」というラベルの下に隠れるため、後から誰も再検証しない。
- 具体例: u1-api GN-5899。時刻付きカラムの変換漏れを全数調査した際、判定基準を Go コードの代入のみに置いた。結果的に該当列はすべて明示代入されており漏れは無かったが、基準としては DB 側の書き込み経路を取りこぼしていた（design-review が指摘）。

## 慣習を踏襲する前に「その慣習が成立している条件」を特定する。条件を満たさない新ケースに機械的に広げない
- タグ: universal, 関心: 規約, 関心: 裏取り, 関心: 移行
- 対象/場面: 既存コードの慣習（データ表現・命名・変換方法）に合わせて新しいフィールドや処理を追加するとき。とくに「他がこうしているから同じにする」で決めそうになったとき。
- 判断:
  - 慣習が**なぜ壊れずに回っているのか**を特定する。多くの慣習は明示されていない前提条件の上に成立しており、条件を満たさないケースに広げると静かに壊れる。
  - 条件を特定したら、**新しいケースがその条件を満たすか**を照合する。満たさないなら慣習から外れるのが正しく、外れることを設計判断として明記する。
  - 判明した成立条件は**コード外の文書だけに書かない**。API 契約・型・関数名など、次の実装者が必ず見る場所に残す。
- 理由: 「既存に合わせた」は一見安全な判断に見えるが、成立条件を確認していない踏襲は**条件が崩れる最初のケースで破綻する**。しかも既存と同じ書き方をしているため、レビューでも「既存踏襲」として見過ごされる。
- 具体例: u1-api GN-5899。この API は日時をすべて「JST の壁時計を UTC ラベル（`...Z`）で返す」慣習だった。フロント（u1-web）は `dayjs(str).format()` で**絶対時刻として解釈**するため、この慣習は**時刻部が常に `00:00:00` だから**成立していた（`T00:00:00Z` は +9h しても同じ日付）。時刻を含む値を同じ形式で返していた 2 箇所（`MaterialInventoryHistory.executedAt` / `Notice.uploadedAt`）は実際に 9 時間ずれ、前者は「実査日が JST 15:00 以降で翌日表示」という実バグになっていた。新規の `updatedAt` は慣習に合わせず `+09:00` 付きの絶対時刻で返す判断とし、成立条件（日付フィールドは時刻部 00:00:00）を OpenAPI の description に明記して契約側に残した。
- 関連: 「着手前に現状の仕様・既存実装をコードで裏取りする」（同根）。「実装とは制約を付けること」（表現の違いを description で制約する点）。

## 上流タスクが「下流側の設計事項」として明示的に委譲した論点は、下流のタスク定義書に引き継ぐ
- タグ: universal, 関心: 裏取り, 関心: 設計, 関心: タスク定義
- 対象/場面: 別リポジトリ・別チケットの成果物（新設 API フィールド、新スキーマ、新イベント）を消費する実装タスクを設計するとき。
- 判断:
  - 上流タスクの定義書・PR 説明の「懸念点」「受け入れたリスク」「○○側の設計事項」を**必ず読み、下流の前提節へ転記する**。上流が明示的に委譲した論点は、下流で誰も拾わなければ**どこにも所有者がいないまま実装される**。
  - 転記時は「上流 doc の何行目」まで残す。要約だけだと、次に読む人が原典に戻れない。
  - 委譲された論点のうちユーザーの合意が要るもの（挙動の許容範囲・受け入れるリスク）は、**確認事項に上げて承認を取る**。設計者が黙って一方に倒さない。
- 理由: 型・シグネチャの裏取りは「確認済み」というラベルが付きやすいが、**その値が何を意味するか（いつ・何をきっかけに変わるか）**は型に現れない。型だけ確認して「前提（確認済み）」と書くと、意味論の未確認が確認済みの顔で通る。
- 具体例: u1-web GN-5900（着荷予定景品に「24時間以内なら更新バッジ」）。当初のタスク定義書は `PrizeDelivery.updatedAt` の型・required・行番号だけを裏取りして「確認済み」としていた。実際には上流 u1-api GN-5899 が 4 点を委譲していた: (1) 更新は日次バッチ（JST 8:00）でしか起きず「24時間以内」は実質「直近のバッチ分」で 8:00 に対象集合が入れ替わる（上流 doc が明示的に「u1-web 側の設計事項」と記載）、(2) 画面に表示していない項目の変更でもバッジが点灯する、(3) リリース直後は `updated_at == created_at`、(4) 一括 UPDATE で全店舗が一斉点灯。design-review が blocker として指摘。
- 関連: 「着手前に現状の仕様・既存実装をコードで裏取りする」（本エントリは裏取り対象が「型」でなく「意味論」である点が違い）。「『全数調査』の判定基準は、アプリコード外の書き込み経路も対象に含める」。

## 多角的検討は「どう見せるか・どう書くか」でなく、機能の価値を決める判定条件から始める
- タグ: universal, 関心: 設計, 関心: 多角的視点
- 対象/場面: タスク定義書に「設計上の選択肢と判断」を書くとき。複数案を並べて比較したつもりになったとき。
- 判断:
  - 並べた論点が**表現・実装機構（表示スタイル / 関数の置き場所 / 使う部品）に偏っていないか**を確認する。それらは差し替えが容易で、間違えても後から直せる層。
  - **機能の価値を決めるのは「いつ発火するか・何を条件とするか」の判定ロジック**。ここが単一案のままなら、多角的検討はまだ始まっていない。
  - 条件が要件文言で与えられていても（例:「24時間以内」）、**実データの更新周期・粒度と噛み合っているか**を代替案と並べて検証する。要件変更が不要でも、その比較を通じて初めて「ユーザーに確認すべき副作用」が見える。
- 理由: 表現面の比較は書きやすく、選択肢を 3 つ並べれば「多角的に検討した」という体裁が整う。しかし後から最も高くつくのは判定条件の誤りであり、そこが 1 案のまま通ると設計レビューでも「検討済み」として素通りする。
- 具体例: u1-web GN-5900。当初の「多角的検討」は表示スタイル / 関数の置き場所 / バッジ部品の 3 論点で、すべて表現面だった。実データは日次バッチ（JST 8:00）でしか更新されないため、判定条件には「24時間以内」と「当日バッチ判定（＝更新日が本日か）」の 2 案があり、後者は 0:00〜8:00 に一切点灯しないという致命的な副作用を持つ。この比較をして初めて「8:00 境界で対象集合が入れ替わる」という承認すべき挙動が言語化できた。
- 関連: 「上流タスクが『下流側の設計事項』として明示的に委譲した論点は、下流のタスク定義書に引き継ぐ」（GN-5900 の同一レビューで併発）。

## 「その方式は実現不能」を代替案の却下理由にする前に、不能が設定・生成物由来でないか裏取りする
- タグ: universal, react, 関心: 多角的検討, 関心: 裏取り
- 対象/場面: 移行・方式選定の設計で、「ツールが X に対応していないから Y でいくしかない」と選択肢を1つに絞る場面。とくにコード生成ツール（Orval / protoc / codegen 系）の出力を見て「生成されていない＝生成できない」と結論するとき。
- 判断: **「生成物に無い」と「生成できない」を区別する。** 設定ファイル（`orval.config.ts` 等）とツールの対応状況を確認してから却下理由を書く。裏取りの結果 (a) 本当に不能なら「不能」と書く、(b) 可能だが採らないなら「**可能だが、〜の理由で採らない**」と天秤を明記する。**選択肢が「不能」で消えた設計は、多角的検討をした形跡が残らない**ため、後続の読者もその前提を疑わなくなる。
- 理由: 「不能」と「不採用」は意思決定として全く違う。不能なら議論の余地はないが、不採用は前提が変われば覆る（他所が同じ方式に移れば一貫性の理由が消える等）。誤って「不能」と記録すると、**その選択肢は二度と検討対象に戻らない**。しかも生成物由来の制約は設定1行で変わることが多く、誤判定のコストに対して確認コストが極端に低い。
- 具体例: u1-web GN-5901（logistics の TanStack Query 移行）。35本のタスク定義書が「Orval は Suspense 版 hook を生成していない」と書き、非 Suspense 方式を唯一の選択肢として設計していた。design-review が「orval 8.22.0 は `override.query.useSuspenseQuery` に対応しており、`orval.config.ts` にその設定が無いだけ」と指摘。移行コストの大半（Suspense 消失に起因する罠A〜C・構造の持ち上げ）はこの単一前提から派生していた。結論自体は非 Suspense のままで妥当（先行移行が全て非 Suspense のため一貫性を優先）だが、**天秤にかけた記録が無いことが問題**だった。
- 関連: 「設計・実装は多角的な視点で考える」（L185。1案しか出ていない設計）。「着手前に現状の仕様・既存実装をコードで裏取りする」（L127）。

## 並列作業の規約は、指示同士が実依存グラフ上で衝突しないか突き合わせてから配る
- タグ: universal, 関心: 構造, 関心: 一貫性, 関心: 並列実行
- 対象/場面: 複数エージェント／複数人が同一規約に従って並列作業する計画を書く場面。「担当範囲外を触るな」と「触ったディレクトリ内は全部揃えろ」のような、**単体では正しいが交差点で両立しない指示**を同じ文書に置くとき。
- 判断: 規約を配る前に、**指示同士の交差点を実依存グラフ（import / 参照関係）で洗う**。衝突が1件でもあれば、(a) 例外を名指しで明記する（「G8 のみ このファイルの追随修正を許可」）、(b) どちらかの指示の適用範囲を狭める、のどちらかで**曖昧さを残さない**。「常識で判断せよ」に委ねない。
- 理由: 並列実行者は衝突に気づいても**その場で黙って一方を選ぶ**（聞き返すコストが高く、どちらも規約に書いてあるため「破った」自覚も生じない）。選択は実行者ごとに割れ、結果は一貫性の欠如として後段でまとめて表面化する。しかも「規約に書いてある」ため、レビューでも検出されにくい。交差点は依存グラフを1回 grep すれば列挙できる。
- 具体例: u1-web GN-5901。規約に「触った `-components/` 内の PascalCase は全て kebab-case にリネーム」と「担当ディレクトリ外のファイルを変更しない」を併記し、リネーム例として `InventoryPrizePlacements.tsx` を挙げた。design-review が「まさにその例のファイルは `src/components/organisms/prizes/InventoryPrizePlacementsFilter.tsx` と**相互 import** しており、リネームすると担当外の修正が必須」と指摘（`src` 全体で routes→organisms の逆方向 import はこの1件のみ）。名指しの例外として規約に明記して解消した。
- 関連: 「同種の関数の置き場所は分散させず一箇所に統一する」（L193。並列時に判断が割れると一貫性が崩れる同根）。「上流タスクが下流側の設計事項として委譲した論点は下流の定義書に引き継ぐ」（L331）。

## 「使われていない」という否定的結論は、識別子検索だけで確定させない（文字列リテラル経由の参照が落ちる）
- タグ: universal, 関心: 裏取り, 関心: コード分析
- 対象/場面: 「このカラム／フィールドはビジネスロジックで使われていない」を根拠に、変更や削除を安全と判断するとき。
- 判断:
  - **否定的結論（＝存在しない）は、肯定的結論より高い証明コストがかかる**。1つの検索手段でヒットゼロだったことは、存在しないことの証明にならない。
  - 最低2系統で当たる: (a) **Go の識別子**（`CharterFlightDate`）、(b) **DB カラム名の文字列リテラル**（`"charter_flight_date"`）。ORM の scope・生 SQL・動的なカラム指定は識別子検索に一切かからない。
  - **検索ツールのフラグ誤用で出力が壊れていないかを疑う**。`rg -r` は replace であって recursive ではない。壊れた出力は「マッチが無い」ではなく「マッチが変な形で出る」ため、否定的結論と組み合わさると気づけない。ヒット行が意味不明なら、まず自分のコマンドを疑う。
  - 素通し（pass-through）だと結論した項目は、**他フィールドの導出元やフォールバックになっていないか**も併せて見る。「レスポンスに詰めるだけ」に見えて、隣の行で別フィールドの計算に使われていることがある。
- 理由: 「使われていない」は変更・削除の許可証として機能してしまい、いったんタスク定義書に「確認済み」として書かれると誰も再検証しない。しかも検出漏れは「その項目を触った後」にしか表面化しない。
- 具体例: u1-api 統合景品マスタ TOBE 対応。`charter_flight_date` を「ビジネスロジックでの利用ゼロ」と結論したが誤りだった。(1) `prize_delivery_service.go:54-57` は `scopes.ByDateRange(from, to, "charter_flight_date")` と**文字列リテラル**で DB 検索条件に使っており Go 識別子の検索にかからない、(2) `entities/oa.go:223-231` は `machineInputDate` の3番目のフォールバックで、`charterFlightDate` を OA に詰める行の**数行上**にあったのに読み飛ばした。直接の原因は最初の grep で `rg -rn "CharterFlightDate|..."` と `-r` を replace オプションとして誤用し、`"charter_flight_date"` が `"n"` に置換された出力をそのまま読んだこと。design-review が blocker として指摘。
- 関連: 「検索結果を head / limit で打ち切ったまま『全件確認した』と結論づけない」（L207。同じ否定的結論の early-stop）。「『全数調査』の判定基準は、アプリコード外の書き込み経路も対象に含める」（L311）。

## 「無変更で安全」の根拠が“未使用”なのか“他項目が必ず埋まるという業務側の約束”なのかを区別する
- タグ: universal, 関心: 裏取り, 関心: 設計, 関心: 移行
- 対象/場面: 外部システム（データ基盤・上流サービス）の出力形式が変わるとき、自システムの改修要否を判定する場面。「うちは値を解釈していないから無変更でいい」と結論しそうなとき。
- 判断:
  - 「無変更で安全」と書く前に、その安全性が **(a) その項目を一切参照していない** のか **(b) 参照はしているが、別項目が必ず埋まるので実害が出ない** のかを分ける。
  - **(b) は業務側の約束への依存であり、コードの性質ではない**。約束が破れた行が1件でも来れば壊れる。タスク定義書には「〜が守られる限り挙動は変わらない」と条件付きで書き、**約束が破れた場合に何が起きるか**（行が落ちる／NULL になる／例外になる）まで書く。
  - 段階移行・並行運用がある場合は、**旧ソース由来のデータが約束を満たしていない可能性**を確認事項に上げる。新形式が約束を守っていても、DB に残る旧データは守っていない。
  - 検知の必要性も設計事項に含める（例: 該当項目が全て NULL の行数をバッチでログ出力する）。
- 理由: (a) と (b) は結論（無変更）が同じなので、書き分けないと同じ強度の判断に見える。しかし (b) は**外部の運用が変われば無告知で壊れる**うえ、壊れ方が「エラー」でなく「一覧から静かに消える」形になりやすく、発覚が遅れる。
- 具体例: u1-api 統合景品マスタ TOBE 対応。「チャーター便日付が不要になる」に対し当初「nullable かつロジック未使用なので不要」と判定した。実際は `machineInputDate` のフォールバック（`specified_entry_date` → `on_location_release_date` → `charter_flight_date` → `arrive_at`）と着荷景品検索の OR 条件で使われており、無変更で済む根拠は「指定投入日 or オンロケ解禁日を必ず入れる」という**業務側の約束**だった。3つとも NULL の行が来ると着荷景品一覧から静かに落ちる。Access→Kintone の3〜4ヶ月並行期間中は旧ソース由来データが混在するため、なおさら条件付きの判定として書く必要があった。
- 関連: 「慣習を踏襲する前に『その慣習が成立している条件』を特定する」（L320。成立条件を明示する点で同根）。「前提が変わったら、その前提の上に得た許可・結論も失効させる」（L250）。

## レビュー指摘への訂正こそ、元の記述と同じ強度で裏取りする（訂正は「検証済み」の空気をまとう）
- タグ: universal, 関心: 裏取り, 関心: レビュー
- 対象/場面: 設計レビュー・コードレビューの指摘を受けて記述を書き直すとき。とくに「指摘のとおりでした、直します」と素早く応じる場面。
- 判断:
  - **訂正文に新しい事実主張（ファイル名・行番号・「〜は〜になっている」）を書くなら、それも一次情報で確認する。** 指摘を受けて動揺している状態は、記憶や推測で埋めやすい。
  - 指摘が「Xは誤り」であっても、**正しい代わりが何かはレビュアーも言っていない**ことが多い。指摘の否定部分だけを受け入れ、肯定部分（差し替える内容）は自分で調べる。
  - 訂正した箇所は**次のレビューで重点的に見てもらう**。訂正は「一度レビューを通った」ように見えて、実際には未レビューの新規記述である。
  - 「本リポジトリ外だから確認しない」のようなスコープによる免除も、**実際に確認可能かを先に確かめる**。隣のリポジトリがローカルに存在するなら、スコープ外であることと調査しないことは別。
- 理由: 訂正は「指摘に応じた」という文脈が付くため、読み手も書き手も検証を緩める。結果、1巡目の誤りを直す過程で2巡目の誤りが生まれ、しかもそれは「レビュー反映済み」というラベルの下に隠れる。
- 具体例: u1-api 統合景品マスタ TOBE 対応。1巡目レビューで「`CreatePrizes` は map 走査なので戻り値の順序が非決定。参考実装をそのまま真似ると flaky」と指摘され、訂正文に「参考実装 `importDatabricksSeamsItemStocks/exec_test.go` は戻り値が map なので順序問題が出ていない」と書いた。実際には同ファイルの `TestCalcLogicalStocks` は **slice 戻り値を対象に既に `cmpopts.SortSlices` を使っており**（`exec_test.go:216-219`）、倣うべき正しい手本だった。2巡目レビューが major として検出。同じ2巡目で「u1-web はリポジトリ外だから確認しない」も、u1-web がローカルに存在し 10 分で調査できることが判明した。
- 具体例2（**同一タスクで再発。1回の注意では直らない**）: 上記の訂正を反映した2巡目レビューで、今度は A-5（論理削除案）の説明に「gorm の soft delete に乗るのでクエリ改修が要らない」と書いた。実際にはこのリポジトリは **`gorm.DeletedAt` を一切使っておらず**（`rg "gorm.DeletedAt"` で 0 件、生成モデルは `sql.NullTime`）、論理削除は各 repo が手書きで `Where("deleted_at IS NULL")` を足す方式。しかもこれは**選択肢どうしの比較表**、つまりユーザーの意思決定材料そのものに誤りを混ぜたことになる。3巡目レビューが major として検出。
- **再発を踏まえた運用**: レビュー指摘に応じる編集は「訂正」ではなく**新規記述**として扱い、書いた直後に自分で一次情報に当てる。とくに **(a) 選択肢の比較表・天秤の材料**、**(b)「〜に乗るので〜が不要」型の主張**（フレームワーク/既存機構への依存を根拠にするもの）は、思い込みが入りやすいので必ず grep で確認する。
- 関連: 「『使われていない』という否定的結論は、識別子検索だけで確定させない」（同一タスクで併発）。「慣習を踏襲する前に『その慣習が成立している条件』を特定する」（L320。「gorm を使っているはず」という未検証の前提が同根）。「前提が変わったら、その前提の上に得た許可・結論も失効させる」（L250）。

## 検証手順を書くときは、その手順が使う経路・パラメータが実在するかをコードで確認する
- タグ: universal, 関心: 裏取り, 関心: 検証
- 対象/場面: タスク定義書・Runbook に「こう実行して確認する」という検証手順を書くとき。dry-run・ステージング投入・再現コマンドなど。
- 判断:
  - **手順に出てくるフラグ・パラメータ・パスは、実装側に存在するかを1件ずつ確認する。** 「片方のバッチにあるから、もう片方にもあるはず」は通らない。
  - パスやキーを引数に取る手順では、**それがローカルパスなのか外部ストレージのキーなのか**を実装で確かめる。名前（`csvPath` 等）は嘘をつく。
  - 手順が実行不能だと判明したら、**代替手段を書く**か「この経路は検証できない」と明記する。書けないことを書かないと、次の人が同じ壁に当たる。
  - 検証手段が無いこと自体が設計課題なら、**「検証用パラメータを追加するか」を判断事項として上げる**。
- 理由: 検証手順は「最後に書く付録」になりやすく、裏取りが最も緩む。しかもリスクの高い変更ほど検証手順に依存するため、そこが空手形だと**最も守りたい場面で守りが無い**。実行して初めて気づくが、実行するのは切替当日である。
- 具体例: u1-api 統合景品マスタ TOBE 対応。検証プロトコルに「新形式サンプルを dry-run で流す」手順を書いたが、(1) `csvPath` は S3 オブジェクトキー（`prod/` 配下）でありローカルパスではない、(2) **景品マスタ側の `importDatabricksPrizes` にはパス上書き手段が存在しない**（`exec.go:72-76` で S3 キーをハードコード、`params` から読むのは `dryRun` のみ）ため、書いた手順では ASIS ファイルを読むだけで新形式の検証にならなかった。本タスクの実質リスクを唯一検証する「必須」セクションが実行不能だった。
- 関連: 「テストは『検出したい性質を実際に検出できるか』を実測で裏取りする」（L298。検証力ゼロという同じ帰結）。

## 外部マスタの「形式変更」を評価するとき、属性値の変化と主キーの連続性を別次元として扱う
- タグ: universal, 関心: 移行, 関心: 設計, 関心: データ
- 対象/場面: 外部システム（データ基盤・基幹システム）が供給するマスタの形式が変わるとき、自システムへの影響を見積もる場面。
- 判断:
  - 影響を「どの項目の値がどう変わるか」で洗うと、**主キーそのものが変わる可能性が視野から落ちる**。属性値の変化とキーの連続性は必ず別項目として立てる。
  - キーが変わりうるなら、**FK 参照数・論理削除の発火条件・履歴テーブルへの波及**を数える。属性値の変化とは影響の桁が違う。
  - 洗い替え型の取込バッチは「ファイルに存在しないキー＝削除」を実装していることが多い。**採番体系の変更は、そのロジックにとって「全件削除＋全件新規」と区別がつかない**。
  - 上流が「過去データも全部移行する」と言っていても、それは**行の網羅性の話であってキーの同一性の保証ではない**。明示的に確認する。
- 理由: 形式変更という言葉が属性のフォーマットを連想させるため、キーの話が議題に上がらないまま設計が進む。しかも取込バッチは正常に動き、エラーも出さずにマスタを総入れ替えする。
- 具体例: u1-api 統合景品マスタ TOBE 対応（Access→Kintone）。変更点として挙がったのはサイズ区分表記・分類の追加・ハイフンの全半角で、いずれも u1-api が値を解釈しないため「コード変更ゼロで追従」と結論した。しかし `importDatabricksPrizes/exec.go:235-241` は新ファイルに無い `prize_cd` に `deleted_at` を立てる実装で、採番体系が変われば**既存マスタ全件が論理削除される**。`prizes.prize_cd` は 27 箇所の FK 参照先（`schema_prizes.sql` 20 / `schema_archives.sql` 6 / `schema_common_depended.sql` 1）。購買データ側では同種の懸念（`snowflake_key` の採番衝突）を確認事項に立てていたのに、マスタ側だけ落ちていた（2巡目レビューが major として検出）。
- 関連: 「『無変更で安全』の根拠が“未使用”なのか“他項目が必ず埋まるという業務側の約束”なのかを区別する」（同一タスク）。「『全数調査』の判定基準は、アプリコード外の書き込み経路も対象に含める」（L311）。

## キャッシュ層を移行するとき、「別キャッシュであること」に依存したロジックが壊れていないか確認する
- タグ: universal, 関心: 移行, 関心: データ, 関心: 裏取り
- 対象/場面: 呼び出し側がキーを自由に決められる自前キャッシュ（`useResource` の `resourceKey` 等）から、キーが自動正規化される仕組み（TanStack Query の `queryKey` は API パス＋params から生成）へ移行する場面。
- 判断:
  - **同一 API を複数箇所から取得し、かつ取得結果どうしを突き合わせている実装**を探す。差分表示・before/after 判定・「移動した数」のような計算がこれに当たる。
  - キーに**コンポーネント名などの人工的な接頭辞**が入っていたら、それは「意図的に分離した」というシグナル。コメントが無くても分離の意図を疑う。
  - キーが統合されると、片方の `refetch` がもう片方の観測値も更新する。**before と after が同一データ由来になり、差分が恒久的に 0 になる**。ローディングのゲート（`isFetching` 等）では防げない（過渡現象ではないため）。
  - 移行先が queryKey の上書きに対応しているかを**生成コードで確認する**。対応していれば旧の分離をそのまま保存できる。
- 理由: キャッシュキーは「性能・再取得のための実装詳細」と見なされやすく、**それが機能要件を支えていることが視野から落ちる**。統合しても型は通り、テストも通り、画面も描画されるため、差分が 0 になっていることに気づけない。
- 具体例: u1-web GN-5901 Phase 2（logistics 共有テンプレート）。`MaterialStockDetails.tsx:106` が `resourceKey` に `InventoryMaterialStockDetails:` という接頭辞を付けて子コンポーネントと分離しており、FIXME コメントで理由を明記していた。`ConfirmMenu` の「移動した数」（`MaterialMoveToMachine.tsx:697`）は親＝移動前 / 子＝`refetchForce` 後＝移動後の差分で成立していたため、Orval のデフォルト queryKey に任せると**恒久的に 0** になる。設計時は「一瞬 0 が見える過渡現象」と誤認し `isFetching` ゲートで対処するとしていた（design-review が blocker として検出）。
- 関連: 「『その方式は実現不能』を却下理由にする前に、不能が設定・生成物由来でないか裏取りする」（同一タスクで再発。「queryKey を分けることは Orval では不可能」と書いたが、生成コードは `queryOptions?.queryKey ?? …` で上書きに対応しており、リポジトリ内に使用実績が2件あった）。

## `<Suspense>` の担当範囲は、JSX 上の位置ではなく「suspend するフックがどのコンポーネントで呼ばれているか」で決まる
- タグ: react, 関心: 移行, 関心: 裏取り
- 対象/場面: Suspense 方式のデータ取得から非 Suspense（`useQuery` 等）へ移行し、`<Suspense>` を撤去して条件描画に置き換える場面。
- 判断:
  - **`<Suspense>` は、それを返しているコンポーネント自身の suspend を捕捉しない。** React は suspend したコンポーネントより**上位**の最も近い boundary で捕捉する。
  - したがって「この `<Suspense>` が内包しているクエリ」を JSX の入れ子だけで判定してはいけない。**取得フックがどのコンポーネント本体で呼ばれているか**を1件ずつ確認する。
  - 自コンポーネントで取得している場合、実際に出ているのは**上位（レイアウト等）の fallback** であり、見え方は「ローカルのスピナー」ではなく「見出しごとコンテンツ全体の差し替え」になる。撤去後の再現方法がまるごと変わる。
- 理由: 「`<Suspense>` の中に書いてあるものが対象」という直感が強く、しかも JSX を読むだけだと正しく見えてしまう。誤ると「現行に存在しない見え方」を再現しようとして、ローディング表示の互換性要件を静かに破る。
- 具体例: u1-web GN-5901 Phase 2。`MaterialMoveToMachine.tsx:128` の `<Suspense fallback={<CircularProgress/>}>` が同ファイル `:93` の取得を内包していると誤認したが、`:93` は `<Suspense>` を返す当のコンポーネント本体にあり、捕捉していたのは `MainContentLayout.tsx:76` の `<Suspense fallback={<LoadingBox/>}>` だった。現行の遷移時は見出しごと全面が `LoadingBox` に差し替わっており、設計書が書いた「見出しは残して内側だけスピナー」は現行に存在しない挙動だった（design-review が blocker として検出）。同じタスクの Prize 系6箇所は取得が子コンポーネントにあり、こちらは JSX どおりの対応で正しかった。**同じファイル群でも箇所ごとに違う**。
- 関連: 「データ取得の移行では『取得の実現方式』ごとに変わる挙動をコードで裏取りする」（L274 の具体系）。

## キャッシュ寿命が変わると、「マウント時に一度だけ確定する値」が古くなる
- タグ: react, 関心: 移行, 関心: データ
- 対象/場面: アンマウント時にキャッシュを破棄する取得層から、`gcTime` 等でキャッシュを保持する層（TanStack Query 等）へ移行する場面。とくにモーダル・ウィザードのように**開閉を繰り返すコンポーネント**。
- 判断:
  - 移行対象に `useForm({ defaultValues, resolver })` / `useState(初期値)` / `useMemo(..., [])` のような**マウント時に一度だけ確定する値**があるか探す。その入力が移行後にキャッシュ由来になりうるなら要注意。
  - 旧実装がアンマウント時にキャッシュを捨てていた場合、**「開くたびに必ず最新」が暗黙の前提**になっている。移行後は2回目以降キャッシュヒットし、`isPending=false` で即マウントされて**古い値が凍結する**。
  - ゲートに **`isPending` ではなく `isFetching` を使う**（あるいは `reset()` で追随させる）。`isPending` は「キャッシュが無い」しか見ないため、再取得中を素通りする。
  - react-hook-form では `resolver` は毎レンダー更新されるが **`defaultValues` は追随しない**（`reset` 時のみ）。「resolver が追随するから大丈夫」は成り立たない。
- 理由: 初回だけ動作確認すると必ず通る。2回目以降にしか出ず、しかも「古い値が入っている」だけでエラーにならないため、レビューでもテストでも捕まりにくい。
- 具体例: u1-web GN-5901 Phase 2。移動モーダルのゲートを `isPending` にすると、同一画面で閉じて開き直したときキャッシュヒットして移動前スナップショットのまま `MoveToBoothModalForm` がマウントされ、`defaultValues: { stock: ... }` と `zodResolver(createValidationSchema(placementMoveFrom.stock))`（`PrizeMoveToBooth.tsx:306-309`）が旧在庫で固定される。入力欄が実在庫より大きい値でプリフィルされ、保存すると「移動前の在庫数を越えています」で弾かれる。旧 `useResource` は `useCache=false` でアンマウント時に `resourceMap.delete(key)` していた（`useResource.ts:57-68`）ため開くたびゼロから取得していた（design-review 2巡目が blocker として検出）。
- 関連: 「キャッシュ層を移行するとき、『別キャッシュであること』に依存したロジックが壊れていないか確認する」（キーの話。本項は**寿命**の話で別軸）。「`<Suspense>` の担当範囲は…」（同一タスクで併発）。

## CI/CD の検証手順を前提にするときは、composite action / 再利用 workflow の入力デフォルト値まで辿る
- タグ: universal, 関心: 裏取り, 関心: CI/CD, 関心: 検証手順
- 対象/場面: 「このブランチのコードを CI から手動実行して事前検証できる」のような**運用手順を設計の前提に置く**とき。とくに `workflow_dispatch` + `uses: ./.github/actions/*` の組み合わせ。
- 判断:
  - **「呼び出し元に指定が無い ⇒ 呼び出し元のコンテキストが使われる」は composite action では成立しない。** 呼び出し先が同じ入力を持ち、**デフォルト値で上書きしてくる**ことがある。
  - `uses: ./.github/actions/*` / `uses: ./.github/workflows/*.yml` を含む workflow の挙動を前提にするなら、必ず**呼び出し先の定義を開き**、`inputs.*.default` と「呼び出し元が渡していない入力の一覧」を突き合わせる。
  - とくに `actions/checkout` の `ref` / `path` / `clean` は**後段の全ステップの入力を丸ごと差し替える**ので最優先で確認する（`clean` 既定 true = 前の checkout の成果物が消える）。
  - 同種の workflow が複数あるなら**横並びで diff を取る**。片方だけ入力を渡していない＝どちらかが意図的な差か抜けかのシグナル。
- 理由: 検証手順は「動くこと」を確認しないまま設計書に書かれがちで、しかもそれが**唯一のリスク統制**になっていることがある。手順が実行不能だと、リスク統制ゼロで本番投入する計画が「検証済み」の顔で承認される。
- 具体例: u1-api GN-5859。`stg_batch_manual.yml:39` の `actions/checkout@v3` に `ref` 指定が無いことは正しく読めていたが、直後に呼ぶ `.github/actions/batch/action.yml:60-62` が `ref: ${{ inputs.branch }}`（default `"development"`）で**同じ workspace に再 checkout**しており、feature ブランチから dispatch しても `development` のコードがビルドされる、が事実だった。`prod_batch_manual.yml:45` は `branch: main` を明示的に渡しており、横並び diff を取れば気づけた。「feature ブランチのまま dry-run 検証できる」という前提が崩れ、それを根拠にした切替方式（案A）の推奨理由まで失効した（design-review が blocker として検出）。
- 関連: 「検証手順を書くときは、その手順が使う経路・パラメータが実在するかをコードで確認する」の特殊化。「前提が変わったら、その前提の上に得た許可・結論も失効させる」。

## 外部マスタ差し替えでは「値が一致する」検証と「ドメイン判定の入力として成立する」検証を別次元にする
- タグ: universal, 関心: データ, 関心: 移行, 関心: 裏取り
- 対象/場面: 外部マスタ・連携ファイルの供給元を切り替え、同じ DB カラムに別ソースの項目をマッピングする場面。
- 判断:
  - サンプル数件の**項目突合（値が一致した）は属性の検証**であって、**判定の検証ではない**。その項目がドメイン判定関数（`IsXxx()` 等）の入力になっているなら、判定ごとに検証を分ける。
  - 判定関数ごとに **AS-IS の該当件数を実データから出し、TO-BE で同数になることを受入基準にする**。単一サンプルは母集団のマーカー保持率を一切保証しない。
  - 判定の**壊れ方の脆さを区別する**: `HasPrefix` は先頭に1文字入るだけで全滅（脆い）／`Contains` は位置に依存しない（頑健）。脆い側を優先して受入基準に入れる。
  - 判定の**用途の重さを区別する**: 表示フラグなのか、バリデーションゲートなのか、金額集計の分岐なのか。重い用途は「たぶん保持される」で通してはいけない。
  - マッピングにフォールバック（`A` が空なら `B`）を入れたなら、**主たる入力は `A`** である。「`B` は◯◯由来だから安全」という説明は、実際に使われるフィールドを説明していない。
- 理由: 供給元の切り替えは「カラムの対応表」として捉えられやすく、対応表が埋まると検証が終わった気になる。しかし文字列カラムは**書式・マーカー・前置文字**という別次元の契約を持っており、そこはロジックが依存していても対応表には現れない。
- 具体例: u1-api GN-5859。`prizes.name` の突合を1件（`K0C301792`）で済ませたが、`name` は `IsKidsMarket()`（`【KM】`/`【ＫＭ】` を Contains・AS-IS 2,212件・**移動と棚設定のバリデーションゲート**）と `IsKuroMaru()`（`●` を HasPrefix・AS-IS 29,119件・**黒丸消費金額の集計分岐**）の唯一の入力だった。しかも AS-IS には `【KM】●ＳＤビッグかつ` のように「`●` を含むが前置しない」名前が多数あり、`HasPrefix` の脆さが顕在化する形だった。さらにマッピングは `name ← seams_item_name`（空なら `item_name`）なのに、安全性の根拠として書いていたのは `item_name` の性質だった（design-review が major として検出）。
- 関連: 「外部マスタの『形式変更』を評価するとき、属性値の変化と主キーの連続性を別次元として扱う」の姉妹則（本項は**文字列の書式・マーカー**の次元）。

## 「無変更で確認済み」リストは、同じ役割を果たす設定資産を全部列挙する。権威はドキュメントで先に確認する
- タグ: universal, 関心: 調査, 関心: 設定, 関心: 裏取り
- 対象/場面: タスク定義書に「変更しないもの（確認済み）」を書くとき。とくにバッチのスケジュール・デプロイ・スキーマのような**設定ファイルが権威**の領域。
- 判断:
  - 対象識別子（バッチ名・ジョブ名等）を **`.github/` だけでなくリポジトリ全体に grep** し、ヒットした全ファイルを列挙するか除外理由を書く。
  - `docs/` に運用ドキュメントがある領域は、**コードより先にドキュメントで「今の権威はどこか」を確認する**。
  - ドキュメントが「以前は X、今は Y」と書いている領域では、**X のファイルがまだ残っていることが多い**。実ファイルの存在だけでは権威を判定できない。古い方を権威として引用すると、その上に載る工程表・反映契機の記述が丸ごとずれる。
  - 設定の**反映が自動か手動か**も確認する（マージで自動適用されるのか、別途 workflow の手動実行が必要か）。ここは切戻しコストの見積りに直接効く。
- 理由: 「変更しない」と書いた瞬間にその項目はレビューの視野から外れる。列挙漏れは「調べた上で対象外」と「見ていない」の区別がつかず、しかも漏れていること自体が指摘されにくい。
- 具体例: u1-api GN-5859。定時実行の権威として `.github/workflows/*_batch_scheduled_master.yml` を引用したが、`docs/Batch.md:5-13` に「以前は GitHub Actions の scheduled workflow で実行していたが ECS Scheduled Tasks (ecschedule) に移行した」と明記があり、実際の権威は `deployments/ecs/{env}/ecschedule.yaml:52-58` だった。無変更リストからこれが丸ごと漏れていた。さらに `docs/Batch.md:17` の「ecschedule の設定変更は自動では反映されない（main マージ + workflow 手動実行が必要）」を見落としていたため、切替方式 B/C の切戻しコストを実際より安く見積もっていた（design-review が major として検出）。
- 関連: 「『全数調査』の判定基準は、アプリコード外の書き込み経路も対象に含める」の設定ファイル版。

## 「先例あり」と言う前に、その先例が同じ機構・同じ呼び出し形かを確かめる
- タグ: universal, 関心: 裏取り, 関心: 設計
- 対象/場面: 設計判断の根拠として「リポジトリ内に先例がある」と書くとき。とくに「不可能だと思っていたが可能だった」という訂正の直後。
- 判断:
  - 引用した先例は、**いま採ろうとしているのと同じ API・同じ呼び出し形**か。別の呼び出し形なら、それは先例ではない。
  - **「機構が存在する」と「その機構を使った実績がある」は別**。前者だけなら「本リポジトリ初出のパターン」と書く。
  - 引用先が**規約で禁じている書き方**をしていないか確認する。禁止パターンを先例として引くと、逆方向に倣うことになる。
  - 「先例あり」と「初出」は意思決定の重みが違う。初出なら、横断一貫性のために**規約へ条件を1項追加する**ところまでを設計に含める。
- 理由: 「不可能」と一度書いた負い目から、訂正時に「可能であるうえに実績もある」と過剰に補強したくなる。grep のヒット件数だけ見て中身の呼び出し形を確認しないと成立してしまう。
- 具体例: u1-web GN-5901 Phase 2。「Orval hook の `queryKey` は上書きできない」→ 指摘を受けて「上書き可能・リポジトリ内に先例2件」と訂正したが、その2件（`prize/meter-reads/-components/prize-meter-reads.tsx:232` / `inventory/execute.material-cylinder.meter-reads.$materialCylinderId/-components/usecase.ts:24`）はいずれも **`useSuspenseQuery` / `useQuery` の直呼び＋手書き `queryFn`** で、Orval hook の上書きではなかった。しかも共通規約が「`useQuery` を直接呼ばない」と禁じている書き方だった。Orval hook の queryKey 上書きは**リポジトリ内 0 件＝当該タスクが初出**（3巡目レビューが major として検出）。
- 関連: 「『その方式は実現不能』を却下理由にする前に、不能が設定・生成物由来でないか裏取りする」（本項はその**訂正側**で起きる失敗）。「レビュー指摘への訂正こそ、元の記述と同じ強度で裏取りする」。

## 完了ゲートの探索範囲に、そのタスクで新規に作るファイルが入っているか確認する
- タグ: universal, 関心: 検証
- 対象/場面: タスク定義書に「`grep` して 0 件なら完了」のような残存確認ゲートを書くとき。
- 判断:
  - **変更対象ファイル一覧の「追加」行が、検証コマンドの探索範囲に全て含まれているか**を突き合わせる。新規ファイルは既存の探索パスの外に置かれることが多い。
  - パスが実在するかだけでなく、**検証したい対象がそのパスの内側にあるか**を確認する。`grep -r A B` は A と B しか見ない。`-r` を付けても列挙していないディレクトリは探索されない。
  - 「このファイルは対象外」と除外理由を書くときは、**そもそも探索範囲に入っているのか**を確かめる。入っていないものを「除外する」と書くと、読み手は範囲を誤解する。
- 理由: 完了ゲートは最後に書くため裏取りが緩む。しかも「0件でした」という報告は成功に見えるので、範囲が狭いことに誰も気づかない。テストが無いタスクほどこのゲートが唯一の防御になる。
- 具体例: u1-web GN-5901 Phase 2。残存 grep の対象が `src/components/templates/Material*` の3ファイルのみで、**本タスクで新設する `src/hooks/useMaterial*.ts` 3本と呼び出し側4ルートの `usecase.ts` が探索範囲外**だった。さらに「`src/hooks/useDeleteMaterialOperationStocks.ts` は必ずヒットするので対象に含めない」という但し書きも誤りで、そのパスはそもそも探索範囲に入っていなかった（3巡目レビューが major として検出）。定義書自身が「テスト0件 → 差分の目視レビューが実質唯一の防御」と書いていた。
- 関連: 「検証手順を書くときは、その手順が使う経路・パラメータが実在するかをコードで確認する」（本項は**範囲**の話で別軸）。

## マーカー依存の洗い出しは「メソッド」でなく「引数」単位で行う。判定テーブルは `IsXxx()` の grep に出ない
- タグ: universal, go, 関心: 調査, 関心: 裏取り, 関心: データ
- 対象/場面: 外部マスタの文字列カラム（品目名・コード等）を差し替えるとき、そのカラムに依存するロジックを全部洗い出す場面。
- 判断:
  - 文字列マーカー依存は `func (m X) IsY() bool { return strings.Contains(...) }` の形だけではない。**`var xxxPrefixes = []categoryKey{{"【KM】", KidsMarket}, ...}` のようなデータ駆動テーブル + 汎用判定関数**として書かれることがある。この形は**関数名にも変数名にも判定対象のカラム名が現れない**ため、`IsKidsMarket` / `prize.Name` の grep では絶対に検出できない。
  - したがって洗い出しは**メソッド名の grep ではなく「そのカラムが何の引数に渡るか」で行う**。`Contains(.*Name`, `HasPrefix(.*Cd`, `RegexpBy(`, `LIKE` のような**引数側 grep**を掛ける。
  - 「ハードコードされた完全一致コードのリスト」も同族。これは grep 対象の文字列すら事前に分からないので、**分類・除外を行う判定関数の実装を必ず開いて読む**ことでしか見つからない。
  - 同じ判定が**複数箇所に再実装**されていることも疑う（メソッド化されているのに別ファイルで `HasPrefix` が直書きされている等）。
- 理由: 「`name` を消費するのはこの4メソッドだけ」という**完全性の主張**が安全性の根拠になる。その主張が崩れると承認判断の土台が丸ごと失効する。しかも漏れた側は grep で出ないので、「調べた」という自信だけが残る。
- 具体例: u1-api GN-5859。`prizes.name` / `prizes.prize_cd` の依存として `models/prizes.go` の `IsFood`/`IsHybrid`/`IsKidsMarket`/`IsKuroMaru` の4メソッドを洗い出して「唯一の入力」と書いたが、`internal/common/domain/entities/item_cd_category.go:35-121` の `GetItemCdCategory(itemCd, itemName)` が丸ごと漏れていた。これは `name` 5マーカー（`ハイブリッド景品`/`長期使用景品`/`正体不明景品`/`【ＫＭ】`/`【KM】`）+ `prize_cd` 5前置（`Z0`/`K0X`/`K0`/`K1`/`K2`）+ **例外コード24件の完全一致リスト**を持つデータ駆動テーブルで、呼び出し元8箇所（見なし棚卸の除外・景品配送取込のフィルタ・棚卸CSVの分類）に効いていた。さらに `prize_inventory_estimation.go:36` に `IsHybrid` の再実装、`consts/models.go:58` に `^HB[0-9]+` の正規表現依存もあった（design-review 2巡目が blocker として検出）。
- 関連: 「否定的な結論（使われていない／影響しない）を識別子検索だけで確定させない」。「外部マスタ差し替えでは『値が一致する』検証と『ドメイン判定の入力として成立する』検証を別次元にする」。

## 主キーは「集合の同一性」と「書式の同一性」を別問として立てる
- タグ: universal, 関心: データ, 関心: 移行
- 対象/場面: 外部マスタの供給元を切り替え、主キーを別ソースの項目に読み替える場面（`prize_cd ← item_code` 等）。
- 判断:
  - 主キーの**書式**（前置コードによる品目分類、`^HB[0-9]+` のような正規表現、例外コードの完全一致リスト）が業務ロジックの入力になっていることがある。
  - この場合、**キー集合が完全に同一でも書式が変われば分類ロジックが壊れる**し、逆に**書式が同じでも集合が変われば FK 参照が孤児化する**。壊れ方も対処も全く違う。
  - 「同一キー体系ですか？」の1問では両方を取りこぼす。**(a) 同じ行が同じキーで来るか (b) キーの書式（前置・桁・例外値）が同じか**の2問に分ける。
  - とくに**例外コードの完全一致リスト**は、キーが1文字変わるだけで**エラーを出さずに静かに外れる**（分類が既定値にフォールバックする）ため、受入基準に件数チェックを必ず入れる。
- 理由: 主キーの読み替えは「対応表が埋まれば終わり」と見なされやすいが、キーは識別子としての役割（集合）と、分類情報を埋め込んだ符号としての役割（書式）を兼ねていることがある。後者は対応表に現れない。
- 具体例: u1-api GN-5859。確認事項を「`item_code` は `prize_cd` と同一キー体系か／想定件数は」の1問にまとめていたが、`K0X` 前置19件（うち例外リスト13件は景品・残り6件は材料）・`^HB[0-9]+` 8件という**書式依存**が別次元で存在した。例外13件は `item_code` が1文字変わるだけでハードコードの完全一致が外れ、景品→材料に誤分類されて棚卸CSVから落ちる（design-review 2巡目が blocker の一部として検出）。
- 関連: 「外部マスタの『形式変更』を評価するとき、属性値の変化と主キーの連続性を別次元として扱う」の続き（本項は主キーの**符号としての役割**）。

## 「バグが是正される」という便益主張は、欠陥主張と同じ強度で ORM/DB のセマンティクスまで降りて確認する
- タグ: universal, go, 関心: 裏取り, 関心: 判断材料
- 対象/場面: 既存バグの修正を scope に含める判断をするとき、「直すと何が良くなるか」を列挙する場面。
- 判断:
  - 欠陥主張（＝直す理由）は裏取りされやすいが、**便益主張（＝直すと何が良くなるか）は裏取りが緩む**。便益は「この作業を今やる／やらない」の意思決定材料そのものなので、同じ強度で確認する。
  - アプリのコード分類ロジックからは自明に見える副作用が、**ORM の展開規則や DB のセマンティクスで打ち消される**ことがある。upsert・auto-timestamp・トリガ・デフォルト値が絡む主張は、必ずライブラリのソースと DDL まで降りる。
  - 「〜が全行更新される」「〜が毎回発行される」のような**量的な主張**は、量が意思決定を左右するので特に確認する。
- 理由: 便益を過大に書くと、scope に含める判断が水増しされた材料の上に乗る。しかも便益は「良い話」なので、レビューでも疑われにくい。
- 具体例: u1-api GN-5859。「差分なしレコードも upsert されるので `updated_at` が全行更新される」を B（既存バグ修正）の便益として挙げたが、gorm v1.31.1 `callbacks/create.go:376-377` の `OnConflict{UpdateAll:true}` 展開は `HasDefaultValue` な列を `DoUpdates` から除外し、`updated_at` は `default:CURRENT_TIMESTAMP(6)` を持つため**対象外**だった。DB 側の `ON UPDATE CURRENT_TIMESTAMP(6)` も値が変わらなければ発火しない。実際に成立する便益は「無駄な upsert 文の発行」だけだった（design-review 2巡目が minor として検出）。なお欠陥主張（差分なしが `newPrizes` に混入し件数ログが判断材料にならない）と修正の主目的は正しかった。
- 関連: 「訂正こそ元の記述と同じ強度で裏取りする」の便益版。「選択肢の比較表・天秤の材料は、結論と同じ強度で裏取りする」を**単一案の便益リスト**にも拡張する。

## 検証環境を前提に置くときは、経路の実在に加えて「入力データの実在」と「受入基準の母数の同一性」を確認事項に立てる
- タグ: universal, 関心: 検証手順, 関心: 裏取り, 関心: CI/CD
- 対象/場面: 「stg で dry-run して確認してから本番投入する」のような**検証環境での事前検証**をリスク統制として設計に置く場面。
- 判断:
  - 実行**経路**が通ることを確認しても、それは検証成立の一部にすぎない。次の2つを別途、確認事項として立てる。
    - **(a) 入力データの実在**: 検証環境側の外部ストレージ／DB に、検証対象の入力（新マスタのファイル等）が実在するか。いつ配置されるか。無ければ検証は 0 回も走らない。
    - **(b) 受入基準の母数の同一性**: 「本番実測値 ± 誤差」型の閾値を使うなら、**その閾値を測った環境と適用する環境が同一母集団か**。部分データの検証環境では閾値が判定として機能しない。
  - 検証環境で成立しない場合の**代替経路**まで設計に書く（本番での dry-run 先行実行、取得元をパラメータ化する等）。「検証環境で確認します」だけで止めない。
  - 取得元・接続先をパラメータで上書きできるかは**実装を見て確認する**（arg として受け付けているか）。上書きできないなら、それ自体が代替経路を狭める制約。
- 理由: 検証手順が唯一のリスク統制になっているとき、その手順が空手形だと**統制ゼロで本番投入する計画が「検証済み」の顔で承認される**。経路の裏取りだけで満足すると、この最後の穴が残る。
- 具体例: u1-api GN-5859。`Stg Manual Batch` の実行経路（composite action の checkout ref 問題）は1巡目の指摘で正しく直したが、(a) stg バケット `u1-databricks-export-stg/prod/mdm_prize_master/` への配置時期 (b) stg `prizes` の件数（受入基準 `【KM】` 2,212件等は prod 実測値）がどちらも確認事項に立っていなかった。加えて `exec.go` が `params` から読むのは `dryRun` だけで取得元パスを上書きできず、代替経路が狭いことも書けていなかった（design-review 2巡目が major として検出）。
- 関連: 「CI/CD の検証手順を前提にするときは、composite action / 再利用 workflow の入力デフォルト値まで辿る」の続き（経路 → データ → 母数の3層目）。

## 「変更対象の集合」を既存の似た述語・似た記述から機械導出せず、用途で導出する
- タグ: universal, sql, 関心: 影響範囲, 関心: 裏取り
- 対象/場面: 既存の横断的な条件（SQL の共通述語、共通ミドルウェア、共通バリデーション等）に**新しい条件を similar に追加する**とき、その適用範囲を決める場面。
- 判断:
  - 「既存の述語 X を持つ箇所の集合」と「新しい述語 Y を足すべき箇所の集合」は**別物**。X が偶然そこにあるのは、X 固有の歴史的理由かもしれない。**「X があるから Y も」は導出ではなく類推**。
  - 対象集合は**用途（誰が何のために呼ぶか）で分類してから決める**。同じクエリが複数用途に共用されている場合は、そこが設計の分岐点（クエリ分離 / サービス層で分ける / 明示ゲートに逃がす）であって、機械適用してはいけない箇所。
  - とくに危険な混在パターン: **認証パス / 管理・書き込みパス / 一意性チェックパス / 外部連携パス**。この4つは同じ「ユーザーを引く」クエリを共用しがちだが、新条件に対する要求が正反対になる（認証は閉じたい、管理は開けたい、一意性は見えていてほしい、外部連携は変えたくない）。
  - 集合を列挙したら、**各要素について「なぜ足すのか」ではなく「足すと誰が壊れるか」を1件ずつ書く**。書けない要素は裏取りできていない。
- 理由: 機械導出は網羅的に見えるので、レビューでも「漏れがない」方向にしか疑われない。だが**多すぎる適用は少なすぎる適用より発見が遅い**（該当ケースが実際に起きるまで壊れていることに気付かない）。しかも「fail-closed で安全側」という説明が付くため、過剰適用が安全策の顔をして通る。
- 具体例: idpf-api GID-1230（ユーザー一時停止）。認証を fail-closed にするため停止述語を追加する対象を「`is_active = true` を持つ READ 13本」と機械導出した。実際にはその13本に、**停止の解除操作自身が通るクエリ**（`queryFetchUserByUUIDForUpdate` → `fetchUserWithAuthInTransaction` は `sql.ErrNoRows` を `ErrUserUnauthorized` に変換する）、**メール重複チェック**、**BanBan/GOC の private_link 検索**が混在しており、そのまま実装すれば「停止したら二度と解除できない」「専用エラーページに到達できない」「停止中の email が空きに見える」が同時に起きた。用途で再分類した結果、**本当に足すべきは 1 本だけ**だった（design-review が blocker 2 件として検出）。
- 関連: 「前提が明確な処理を、前提の違う集合に機械的に共通化しない」の適用範囲版。「fail-closed は安全側だから広く掛けてよい」という直感への反例でもある。

## レビュー指摘を修正したら、同じ主張が書かれた「他の全箇所」を grep して潰す。とくに決定を記録するセクションを最優先で直す
- タグ: universal, 関心: レビュー対応, 関心: 一貫性, 関心: ドキュメント
- 対象/場面: design-review や指摘を受けて設計方針を変えたあと、タスク定義書・設計ドキュメントを更新する場面。
- 判断:
  - 方針を変えたら、**変更前の方針が書かれている箇所を全部 grep で洗い出してから直す**。指摘された箇所だけ直して終わらせない。設計ドキュメントは同じ主張が「決定」「作業内容」「ファイル一覧」「検証プロトコル」「リスク」に**重複して書かれている**のが普通で、1箇所直しても残りが古い指示として生き残る。
  - **最優先で直すのは「決定を記録するセクション」**（§決定事項・§懸念点の【回答済み】など）。実装者はそこを一次情報として読むので、そこに旧方針が残ると**指摘された欠陥がそのまま再現する**。ヘッダに【回答済み】と書き足しただけで本文の旧推奨を残すのが典型的な失敗。
  - 方針変更の**波及先**も洗う。「A に述語を足さない」に変えたなら、A の結果を前提にしていた分岐条件（`ErrNoRows` を見ている等）・テストの期待値・別経路の根拠説明が全部ひっくり返る。**変更点そのものより、変更に依存していた記述の方が見落としやすい。**
  - 撤回した案は削除するか「（旧案・不採用）」と明記する。残すなら**採用案より目立たなくする**。「推奨」という語を撤回済みの案に付けたまま放置しない。
- 理由: レビューは「指摘された箇所」を返すのであって「その指摘が波及する全箇所」を返すわけではない。修正の伝播はレビューを受けた側の責任。伝播が不完全だと、**レビューを通したという事実が安全の錯覚を生み**、次の実装者が古い指示に従って同じ穴を掘る。
- 具体例: idpf-api GID-1230。1巡目 blocker「述語追加対象を13本から1本へ」を反映した際、§述語追加対象の確定 という新セクションは正しく書いたが、**§懸念点2 の本文に「13本」のクエリ番号がそのまま残っていた**（しかもヘッダは【回答済み】）。加えて派生の取り残しが3件 —— `login.go` のゲート条件が「`ErrNoRows` のとき」のままで**述語を外した結果ヒットするようになり一度も発火しない**、パスキー begin の期待値が「401」のままで**書いたテストが必ず落ちる**（通そうとすると回避したはずのアカウント状態オラクルを作る）、`reset_email_phone` の根拠が「述語で弾かれる」と逆。2巡目レビューが blocker 1 / major 2 として再検出した。
- 関連: 「変更対象の集合を既存の似た述語から機械導出せず、用途で導出する」の後始末版。「訂正こそ元の記述と同じ強度で裏取りする」をドキュメント全体の一貫性に拡張したもの。

## 設計判断の「なぜ」を実装機構で説明しない。要件・制約から導く
- タグ: universal, 関心: ドキュメント, 関心: 設計根拠
- 対象/場面: 設計ドキュメント・タスク定義書で「なぜこの挙動なのか」を説明する場面。とくに外部から観測される振る舞い（API レスポンス、エラーコード、UI 表示）の設計理由を書くとき。
- 判断:
  - 「A の下流に B があるので B も同じ結果になる」型の説明は、**そうなりやすい理由**であって**そうすべき理由**ではない。分岐しようと思えば分岐できる以上、機構は選択の正当化にならない。
  - 設計判断の理由は**要件・制約・優先順位**から書く。「要件に X があり、それを満たすには Y を選ぶしかない／Y が最も影響が小さい」の形。機構の説明はそのあとに「実装上もこうなる」と添えるだけ。
  - この誤りは**議論を殺す**のが最大の害。機構は変えられないものとして読まれるので、「じゃあ仕方ない」で終わり、**本来議論すべき優先順位の選択が争点として立たない**。議論のために書いた文書なら致命的。
  - 見分け方: その説明を読んだ相手が「それは変えられないのか？」と聞き返せるか。聞き返せない書き方（＝機構の説明）になっていたら、背後にある選択を掘り起こして書き直す。
- 理由: 実装者は機構を熟知しているので、機構による説明が「腑に落ちる説明」に感じられる。だが読み手が知りたいのは「なぜその選択をしたか」であり、機構はその選択の**結果**でしかない。因果を逆に書いている。
- 具体例: idpf-api GID-1230。RP から停止と退会が同じエラーに見える理由を「停止判定は SQL 述語で行うので、退会と同じく『ユーザーが見つからない』経路に落ちるため」と書いた。実際の理由は要件側の「RP アプリへの影響を最小限にする」＝既存エラーコードを流用する方針であり、**「RP を無改修にすること」を「RP が区別できること」より優先した結果**。この文書は RP 担当とその優先順位を議論するために書いたものだったので、機構で説明した時点で議題そのものが消えていた。
- 関連: 「変更対象の集合を用途で導出する」と同根（実装の都合と設計の要求を取り違える）。

## 具体値（ドメイン・URL・数値・パス）は、実物を見たものだけ書く。それ以外は変数名で書く
- タグ: universal, 関心: 裏取り, 関心: ドキュメント, 関心: 捏造防止
- 対象/場面: 説明・資料・タスク定義書で、動作を具体例で示すとき。とくに「例えば」「たとえば」と書いて URL・ドメイン・ホスト名・数値を出す場面。
- 判断:
  - **具体値は、コードか設定ファイルで実物を見たものだけ書く。** 見ていないなら `<API_DOMAIN>` のように変数名・プレースホルダで書く。
  - **「例として書いた」は免罪符にならない。** 読み手には確認済みの事実と同じ形で届く。とくに実在しそうな形（`id.example.jp` のようなドメイン、それらしい数値）は、そのまま事実として引用される。
  - 環境変数の値は**リポジトリに無いのが普通**（SSM / Terraform / Secrets Manager 側）。`.env.example` にローカル値があれば「ローカル開発の値」と明示して引用し、本番値は「リポジトリに無い」と書く。
  - **ドメインが分かれている可能性を常に疑う。** API とフロントが別ドメインなのは Web では普通。単一ホストを仮定した URL を書く前に、URL を組み立てているコード（`WebURL` 相当）を読む。
- 理由: 具体値は読み手が最も信用する部分で、かつ最も検証されにくい。パスや関数名と違って「そのファイルを開けば分かる」ものではないため、誤りが下流へそのまま流れる。しかも書き手には「例のつもり」という自覚があるので、訂正の必要性に気づかない。
- 具体例: idpf-api GID-1230。RP と IDPF の通信を説明する際に `https://id.genda.jp/authorize?...` と書いた。このドメインはコードにも設定にも存在せず、私が作った。実際は `env.Must_API_DOMAIN()`（API）と `env.Must_FRONT_DOMAIN()`（画面）の**2つの別ドメイン**があり、画面側は `/web/<lang>/<path>.html` という別の形をしていた（`internal/idpf/url.go` の `WebURLContext`、`internal/servicepath` の `Prefix = "/web"`）。ユーザーに「捏造すんな」と指摘されるまで、資料にもそのまま書いていた。
- 関連: 「訂正こそ元の記述と同じ強度で裏取りする」（本項は**具体値**に特化した系）。「『使われていない』という否定的結論を識別子検索だけで確定させない」（どちらも検証コストの低さに対して被害が大きい）。

## 外部ライブラリのフックに実装方針を載せる前に、そのフックの「署名」を読む。名前から機能を推定しない
- タグ: universal, 関心: 裏取り, 関心: 設計根拠, 関心: 実現可能性
- 対象/場面: 設計ドキュメントで「フレームワークの拡張点 X を使ってこうする」と方針を立てる場面。gqlgen / gin / grpc の interceptor、Rails の around_action、React の Effect 系など、**フックの候補が複数あり名前が似ている**とき。
- 判断:
  - **「そのフックが存在すること」の確認と「そのフックが必要な情報を渡してくること」の確認は別。** 前者だけ済ませて後者を飛ばすと、設計が根元から成立しない。
  - **確認するのは grep で見つけた行番号ではなく、型シグネチャそのもの**。とくに **戻り値**（エラーが返るか）と **引数の型**（生 AST か、型付きの値か）。ここに実現可能性が全部乗っている。
  - 候補が複数あるときは**署名を並べた表を作る**。名前の意味（Root/Around/Before）で選ばず、必要な情報が流れてくるかで選ぶ。「より限定的な名前の方が適切そう」は罠で、限定的なフックほど渡される情報が少ない。
  - 生成コード（`generated.go` 等）があるなら**そこでフックが実際にどう呼ばれているか**を読む。ドキュメントコメントより生成コードの方が信用できる（後述の実例参照）。
- 理由: フックの名前は「どこで呼ばれるか」を表すが、設計が依存するのは「何を渡されるか」。この2つは相関するが一致しない。しかも設計書の段階では動かして確かめられないので、署名を読まない限り誤りが実装着手まで生き残る。「実装時に確認する」と書いて先送りすると、**設計判断そのものが覆る**種類の欠陥を、実装フェーズのコストで踏むことになる。
- 具体例: idpf-api GID-1568（管理画面の監査ログ）。「mutation 単位で記録したいのだから root field 用のフックが適切」と考えて gqlgen の `AroundRootFields` を採用し、「操作前に INSERT → 完了後に結果を UPDATE する2相記録」を設計の中核に据えた。実際には `RootFieldMiddleware func(ctx, next RootResolver) Marshaler` で **error を返さない**ため成否の判定ができず、`RootFieldContext.Field` は生 AST なので**型付き引数も取れない**。正解は `AroundFields`（`FieldMiddleware func(ctx, next Resolver) (res any, err error)`）で、`fc.Args` に型付き input が入る。design-review が blocker として検出。**フックの存在（`server.go:104`）だけ確認して署名を読んでいなかった**のが原因。
- 補足（ドキュメントコメントより生成コード）: 同件で `RootFieldContext.Object` にはコメントで "The name of the type this field belongs to" とあるが、生成コードは `RootFieldContext{Object: field.Name}` で**フィールド名**を入れている。コメントを信じると条件が常に false になる。
- 関連: 「『その方式は実現不能』を代替案の却下理由にする前に裏取りする」の裏返し（**採用側の実現可能性**も同じ強度で裏取りが要る）。「『先例あり』と言う前に、その先例が同じ機構・同じ呼び出し形かを確かめる」。

## fail-closed の宣言テーブル（ホワイトリスト）に書く名前は、実定義から機械的に取る。間違っても例外にならず静かに壊れる
- タグ: universal, 関心: 裏取り, 関心: 安全側設計, 関心: 可観測性
- 対象/場面: 「宣言が無いものは記録しない／通さない」型の設計で、対象ごとの設定を表にする場面。監査ログの対象フィールド、マスキング対象、権限マップ、フィーチャーフラグの対応表など。
- 判断:
  - **fail-closed は「間違いが例外にならない」設計である**ことを自覚する。fail-open なら誤りが事故として顕在化するが、fail-closed の誤りは「何も起きない」＝正常系と見分けがつかない。**安全側に倒したことで、壊れたことに気づく手段まで失っている。**
  - だから宣言テーブルの**キー名・フィールド名は必ず実定義（スキーマ・型定義）を開いて写す**。記憶や命名規約からの推測で書かない。似た名前が混在している（`userID` / `userId` / `id`）のが普通。
  - 表を作ったら**「実定義を確認した行」と「していない行」を明示的に区別する**。全行確認できていないのに一様な表として出すと、確認済みの精度が未確認の行にまで転移して見える。
  - 可能なら**宣言の網羅性・整合性をテストか生成で担保する**（全対象を列挙した定数と突き合わせる等）。人間が表を保守する限り、新規追加のたびに同じ穴が開く。
- 理由: fail-closed 設計を採る動機は「書き忘れても危険側に倒れないこと」だが、その代償として「書き忘れ／書き間違いが検出できない」が付いてくる。この代償は設計判断として意識されにくく、「安全側にした」という満足で確認が緩む。**安全側設計ほど、宣言の中身の裏取りを厳しくする必要がある。**
- 具体例: idpf-api GID-1568。監査ログのミドルウェアが「宣言の無い mutation は操作名だけ記録する」fail-closed 設計にした上で、20 mutation 分の「対象 ID の取り出し元」を表にした。実スキーマと突き合わせると `updateUser` は `input.id` ではなく `EditUser.userID`、`grantLimitedPoint` は `userID` ではなく `userId`、`revokeLimitedPoint` は `grantID` ではなく `grantId`、`CreateCampaignInput` には `id` が無い、`regrantSurveyPointGrants` は表から欠落、と5件が誤っていた。**どれも実装すれば「target_id が空のまま静かに記録され続ける」**。design-review が major として検出。
- 関連: 「変更対象の集合を機械導出せず用途で導出する」（あちらは**多すぎる適用**、本項は**間違った内容**）。「具体値は実物を見たものだけ書く」の識別子版。

## レイヤー違反を1本指摘されたら、その部品が作る依存エッジを全部列挙する。指摘された1本だけ潰さない
- タグ: universal, 関心: レイヤー境界, 関心: レビュー対応, 関心: 裏取り
- 対象/場面: レビューで「この依存は許可されていない」と指摘され、部品の置き場所を変える／port interface を挟む場面。
- 判断:
  - 修正する前に、**その部品が import する必要のあるパッケージを全部書き出し、1件ずつ許可表と突き合わせる**。指摘された1本を潰して終わりにしない。
  - とくに**同じ層の隣接コンポーネント**が危ない。「DB へ書く」は疑われるので指摘されるが、「生成コードの型を使う」「フレームワークのモデルに触る」は無自覚に import されるため指摘から漏れる。
  - 許可表に**エントリが無いコンポーネント**（依存先が未定義）は「無制約」か「依存禁止」か**ツールの挙動を確認するまで分からない**。分からないまま「lint は通るはず」と書かない。確認項目として残す。
  - 置き場所を決めるときは、**必要な依存を全部すでに許可されている層**を探す方が、port interface を何枚も挟むより早くて壊れない。
- 理由: レビューは指摘した1本しか返さない。だが依存は部品が持つ import の集合であって、レビュアーが挙げた1件ではない。**「指摘された箇所を直した」で安心すると、同種の違反が隣に残る**。しかも lint が「許可表に無いエッジ」を検出できるかどうかは設定次第なので、実行して初めて分かることがある。
- 具体例: idpf-api GID-1568（管理画面の監査ログ）。1巡目レビューで「`adminapi → driver` は arch-lint が『消したい』と書いているエッジ」と指摘され、port interface + DI 注入に直した。しかし同じミドルウェアは `fc.Args["input"].(gqlmodel.EditUser)` で **`admingraph/gqlmodel` の型**も使う設計で、**`adminapi.mayDependOn` に `admingraph` は入っていない**（`[usecase, driver, adminapi]` のみ）。2巡目レビューが major として再検出。正解は `internal/app/`（`app.mayDependOn` が `admingraph`/`driver`/`adminapi` を全部含む）に置くことで、**port interface を挟むより単純に解決した**。
- 関連: 「レビュー指摘を修正したら、同じ主張が書かれた他の全箇所を grep して潰す」の依存グラフ版。

## 要件↔設計の対応表を書いたら、各行を成果物の実体と突き合わせる。表は「満たしている」空気を作る
- タグ: universal, 関心: 裏取り, 関心: ドキュメント, 関心: 要件充足
- 対象/場面: PRD・要件定義と自分の設計を突き合わせる対応表（トレーサビリティマトリクス）を書く場面。「この要件は §X で満たす」の形。
- 判断:
  - 表の各行について、**参照先を実際に開いて、その要件を満たす記述・列・項目が本当にあるか確認する**。「§5.1 の列で満たす」と書いたら DDL を開いて列を数える。
  - **「すべて〜で満たす」という一括の書き方をしない。** 要件項目を1つずつ列挙し、どれがどこに対応するかを1対1で書く。一括表現は、その中の1つが欠けていても表面上は成立して見える。
  - **要件側が列挙形式（「A／B／C／D」）なら、設計側も同じ粒度で列挙する。** 粒度を落とした瞬間に欠落が隠れる。
  - 逆向きも見る: **設計にあって要件に無いもの**（勝手に足したもの）も表に出す。
- 理由: 対応表は「照合済み」という強い信号を発するため、**書いた本人も読み手も、中身を再確認しなくなる**。しかも表は要件を要約して転記するので、要約の過程で落ちた項目は表の上では存在しないことになる。検証コストが最も低いのに被害が最も見えにくい成果物。
- 具体例: idpf-api GID-1568。PRD の Must 記録項目「日時／実行者／対象アカウントID／操作種別／変更前後の値／**理由（ある場合）**」に対し、対応表に「すべて `admin_operation_logs` の列で満たす」と書いた。**実際の DDL に `reason` 列は無かった**。さらに別セクションでは「停止理由は監査ログに重複して積まない（別テーブルを正とする）」と明記しており、**設計は要件と正反対の方向に決めていた**。2巡目レビューが major として検出。1対1で列挙していれば、書いた時点で気付けた。
- 関連: 「『無変更で確認済み』リストは、同じ役割を果たす設定資産を全部列挙する」（どちらも「確認した体裁の一覧」が検証を止める）。

## 閲覧権限を絞るときは「その操作を実行できる主体の集合」と突き合わせる。操作できて記録を見られない構成を作らない
- タグ: universal, 関心: 権限設計, 関心: 要件充足, 関心: 監査
- 対象/場面: 監査ログ・操作履歴・管理機能の閲覧権限を設計する場面。「最上位グループ限定にしておけば安全」と考えたとき。
- 判断:
  - **閲覧権限を決める前に、対象の操作を「実行できる主体の集合」を実装から列挙する。** 実行できる集合より閲覧できる集合が狭いと、**「操作はできるが自分がした操作の記録を見られない」**構成になる。
  - **要件書が指名している主対象者が、実在する権限グループにマッピングできるかを確認する。** 「CS チーム」のような業務上の役割が、システム上のグループとして存在するとは限らない。存在しないなら、グループ新設か既存グループへの相乗りかの判断が要る（＝要件書の想定より作業が増える）。
  - 「最上位グループ限定」は安全側に見えるが、**要件の主対象者を締め出せば機能そのものが目的を果たさない**。安全と有用性の天秤であって、片側だけ最適化しない。
  - 粒度を分けられないか検討する: **一覧本体（誰が・いつ・何を）は広く、PII を含む詳細だけ狭く**、が多くの場合に成立する。
- 理由: 権限を絞る判断は「厳しくしておけば怒られない」方向にバイアスがかかり、実装者が単独で決めがち。だが監査ログの閲覧権限は、実行権限との組み合わせで初めて意味が決まる。片側だけ見て決めると、要件の主対象者に届かない機能ができる。
- 具体例: idpf-api GID-1568。監査ログの閲覧を `@requireGroups(any: [ADMINS])` にすると設計した。だが PRD の対象ユーザーは **CS チーム**で、唯一のユーザーストーリーも「CS担当者として履歴を一覧で確認したい」（Must）。実在するグループは `ADMINS`/`POINT`/`COMBO` の3つだけで **CS 用が無い**。さらに監査対象の `updateUser`/`deleteUser` には `@requireGroups` が付いておらず、**ADMINS でない運用者が退会・プロフィール編集を実行できる**。＝操作はできるが記録は見られない。2巡目レビューが major として検出。
- 関連: 「設計判断の『なぜ』を実装機構で説明しない。要件・制約から導く」（要件側の主対象者を見ずに機構側の都合で決めた例）。

## フィーチャーフラグは「機能の入口」ではなく「機能に到達しうる全経路」に掛かっているかを確認する
- タグ: universal, 関心: フィーチャーフラグ, 関心: リリース安全性, 関心: 裏取り
- 対象/場面: 新機能をフラグで包んで「OFF なら何も出ない」と設計する場面。ページ／ルート／エンドポイントにゲートを 1 つ置いた時点で完了と考えたとき。
- 判断:
  - **ゲートを書く前に、その機能へ到達しうる経路を全部列挙する。** 入口本体（ページ・ルート・ハンドラ）だけでなく、**そこへ誘導する導線**（バナー・メニュー項目・リンク・通知・メール文面・他機能からの遷移）も経路である。
  - **導線は入口とは別のモジュールの出力であることが多い。** 入口を消しても、導線を含むモジュールはビルド・デプロイされ続ける。入口のゲートは導線を止めない。
  - **「OFF なら成果物に含まれない」と書く前に、その成果物にどのファイルの出力が入るかを確認する。** 静的ビルド・ツリーシェイキング・ルーティングの仕組みを推測で語らない。
  - 止まらない導線は**壊れたリンク**になる（存在しない URL への遷移）ので、単に「余計なものが見える」より悪い。
  - 検証項目も経路単位で書く。**「設定ファイルにキーを置かないことを確認」は検証になっていない**。成果物を実際に検索して導線の痕跡が無いことを確かめる。
- 理由: フラグの設計は「機能」を単位に考えるが、ユーザーから見た機能は「入口＋そこへ至る導線」で、両者はコード上ふつう別の場所にある。入口だけ塞ぐと、**フラグ OFF のはずの環境に導線だけが残り、踏むと壊れる**という最悪の中間状態ができる。しかも入口のゲートは目立つので「対応済み」の空気を作り、導線の検証が飛ぶ。
- 具体例: idpf-api GID-1856。新機能のページに「フラグ OFF なら 404」を置き、「OFF の環境ではページも導線も成果物に含まれない」と設計書に書いた。実際にはバナーとヘッダー導線はマイページ側のファイルの出力で、フラグの有無に関わらずビルドされる。同じリポジトリの先例は導線コンポーネント内でフラグを判定して `null` を返しており、その先例を「参考にする既存コード」に挙げながらゲートの存在を見落としていた。設計レビューが blocker として検出。
- 関連: 「『使われていない』という否定的結論は、識別子検索だけで確定させない」（どちらも「経路の全列挙」を怠った例）。

## 設定値を足すときは、環境ごとの供給経路を列挙する。代表的な 1 ファイルに足して「全環境に入った」としない
- タグ: universal, 関心: 設定管理, 関心: 検証手順, 関心: 裏取り
- 対象/場面: 環境変数・設定値を新規に足す場面。サンプル設定ファイル（`.env.example` 等）や本番のデプロイ定義に足して完了と考えたとき。
- 判断:
  - **設定が実際に届く経路は環境ごとに別物**であることを前提に、**環境を列挙して 1 つずつ経路を確認する**（ローカル／ユニットテスト／統合・E2E／CI／各デプロイ先）。同じ変数名でも、供給元がサンプルファイル・CI の `env:` ブロック・起動スクリプト・デプロイ定義・シークレットストアとバラバラなことがある。
  - **既存の同種フラグが「どの環境に無いか」も確認する。** ある環境にエントリが無いのは、不要だからか、その環境ではその機能を使っていないからで、**新機能でも同じでよいとは限らない**。
  - **サンプル設定ファイルが「必須変数リスト」の生成入力になっていないか確かめる。** なっている場合、そこに足すと未設定時に起動が失敗する（＝安全側どころか事故）。
  - テスト・E2E を成立させる設定は、**テストの変更対象ファイル一覧に入れる**。実装ファイルの一覧にしか無いと、テストが「常に失敗する」または「常に素通りする」状態で気付かれない。
- 理由: 設定は「1 箇所に書けば全体に効く」ように見えるが、実際は供給経路ごとに独立した写しがある。代表的な 1 ファイルに足すと**足した感覚だけ**が残り、他経路の欠落は「その経路を実際に走らせるまで」表面化しない。とくに E2E は失敗しても原因が機能側に見えるため、設定の欠落だと気付くまでが長い。
- 具体例: idpf-api GID-1856。新機能のフラグをローカル用サンプル設定とデプロイ定義に足したが、**E2E はそのどちらも読まず**、CI ワークフローの `env:` ブロックと起動スクリプトから環境変数を組み立てていた。結果、E2E 環境ではフラグが未設定＝ OFF となり、設計した E2E シナリオが全て機能側の 404 で落ちる状態だった。設計レビューが blocker として検出。
- 関連: 「CI/CD の検証手順を前提にするときは、composite action / 再利用 workflow の入力デフォルト値まで辿る」（どちらも「設定がどこから来るか」の追跡不足）。

## テスト容易性のための注入は、非決定要素を列挙して漏れなく行う。1 つに適用した論拠は他にもそのまま当てはまる
- タグ: universal, 関心: テスト容易性, 関心: DI, 関心: 一貫性
- 対象/場面: 時刻・乱数・ID 採番・外部 I/O などの非決定要素を持つロジックを設計する場面。片方だけ注入可能にして満足したとき。
- 判断:
  - **設計を書く時点で、その処理に含まれる非決定要素を列挙する**（現在時刻／乱数／UUID・連番の採番／ホスト名・環境変数／外部応答）。列挙してから、どれを注入するかを決める。
  - **1 つを注入する論拠（「注入しないと○○のテストが書けない」）は、他の非決定要素にもそのまま当てはまらないか確認する。** 片方だけ注入する設計は、たいてい論拠の適用漏れであって意図的な選択ではない。
  - **「結果を決めているのはどれか」で優先度を判断する。** 分岐の結果を直接決める要素が注入できないと、テストは**別の入力で代用**することになり、**意図と違う経路を通ったまま緑になる**（＝テストの骨抜き）。
  - 注入の形は既存の先例に揃える。**公開フィールドで差し替える方式は外部から書き換えられる**ので、金銭・権限に関わる値では二段コンストラクタなど書き換え不能な形を選ぶ。
- 理由: 非決定要素は「時刻」だけが強く意識されやすく、乱数や採番は見落とされる。しかし確率分岐・重複回避の中心にあるのは後者であることが多い。片方だけ注入できる状態でテストを書くと、書ける範囲でしか書かなくなり、**書けなかったケースが「テスト済み」の体裁の中に埋もれる**。
- 具体例: idpf-api GID-1856。確率抽選のユースケースで、時刻については「注入しないと日付境界のテストが書けない」と明示的に論証して注入したのに、**当落を直接決める乱数には同じ論証を適用せず**、注入経路を用意していなかった。確率 5% / 0.1% の当選ケースを決定論的に書けず、上限確保の戻り値を偽装して代用すると別経路を通ってしまう状態だった。設計レビューが major として検出。
- 関連: 「テストは『検出したい性質を実際に検出できるか』を実測で裏取りする」（どちらもテストが緑でも検証力がゼロになる形）。
