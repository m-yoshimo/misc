# design-review v2 — レビュー基準

外部の design-review エージェントが「Claude の成果物（タスク定義書・実装 diff）」を照合するための基準。
Claude 自身が守るルール（注入 feedback）ではなく、**別の目（レビュー担当）が使う採点表**。判定者を実装者から分離するのが目的。

## v1 との違い（なぜ作り直したか）

v1 は `design_review_rubric.md`（照合観点）と `design_philosophy.md`（具体教訓）の2ファイル構成だった。
建前は「philosophy = 生ログ / rubric = その要約」だが、**実態は双方向に独自追記され同期が切れていた**:

- philosophy 後半の項目群（Suspense / fail-closed / フィーチャーフラグ / 完了ゲート / 主キー / キャッシュ寿命 …）は rubric に1件も反映されていない
- 逆に rubric にしか無い項目もある（map 命名規則 `vByKey`、破壊的変更）

原因は「要約を作り直す工程が誰の仕事でもない」こと。
v2 では **判定・理由・具体例を1エントリの中のフィールドにした**ので、「どちらに書くか」という判断自体が消える。

## 構成

| ファイル | 役割 |
|---|---|
| `00-principles.md` | 設計原則 P1〜P5。全レビュアーが必読。個別ルールが衝突したときの最終裁定はここに帰る |
| `severity.md` | blocker / major / minor / question の判定基準 |
| `INDEX.md` | 全ルールの1行索引（ID・タイトル・severity・scope）。**レビュアーはまず索引だけを読み、当たったルールの本文だけ深掘りする** |
| `rules/R1〜R8` | ルール本体。カテゴリごとに1ファイル＝レビュアー1体の担当範囲 |

## エントリ形式

```markdown
### R1-03: <タイトル>
- severity: major          # 既定値。文脈で上下しうる（severity.md 参照）
- scope: both              # design=タスク定義書 / code=実装diff / both
- tags: universal, go
- 由来: ユーザー指摘        # ユーザー指摘 / ユーザー判断 / Claude 提案
- 判定: <レビュアーが当てる基準。何があれば違反か。ここが空なら照合対象ではない参考教訓>
- 理由: <なぜ。これが無いと次の場面で適用判断できない>
- 具体例: <汎用化の元になった実際の指摘>
- 関連: <他ルールの ID>
```

- **`判定` があるものが照合観点**。`判定` の無いエントリは参考教訓であり、単独で指摘の根拠にしない。
- **`scope`** により、タスク定義書レビュー（設計）と実装 diff レビュー（コード）で当てる観点を出し分ける。
- **`由来`** は「**誰の判断でこのルールが入ったか**」を示す。事例の有無ではなく**判断の出所**を記録するためのもの。

| 値 | 意味 | 件数 |
|---|---|---|
| `ユーザー指摘` | 実際に指摘された事象の一般化（`具体例` を伴う） | 69 |
| `ユーザー判断` | 事例はないが、ユーザーが妥当と判断して置いた観点（v1 rubric 由来のものを含む） | 11 |
| `Claude 提案` | Claude が追加した。**ユーザーの承認が済むまでこの値のまま** | 0 |

**`Claude 提案` のルールを唯一の根拠に blocker を出さない。** 過去に実装者が調査資料由来の主張を指針として書き込み「僕が言った内容と全く違う、自己解釈を広げすぎ」と指摘された経緯があり、この区別はその再発を検出するためにある（→ `00-principles.md`「このルーブリックに適用してはいけないもの」）。

## 運用

- **新しい違反クラスを見つけたら `rules/` に追記し、`INDEX.md` に1行足す。** 基準を機械側で育てる（Claude の自己申告に依存しない）。
- 追記は該当カテゴリのファイルへ。どこにも当てはまらない新カテゴリが必要なら R9 以降を作る。
- ID は**再利用しない**。削除したルールの ID は欠番のまま残す（過去の findings が参照しているため）。

## このルーブリックは網羅を主張しない

**多くのルールは「実際に指摘された事象の一般化」であり、一般原則からの演繹ではない。** だから大半に `具体例`（実チケット・実リポジトリ）が付いている。

**ただし、事例があることは追加の必須条件ではない。** 一般論として妥当なら事例なしで足してよい（その場合 `具体例` は空で、`由来: ユーザー判断` になる）。
記録すべきなのは事例の有無ではなく、**誰の判断で入ったか**（`由来`）である。

いずれにせよ **「ルールが無い ＝ その領域に懸念が無い」ではない。まだ起きていない、あるいはまだ書いていない、というだけ。**
カテゴリごとの件数も、リスクの大きさではなく直近のプロジェクト分布を反映している（例: R7 の多くは u1-web の TanStack Query 移行、R8 の多くは idpf-api 由来）。

レビュアーは、このルーブリックに載っていない観点で明らかな問題を見つけた場合、`rule_id: "NEW"` として報告してよい（基準への追記はユーザーの承認事項）。
逆に、**ルールに当たらないものを無理に既存 ID に当てはめない**こと。

これは R4（網羅性を主張する検索を打ち切るな／「確認済み」ラベルが再検証を止める）の思想を、ルーブリック自身に適用したものである。

## プロジェクト固有の規約を、このルーブリックに書かない

ここに書くのは**技術・プロジェクト非依存の観点**だけ。特定リポジトリの規約（層別の型命名、adapter の統一形、DB エラー判定の集約先、特定 helper の名前など）は、
各プロジェクトの `<project>/.claude/notes/project_review_rules.md` に `PJ-` 接頭辞で書き、レビュー時に合成する。

**理由:** 汎用ルーブリックに特定プロジェクトの helper 名が混ざると、別プロジェクトのレビューで存在しない資産を根拠に指摘が出る。
（v2 作成時、実際に pointpf-api 固有の規約を R2-02 に混入させて監査で検出された。）

## このルーブリックに書いてはいけないもの

`research-constraint-first-design.md` 等の**調査・学習資料に由来する主張**（Metz / Dodds の「重複を選ぶ」、DRY 原義、YAGNI 等）を、ユーザーの確定指針として書かない・レビュー基準として適用しない。
これらはユーザーが**勉強目的**で依頼した調査結果であり、確定した設計指針ではない。過去に実装者がこれを指針として書き込み「僕が言った内容と全く違う、自己解釈を広げすぎ」と指摘された経緯がある。
