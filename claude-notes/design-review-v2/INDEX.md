# ルール索引

**レビュアーはまずこの索引だけを読み、当たったルールの本文だけを深掘りする。**
本文は `rules/<カテゴリ>.md` にあり、各ルールは `### <ID>:` で始まる。

- `scope`: **design** = タスク定義書（設計）に当てる ／ **code** = 実装 diff に当てる ／ **both** = 両方
- `sev`: 既定 severity（`severity.md` の定義で上下させてよい）

---

## 原則（00-principles.md） — 全レビュアー必読

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| P1 | major | both | 一貫性・可読性・堅牢性・拡張性を、代償を明示せずに犠牲にしていないか |
| P2 | major | design | 仕様の矛盾・問題に気づける材料があるのに、代替案を検討せず言われたまま実装していないか |
| P3 | major | both | 「差分が小さい」「無改修で済む」を**選定理由**にしていないか |
| P4 | major | both | 破壊的変更・データが絡む変更で、影響を見極めた判断になっているか |
| P5 | question | both | **リスク／影響とメリットの天秤が記述されているか**（ルール衝突はここに上がるが、**結論は決めず記述の有無を見る**） |

## R1: レイヤー境界・責務・依存方向（`rules/R1-layering.md`）

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R1-01 | blocker | both | 内側の層が外側の層を import していないか |
| R1-02 | major | both | 複数ストアへの横断的処理が repository 層の合成オブジェクトになっていないか（Service 層へ） |
| R1-03 | major | both | 対称性を揃えるためだけのロジック無し委譲レイヤを足していないか。非対称を欠陥扱いしていないか |
| R1-04 | major | both | 共通基盤が他フィーチャの service / usecase に依存していないか（repository のみか） |
| R1-05 | major | both | 相互依存しやすいフィーチャ間で cross-import していないか（各自に同等実装を持たせる） |
| R1-06 | major | both | usecase が service を具象型で import していないか（domain の interface 経由か） |
| R1-07 | major | both | 取得サービスが責務外の別エンティティを取得していないか |
| R1-08 | major | both | 異種データを1スライスに concat して型・情報を落としていないか |
| R1-09 | minor | both | 表示専用の文字列をデータ層の定数から組み立てていないか |
| R1-10 | major | both | 副作用の呼び出し経路が追えるか／共通化先が責務的に正しいか（共通化自体は否定しない） |
| R1-11 | major | both | レイヤー違反の修正が、指摘された1本だけで終わっていないか（依存エッジを全列挙したか） |
| R1-12 | major | both | 各関数／型が単一の責務か。「〜と〜」で繋がるなら分割を検討したか |

## R2: 共通化・抽象化・制約（`rules/R2-abstraction.md`）

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R2-01 | major | both | 共有ヘルパーを片方の usecase に置いて usecase 間依存を作っていないか |
| R2-02 | major | code | 既存の変換関数・共通 helper を再発明していないか |
| R2-03 | minor | both | 既存プリミティブの合成で表現できないか。依存方向が下から上か。紛らわしい命名でないか |
| R2-04 | major | both | 不要なジェネリクス・過剰な汎用性がないか。型で「できないこと」を表せないか |
| R2-05 | major | both | 前提が確定している処理に、汎用 API 由来の再導出・突合・防御分岐を持ち込んでいないか |
| R2-06 | blocker | both | 適用対象の集合を「既存の似た述語」から機械導出していないか（用途で導出したか） |
| R2-07 | major | both | 引数注入への汎用化で deps 追加・安定参照が要ることを見落としていないか |

## R3: 一貫性・規約踏襲・命名・可読性（`rules/R3-consistency.md`）

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R3-01 | major | both | 書く前に同 feature の既存同種ファイルを読み、その流儀を真似ているか |
| R3-02 | minor | code | 依存の渡し方で変数宣言と inline を混ぜていないか |
| R3-03 | minor | code | DI フィールド順が database → repo → service か。New 引数・リテラルも同順か |
| R3-04 | minor | code | 同一ファイル内に慣用形があるのに独自の if-init を持ち込んでいないか |
| R3-05 | major | both | 少数派パターンを (a)限定用途 /(b)意図的例外 /(c)単純な不整合 に分類したか（修正対象は c のみ） |
| R3-06 | blocker | both | 慣習を踏襲する前に「その慣習が成立している条件」を特定し、新ケースが満たすか照合したか |
| R3-07 | minor | both | 同種の関数（matcher 等）の置き場所が usecase 側と共通側に散らばっていないか |
| R3-08 | major | both | ユーザー可視文字列を造語していないか（コードベース全体に grep して照合したか） |
| R3-09 | minor | both | 特定文脈専用の関数に汎用的に見える一般名を付けていないか |
| R3-10 | minor | code | map/set の命名規則（`vByKey` / `vsByKey` / `{Key}Set`）に従っているか |
| R3-11 | minor | code | コード再説明・出所付記・実況コメントを書いていないか（**非自明なドメイン知識は残す**） |
| R3-12 | minor | both | 命名・分割・制御フローが読み手の認知負荷を下げているか |
| R3-13 | major | design | 並列作業の規約に、交差点で両立しない指示が同居していないか（依存グラフで洗ったか） |

## R4: 裏取り・調査の網羅性（`rules/R4-verification.md`） — **厳しめに倒す**

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R4-01 | blocker | both | 着手前に現状の仕様・既存実装をコードで確認し、依頼の前提が事実か裏取りしたか |
| R4-02 | blocker | both | 網羅性を主張する検索で `head`/`limit` により出力を打ち切っていないか |
| R4-03 | major | both | 書き込み経路の調査に、DB デフォルト値・`ON UPDATE`・トリガ・外部投入を含めたか |
| R4-04 | blocker | both | 「使われていない」を識別子検索だけで確定していないか（文字列リテラル経由も見たか） |
| R4-05 | blocker | both | マーカー依存の洗い出しをメソッド名 grep で済ませていないか（引数単位・判定テーブルを開いたか） |
| R4-06 | major | both | 「無変更で安全」の根拠が“未使用”か“業務側の約束”かを書き分けたか |
| R4-07 | major | both | レビュー指摘への訂正文に含まれる新しい事実主張を、一次情報で確認したか |
| R4-08 | major | both | 「先例あり」の先例が、同じ機構・同じ呼び出し形か。「機構が存在する」だけではないか |
| R4-09 | major | design | 「無変更で確認済み」リストがリポジトリ全体の grep に基づくか。権威をドキュメントで先に確認したか |
| R4-10 | blocker | both | 採用するフックの**型シグネチャ**（戻り値・引数の型）を読んだか。名前から機能を推定していないか |
| R4-11 | minor | design | 「直すと何が良くなるか」の便益主張を、ORM/DB のセマンティクスまで降りて確認したか |
| R4-12 | blocker | design | 上流タスクが「下流側の設計事項」として委譲した論点を、下流の前提節に転記したか |

## R5: テスト・検証力・検証手順（`rules/R5-testing.md`） — **厳しめに倒す**

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R5-01 | major | both | **ビジネスロジックの変更にはテスト必須**。それ以外は「壊れたとき何が検出するか」が特定できるか |
| R5-02 | major | code | `gomock.Any()` を第1引数（context/db）以外に使っていないか |
| R5-03 | major | code | 各 mock の EXPECT が単体で成立しているか（他 mock の ret/args を流用していないか） |
| R5-04 | major | code | 共有テストヘルパの不具合を per-test の回避策で凌いでいないか。matcher の `Matches` は冪等か |
| R5-05 | major | both | **実装から当該変換を外すとテストが FAIL するか実測したか**（比較器の意味論で検出力ゼロでないか） |
| R5-06 | major | both | 非決定要素（時刻／乱数／採番／外部応答）を列挙し、注入の論拠を全部に適用したか |
| R5-07 | blocker | design | 検証手順のフラグ・パラメータ・パスが実装側に実在するか1件ずつ確認したか |
| R5-08 | blocker | design | composite action / 再利用 workflow の `inputs.*.default` まで辿ったか（checkout の `ref` 特に） |
| R5-09 | major | design | 検証環境の「入力データの実在」と「受入基準の母数の同一性」を確認事項に立てたか |
| R5-10 | major | design | 完了ゲートの探索範囲に、そのタスクで新規に作るファイルが入っているか |

## R6: 設計判断・多角的検討・スコープ・ドキュメント記述（`rules/R6-decision.md`）

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R6-01 | major | design | **1案しか出ていない設計は比較材料の欠如として問う**。代替の構造・方式を俎上に載せたか |
| R6-02 | major | design | 多角的検討の論点が表現・機構に偏っていないか（**判定条件が単一案なら検討は始まっていない**） |
| R6-03 | major | design | 「実現不能」で選択肢を消していないか（「生成物に無い」と「生成できない」は別） |
| R6-04 | major | both | 前提が消えたのに、その前提で得た許可・結論を持ち越していないか |
| R6-05 | major | design | 設計判断の「なぜ」を実装機構で説明していないか（要件・制約から導いているか） |
| R6-06 | blocker | design | 方針変更を全箇所に伝播したか。**決定を記録するセクションに旧方針が残っていないか** |
| R6-07 | major | design | 要件↔設計の対応表の各行を成果物の実体と突き合わせたか（「すべて〜で満たす」と書いていないか） |
| R6-08 | blocker | both | 具体値（ドメイン・URL・数値・パス）が実物を見たものだけか（**捏造していないか**） |

## R7: 移行・既存挙動の保存（`rules/R7-migration.md`）

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R7-01 | blocker | both | 参照実装の逐語コピーで、対象固有のフィルタ・分岐・型意味論の差を落としていないか |
| R7-02 | blocker | both | 取得方式の変更で「ローディングの見え方」「状態の保持スコープ」が変わることを裏取りしたか |
| R7-03 | major | both | 成功トーストの発火点が前にずれ、「成功通知＋沈黙の失敗」の窓が生まれていないか |
| R7-04 | blocker | both | キャッシュキーの統合で、「別キャッシュであること」に依存した差分計算が壊れていないか |
| R7-05 | blocker | both | キャッシュ寿命の延長で「マウント時に一度だけ確定する値」が凍結しないか（`isPending` でゲートしていないか） |
| R7-06 | blocker | both | `<Suspense>` の担当範囲を JSX の入れ子で判定していないか（取得フックの位置で決まる） |
| R7-07 | blocker | both | 外部マスタの形式変更で、属性値の変化と**主キーの連続性**を別項目として立てたか |
| R7-08 | blocker | both | 主キーの「集合の同一性」と「書式の同一性」を2問に分けたか |
| R7-09 | major | both | 値の突合（属性の検証）と、ドメイン判定の入力として成立するかの検証を分けたか |

## R8: データ・安全性・権限・リリース制御（`rules/R8-safety.md`） — **厳しめに倒す**

| ID | sev | scope | 一行判定 |
|---|---|---|---|
| R8-01 | major | both | fail-closed の宣言テーブルのキー名を、実定義を開いて写したか（**間違っても例外にならない**） |
| R8-02 | major | design | 閲覧権限を「その操作を実行できる主体の集合」と突き合わせたか。要件の主対象者に届くか |
| R8-03 | blocker | design | フラグが入口だけでなく**導線を含む全経路**に掛かっているか |
| R8-04 | blocker | design | 設定値の供給経路を環境ごとに列挙したか（E2E / CI が別経路のことが多い） |
