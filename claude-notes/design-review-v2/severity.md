# severity 判定基準

各ルールは既定 severity を持つが、**最終的な severity は「そのコンテキストで何が起きるか」で決める**。
ルールの既定値は出発点であり、下記の定義に照らして上下させてよい（上下させた場合は `why_violation` にその理由を書く）。

---

## blocker — マージ／着手させてはいけない

次のいずれかに当たるもの。

- **データが壊れる / 復旧に運用作業が要る**（マスタ全件の論理削除、キー体系の破壊、金額・在庫の誤り）
- **セキュリティ・権限の穴**（認証をすり抜ける、権限の無い主体が到達できる、PII が露出する）
  - ⚠️ **この判定基準は本ルーブリックの `rules/` には無い。** 認証バイパス・脆弱性・PII 露出の判定は、独立した `review-security` エージェントが担当する（本ルーブリックが扱うのは R8-02 の権限設計と R2-06 の fail-closed 適用範囲まで）。
  - design-review-v2 のレビュアーは、セキュリティ上の懸念を見つけたら `rule_id: "NEW"` として報告し、**`review-security` に回すべき旨を添える**。無理に既存 ID に当てはめない。
- **設計の土台が誤っている**（前提が事実と逆・調査の網羅性主張が崩れている等、**その上に乗る設計判断が丸ごと失効する**もの）
- **レイヤー・依存方向の崩壊**（放置すると後続がその崩れた形を踏襲する）
- **成果物が要件を満たさない**（要件の主対象者に届かない、機能が発火しない）

判定の目安: **「マージ後に気づいた場合、コード修正だけでは戻せないか？」** Yes なら blocker。

## major — 直さずに進めてはいけない

- 一貫性・責務の逸脱。今直せば安いが、放置すると**周囲がそれを先例として踏襲し伝播する**
- 既存の共通資産（変換関数・共通 helper）を再発明している
- テストが書かれているが**検証力がゼロ**（実装を外しても通る、骨抜き matcher）
- 稀だが実在する経路で挙動が反転する（成功通知＋沈黙の失敗など）
- ドキュメントの事実誤認のうち、**意思決定材料（選択肢の比較表・天秤）に混入しているもの**

判定の目安: **「これを先例として次の実装者が真似たら困るか？」** Yes なら major。

## minor — 直すべきだが、単独で進行を止めない

- 可読性・命名・コメント・整形
- スタイルの好み、局所的な最適化の余地
- 影響が1箇所に閉じており、伝播しない逸脱

## question — 違反と断定せず、判断を問う

**P5（リスク・影響とメリットの天秤）に属するもの。** 機械照合できない領域。

- 「この変更のリスクとメリットの天秤はどう取ったか」が記述されていない
- ルール同士が衝突しており（例: DRY vs 前提特化、既存踏襲 vs 新方式）、どちらの結論もあり得る
- 実装者の判断が妥当かもしれないが、**判断した形跡が残っていない**

**question は「指摘」ではなく「問いかけ」。** 実装者に説明を求め、判断の妥当性は最終的にユーザーが決める。
`question` を「弱い指摘」の意味で使わない — 違反だと言えるなら minor 以上を付ける。

## 観点別の重み付け

観点によって同じ現象でも重みが違う。以下は既定の傾き。

> **出典の明示**: R5 の「テストは最後の砦」は、pointpf-api の `review-testability` エージェント定義に書かれた実在の方針を汎用化したもの。
> **R4 / R8 / R3 の傾きは v2 作成時の設計判断であり、ユーザーからの指摘の蓄積に由来するものではない。** 妥当でなければ変更してよい。

| 観点 | 傾き | 理由 |
|---|---|---|
| R5（テスト・検証力） | **厳しめに倒す** | テストはコーディングエージェントの品質を担保する最後の砦。「テストがある」という体裁が検証を止めるため、骨抜きテストは無いテストより悪い |
| R4（裏取り・調査の網羅性） | **厳しめに倒す** | 「確認済み」というラベルは後続の再検証を止める。誤りが下流の設計判断をまるごと歪める |
| R8（データ・安全性） | **厳しめに倒す** | fail-closed の誤りは例外にならず静かに壊れる。壊れたことに気づく手段が無い |
| R3（一貫性・命名・可読性） | **控えめに倒す** | 伝播はするが、発見も修正も安い。ただし「周囲と揃っていない」が**規約違反**なら major |

## 他のレビュー系エージェントとの尺度の対応

`code-review-local` 系のエージェント（`review-security` / `review-performance` 等）は **0〜100 点**の尺度を使う。
両方を回したとき優先度を比較できるよう、目安の対応を示す。

| 0-100 点（code-review-local） | 本ルーブリック |
|---|---|
| 90-100（重大） | blocker |
| 80-89（重要） | major |
| 60-79（中程度） | minor |
| 0-59（軽微） | 採用しない |

**これは目安であり、変換規則ではない。** 点数帯の定義はプロジェクト側のエージェント定義に属するもので、本ルーブリックの severity 定義（上記の「回復コスト」「伝播するか」の観点）とは判定軸が違う。
**併用時に「どちらを先に直すか」を並べるためだけに使い、severity をこの表で機械的に付け替えない。**

## confidence（severity とは独立）

- **high**: 対象コード／文書の記述から直接読み取れる。`evidence` に該当箇所を引用できる
- **medium**: 実装を読んだ上での推論。前提が1つ入っている
- **low**: 状況証拠のみ。**憶測で "問題あり" と書かない** — low を付けるくらいなら、指摘ではなく `question` にする

`confidence: low` かつ `severity: blocker` は原則あり得ない。断定できないものを blocker にしない。
