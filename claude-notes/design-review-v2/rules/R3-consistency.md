# R3: 一貫性・規約踏襲・命名・可読性

多くの設計ミスは「既存を見る前に書き始めた」ことに起因する。
ただし**既存踏襲も新方式もそれ自体は正義ではない**（R6-01 と対で使う）。
衝突は P5 に上げる。**P5 は結論を決めない** — 天秤にかけずどちらかを機械適用した設計が指摘対象であり、天秤にかけた上での結論はどちらでも可（判断が記述されているか、を見る）。

---

### R3-01: 書く前に読む。同 feature の既存同種ファイルの流儀を真似ているか
- severity: major
- scope: both
- tags: universal, 一貫性
- 由来: ユーザー判断
- 判定: 新規 usecase / factory / repo / 変換を書く前に、**同 feature の既存同種ファイルを読み、その流儀を真似ているか**。
  - 周囲と**違う**書き方をしているなら、それは意図的な逸脱か、単に読まずに書いたのか。
  - 周囲と**揃っている**場合も、「**意図的な追随か、それとも既存を唯一の前提に固定したのか**」を問う。**既存踏襲はそれ自体では正当化にならない**（→ R6-01）。
  - この両方向を問うのは、R6-01（多角的検討）が `scope: design` のため**実装 diff のレビューでは発火しない**から。片側（既存に揃っていない）だけが検出される状態を避ける。
- 理由: 多くの設計ミスの根本原因。周囲と揃っていれば読み手の負担が減り、レビューでも引っかからない。

### R3-02: DI・呼び出しの書き方をコードベースの流儀に一貫させる（変数宣言 vs inline を混ぜない）
- severity: minor
- scope: code
- tags: universal, go, 一貫性, 可読性
- 由来: ユーザー指摘
- 判定: コンストラクタへの依存の渡し方で、**変数宣言と inline `NewXxx()` を混ぜていないか**。周囲の同種コードの流儀に合わせているか。
- 理由: 混在は読みにくく、レビューで必ず引っかかる。
- 具体例: u1-api GN-5811。factory で一部 repo を inline `NewXxx()` で渡し他は変数、と混在させて「書き方がやばすぎ」と指摘された。

### R3-03: DI 構造体のフィールド順は database → repo → service。New 関数・構造体リテラルも同順
- severity: minor
- scope: code
- tags: go, 構造, 可読性
- 由来: ユーザー指摘
- 判定: フィールド順が `database` → repo 群 → service 群になっているか。**`New` 関数の引数順と構造体リテラルの順が、構造体フィールドと同一**か。既存に service を足すとき repo 群の中に挿入していないか。
- 理由: 種別ごとに並ぶと依存の構成が一目で読める。位置引数の構造体リテラルでは並びがズレると別フィールドに代入され事故になる（型が合えばコンパイルも通る）。
- 具体例: u1-api GN-5760。Worker が mutation サービスを repo 群の中に挿入していたのを指摘され、service 群（末尾側）へ移動した。

### R3-04: エラーハンドリングは既存コードの慣用形に合わせる。独自の if-init パターンを新規に持ち込まない
- severity: minor
- scope: code
- tags: go, 可読性, 一貫性
- 由来: ユーザー指摘
- 判定: 同一ファイル内に慣用形があるのに、独自の長い if-init 形式（`if localErr := call(); localErr != nil && !errors.Is(...) { ... }` 等）を新規に持ち込んでいないか。
- 理由: 独自パターンは「なぜここだけ違うのか」を考えさせる。**同一ファイル内に既に慣用形があるなら必ずそれに合わせる。**
- 具体例: u1-api GN-5760。recent/archive の Delete で独自形を書き「こんな書き方をしているコードがあるか？」と指摘された。同ファイル内の他の Delete は全て `if errors.Is(err, X) { err = nil }; if err != nil { return }` の慣用形だった。

### R3-05: 「少数派パターン」は3種類に分類する。少数派＝不整合ではない
- severity: major
- scope: both
- tags: universal, コード分析, 規約
- 由来: ユーザー判断
- 判定: 「規約から外れたコード」を検出したとき、機械的に多数派へ揃えようとしていないか。必ず次の3つに分類したか。
  - **(a) ユースケース限定型**: そのパターンを必要とする文脈がそもそも限られている。数が少ないのは当然で正しい → Guideline に「この文脈でだけ使う」と明記する対象
  - **(b) 意図的な例外**: 例外として意図して対応しているケース → Guideline に「これは例外」と明記する対象
  - **(c) 単純な不整合**: 書き方が揃っていないだけ → **修正対象はこれだけ**
- 理由: (a)(b) を機械的に「少数派だから直す」とすると正しい設計を壊す。(a)(b) は消すのではなく「なぜ少数なのか」を明文化する。
- 補足: 規約の棚卸しはサンプルでなく**全コードを列挙して**行う（全件列挙 → バリアントにクラスタ → (a)(b)(c) に分類）。
- 関連: R4-02（検索を打ち切ったまま網羅を主張しない）

### R3-06: 慣習を踏襲する前に「その慣習が成立している条件」を特定する
- severity: blocker
- scope: both
- tags: universal, 規約, 裏取り, 移行
- 由来: ユーザー指摘
- 判定: 「他がこうしているから同じにする」で決めていないか。
  - 慣習が**なぜ壊れずに回っているのか**（明示されていない前提条件）を特定したか
  - **新しいケースがその条件を満たすか**を照合したか。満たさないなら慣習から外れるのが正しく、外れることを設計判断として明記する
  - 判明した成立条件を**コード外の文書だけに書いていないか**。API 契約・型・関数名など、次の実装者が必ず見る場所に残す
- 理由: 成立条件を確認していない踏襲は**条件が崩れる最初のケースで破綻する**。しかも既存と同じ書き方なので、レビューでも「既存踏襲」として見過ごされる。
- 具体例: u1-api GN-5899。この API は日時を「JST の壁時計を UTC ラベル（`...Z`）で返す」慣習だったが、フロントが絶対時刻として解釈するため、この慣習は**時刻部が常に `00:00:00` だから**成立していた。時刻を含む値を同形式で返していた2箇所は実際に9時間ずれ、うち1件は「実査日が JST 15:00 以降で翌日表示」という実バグだった。新規フィールドは慣習に合わせず `+09:00` 付きで返し、成立条件を OpenAPI の description に明記した。

### R3-07: 同種の関数（matcher 等）の置き場所は分散させず一箇所に統一する
- severity: minor
- scope: both
- tags: universal, 一貫性, 構造
- 由来: ユーザー指摘
- 判定: 同種の関数（matcher・比較関数など）が、usecase 側と共通側に散らばっていないか。どちらか一方に統一されているか。
- 理由: 置き場所が揃っていれば、どこに同種の判定があるか一目で分かる。ジェネリクスだと散らばりやすい。
- 具体例: u1-web GN-5832。`matchesPlanPoint` が共通側にある一方 `matchesMeterReadPoint` は usecase 側にあり、「一貫性大事、どちらかに統一」と指示され共通側に揃えた。

### R3-08: ユーザー可視文字列（ラベル / ボタン / メッセージ）を造語しない
- severity: major
- scope: both
- tags: universal, react, 規約, 可読性
- 由来: ユーザー指摘
- 判定: **文字列を発明していないか。** 実装前に同種 UI の文言をコードベース全体で grep し、以下を照合したか。
  1. 圧倒的多数の定型があるか
  2. 同一画面・同一機能ファミリの兄弟が何を使っているか
  3. 意味的に最も近い先行実装が何を使っているか
  - 複数系統が競合する場合、どれに揃えるべきかを**ユーザーに確認**する。既存文言のどれも意味が合わない場合も、勝手に新語を作らない。
- 理由: UI 文言は製品の一貫性そのもの。造語や近くの1例からのコピペは、同一系統の他所と食い違い、「他のコードを一切見ていない」と映る。行番号や型と違い**ツールで自動検証されない**ぶん、明示的に grep 照合しないと必ず捏造が紛れる。
- 具体例: u1-web GN-5831/5832。絞り込みラベルを実績フロアマップから借りて `"ブース・景品検索"` としたが、同系統の兄弟も同一画面も `"絞り込み"`（約35ファイル）だった。続く GN-5832 では `"プライズ機種名検索"` という**コードベースに存在しない造語**を定義書に書き、「勝手に定義」「他のコードを一切見ていない」と指摘された。
- 関連: R6-08（具体値は実物を見たものだけ書く）

### R3-09: 共有ヘルパの名前は用途スコープを名前に込める（汎用に見える名前を避ける）
- severity: minor
- scope: both
- tags: universal, 命名, 可読性
- 由来: ユーザー指摘
- 判定: 特定の文脈専用の関数に、汎用的に見える一般名（`isSearchEmpty`, `format`, `validate` 等）を付けていないか。名前で「これは○○専用」と分かるか（`isFloorMapSearchEmpty`）。
- 理由: 名前は最初のドキュメント。スコープを名前に込めると、無関係な文脈での流用を名前の時点で抑止できる。
- 具体例: u1-web GN-5833。`isSearchEmpty` を「このままだと他のリスト形式の絞込みでも使うものに見える」と指摘され `isFloorMapSearchEmpty` にリネームした。

### R3-10: map / set の命名規則に従う
- severity: minor
- scope: code
- tags: universal, 命名
- 由来: ユーザー判断
- 判定: `map[K]V` → `vByKey` ／ `map[K][]V` → `vsByKey` ／ set は `{Key}Set` 等の規則に従っているか。複数形/単数形の違い・返り値型違いで紛らわしい命名を新設していないか。
- 理由: 型が名前から読めると、宣言に戻らずに読める。

### R3-11: コメントは非自明な WHY だけを書く
- severity: minor
- scope: code
- tags: universal, 可読性, コメント
- 由来: ユーザー指摘
- 判定: 次を書いていないか。
  - (a) 型名・変数名・処理をそのまま言い換えただけの説明
  - (b) 出所・由来の付記（「実績に倣う」「〜と同じ重ね方」）
  - (c) アクションの実況（直後のコードが言っていること）
  - **同じ WHY を複数の呼び出し側に重複させていないか** — 共有関数の使用理由は定義側に1回だけ書き、呼び出し側は関数名で参照到達させる
  - 周辺コードのコメント密度に合っているか
- 理由: 冗長コメントは可読性を下げ、コードとズレて陳腐化する。
- 注意（**過剰削除も指摘対象**）: 型や近接コードから読めない**ドメイン知識**（例: 「検索語＝プライズ機種名で、それが `boothName` に対応する」）は、1行でも WHY として残す。**「再説明か WHY か」の線引きが判断の核。**
- 具体例: u1-web GN-5833。型を言い換えたコメント・出所の付記・重複した WHY を削除し、WHY は定義側へ集約。一方で非自明なドメイン理由は minor 指摘を受けて1行に圧縮して復活させた。

### R3-12: 可読性を常に意識しているか
- severity: minor
- scope: both
- tags: universal, 可読性
- 由来: ユーザー判断
- 判定: 命名・関数分割・整形・制御フローが、読み手の認知負荷を下げているか。「動く」だけで「読みやすい」が後回しになっていないか。
- 理由: P1 の直接の適用。

### R3-13: 並列作業の規約は、指示同士が実依存グラフ上で衝突しないか突き合わせてから配る
- severity: major
- scope: design
- tags: universal, 一貫性, 並列実行
- 由来: ユーザー指摘
- 判定: 複数エージェント／複数人が同一規約に従って並列作業する計画で、**単体では正しいが交差点で両立しない指示**（「担当範囲外を触るな」と「触ったディレクトリ内は全部揃えろ」等）が同居していないか。
  - 規約を配る前に、指示同士の交差点を**実依存グラフ（import / 参照関係）で洗った**か
  - 衝突が1件でもあれば (a) 例外を名指しで明記する (b) どちらかの適用範囲を狭める、のどちらかで曖昧さを残さない。「常識で判断せよ」に委ねない
- 理由: 並列実行者は衝突に気づいても**その場で黙って一方を選ぶ**（聞き返すコストが高く、どちらも規約に書いてあるため「破った」自覚も生じない）。選択は実行者ごとに割れ、一貫性の欠如として後段でまとめて表面化する。
- 具体例: u1-web GN-5901。「触った `-components/` 内の PascalCase は全て kebab-case にリネーム」と「担当ディレクトリ外を変更しない」を併記し、リネーム例に挙げたファイルがまさに担当外ファイルと**相互 import** していた（`src` 全体で routes→organisms の逆方向 import はこの1件のみ）。名指しの例外として明記して解消した。
