# R7: 移行・既存挙動の保存

移行タスクは「ロジックが同じなら挙動も同じ」と書かれがちだが、**実現方式が変わると見え方・状態寿命・キャッシュ境界が静かに変わる。**
型が通り、テストが通り、画面も描画されるため、退行が検出されない。

---

### R7-01: 参照実装をテンプレとして踏襲するとき、対象固有のロジック／分岐／ガードの脱落を差分で洗い出す
- severity: blocker
- scope: both
- tags: universal, react, 構造, 仕様忠実
- 由来: ユーザー指摘
- 判定: 既存の「兄弟」実装をテンプレにして移行・再構成するとき、**逐語コピーせず対象固有の要素との差分を明示的に洗い出した**か。とくに
  1. 対象だけが持つ**フィルタ／除外条件**
  2. 対象だけの**分岐・ガード**
  3. 参照側と**データ型の意味論が違う点**（例: 常に配列 vs 未取得 undefined）
  - 参照実装との**非対称は「固有責務のシグナル」**であり、揃えて消すのでなく意図として残す。定義書には「参照と非対称になる箇所」を固有理由付きで列挙する
- 理由: 参照実装は「型」であって「仕様」ではない。テンプレ化は速いが、対象固有の業務ロジックは参照側に無いため**沈黙して落ちる**（コンパイルは通るので気づきにくく、退行として本番で出る）。落ちるのは往々にして「その画面だけの例外扱い」＝業務上重要な分岐。
- 具体例: u1-web GN-5704。参照実装 material の導出 atom をそのまま真似る設計を書いたが、prize 側は `.filter(p => p.placementName !== '荷捌き')` と**荷捌きを明示除外**する prize 固有ロジックを持っていた（UI「荷捌きは棚卸未完了でも確定可能」を支える）。逐語コピーしていたら確定不可の退行になっていた。併せて「参照 atom は未取得 undefined を返すのに、現行判定は常に配列前提」の型意味論差も指摘された。
- 関連: R1-03（非対称は責務分布のシグナル）、R3-08（兄弟からの借用時の照合）、R3-11（参照踏襲時に不要物を"増やす"逆方向の失敗）

### R7-02: データ取得の移行では「取得の実現方式」ごとに変わる挙動をコードで裏取りする
- severity: blocker
- scope: both
- tags: universal, react, tanstack-query, 挙動保存, 移行
- 由来: ユーザー指摘
- 判定: 「現状こう見えているはず」を憶測で書いていないか。次の2軸は移行で暗黙に変わりやすい。
  - **ローディング／エラーの見え方**: Suspense 方式（未取得時に Promise/例外を throw し上位の `<Suspense fallback>` がスピナーを出す）と、非 Suspense の `useQuery`（throw せず `data=undefined` を返す）では、**何もしないと空表示のちらつき**になる。`isPending` を明示的にローディング UI へ接続して初めて現行の見え方が保てる
  - **状態の保持スコープ**: module-scope の Jotai `atom` はアプリ生存中値が残り**画面離脱→再訪で保持**される。`useState` はアンマウントで**リセット**。「単一コンポーネントに集約されたから useState でよい」と機械的に倒すと、cross-navigation 保持という既存挙動を黙って壊す
  - 参照実装踏襲時は、対象固有の「保持要否」「Suspense か否か」を差分で洗い出したか
- 理由: データ取得の移行はロジックだけでなく**見え方と状態寿命**を静かに変える。テストや typecheck は通っても、スピナーが消える・フィルタが再訪で飛ぶといった退行は動かして初めて分かる。裏取りせず「現行維持」と書くと、その一文が誤った実装ガイドになり**退行を承認済みの顔で通す**。
- 具体例: u1-web GN-5883。定義書に「現行は取得中に空テーブルが一瞬見える／現行挙動を維持」と憶測で書いたが、実際は `useResource` の throw → 上位 `<Suspense fallback={<LoadingBox/>}>` でスピナー表示（**前提が事実と逆**）。さらに日付範囲を `useState` に倒しかけたが、元は module-scope atom で画面再訪時も保持される挙動だった。

### R7-03: submit 移行では「成功トーストの発火点」と「mutation 後の命令的後処理」の分離を意識する
- severity: major
- scope: both
- tags: universal, react, tanstack-query, 挙動保存, エラーハンドリング
- 由来: ユーザー指摘
- 判定: 旧送信（`useSubmitting` の `submitPromises` 等）から `useXxxMutation` + `MutationCache`（`meta.subject` でトースト集約）へ移すとき、
  - **成功トーストの発火点が移行で前にずれる**ことを把握したか。`useSubmitting` は `promise` 全体（patch + 後処理）が resolve して初めて成功トーストを出す＝**patch と後処理が1つの成功単位**。`MutationCache.onSuccess` は **patch 成功時点で即発火**し、`mutateAsync` の外に置いた後処理とは切り離される
  - この分離により **「成功通知＋沈黙の失敗」** が生まれる: ①成功トースト表示済み ②後処理の例外が unhandled で伝播 ③mutation 自体は成功のため error トーストは出ない ④後処理が担う状態更新は未達
  - 対処の選択肢を明示的に俎上に載せたか: (a) 後処理を mutation の成功単位に載せ直す (b) 後処理をやめて mutation の入力値で楽観更新 (c) 稀ケースとして**既知の許容差分**と文書化し "behavior-preserving" の文言を成功経路に限定する。いずれにせよ**失敗経路を設計に書く**
  - **後処理が失敗しうる I/O（再取得 GET 等）かどうか**を差分で見たか（参照実装の後処理が `router.history.back()` のような fallible でない処理だと、この罠は顕在化しない）
- 理由: 送信移行はトーストをロジックから `MutationCache` へ剥がすため、**「いつ成功と告げるか」の時点が移動する**。この時間差に後処理を挟むと、成功を告げた後に静かに失敗する窓が生まれる。テスト・typecheck は通り、成功パスの手動確認でも見えない。
- 具体例: u1-web sales-reports.settings。3 mutation が現行 `patch → getArcade 再取得 → setArcade → onClose` を1成功単位で実行していたが、移行すると成功トーストが patch 直後に発火し、後続 GET が失敗すると「成功トースト＋error トースト無し＋atom 未更新」に反転する（major 指摘）。

### R7-04: キャッシュ層を移行するとき、「別キャッシュであること」に依存したロジックが壊れていないか確認する
- severity: blocker
- scope: both
- tags: universal, react, 移行, データ
- 由来: ユーザー指摘
- 判定: 呼び出し側がキーを自由に決められる自前キャッシュから、キーが自動正規化される仕組み（TanStack Query の `queryKey` は API パス＋params から生成）へ移行するとき、
  - **同一 API を複数箇所から取得し、かつ取得結果どうしを突き合わせている実装**を探したか（差分表示・before/after 判定・「移動した数」のような計算）
  - キーに**コンポーネント名などの人工的な接頭辞**が入っていたら、それは「意図的に分離した」というシグナル。コメントが無くても分離の意図を疑う
  - キーが統合されると、片方の `refetch` がもう片方の観測値も更新する。**before と after が同一データ由来になり、差分が恒久的に 0 になる**。ローディングのゲート（`isFetching` 等）では防げない（過渡現象ではない）
  - 移行先が queryKey の上書きに対応しているかを**生成コードで確認**したか
- 理由: キャッシュキーは「性能・再取得のための実装詳細」と見なされやすく、**それが機能要件を支えていることが視野から落ちる**。統合しても型は通り、テストも通り、画面も描画されるため、差分が 0 になっていることに気づけない。
- 具体例: u1-web GN-5901 Phase 2。`MaterialStockDetails.tsx:106` が `resourceKey` に人工接頭辞を付けて子コンポーネントと分離しており（FIXME コメントで理由を明記）、「移動した数」は親＝移動前 / 子＝refetch 後＝移動後の差分で成立していた。デフォルト queryKey に任せると**恒久的に 0** になる。設計時は「一瞬 0 が見える過渡現象」と誤認し `isFetching` ゲートで対処するとしていた。
- 関連: R6-03（同一タスクで「queryKey を分けるのは不可能」と却下理由を書いていた）、R4-08（その訂正で挙げた「先例2件」も誤りだった）

### R7-05: キャッシュ寿命が変わると、「マウント時に一度だけ確定する値」が古くなる
- severity: blocker
- scope: both
- tags: react, 移行, データ
- 由来: ユーザー指摘
- 判定: アンマウント時にキャッシュを破棄する取得層から、`gcTime` 等でキャッシュを保持する層へ移行するとき、とくにモーダル・ウィザードのように**開閉を繰り返すコンポーネント**について、
  - `useForm({ defaultValues, resolver })` / `useState(初期値)` / `useMemo(..., [])` のような**マウント時に一度だけ確定する値**があるか探したか
  - 旧実装がアンマウント時にキャッシュを捨てていたなら、**「開くたびに必ず最新」が暗黙の前提**になっている。移行後は2回目以降キャッシュヒットし、`isPending=false` で即マウントされて**古い値が凍結する**
  - ゲートに **`isPending` ではなく `isFetching` を使った**か（あるいは `reset()` で追随させる）。`isPending` は「キャッシュが無い」しか見ないため再取得中を素通りする
  - react-hook-form では `resolver` は毎レンダー更新されるが **`defaultValues` は追随しない**（`reset` 時のみ）
- 理由: 初回だけ動作確認すると必ず通る。2回目以降にしか出ず、しかも「古い値が入っている」だけでエラーにならないため、レビューでもテストでも捕まりにくい。
- 具体例: u1-web GN-5901 Phase 2。移動モーダルのゲートを `isPending` にすると、同一画面で閉じて開き直したときキャッシュヒットして移動前スナップショットのままマウントされ、`defaultValues` と `zodResolver(createValidationSchema(...))` が旧在庫で固定される。入力欄が実在庫より大きい値でプリフィルされ、保存すると弾かれる。
- 関連: R7-04（キーの話。本項は**寿命**の話で別軸）

### R7-06: `<Suspense>` の担当範囲は、JSX 上の位置ではなく「suspend するフックがどのコンポーネントで呼ばれているか」で決まる
- severity: blocker
- scope: both
- tags: react, 移行
- 由来: ユーザー指摘
- 判定: Suspense 方式から非 Suspense へ移行し `<Suspense>` を撤去する設計で、
  - **`<Suspense>` は、それを返しているコンポーネント自身の suspend を捕捉しない。** React は suspend したコンポーネントより**上位**の最も近い boundary で捕捉する
  - 「この `<Suspense>` が内包しているクエリ」を JSX の入れ子だけで判定していないか。**取得フックがどのコンポーネント本体で呼ばれているか**を1件ずつ確認したか
  - 自コンポーネントで取得している場合、実際に出ているのは**上位（レイアウト等）の fallback** であり、見え方は「ローカルのスピナー」ではなく「見出しごとコンテンツ全体の差し替え」になる
- 理由: 「`<Suspense>` の中に書いてあるものが対象」という直感が強く、JSX を読むだけだと正しく見えてしまう。誤ると「現行に存在しない見え方」を再現しようとして、ローディング表示の互換性要件を静かに破る。
- 具体例: u1-web GN-5901 Phase 2。`MaterialMoveToMachine.tsx:128` の `<Suspense>` が同ファイル `:93` の取得を内包していると誤認したが、`:93` は `<Suspense>` を返す当のコンポーネント本体にあり、捕捉していたのは `MainContentLayout.tsx:76` の boundary だった。設計書が書いた「見出しは残して内側だけスピナー」は現行に存在しない挙動だった。**同じファイル群でも箇所ごとに違う**（同タスクの Prize 系6箇所は JSX どおりで正しかった）。

### R7-07: 外部マスタの「形式変更」を評価するとき、属性値の変化と主キーの連続性を別次元として扱う
- severity: blocker
- scope: both
- tags: universal, 移行, データ
- 由来: ユーザー指摘
- 判定: 外部システムが供給するマスタの形式変更で、
  - 影響を「どの項目の値がどう変わるか」だけで洗っていないか。**主キーそのものが変わる可能性**を別項目として立てたか
  - キーが変わりうるなら、**FK 参照数・論理削除の発火条件・履歴テーブルへの波及**を数えたか
  - 洗い替え型の取込バッチは「ファイルに存在しないキー＝削除」を実装していることが多い。**採番体系の変更は、そのロジックにとって「全件削除＋全件新規」と区別がつかない**
  - 上流が「過去データも全部移行する」と言っていても、それは**行の網羅性の話であってキーの同一性の保証ではない**
- 理由: 「形式変更」という言葉が属性のフォーマットを連想させるため、キーの話が議題に上がらないまま設計が進む。しかも取込バッチは正常に動き、エラーも出さずにマスタを総入れ替えする。
- 具体例: u1-api 統合景品マスタ TOBE 対応（Access→Kintone）。変更点はサイズ区分表記・分類の追加・ハイフンの全半角で「コード変更ゼロで追従」と結論したが、取込バッチは新ファイルに無い `prize_cd` に `deleted_at` を立てる実装で、採番体系が変われば**既存マスタ全件が論理削除**される。`prizes.prize_cd` は 27 箇所の FK 参照先だった。購買データ側では同種の懸念を確認事項に立てていたのに、マスタ側だけ落ちていた。

### R7-08: 主キーは「集合の同一性」と「書式の同一性」を別問として立てる
- severity: blocker
- scope: both
- tags: universal, データ, 移行
- 由来: ユーザー指摘
- 判定: 主キーを別ソースの項目に読み替えるとき、
  - 主キーの**書式**（前置コードによる品目分類、正規表現、例外コードの完全一致リスト）が業務ロジックの入力になっていないか
  - **キー集合が完全に同一でも書式が変われば分類ロジックが壊れる**し、逆に**書式が同じでも集合が変われば FK 参照が孤児化する**。壊れ方も対処も全く違う
  - 「同一キー体系ですか？」の1問では両方を取りこぼす。**(a) 同じ行が同じキーで来るか (b) キーの書式（前置・桁・例外値）が同じか**の2問に分けたか
  - とくに**例外コードの完全一致リスト**は、キーが1文字変わるだけで**エラーを出さずに静かに外れる**ため、受入基準に件数チェックを必ず入れる
- 理由: 主キーの読み替えは「対応表が埋まれば終わり」と見なされやすいが、キーは識別子としての役割（集合）と、分類情報を埋め込んだ符号としての役割（書式）を兼ねていることがある。後者は対応表に現れない。
- 具体例: u1-api GN-5859。確認事項を「`item_code` は `prize_cd` と同一キー体系か／想定件数は」の1問にまとめていたが、`K0X` 前置19件（うち例外リスト13件は景品・残り6件は材料）・`^HB[0-9]+` 8件という**書式依存**が別次元で存在した。例外13件は1文字変わるだけで完全一致が外れ、景品→材料に誤分類されて棚卸 CSV から落ちる。
- 関連: R7-07（形式変更の続き。本項は主キーの**符号としての役割**）

### R7-09: 外部マスタ差し替えでは「値が一致する」検証と「ドメイン判定の入力として成立する」検証を別次元にする
- severity: major
- scope: both
- tags: universal, データ, 移行
- 由来: ユーザー指摘
- 判定: 同じ DB カラムに別ソースの項目をマッピングするとき、
  - サンプル数件の**項目突合（値が一致した）は属性の検証**であって**判定の検証ではない**。その項目がドメイン判定関数（`IsXxx()` 等）の入力になっているなら、判定ごとに検証を分けたか
  - 判定関数ごとに **AS-IS の該当件数を実データから出し、TO-BE で同数になることを受入基準にした**か。単一サンプルは母集団のマーカー保持率を一切保証しない
  - 判定の**壊れ方の脆さを区別**したか: `HasPrefix` は先頭に1文字入るだけで全滅（脆い）／`Contains` は位置に依存しない（頑健）
  - 判定の**用途の重さを区別**したか: 表示フラグか、バリデーションゲートか、金額集計の分岐か。重い用途は「たぶん保持される」で通さない
  - マッピングにフォールバック（`A` が空なら `B`）を入れたなら、**主たる入力は `A`**。「`B` は◯◯由来だから安全」は実際に使われるフィールドを説明していない
- 理由: 供給元の切り替えは「カラムの対応表」として捉えられやすく、対応表が埋まると検証が終わった気になる。しかし文字列カラムは**書式・マーカー・前置文字**という別次元の契約を持っており、そこはロジックが依存していても対応表には現れない。
- 具体例: u1-api GN-5859。`prizes.name` の突合を1件で済ませたが、`name` は `IsKidsMarket()`（`【KM】` を Contains・AS-IS 2,212件・**移動と棚設定のバリデーションゲート**）と `IsKuroMaru()`（`●` を HasPrefix・AS-IS 29,119件・**黒丸消費金額の集計分岐**）の唯一の入力だった。AS-IS には `【KM】●ＳＤビッグかつ` のように「`●` を含むが前置しない」名前が多数あり、`HasPrefix` の脆さが顕在化する形だった。さらにマッピングは `name ← seams_item_name`（空なら `item_name`）なのに、安全性の根拠に書いていたのは `item_name` の性質だった。
- 関連: R4-05（マーカー依存の洗い出し）
