# R1: レイヤー境界・責務・依存方向

各レイヤが守っている**構成の不変条件（invariant）**を、利便性のために壊していないか。

---

### R1-01: 依存は下向き。domain / app が上位レイヤを import しない
- severity: blocker
- scope: both
- tags: universal
- 由来: ユーザー判断
- 判定: 内側の層（domain / entity）が外側の層（usecase / adapter / handler）を import していないか。プロジェクトの依存許可表（arch-lint 設定・CodingDesign.md 等）があればそれと突き合わせる。
- 理由: 依存方向が崩れると循環と結合が広がり、内側の層を単独でテスト・再利用できなくなる。

### R1-02: 横断的・統一的処理は Service 層に置く
- severity: major
- scope: both
- tags: universal, go, 構造, 共通化
- 由来: ユーザー指摘
- 判定: 「複数のデータストア（テーブル / repo）へ同時に書き込む」「複数の下位コンポーネントを束ねて1つの統一操作にする」処理が、**下位レイヤ（repository）に合成オブジェクトとして置かれていないか**。
- 理由: repository は「1 model = 1 repo」という構成を取っている。複数 repo を束ねる合成 repo を repository 層に置くと、その全体設計が崩れる。横断処理を束ねる責務はもともと Service 層が担う。利便性（既存インターフェースに drop-in できる等）のために層の不変条件を破ると、後から読む人がレイヤの規則を信頼できなくなる。
- 具体例: u1-api GN-5760。archive と recent の2テーブルへ dual-write する処理を `IPrizeMeterReadRepo` を実装する `PrizeMeterReadDualWriteRepo` として repository 層に置こうとして却下された。

### R1-03: 抽象／レイヤは責務が実在する箇所にのみ置く。対称性のための空ラッパを作らない
- severity: major
- scope: both
- tags: universal, go, 構造
- 由来: ユーザー指摘
- 判定: ロジックの無い委譲レイヤが「他方と構成を揃えるため」だけに足されていないか。**非対称であること自体を欠陥として扱っていないか。**
- 理由: 空の委譲レイヤは読み手に「ここに固有責務がある」と誤認させ追跡コストを増やす。非対称は欠陥ではなく、責務分布を表すシグナルになり得る（どこに何の責務があるか一目で分かる）。
- 具体例: u1-api。prize_meter_read は usecase に archive 参照責務が無いため query service を作らない。prize_booth_sales は必要なので持つ。両者を対称化するより、必要な側だけが持つ非対称の方が責務が明示的、と判断された。
- 関連: R7-01（参照実装踏襲時の非対称は「固有責務のシグナル」）

### R1-04: 共通基盤（common）パッケージは原則 repository にのみ依存する
- severity: major
- scope: both
- tags: go, 構造, 依存方向
- 由来: ユーザー指摘
- 判定: common / shared / pkg のような共通基盤が、他フィーチャの **app/services・usecase・domain/services** に依存していないか。依存先が domain/repos（データアクセス境界）に限定されているか。
- 理由: common は最も多くから参照される土台。ここが特定フィーチャのサービス層に依存すると依存グラフが汚れ、循環・結合が広がる。
- 具体例: u1-api GN-5760。prizes の mutation service を common の service に注入しようとして却下。common 側に同等の mutation service を新設し、prizes/domain/repos から組み立てる方針にした。

### R1-05: 相互依存しやすいフィーチャ間は、cross-import より「各フィーチャに同等実装を持たせる」
- severity: major
- scope: both
- tags: universal, go, 構造, 依存方向
- 由来: ユーザー指摘
- 判定: 共有実装を一方のフィーチャに置いて他方から cross-import していないか。共有してよいのは下位の安定層（domain/repos・domain/models 等）のみ。
- 理由: 相互依存しやすい関係で cross-import を許すと双方向依存・循環に陥る。実装を各自に持たせれば依存方向が一方向に保たれ、各フィーチャを独立して読める・変更できる。**DRY より依存の清潔さを優先**する判断。
- 具体例: u1-api。report と prize は相互依存が発生しやすいためそれぞれに実装を持たせている。GN-5760 でも prizes と common の双方に mutation service を置き、共有層は domain/repos と domain/models に限定した。
- 関連: R2 全般（DRY と正面から衝突する。衝突は P5 に上げるが、**P5 は結論を決めず「天秤が記述されているか」を見る**）

### R1-06: usecase は service を具象で参照しない。domain の interface 経由にする
- severity: major
- scope: both
- tags: go, 構造, 依存方向
- 由来: ユーザー指摘
- 判定: usecase が service を `app/services` 等の**具象型で import** していないか。`domain/services` に interface を定義してそれ経由になっているか（factory が具象を生成して interface 引数に渡す形）。service 同士の同一パッケージ内利用は具象でよい。
- 理由: app→app の具象結合を避け、依存を domain interface に集約する。テストも interface mock で差し替え可能になる。**プロジェクトの設計ドキュメントに明記された基礎規約は、実装前に読んで従う。**
- 具体例: u1-api GN-5760。usecase が mutation サービスを `prize_services "internal/prizes/app/services"` の具象で参照していたのを指摘され、`domain/services` に interface を定義して経由する形に修正した。

### R1-07: query / 取得サービスに、別リポジトリの取得（責務外）を混ぜない
- severity: major
- scope: both
- tags: universal, レイヤー分離, 責務
- 由来: ユーザー指摘
- 判定: 取得サービスが、ソートや突合のために**自分の責務外の別エンティティ**を取得していないか。それを既に持っている呼び出し側（usecase）で行うべきではないか。
- 理由: 責務混在は「何のためのサービスか」を壊す。呼び出し側は既に必要データを持っていることが多い。
- 具体例: u1-api GN-5811。`FindByDateRange`（sales 取得）内で booth_name ソートのため boothRepo.Find していたのを撤去し、usecase 側で突合する形に修正した。

### R1-08: 異種のデータを1スライスに concat して情報を落とさない
- severity: major
- scope: both
- tags: universal, 責務, 返り値設計
- 由来: ユーザー指摘
- 判定: 型の違うデータを無理やり1つのスライス／配列に変換・結合して返していないか。**型を保って分割して返し**、変換・紐付けは呼び出し側に委ねられないか。
- 理由: 型を潰すと、呼び出し側は失われた情報を再導出するか、全体を同一視して扱うしかなくなる。
- 具体例: u1-api GN-5811。tone を Convert して単一スライスに concat せず、boothSales と tone を別々の返り値にして usecase 側で booth に突合する、と指摘された。

### R1-09: データ層の定数を UI の装飾文言に流用しない
- severity: minor
- scope: both
- tags: universal, react, 命名, レイヤ境界
- 由来: ユーザー指摘
- 判定: 表示専用の文字列（注記・バッジ・補助文言）を、たまたま字面が同じデータ層の定数（CSV 列名・API フィールドラベル・DB カラム名）から組み立てていないか。
  - 判定法: **その文字列はデータとして保存・送信・出力されるか？** されないなら UI 専用であり、データ層の定数とは別物。
  - DRY の適用単位は「字面」ではなく「概念」。同じ語でも独立に変わってよい（むしろ変われるべき）なら流用しない。
- 理由: 読み手にとって「これはデータに入る値なのか、画面だけの飾りなのか」の境界が消える。定数参照が防ぐ「乖離」は、独立に変わってよい2つの文字列の間にはそもそも存在しない問題であり、**存在しないリスクを回避するために可読性を売っている**。
- 具体例: u1-web GN-5857。CSV プレビューの注記文言を `SP_ASSIST_CSV_COLUMNS.recommendedAssistPrice`（CSV 列名定数）で組み立てたところ、「僕は列名とは認識できず、CSV の値と勘違いした。そのままハードコードして良い、UI 部分だし」と指摘された。
- 関連: R3-08（可視文字列の"内容"。本項は"出所"）、R3-09（名前で適用範囲を伝える）

### R1-10: 副作用の共通化は禁じない。呼び出し経路が追え・責務が混ざらない形にする
- severity: major
- scope: both
- tags: universal, backend, react, 構造, 副作用
- 由来: ユーザー指摘
- 判定（**原則。絶対禁止ではない**）: 副作用（外部 API 呼び出し・DB 書き込み・mutation）の置き場所について、次の2条件を満たすか。
  1. その副作用が**どの経路（どのページ・ルート／どの API）を起点に走るかが追いやすい**こと
  2. 共通化先が**責務的に正しい**（無関係な文脈・異なるドメインに紛れ込まない）こと
  - **フロント（React / TanStack Query）**: 原則、再利用可能な共通 UI コンポーネント（view）の中で副作用を呼ばない。副作用は経路が特定できる `usecase.ts` が所有し、UI へは `onXxx?: (req) => Promise<void>` コールバックで注入（presentational 化）。
  - **バックエンド**: 目的別 service への集約は可。ただし異なるドメインの処理に紛れ込ませない。
  - いずれも原則であり、特殊ケースはある。逸脱するなら、経路の追いやすさ・責務の妥当性を別手段で担保できるかを吟味した上で判断する。
- 理由: 副作用は「いつ・どこ起点で状態が変わるか」が可読性・デバッグ性の要。共通化の可否が本質ではなく、**経路が追えるか／責務が混ざっていないか**が本質。「呼び出し側無改修」という短期の省コストより、副作用の経路が構造から追える保守性を優先する。
- 具体例: u1-web GN-5703。複数ルートで使う共有 modal に mutation を持たせる案（呼び出し元無改修）を提案し、「共有 UI に副作用を埋めると経路が追えず使い回しもしにくい」と却下された。modal を presentational 化し mutation は各ルート usecase が所有する形に確定。
- 関連: P3（「呼び出し元無改修」を選定理由にした例）、R6-01（1案しか出ていない設計）

### R1-11: レイヤー違反を1本指摘されたら、その部品が作る依存エッジを全部列挙する
- severity: major
- scope: both
- tags: universal, レイヤー境界, レビュー対応
- 由来: ユーザー指摘
- 判定: レイヤー違反の修正が、**指摘された1本だけ**を潰して終わっていないか。その部品が import する必要のあるパッケージを全部書き出し、1件ずつ許可表と突き合わせたか。
  - とくに**同じ層の隣接コンポーネント**が危ない。「DB へ書く」は疑われるが、「生成コードの型を使う」「フレームワークのモデルに触る」は無自覚に import されるため漏れる。
  - 許可表に**エントリが無い**依存先は「無制約」か「禁止」かツールの挙動を確認するまで分からない。分からないまま「lint は通るはず」と書かない。
  - 置き場所を決めるときは、**必要な依存を全部すでに許可されている層**を探す方が、port interface を何枚も挟むより早くて壊れない。
- 理由: レビューは指摘した1本しか返さない。依存は部品が持つ import の集合であって、レビュアーが挙げた1件ではない。
- 具体例: idpf-api GID-1568。1巡目で「`adminapi → driver` は消したいエッジ」と指摘され port interface + DI に直したが、同じミドルウェアは `admingraph/gqlmodel` の型も使っており `adminapi.mayDependOn` に `admingraph` が無かった。2巡目が major として再検出。正解は `internal/app/`（全部許可されている層）に置くことで、port interface を挟むより単純に解決した。
- 関連: R6-06（指摘の波及先を grep して潰す）

### R1-12: 各関数／型が単一の責務か
- severity: major
- scope: both
- tags: universal, 責務
- 由来: ユーザー判断
- 判定: その関数／型がやっていることを1文で言えるか。「〜と〜」で繋がるなら分割を検討する。変更理由が複数あるものは責務も複数ある。
- 理由: 責務が複数あると変更理由も複数になり、片方の都合で直すともう片方が壊れる。R1-07 / R1-08 はこの観点の具体パターンであり、**そのどちらにも当てはまらない形で単一責務を崩している設計をここで拾う**（この汎用観点が無いと、具体パターンに一致しない責務混在が素通りする）。
- 関連: R1-07（取得サービスに責務外の取得を混ぜない）、R1-08（返り値の型を潰さない）
