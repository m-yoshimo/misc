# R5: テスト・検証力・検証手順

**このカテゴリは厳しめに倒す。**
テストはコーディングエージェントの品質を担保する最後の砦。
「テストがある」「検証する」という**体裁が検証を止める**ため、骨抜きテスト・空手形の検証手順は、無いものより悪い。

---

### R5-01: ビジネスロジックにはテストがあるか。それ以外は、退行を検出する手段が定まっているか
- severity: major
- scope: both
- tags: universal, テスト
- 由来: ユーザー判断
- 判定:
  - **ビジネスロジックの変更にはテストが要る。ここは例外を認めない。** ドメインの規則・計算・状態遷移・条件分岐（金額／在庫／権限／期限／順序の判定など）が該当する。テストが無ければ指摘する。「別 PR で」「自明だから」は理由にならない。
  - **それ以外の変更**（委譲・DTO 変換・設定値・UI 配線・命名の変更など）は、テストの有無ではなく「**この変更が壊れたとき、それを検出するのは何か**」を問う。型 / 既存の統合テスト / 完了ゲートの grep / 差分の目視レビュー のいずれかが特定できるか。
    - **「テストが無い」こと自体は問題ではない。何も検出しないことが問題。**
    - 防御が「目視レビュー」だけなら、その前提で R5-10（完了ゲートの探索範囲）を厳しく見る。
- 理由: ビジネスロジックの退行は、型でもレビューでも捕まらず、本番のデータで初めて出る。一方、それ以外の変更に一律でテストを求めると、テストの体裁だけが増えて R5-02〜R5-06 が問題にしている「検証力ゼロのテスト」を量産する。
- 関連: R5-10（テストが無い変更では完了ゲートが唯一の防御になる）

### R5-02: mock の引数は context（第1引数）以外を `gomock.Any` で省略しない
- severity: major
- scope: code
- tags: go, テスト
- 由来: ユーザー指摘
- 判定: `gomock.Any()` を使ってよいのは **repository 等の第1引数（context / db）だけ**。それ以外の引数（scope・ID・モデル・件数等）が正確な matcher で検証されているか。
- 理由: 引数を Any にすると、誤った scope/ID/データで呼んでもテストが通り、**回帰検出能力が消える**。テストが「呼ばれたこと」しか見ていない。
- 具体例: u1-api GN-5760。Find や BatchUpsert・Delete の期待値を全引数 `gomock.Any()` で省略し、「context 以外で Any を使うな、テストになっていない。同じファイルの他箇所はやっていないのに、なぜ省略したのか」と強く指摘された。

### R5-03: mock の期待値は1つずつ独立（standalone）にする
- severity: major
- scope: code
- tags: go, テスト, 構造
- 由来: ユーザー指摘
- 判定: 各 mock の EXPECT が**単体で成立**しているか。期待する引数・records・返り値が**そのモック専用のテストケースフィールドから明示的に**与えられているか。
  - **他の mock の `ret` や `args` を流用して別 mock の期待値を組み立てていないか**（変換して流用するのも禁止）
- 理由: mock が依存し合うと、テストケース側で各 mock の状況を独立に制御・検証できず、片方を直すと連鎖で壊れる。
- 具体例: u1-api GN-5760。recent の期待値を `archiveMock.ret` の変換と `archiveMock.args[2:]` から導出しており、「各 mock は単体で動くようにし、テストケース側で状況判断できるようにすべき。mock 同士の依存・返り値/引数の使い回しは厳禁」と指摘された。

### R5-04: 共有テストヘルパの不具合は、per-test の回避策でなく本体を直す
- severity: major
- scope: code
- tags: go, universal, テスト, 共通化
- 由来: ユーザー指摘
- 判定: 共有のテストヘルパ（カスタム matcher 等）が原因で個別テストに回避コードが書かれていないか。
  - カスタム matcher の `Matches` が**冪等**か（呼び出しごとに新しい状態に対して評価し、matcher 自身のフィールドを変異させないか）
- 理由: 回避策は同じ不具合に当たるたびにコピーされ、周辺と不整合な独自コードを増やす。gomock は1つの実呼び出しを複数の期待値の matcher に試行するため、`Matches` が状態を蓄積すると後続のマッチが壊れる。影響範囲が広い共有コードでも、修正が「より正しくする」性質なら full suite を通して安全性を裏取りすれば本体修正してよい。
- 具体例: u1-api。`ClauseMatcher.Matches` が永続フィールドへ WHERE 句を適用して蓄積し、同一メソッドに複数 EXPECT があると汚染された。per-test の `freshClauseMatcher` で回避していたが、本体を冪等化して workaround を撤去・標準パターンに統一した。

### R5-05: テストは「検出したい性質を実際に検出できるか」を実測で裏取りする
- severity: major
- scope: both
- tags: universal, go, テスト
- 由来: ユーザー指摘
- 判定: 期待値と実測値を汎用比較器（`cmp.Diff` / `assert.Equal` / `reflect.DeepEqual` / `toEqual`）で突き合わせるテストについて、
  - 「期待値をこう書く」で終わっていないか。**実装から当該変換を一時的に外し、そのテストが FAIL することを実測**したか。落ちないならそのテストは何も検証していない
  - 落ちないなら比較器を変えたか（**シリアライズ結果**（`Format(time.RFC3339)` / JSON 文字列）で比較する、`cmpopts` で比較器を明示する）
  - `Equal` メソッドを持つ型（`time.Time`、`decimal.Decimal` 等）は go-cmp / testify がその型の等価規則へ委譲する。**`time.Time.Equal` は絶対時刻のみを見て `Location` を無視する**ため、tz 変換の正しさは値比較では原理的に検証できない
  - **期待値を実装と同じ関数で組み立ててよいのは、その関数が検証対象でないときだけ**（検証対象そのものを期待値側でも呼ぶとトートロジー）
  - 値比較を残すなら「ここでは値の伝播のみを見る。表現の正しさは○○のテストで担保する」とコメントで役割を明示したか
- 理由: R5-02/03 は**書き方**の問題を扱うが、本件は書き方が正しくても**比較器の意味論により検出力がゼロ**になる別の失敗様式。設計文書に「テストで担保する」と書かれると、レビューでも実装でもそれ以上検証されない。
- 具体例: u1-api GN-5899。`updatedAt` に tz 変換を入れる設計で、期待値を同じ変換関数で包んだ。この変換は絶対時刻を保つため `cmp.Diff` では無変換実装と区別できず、**実装から変換を外しても PASS した**（実測確認済み）。`Format(time.RFC3339)` の文字列比較を追加して初めて FAIL するようになった。

### R5-06: テスト容易性のための注入は、非決定要素を列挙して漏れなく行う
- severity: major
- scope: both
- tags: universal, テスト容易性, DI
- 由来: ユーザー指摘
- 判定: 時刻・乱数・ID 採番・外部 I/O などの非決定要素について、
  - 設計時点で**その処理に含まれる非決定要素を列挙**したか（現在時刻／乱数／UUID・連番の採番／ホスト名・環境変数／外部応答）
  - **1つを注入する論拠（「注入しないと○○のテストが書けない」）が、他の非決定要素にもそのまま当てはまらないか。** 片方だけ注入する設計は、たいてい論拠の適用漏れであって意図的な選択ではない
  - **「結果を決めているのはどれか」で優先度を判断したか。** 分岐の結果を直接決める要素が注入できないと、テストは別の入力で代用することになり、**意図と違う経路を通ったまま緑になる**
  - 注入の形は既存の先例に揃っているか。**公開フィールドで差し替える方式は外部から書き換えられる**ので、金銭・権限に関わる値では書き換え不能な形を選ぶ
- 理由: 非決定要素は「時刻」だけが強く意識され、乱数や採番は見落とされる。しかし確率分岐・重複回避の中心にあるのは後者。片方だけ注入できる状態でテストを書くと、書ける範囲でしか書かなくなり、**書けなかったケースが「テスト済み」の体裁の中に埋もれる**。
- 具体例: idpf-api GID-1856。確率抽選のユースケースで、時刻は「注入しないと日付境界のテストが書けない」と明示的に論証して注入したのに、**当落を直接決める乱数には同じ論証を適用せず**注入経路を用意していなかった。確率 5% / 0.1% の当選ケースを決定論的に書けず、代用すると別経路を通ってしまう状態だった。

### R5-07: 検証手順を書くときは、その手順が使う経路・パラメータが実在するかをコードで確認する
- severity: blocker
- scope: design
- tags: universal, 検証
- 由来: ユーザー指摘
- 判定: タスク定義書・Runbook の検証手順（dry-run・ステージング投入・再現コマンド）について、
  - 手順に出てくる**フラグ・パラメータ・パスが実装側に存在するか**を1件ずつ確認したか。「片方のバッチにあるから、もう片方にもあるはず」は通らない
  - パスやキーを引数に取る手順で、**それがローカルパスなのか外部ストレージのキーなのか**を実装で確かめたか（名前は嘘をつく）
  - 手順が実行不能と判明したら、**代替手段を書く**か「この経路は検証できない」と明記したか
  - 検証手段が無いこと自体が設計課題なら、「検証用パラメータを追加するか」を判断事項に上げたか
- 理由: 検証手順は「最後に書く付録」になりやすく裏取りが最も緩む。しかもリスクの高い変更ほど検証手順に依存するため、そこが空手形だと**最も守りたい場面で守りが無い**。実行して気づくのは切替当日。
- 具体例: u1-api 統合景品マスタ TOBE 対応。「新形式サンプルを dry-run で流す」と書いたが、`csvPath` は S3 オブジェクトキーでローカルパスではなく、**そのバッチにはパス上書き手段が存在しなかった**（`params` から読むのは `dryRun` のみ）。本タスクの実質リスクを唯一検証する「必須」セクションが実行不能だった。

### R5-08: CI/CD の検証手順を前提にするときは、composite action / 再利用 workflow の入力デフォルト値まで辿る
- severity: blocker
- scope: design
- tags: universal, CI/CD, 検証手順
- 由来: ユーザー指摘
- 判定: 「このブランチのコードを CI から手動実行して事前検証できる」型の前提について、
  - **「呼び出し元に指定が無い ⇒ 呼び出し元のコンテキストが使われる」は composite action では成立しない。** 呼び出し先が同じ入力を持ち、**デフォルト値で上書き**してくることがある
  - `uses: ./.github/actions/*` / `./.github/workflows/*.yml` を含むなら、**呼び出し先の定義を開き** `inputs.*.default` と「呼び出し元が渡していない入力の一覧」を突き合わせたか
  - とくに `actions/checkout` の `ref` / `path` / `clean` は後段の全ステップの入力を丸ごと差し替える（`clean` 既定 true ＝ 前の checkout の成果物が消える）
  - 同種の workflow が複数あるなら**横並びで diff** を取ったか
- 理由: 検証手順が**唯一のリスク統制**になっていることがある。手順が実行不能だと、リスク統制ゼロで本番投入する計画が「検証済み」の顔で承認される。
- 具体例: u1-api GN-5859。`stg_batch_manual.yml` の `actions/checkout@v3` に `ref` 指定が無いことは正しく読めていたが、直後に呼ぶ composite action が `ref: ${{ inputs.branch }}`（default `"development"`）で**同じ workspace に再 checkout** しており、feature ブランチから dispatch しても `development` がビルドされる、が事実だった。「feature ブランチのまま dry-run 検証できる」という前提が崩れ、それを根拠にした切替方式の推奨理由まで失効した。

### R5-09: 検証環境を前提に置くときは、「入力データの実在」と「受入基準の母数の同一性」も確認事項に立てる
- severity: major
- scope: design
- tags: universal, 検証手順, CI/CD
- 由来: ユーザー指摘
- 判定: 「stg で dry-run して確認してから本番投入する」型のリスク統制について、実行**経路**の確認に加えて次を立てたか。
  - **(a) 入力データの実在**: 検証環境側の外部ストレージ／DB に、検証対象の入力が実在するか。いつ配置されるか。無ければ検証は0回も走らない
  - **(b) 受入基準の母数の同一性**: 「本番実測値 ± 誤差」型の閾値を使うなら、**その閾値を測った環境と適用する環境が同一母集団か**。部分データの検証環境では閾値が判定として機能しない
  - 検証環境で成立しない場合の**代替経路**（本番での dry-run 先行実行、取得元のパラメータ化）まで書いたか
  - 取得元・接続先をパラメータで上書きできるかを**実装を見て**確認したか
- 理由: 経路の裏取りだけで満足すると、この最後の穴が残る。
- 具体例: u1-api GN-5859。経路（composite action の checkout ref 問題）は1巡目で直したが、(a) stg バケットへの配置時期 (b) stg の件数（受入基準は prod 実測値）がどちらも確認事項に立っていなかった。加えて取得元パスを上書きできず代替経路が狭いことも書けていなかった。

### R5-10: 完了ゲートの探索範囲に、そのタスクで新規に作るファイルが入っているか確認する
- severity: major
- scope: design
- tags: universal, 検証
- 由来: ユーザー指摘
- 判定: 「`grep` して 0 件なら完了」型の残存確認ゲートについて、
  - **変更対象ファイル一覧の「追加」行が、検証コマンドの探索範囲に全て含まれているか**を突き合わせたか。新規ファイルは既存の探索パスの外に置かれることが多い
  - パスが実在するかだけでなく、**検証したい対象がそのパスの内側にあるか**を確認したか
  - 「このファイルは対象外」と除外理由を書くとき、**そもそも探索範囲に入っているのか**を確かめたか
- 理由: 完了ゲートは最後に書くため裏取りが緩む。しかも「0件でした」という報告は成功に見えるので、範囲が狭いことに誰も気づかない。**テストが無いタスクほどこのゲートが唯一の防御になる。**
- 具体例: u1-web GN-5901 Phase 2。残存 grep の対象が3ファイルのみで、**本タスクで新設する hooks 3本と呼び出し側4ルートが探索範囲外**だった。さらに「このファイルは必ずヒットするので対象に含めない」という但し書きも誤りで、そのパスはそもそも探索範囲に入っていなかった。定義書自身が「テスト0件 → 目視レビューが実質唯一の防御」と書いていた。
