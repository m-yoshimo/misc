# R2: 共通化・抽象化・制約

DRY と「前提への特化」は正面から衝突する。**衝突時は P5（リスク・影響とメリットの天秤）で裁定する。**
天秤にかけずどちらかを機械適用した設計が指摘対象であり、天秤にかけた上での結論はどちらでもよい。

---

### R2-01: 共通ロジックを usecase 層に置いて usecase / モジュール間の依存を作らない
- severity: major
- scope: both
- tags: universal, go, 共通化, 構造
- 由来: ユーザー指摘
- 判定: 共有ヘルパーを片方の usecase ファイルに定義して別 usecase から呼んでいないか（= usecase 間依存）。共通変換は **model / entity 層**に置かれているか。
- 理由: usecase 間依存・重複定義は保守性を壊す。
- 具体例: u1-api GN-5811。tone→PrizeBoothSale 変換を各 usecase の共有ヘルパーで行っていたが、「usecase 間依存は NG」と指摘された。

### R2-02: 既存の共通資産を再発明していないか
- severity: major
- scope: code
- tags: universal, 共通化
- 由来: ユーザー指摘
- 判定: 既存の変換関数（`Convert()` 等）や共通 helper を再利用せず、同等のものを新設・再実装していないか。既存関数に**引数を足して使える**のに新関数を作っていないか。
  - **どの共通資産が「既存」なのかはプロジェクトごとに違う。** 具体的な helper 名を当てにいくなら `project_review_rules.md`（`PJ-` 接頭辞）側に書く。ここでは「再利用を試みたか」だけを問う。
- 理由: 同じロジックが複数箇所に散ると、片方だけ直す事故が起きる。既存関数の再利用が最小で一貫する。
- 具体例: u1-api GN-5811。既存の `TonePrizeBoothSale.Convert()` を booth を受けられるよう拡張すれば済むところを、共有ヘルパーを新設していた。

### R2-03: 新しい関数・引数を足す前に、既存関数の合成で表現できないか確認する
- severity: minor
- scope: both
- tags: universal, react, 共通化, 構造
- 由来: ユーザー指摘
- 判定:
  1. 既存プリミティブの**合成**で要件を表現できないか確認したか。足りるなら新規追加しない。
  2. プリミティブ（正規化系）に高レベル関数（offset 計算等）を**内部依存させていないか**。依存方向は「プリミティブを土台にして上へ積む」。
  3. 既存関数と紛らわしい命名（複数形/単数形の違い・返り値型違い）で新設していないか。
- 理由: 関数・引数の数は保守コスト。依存方向を揃えると既存の合成パターンに馴染み、似た命名の乱立は誤用を招く。
- 具体例: u1-web。「当月含む過去3ヶ月の月初」に `getMonthAgo` 新設や `getMonthStart` への offset 引数追加を検討したが、既存の `getMonthStart(getMonthsAgo(2))` の合成で足りた。既存 `getMonthsAgo`(複数形/string) の隣に `getMonthAgo`(単数形/Dayjs) を作るのは紛らわしい。

### R2-04: 実装とは「制約を付けること」。汎用性より制約・可読性を優先し、型で不能を表す
- severity: major
- scope: both
- tags: universal, go, typescript, 構造, 型設計
- 由来: ユーザー指摘
- 判定: **汎用性を上げるほど可読性は落ち、抜け漏れによる不具合・実装漏れのリスクが増える**という前提が置かれているか。具体的に:
  1. 不要なジェネリクス型パラメータを足していないか／剥がせないか
  2. 扱える入力を単一の型に固定し「この型にあるものでしか処理できない」を型で明示できないか
  3. 派生が必要なら `Pick<Base, 'field'>` 等で基底型から絞り、単一の出所を保っているか
  - 「実態が複数あるから汎用化」ではなく「**本当に別物の軸だけをジェネリクスに残す**」。
- 理由: 汎用化は表面上の DRY と引き換えに、呼び出し側の意図が型から読み取れなくなり、想定外の入力を通す余地を生む。制約が強いほど「できないことは書けない」状態になり、コンパイル時に誤用が弾かれる。言語非依存の普遍原則。
- 具体例: u1-web GN-5832。`useFloorMapSearch` の `<T, P>` のうち、検索条件 P は実質同一だったため剥がして `FloorMapSearchParams` に固定し、派生側は `Pick<...>` で絞った。点の型 T は本当に構造が違うので残した。
- 注意: ユーザーが「TS より Go のような型制約の強い言語を好む」と述べた件は**背景の好みであり、能動的な実装ルールとして課すものではない**（本人が明言）。この項をもって TS を否定的に評価しない。
- 関連: 00-principles「このルーブリックに適用してはいけないもの」（この領域の一般化・基準は未確定。調査資料の主張を持ち込まない）

### R2-05: 前提が明確な処理に、汎用的・防御的な処理を持ち込まない
- severity: major
- scope: both
- tags: universal, go, 構造, 過剰設計
- 由来: ユーザー指摘
- 判定: 仕様上の前提（span・対象集合・全行が新規か等）が確定している処理に、**汎用 API が必要とする「入力からの再導出」「1件ずつの突合」「前提が崩れた場合の防御分岐」**を持ち込んでいないか。
  - dual-write の同期なら、span が確定しているなら「対象期間のスナップショットを上書き」で足りる。新規/既存の判定も ID 個別追跡も要らない。
  - 逆に、**前提を持たない汎用 API でこれらが必要になるのは正常**。形の違いは前提の違いのシグナルなので、無理に共通化しない。
- 理由: 前提が保証されている場所に汎用処理を置くと、読む人は「この分岐はどの前提が崩れたときのためか」を追わされ、前提の明確さがコードから消える。
- 具体例1: u1-api GN-5760。dual-write の同期で、書き込んだ records から from/to を計算し boothId 単位で再取得していたのを「span が決まっているのだから span の期間を取得して上書きすればよい」と指摘された。**過剰なのは「スナップショットでないこと」ではなく「前提が明確なのに汎用的な追跡をしたこと」。**
- 具体例2: u1-api GN-5846 `DualBatchUpsertForInitialize`。呼び出し元から前提が見えない汎用 API では、一意キーで archive を読み直して入力行に対応する行だけを書く処理が**正常**（gorm の `INSERT ... ON DUPLICATE KEY UPDATE` の返り ID が信用できないため）。具体例1 と両立する。
- 教訓（このエントリ自身の失敗）: 当初「dual-write の同期は期間スナップショットを上書きでよい」という**結論だけ**を書いていたため、後日、原則ではなく手段（スナップショット）が規範として読まれ、汎用 API にまで機械適用しようとする誤りを招いた。**教訓は結論ではなく原則の形で書く。**
- 関連: P5（DRY 観点と衝突するため天秤で裁定）

### R2-06: 「変更対象の集合」を既存の似た述語・似た記述から機械導出せず、用途で導出する
- severity: blocker
- scope: both
- tags: universal, sql, 影響範囲
- 由来: ユーザー指摘
- 判定: 既存の横断的な条件（SQL の共通述語・共通ミドルウェア・共通バリデーション）に新条件を similar に追加するとき、適用範囲を「既存の述語 X を持つ箇所」から機械導出していないか。
  - 「X があるから Y も」は**導出ではなく類推**。X が偶然そこにあるのは X 固有の歴史的理由かもしれない。
  - 対象集合は**用途（誰が何のために呼ぶか）で分類してから決める**。同じクエリが複数用途に共用されているなら、そこが設計の分岐点。
  - 危険な混在パターン: **認証パス / 管理・書き込みパス / 一意性チェックパス / 外部連携パス**。同じ「ユーザーを引く」クエリを共用しがちだが、新条件への要求が正反対になる（認証は閉じたい、管理は開けたい、一意性は見えていてほしい、外部連携は変えたくない）。
  - 集合を列挙したら、各要素について「なぜ足すのか」ではなく **「足すと誰が壊れるか」を1件ずつ書く**。書けない要素は裏取りできていない。
- 理由: 機械導出は網羅的に見えるので、レビューでも「漏れがない」方向にしか疑われない。だが**多すぎる適用は少なすぎる適用より発見が遅い**。しかも「fail-closed で安全側」という説明が付くため、過剰適用が安全策の顔をして通る。
- 具体例: idpf-api GID-1230。認証を fail-closed にするため停止述語を追加する対象を「`is_active = true` を持つ READ 13本」と機械導出した。実際にはその13本に**停止の解除操作自身が通るクエリ**・メール重複チェック・private_link 検索が混在しており、そのまま実装すれば「停止したら二度と解除できない」「**専用エラーページに到達できない**」「停止中の email が空きに見える」が同時に起きた。用途で再分類した結果、**本当に足すべきは1本だけ**だった（blocker 2件）。
- 関連: R8-01（fail-closed は安全側だから広く掛けてよい、という直感への反例）

### R2-07: 共有フックを「module-import 参照」から「引数注入」に変えると、新たな制約が生まれる
- severity: major
- scope: both
- tags: react, universal, 共通化, リファクタ
- 由来: ユーザー指摘
- 判定: 「本体ロジックは不変・参照だけ差し替え」と書かれていないか。汎用化で以下が新たに要求される:
  1. 引数化した関数を使う `useMemo`/`useCallback` の deps に**その関数を追加**する必要がある（module import 時は非リアクティブで deps 不要だったが、引数化した瞬間 `react-hooks/exhaustive-deps` が要求する＝ lint が落ちる）
  2. 呼び出し側は注入する関数を**モジュールスコープの安定参照**にする必要がある（inline 関数だと毎レンダー identity が変わり、memo 無効化・派生 useCallback の連鎖再生成・effect 暴発を招く）
- 理由: module import は参照が固定で deps に現れないが、引数はレンダーごとに変わりうる。「参照の差し替えだけ」と誤認すると、lint 落ち・パフォーマンス劣化・フォーカス/ズームの暴発など**汎用化前には無かった不具合**を持ち込む。
- 具体例: u1-web GN-5832。ジェネリック化＋引数注入の設計に「本体は現行維持・参照だけ差し替え」と書いたが、design-review が exhaustive-deps と安定参照の2点を指摘した。
- 補足（TanStack Query）: usecase で Orval `useXxxMutation` を包むとき、`useCallback` 内で `mutate`/`mutateAsync` を使うなら **分割代入して deps に入れる**。`mutation` オブジェクト全体を deps に入れると v5 では identity が毎レンダー変わりメモ化が無効になる（`mutation.mutate` を deps に書くと exhaustive-deps が「`mutation` 全体が必要」と警告してこの罠に誘導する）。**他 PR でも頻出の指摘。**
