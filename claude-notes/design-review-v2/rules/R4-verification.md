# R4: 裏取り・調査の網羅性（証拠の質）

**このカテゴリは厳しめに倒す。**
「確認済み」というラベルは後続の再検証を止める。誤った前提は、その上に乗る設計判断を**まるごと**歪める。
指摘するときは「何を根拠に確認済みと言えるか」を必ず問う。

---

### R4-01: 着手前に現状の仕様・既存実装をコードで裏取りする
- severity: blocker
- scope: both
- tags: universal, 進め方, 要件確認
- 由来: ユーザー指摘
- 判定: 実装（やタスク定義作成）に入る前に、関連する**現状の仕様・既存実装をコードで確認**し、依頼の前提が事実かを裏取りしたか。前提が崩れていれば、対応の要否そのものから問い直しているか。
- 理由: 前提が誤っていると、作ったタスク定義・実装ごと丸ごと無駄になる（最悪、意図と逆方向の変更をする）。
- 具体例: u1-web GN-5779。「過去3ヶ月しか保持しないので日付選択を限定する」という依頼で実装まで進めたが、既存 UI は元々「編集可能期限＝過去31日」で保持期間より**厳しく**制限済みだった。変更は不要（むしろ選択範囲を広げる逆方向の変更）で、全て revert した。

### R4-02: 検索結果を head / limit で打ち切ったまま「全件確認した」と結論づけない
- severity: blocker
- scope: both
- tags: universal, コード分析
- 由来: ユーザー指摘
- 判定: **網羅性を主張する検索で、出力を打ち切っていないか。** `| head -N` を付けたコマンドの結果から「これで全部」と結論づけていないか。
  - 網羅を確かめるときは打ち切らない形（`grep -rl` / `grep -c` / `sort | uniq -c`）で件数・ファイル一覧そのものを取る
  - **「探索のための grep（打ち切ってよい）」と「網羅を主張するための grep（打ち切ってはいけない）」を区別**しているか
- 理由: 「裏取りした」という記述だけが残り、実際には先頭 N 行しか見ていない状態が生まれる。裏取り済みと明記された前提には後続の設計判断が乗るため、誤りが下流をまるごと歪める。しかも「確認済み」と書かれているせいで誰も再確認しない。
- 具体例: u1-api GN-5839。`grep ... | head -30` の出力が1ファイルの行で埋まっていたため「1ファイルにのみ残存」と定義書の「前提（すべて実コードで裏取り済み）」に断言した。実際は8ファイルに残存しており、この誤りは「これだけリネームすれば一貫する」という設計判断そのものを誤らせていた。

### R4-03: 「全数調査」の判定基準に、アプリコード外の書き込み経路も含める
- severity: major
- scope: both
- tags: universal, コード分析
- 由来: ユーザー指摘
- 判定: 書き込み経路の全数調査で、判定基準をアプリコードの代入だけに置いていないか。**スキーマのデフォルト値・`ON UPDATE` 句・トリガ・外部システムからの直接投入**も書き込み経路として見たか。
  - 調査結果には「**どの経路を見たか**」を明記する。見ていない経路があるなら「見ていない」と書く。網羅したように書いて実は片側しか見ていない、が最も危険。
- 理由: `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` はコード上に代入が現れないまま値を生む。基準の穴は「調査済み」というラベルの下に隠れる。
- 具体例: u1-api GN-5899。時刻付きカラムの全数調査で判定基準を Go コードの代入のみに置いた（結果的に漏れは無かったが基準として DB 側を取りこぼしていた）。

### R4-04: 「使われていない」という否定的結論を、識別子検索だけで確定させない
- severity: blocker
- scope: both
- tags: universal, コード分析
- 由来: ユーザー指摘
- 判定: 「このカラム／フィールドは使われていない」を根拠に変更・削除を安全と判断していないか。
  - **否定的結論（＝存在しない）は、肯定的結論より高い証明コストがかかる。** 1つの検索手段でヒットゼロは、存在しないことの証明にならない
  - 最低2系統で当たったか: (a) **言語の識別子**（`CharterFlightDate`）、(b) **DB カラム名の文字列リテラル**（`"charter_flight_date"`）。ORM の scope・生 SQL・動的なカラム指定は識別子検索に一切かからない
  - **検索ツールのフラグ誤用で出力が壊れていないか**を疑ったか（`rg -r` は replace であって recursive ではない）。ヒット行が意味不明なら、まず自分のコマンドを疑う
  - 素通し（pass-through）と結論した項目が、**他フィールドの導出元やフォールバック**になっていないかも見たか
- 理由: 「使われていない」は変更・削除の許可証として機能し、いったん「確認済み」と書かれると誰も再検証しない。検出漏れは「その項目を触った後」にしか表面化しない。
- 具体例: u1-api 統合景品マスタ TOBE 対応。`charter_flight_date` を「利用ゼロ」と結論したが、(1) 別ファイルが `scopes.ByDateRange(from, to, "charter_flight_date")` と**文字列リテラル**で使用、(2) 数行上で別フィールドのフォールバックに使用、と誤りだった。直接の原因は `rg -rn` の `-r` を replace として誤用し、壊れた出力をそのまま読んだこと。

### R4-05: マーカー依存の洗い出しは「メソッド」でなく「引数」単位で行う
- severity: blocker
- scope: both
- tags: universal, go, 調査, データ
- 由来: ユーザー指摘
- 判定: 文字列カラムに依存するロジックの洗い出しを、`IsXxx()` のようなメソッド名の grep で済ませていないか。
  - 文字列マーカー依存は **`var xxxPrefixes = []categoryKey{{"【KM】", KidsMarket}, ...}` のようなデータ駆動テーブル + 汎用判定関数**として書かれることがある。この形は**関数名にも変数名にも判定対象のカラム名が現れない**ため、メソッド名の grep では絶対に検出できない
  - 洗い出しは**「そのカラムが何の引数に渡るか」で行う**（`Contains(.*Name`、`HasPrefix(.*Cd`、`LIKE` のような引数側 grep）
  - 「ハードコードされた完全一致コードのリスト」も同族。grep 対象の文字列すら事前に分からないので、**分類・除外を行う判定関数の実装を必ず開いて読む**
  - 同じ判定が**複数箇所に再実装**されていないかも疑う
- 理由: 「`name` を消費するのはこの4メソッドだけ」という**完全性の主張**が安全性の根拠になる。その主張が崩れると承認判断の土台が丸ごと失効する。しかも漏れた側は grep で出ないので、「調べた」という自信だけが残る。
- 具体例: u1-api GN-5859。`prizes.name` / `prize_cd` の依存として4メソッドを洗い出し「唯一の入力」と書いたが、別パッケージの `GetItemCdCategory(itemCd, itemName)` が丸ごと漏れていた（name 5マーカー + prize_cd 5前置 + **例外コード24件の完全一致リスト**を持つデータ駆動テーブル、呼び出し元8箇所）。さらに別ファイルに同判定の再実装と正規表現依存もあった。
- 関連: R4-04（同じ「否定的結論」の失敗）

### R4-06: 「無変更で安全」の根拠が“未使用”なのか“業務側の約束”なのかを区別する
- severity: major
- scope: both
- tags: universal, 移行
- 由来: ユーザー指摘
- 判定: 「無変更で安全」の根拠が **(a) その項目を一切参照していない** のか **(b) 参照はしているが、別項目が必ず埋まるので実害が出ない** のか、書き分けられているか。
  - **(b) は業務側の約束への依存であり、コードの性質ではない。** 約束が破れた行が1件でも来れば壊れる
  - (b) なら「〜が守られる限り挙動は変わらない」と条件付きで書き、**約束が破れた場合に何が起きるか**（行が落ちる／NULL になる／例外になる）まで書く
  - 段階移行・並行運用があるなら、**旧ソース由来のデータが約束を満たしていない可能性**を確認事項に上げる
  - 検知の必要性も設計事項に含める（該当項目が全て NULL の行数をログ出力する等）
- 理由: (a) と (b) は結論が同じなので、書き分けないと同じ強度の判断に見える。しかし (b) は**外部の運用が変われば無告知で壊れる**うえ、壊れ方が「一覧から静かに消える」形になりやすく発覚が遅れる。
- 具体例: u1-api 統合景品マスタ TOBE 対応。「nullable かつロジック未使用なので不要」と判定したが、実際はフォールバック連鎖と OR 条件で使われており、無変更で済む根拠は「指定投入日 or オンロケ解禁日を必ず入れる」という**業務側の約束**だった。3つとも NULL の行が来ると一覧から静かに落ちる。

### R4-07: レビュー指摘への訂正こそ、元の記述と同じ強度で裏取りする
- severity: major
- scope: both
- tags: universal, レビュー
- 由来: ユーザー指摘
- 判定: 指摘を受けて書き直した記述に、**新しい事実主張**（ファイル名・行番号・「〜は〜になっている」）が含まれていないか。含まれるなら、それも一次情報で確認したか。
  - 指摘が「X は誤り」でも、**正しい代わりが何かはレビュアーも言っていない**ことが多い。否定部分だけ受け入れ、差し替える内容は自分で調べる
  - 「本リポジトリ外だから確認しない」のようなスコープによる免除も、**実際に確認可能かを先に確かめる**
  - とくに **(a) 選択肢の比較表・天秤の材料**、**(b)「〜に乗るので〜が不要」型の主張**（フレームワーク/既存機構への依存を根拠にするもの）は思い込みが入りやすい
- 理由: 訂正は「指摘に応じた」という文脈が付くため、読み手も書き手も検証を緩める。結果、1巡目の誤りを直す過程で2巡目の誤りが生まれ、それは「レビュー反映済み」というラベルの下に隠れる。**訂正は「一度レビューを通った」ように見えて、実際には未レビューの新規記述。**
- 具体例: u1-api 統合景品マスタ TOBE 対応。1巡目の指摘への訂正文に「参考実装は戻り値が map なので順序問題が出ていない」と書いたが、同ファイルの別テストが既に `cmpopts.SortSlices` を使っており倣うべき手本だった（2巡目が major 検出）。**同一タスクで再発**し、3巡目でも「gorm の soft delete に乗るのでクエリ改修が要らない」と書いたが、そのリポジトリは `gorm.DeletedAt` を一切使っていなかった（しかも**選択肢の比較表＝意思決定材料**に誤りを混ぜた）。
- 関連: R6-06（指摘の波及先を grep して潰す）

### R4-08: 「先例あり」と言う前に、その先例が同じ機構・同じ呼び出し形かを確かめる
- severity: major
- scope: both
- tags: universal, 設計
- 由来: ユーザー指摘
- 判定: 設計判断の根拠として「リポジトリ内に先例がある」と書くとき、
  - 引用した先例は**いま採ろうとしているのと同じ API・同じ呼び出し形**か。別の呼び出し形なら先例ではない
  - **「機構が存在する」と「その機構を使った実績がある」は別。** 前者だけなら「本リポジトリ初出のパターン」と書く
  - 引用先が**規約で禁じている書き方**をしていないか
  - 初出なら、横断一貫性のために**規約へ条件を1項追加する**ところまでを設計に含める
- 理由: 「不可能」と一度書いた負い目から、訂正時に「可能であるうえに実績もある」と過剰に補強したくなる。grep のヒット件数だけ見て中身の呼び出し形を確認しないと成立してしまう。
- 具体例: u1-web GN-5901 Phase 2。「Orval hook の `queryKey` は上書きできない」→ 指摘を受けて「上書き可能・先例2件」と訂正したが、その2件はいずれも `useQuery` の直呼び＋手書き `queryFn` で Orval hook の上書きではなく、しかも共通規約が禁じている書き方だった。実際は**リポジトリ内 0 件＝当該タスクが初出**（3巡目が major 検出）。
- 関連: R6-03（「実現不能」の裏取り。本項はその**訂正側**）

### R4-09: 「無変更で確認済み」リストは、同じ役割を果たす設定資産を全部列挙する。権威はドキュメントで先に確認する
- severity: major
- scope: design
- tags: universal, 調査, 設定
- 由来: ユーザー指摘
- 判定: 「変更しないもの（確認済み）」を書くとき、
  - 対象識別子を **`.github/` などの当たりを付けた場所だけでなくリポジトリ全体に grep** し、ヒットした全ファイルを列挙するか除外理由を書いたか
  - `docs/` に運用ドキュメントがある領域は、**コードより先にドキュメントで「今の権威はどこか」を確認**したか
  - ドキュメントが「以前は X、今は Y」と書いている領域では、**X のファイルがまだ残っていることが多い**。実ファイルの存在だけでは権威を判定できない
  - 設定の**反映が自動か手動か**を確認したか（切戻しコストの見積りに直結）
- 理由: 「変更しない」と書いた瞬間にその項目はレビューの視野から外れる。列挙漏れは「調べた上で対象外」と「見ていない」の区別がつかない。
- 具体例: u1-api GN-5859。定時実行の権威として `.github/workflows/*_batch_scheduled_master.yml` を引用したが、`docs/Batch.md` に「ecschedule に移行した」と明記があり実際の権威は `deployments/ecs/{env}/ecschedule.yaml` だった。さらに「ecschedule の設定変更は自動では反映されない」を見落とし、切戻しコストを実際より安く見積もっていた。

### R4-10: 外部ライブラリのフックに実装方針を載せる前に、そのフックの「署名」を読む
- severity: blocker
- scope: both
- tags: universal, 実現可能性
- 由来: ユーザー指摘
- 判定: 「フレームワークの拡張点 X を使ってこうする」と方針を立てるとき、
  - **「そのフックが存在すること」の確認と「そのフックが必要な情報を渡してくること」の確認は別。** 後者を飛ばしていないか
  - 確認したのは grep で見つけた行番号ではなく**型シグネチャそのもの**か。とくに**戻り値**（エラーが返るか）と**引数の型**（生 AST か、型付きの値か）
  - 候補が複数あるなら**署名を並べた表**を作ったか。名前の意味（Root/Around/Before）で選んでいないか。**限定的な名前のフックほど渡される情報が少ない**
  - 生成コード（`generated.go` 等）があるなら**そこでフックが実際にどう呼ばれているか**を読んだか（ドキュメントコメントより生成コードの方が信用できる）
- 理由: フックの名前は「どこで呼ばれるか」を表すが、設計が依存するのは「何を渡されるか」。設計書の段階では動かして確かめられないので、署名を読まない限り誤りが実装着手まで生き残り、**設計判断そのものが覆る**欠陥を実装フェーズのコストで踏む。
- 具体例: idpf-api GID-1568。gqlgen の `AroundRootFields` を採用し「操作前に INSERT → 完了後に UPDATE する2相記録」を設計の中核に据えたが、`RootFieldMiddleware` は **error を返さない**ため成否判定ができず、`Field` は生 AST なので型付き引数も取れなかった。正解は `AroundFields`。**フックの存在だけ確認して署名を読んでいなかった。** 同件で `RootFieldContext.Object` はコメントと生成コードの挙動が食い違っており、コメントを信じると条件が常に false になる。

### R4-11: 「バグが是正される」型の便益主張も、欠陥主張と同じ強度で裏取りする
- severity: minor
- scope: design
- tags: universal, go, 判断材料
- 由来: ユーザー指摘
- 判定: 「直すと何が良くなるか」の便益主張が裏取りされているか。
  - アプリのコードからは自明に見える副作用が、**ORM の展開規則や DB のセマンティクスで打ち消される**ことがある。upsert・auto-timestamp・トリガ・デフォルト値が絡む主張は、ライブラリのソースと DDL まで降りる
  - 「〜が全行更新される」「〜が毎回発行される」のような**量的な主張**は、量が意思決定を左右するので特に確認する
- 理由: 欠陥主張（＝直す理由）は裏取りされやすいが、便益主張は緩む。便益は「この作業を今やる／やらない」の意思決定材料そのもの。しかも「良い話」なのでレビューでも疑われにくい。
- 具体例: u1-api GN-5859。「差分なしレコードも upsert されるので `updated_at` が全行更新される」を便益に挙げたが、gorm の `OnConflict{UpdateAll:true}` 展開は `HasDefaultValue` な列を除外するため `updated_at` は対象外だった。実際に成立する便益は「無駄な upsert 文の発行」だけだった。

### R4-12: 上流タスクが「下流側の設計事項」として明示的に委譲した論点は、下流の定義書に引き継ぐ
- severity: blocker
- scope: design
- tags: universal, 設計, タスク定義
- 由来: ユーザー指摘
- 判定: 別リポジトリ・別チケットの成果物（新設 API フィールド、新スキーマ、新イベント）を消費する設計で、
  - 上流タスクの定義書・PR 説明の「懸念点」「受け入れたリスク」「○○側の設計事項」を**読み、下流の前提節へ転記**したか
  - 転記時に「上流 doc の何行目」まで残したか（要約だけだと原典に戻れない）
  - 委譲された論点のうち**ユーザーの合意が要るもの**（挙動の許容範囲・受け入れるリスク）を確認事項に上げたか
- 理由: 型・シグネチャの裏取りは「確認済み」というラベルが付きやすいが、**その値が何を意味するか（いつ・何をきっかけに変わるか）**は型に現れない。上流が明示的に委譲した論点は、下流で誰も拾わなければ**どこにも所有者がいないまま実装される**。
- 具体例: u1-web GN-5900。`PrizeDelivery.updatedAt` の型・required・行番号だけを裏取りして「確認済み」としたが、上流 u1-api GN-5899 が4点を委譲していた: (1) 更新は日次バッチ（JST 8:00）でしか起きず「24時間以内」は実質「直近のバッチ分」（上流 doc が明示的に「u1-web 側の設計事項」と記載）、(2) 画面に表示していない項目の変更でもバッジが点灯、(3) リリース直後は `updated_at == created_at`、(4) 一括 UPDATE で全店舗が一斉点灯。
