# R6: 設計判断・多角的検討・スコープ・ドキュメント記述

主にタスク定義書（設計）に当てるカテゴリ。
実装者は自分の盲点（既存手法・最初の案へのアンカー）に気づきにくいので、**分離した評価者が事後に必ずチェックする。**

---

### R6-01: 設計が多角的な視点で検討されているか（最初の案・既存手法に固定されていないか）
- severity: major
- scope: design
- tags: universal, 設計プロセス
- 由来: ユーザー指摘
- 判定: 最初の案・既存手法だけに固定せず、**別の構造・別方式（既存の枠にない代替を含む）を俎上に載せて比較**したか。
  - **1案しか出ていない設計は「比較材料が欠けている」疑いとして問い**、代替の視点・手法を提示する
  - 「選択肢として並べる」「トレードオフで評価する」「迷ったら聞く」は多角的に考えた**結果への対処（downstream）**であって、それ自体が目的ではない。**真に多角的なら、選択肢は促される前に出ている**
  - 既存踏襲も新方式も**それ自体は正義ではない**。両者は P5（リスク／影響とメリットの天秤）に帰る（影響範囲＝方式混在による一貫性の毀損 × 品質改善）
- 理由: 1案しか出さないと、最も制約が強く保守的な案に到達できない（比較して初めて辿り着く）。この盲点は自己申告で埋まらない。
- 具体例: u1-web GN-5832。`useFloorMapSearch` の `P` ジェネリクス指摘時に既存実装を擁護（現状肯定にアンカー）し、畳めることに自力で気づけなかった。別方式もユーザー提案で初めて俎上に載った。＝促されてからしか比較できていなかった。
- 関連: R3-01（既存パターンへの追随。本項はその**対の歯止め**）、R2-04（制約優先の原則と対で使う）

### R6-02: 多角的検討は「どう見せるか・どう書くか」でなく、機能の価値を決める判定条件から始める
- severity: major
- scope: design
- tags: universal, 設計, 多角的視点
- 由来: ユーザー指摘
- 判定: 並べた論点が**表現・実装機構（表示スタイル / 関数の置き場所 / 使う部品）に偏っていないか**。それらは差し替えが容易で、間違えても後から直せる層。
  - **機能の価値を決めるのは「いつ発火するか・何を条件とするか」の判定ロジック。ここが単一案のままなら、多角的検討はまだ始まっていない**
  - 条件が要件文言で与えられていても（例:「24時間以内」）、**実データの更新周期・粒度と噛み合っているか**を代替案と並べて検証したか
- 理由: 表現面の比較は書きやすく、3つ並べれば「多角的に検討した」という体裁が整う。しかし後から最も高くつくのは判定条件の誤りであり、そこが1案のまま通ると設計レビューでも「検討済み」として素通りする。
- 具体例: u1-web GN-5900。当初の「多角的検討」は表示スタイル / 関数の置き場所 / バッジ部品の3論点で、すべて表現面だった。実データは日次バッチ（JST 8:00）でしか更新されないため、判定条件には「24時間以内」と「当日バッチ判定」の2案があり、後者は 0:00〜8:00 に一切点灯しない致命的な副作用を持つ。この比較をして初めて「8:00 境界で対象集合が入れ替わる」という承認すべき挙動が言語化できた。

### R6-03: 「その方式は実現不能」を代替案の却下理由にする前に、不能が設定・生成物由来でないか裏取りする
- severity: major
- scope: design
- tags: universal, 多角的検討
- 由来: ユーザー指摘
- 判定: 「ツールが X に対応していないから Y でいくしかない」と選択肢を1つに絞っていないか。
  - **「生成物に無い」と「生成できない」を区別**したか。設定ファイル（`orval.config.ts` 等）とツールの対応状況を確認したか
  - 裏取りの結果 (a) 本当に不能なら「不能」と書く、(b) 可能だが採らないなら「**可能だが、〜の理由で採らない**」と天秤を明記する
- 理由: 「不能」と「不採用」は意思決定として全く違う。不採用は前提が変われば覆るが、**誤って「不能」と記録するとその選択肢は二度と検討対象に戻らない**。しかも生成物由来の制約は設定1行で変わることが多く、誤判定のコストに対して確認コストが極端に低い。
- 具体例: u1-web GN-5901。35本のタスク定義書が「Orval は Suspense 版 hook を生成していない」と書き、非 Suspense を唯一の選択肢として設計していた。実際は orval 8.22.0 が `override.query.useSuspenseQuery` に対応しており、設定が無いだけだった。移行コストの大半がこの単一前提から派生していた。**結論自体（非 Suspense）は妥当だったが、天秤にかけた記録が無いことが問題。**
- 関連: R4-08（訂正側で起きる失敗）、R4-10（採用側の実現可能性も同じ強度で裏取りが要る）

### R6-04: 前提が変わったら、その前提の上に得た許可・結論も失効させる
- severity: major
- scope: both
- tags: universal, スコープ, 判断の誠実さ
- 由来: ユーザー指摘
- 判定: 条件付きの許可（「〜なら、そうして良い」）を得た後に設計方針が変わり、**元の論点自体が消滅している**のに、許可だけ持ち越して変更を実行していないか。
  - 方針を変えた瞬間に、**その方針変更で不要になった作業を洗い出して落とした**か
  - **後から見つけた別の利点（バグ修正など）を、その変更の理由に横滑りさせていないか。** 時系列を偽らない。「やると決めた後に見つけた利点」は理由ではなく副産物であり、単独で改めてスコープ判断にかける
  - 判定法: **「この変更を戻したら、要件は満たせなくなるか？」に No なら、それは要件由来ではない**
- 理由: 条件付き許可は「その条件が成立している世界」への許可であって白紙委任ではない。前提が変わったのに結論だけ残すと、**誰も必要としていない変更が「承認済み」の顔をして混入する**。さらに後から見つけた利点を理由として語ると、レビュアーにも「要件由来の変更」に見えてスコープ逸脱が検出されなくなる。
- 具体例: u1-web GN-5857。スキーマに入れる前提で「共有スキーマは分けて良い」という条件付き許可を得たが、その後フォールバックを別の場所に置く設計に決めた時点で**懸念は消滅していた**。許可だけ持ち越して分割を実行し、さらに分割**後**に知った既存バグを分割の理由として説明した。「変更理由はバグ修正か？要件か？」で発覚し、要件は変更なしで通ることを実証して全 revert した（9 files→7 files）。

### R6-05: 設計判断の「なぜ」を実装機構で説明しない。要件・制約から導く
- severity: major
- scope: design
- tags: universal, ドキュメント, 設計根拠
- 由来: ユーザー指摘
- 判定: 「A の下流に B があるので B も同じ結果になる」型の説明になっていないか。それは**そうなりやすい理由**であって**そうすべき理由**ではない。
  - 設計判断の理由が**要件・制約・優先順位**から書かれているか（「要件に X があり、それを満たすには Y を選ぶしかない／Y が最も影響が小さい」の形）
  - 見分け方: **その説明を読んだ相手が「それは変えられないのか？」と聞き返せるか。** 聞き返せない書き方（＝機構の説明）なら、背後にある選択を掘り起こして書き直す
- 理由: この誤りは**議論を殺す**のが最大の害。機構は変えられないものとして読まれるので「じゃあ仕方ない」で終わり、**本来議論すべき優先順位の選択が争点として立たない**。議論のために書いた文書なら致命的。
- 具体例: idpf-api GID-1230。RP から停止と退会が同じエラーに見える理由を「停止判定は SQL 述語で行うので、退会と同じ経路に落ちるため」と書いた。実際の理由は「RP を無改修にすること」を「RP が区別できること」より優先した結果。この文書は RP 担当とその優先順位を議論するためのものだったので、機構で説明した時点で議題そのものが消えていた。

### R6-06: レビュー指摘を修正したら、同じ主張が書かれた「他の全箇所」を grep して潰す
- severity: blocker
- scope: design
- tags: universal, レビュー対応, 一貫性, ドキュメント
- 由来: ユーザー指摘
- 判定: 方針を変えたあと、**変更前の方針が書かれている箇所を全部 grep で洗い出してから直した**か。指摘された箇所だけ直して終わっていないか。
  - **最優先で直すのは「決定を記録するセクション」**（§決定事項・§懸念点の【回答済み】など）。実装者はそこを一次情報として読むので、旧方針が残ると**指摘された欠陥がそのまま再現する**。ヘッダに【回答済み】と書き足しただけで本文の旧推奨を残すのが典型
  - 方針変更の**波及先**を洗ったか。「A に述語を足さない」に変えたなら、A の結果を前提にしていた分岐条件・テストの期待値・別経路の根拠説明が全部ひっくり返る。**変更点そのものより、変更に依存していた記述の方が見落としやすい**
  - 撤回した案は削除するか「（旧案・不採用）」と明記したか。**「推奨」という語を撤回済みの案に付けたまま放置していないか**
- 理由: レビューは「指摘された箇所」を返すのであって「その指摘が波及する全箇所」を返すわけではない。伝播が不完全だと、**レビューを通したという事実が安全の錯覚を生み**、次の実装者が古い指示に従って同じ穴を掘る。
- 具体例: idpf-api GID-1230。1巡目 blocker「述語追加対象を13本から1本へ」を反映した際、新セクションは正しく書いたが**§懸念点2 の本文に「13本」がそのまま残っていた**（ヘッダは【回答済み】）。派生の取り残しも3件 —— ゲート条件が旧のままで**一度も発火しない**、テストの期待値が旧のままで**書いたテストが必ず落ちる**、別経路の根拠が逆。2巡目が blocker 1 / major 2 として再検出した。
- 関連: R4-07（訂正の裏取り）、R1-11（依存グラフ版）

### R6-07: 要件↔設計の対応表を書いたら、各行を成果物の実体と突き合わせる
- severity: major
- scope: design
- tags: universal, ドキュメント, 要件充足
- 由来: ユーザー指摘
- 判定: トレーサビリティ表（「この要件は §X で満たす」）について、
  - 表の各行の**参照先を実際に開いて、その要件を満たす記述・列・項目が本当にあるか**確認したか（「§5.1 の列で満たす」と書いたら DDL を開いて列を数える）
  - **「すべて〜で満たす」という一括の書き方をしていないか。** 要件項目を1つずつ列挙し1対1で書く。一括表現は、その中の1つが欠けていても表面上は成立して見える
  - **要件側が列挙形式（「A／B／C／D」）なら、設計側も同じ粒度で列挙**したか。粒度を落とした瞬間に欠落が隠れる
  - 逆向き（**設計にあって要件に無いもの**）も表に出したか
- 理由: 対応表は「照合済み」という強い信号を発するため、**書いた本人も読み手も中身を再確認しなくなる**。しかも要約の過程で落ちた項目は表の上では存在しないことになる。検証コストが最も低いのに被害が最も見えにくい。
- 具体例: idpf-api GID-1568。PRD の Must 記録項目「日時／実行者／対象アカウントID／操作種別／変更前後の値／**理由（ある場合）**」に対し「すべて `admin_operation_logs` の列で満たす」と書いたが、**実際の DDL に `reason` 列は無かった**。さらに別セクションでは「停止理由は監査ログに積まない」と明記しており、**設計は要件と正反対の方向に決めていた**。

### R6-08: 具体値（ドメイン・URL・数値・パス）は、実物を見たものだけ書く
- severity: blocker
- scope: both
- tags: universal, ドキュメント, 捏造防止
- 由来: ユーザー指摘
- 判定: 説明・資料・タスク定義書の具体例に、**コードか設定ファイルで実物を見ていない具体値**が書かれていないか。見ていないなら `<API_DOMAIN>` のようにプレースホルダで書く。
  - **「例として書いた」は免罪符にならない。** 読み手には確認済みの事実と同じ形で届く。とくに実在しそうな形（それらしいドメイン・数値）はそのまま事実として引用される
  - 環境変数の値は**リポジトリに無いのが普通**（SSM / Terraform / Secrets Manager 側）。`.env.example` から引くなら「ローカル開発の値」と明示し、本番値は「リポジトリに無い」と書く
  - **ドメインが分かれている可能性を常に疑う。** API とフロントが別ドメインなのは普通。単一ホストを仮定した URL を書く前に、URL を組み立てているコードを読む
- 理由: 具体値は読み手が最も信用する部分で、かつ最も検証されにくい。パスや関数名と違って「そのファイルを開けば分かる」ものではないため、誤りが下流へそのまま流れる。しかも書き手には「例のつもり」という自覚があるので、訂正の必要性に気づかない。
- 具体例: idpf-api GID-1230。RP と IDPF の通信の説明に `https://id.genda.jp/authorize?...` と書いた。このドメインはコードにも設定にも存在せず**捏造だった**。実際は API 用と画面用の2つの別ドメインがあり、画面側は `/web/<lang>/<path>.html` という別の形をしていた。
- 関連: R3-08（可視文字列の造語）
