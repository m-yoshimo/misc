## 1. 一番大事な結論 — 何が効いて、何が効かなかったか

2026-09-11 に**同一セッション内で実測**した。推測ではない。

| 手段 | 効いたか | 証拠 |
|---|---|---|
| **`deny`（実行を止める）** | **効く** | 自分のテストスクリプトも、自分の `cat > file <<EOF` も実際に止まった。止められた以上、実行できない |
| **警告（`additionalContext`）** | **効かない** | SAFE-12 を、警告フックを配線した**当日に、警告を読んだうえで6回**破った。うち1回は「ファイルに保存してから読む」の保存側を `head -24` で切っている |
| **ルール文言の精緻化** | **効果を観測できなかった** | 64ルール全部に `判定` フィールドを付けて判定可能性を上げたが、遵守率は上がっていない。上がったのは「後から数えられる」ことだけ |
| **事後監査（`/rule-audit`）** | **数えられるが、防げない** | 26件の違反を検出した。ただし監査中に起きた違反は原理的に拾えない（§5） |

**ここから導いた方針**:

> **ルールを分かりやすく書き直しても直らない。「判定を機械が当てられる形に書き換えて `deny` に移せるか」を考えるべき。**

SAFE-12 がその実例。旧 `判定` は「出力量が確実に小さいと分かっていないコマンド」という**私の主観**で、
フックが当てられず警告止まりだった。これを「**パイプラインの先頭が許可列挙にあるか**」に書き換えたら `deny` に移せた。

**ただし全部が移せるわけではない。** SAFE-10（ルート再帰 grep）と META-01（`/tmp`）は例外が
「どうしても必要なら**目的を添えて事前に確認**する」「**ユーザーが明示的に** `/tmp` を指定したとき」で、
**例外の本体が会話の中にある**。ツール入力の文字列には現れないので、同じ手が使えない。
2026-09-11 時点で警告のまま残してあり、**SAFE-12 の deny 化が効いたかを見てから判断する**ことになっている（未決）。

## 2. 構造をこう決めた理由

### 2-1. 索引を「重要度順」でなく「場面順」にした

**決定打は、注入の仕組みを実際に読んだこと**（`~/.claude/settings.json`）。

| フック | 何を注入するか | 頻度 |
|---|---|---|
| `UserPromptSubmit` | **MEMORY.md だけ** | **毎ターン** |
| `SessionStart` | `feedback_*.md` 全文（約9万字） | セッション開始時に1回だけ |

つまり**判断の瞬間に目の前にあるのは MEMORY.md だけ**で、本文はコンテキスト圧縮が起きると落ちる。
**だから索引の並び順が遵守率を左右する。** ファイル分割そのものの寄与は小さい。

旧構成は重要度（blocker / major / minor）で並んでいた。**重要度はトリガーではない。**
回答を送る直前に効く9件は blocker 3・major 4・minor 2 に散っていて、
「いまこの瞬間に効くルールの一覧」として引けなかった。場面順にするとこれが1つの表にまとまる。

**重要度は捨てていない。** 各行の先頭に 🔴🟡⚪ で残した。

### 2-1b. 🔴 サブエージェントにはルールが1文字も届かない（2026-09-11 実測）

**同じ `settings.json` に書いてあっても、フックのイベントによって発火範囲が違う。**

| イベント | 発火範囲 | 中身 |
|---|---|---|
| `UserPromptSubmit` / `SessionStart` | **メインセッションのみ** | MEMORY.md・ルール本文の注入 |
| `PreToolUse` / `PostToolUse` | **サブエージェントでも発火する** | `rule_guard.py` / `memory_lint.py` |

**確かめ方**: サブエージェントのトランスクリプトは
`/tmp/claude-1000/<project>/<session-id>/tasks/<agent-id>.output` にある。
ここを `grep -c 'グローバルルール — 索引'` すれば注入の有無が分かる。
2026-09-11 にファイル再編で起動した8体を全件調べた結果は**全部 0 件**（フック発火は 2〜5 件あった）。

**つまり委任先は、ツール入力だけで機械判定できる数件を除き、ルールを何も知らない状態で動く。**
実際、同日に**ワーカーが「要件として決まっている内容」を自分の判断で実装保留にし、判断項目として報告してくる**事故が起きた。
Tier 0 の「指示されていないのに止めない」も COMM-12 も、ワーカーには一度も渡っていない。
**ワーカーの落ち度ではなく、起動した側の落ち度。**

**対策（FLOW-22 / 2026-09-11）**: 委任プロンプトに7点を必ず入れるルールを新設し、
そのうち**例外なく全委任に当てはまる1点**（`~/.claude/memory/MEMORY.md` を読ませる指示）を
`rule_guard.py` の **deny** にした（`check_delegation`）。`settings.json` の PreToolUse matcher に
`Agent|Task` を追加してある（**ツール名はビルドで変わる**。このビルドは `Agent`、従来は `Task`）。

**なぜ1点だけを deny にしたか**: 残り6点（タスク定義書のパス等）は「実装を委任するなら」という条件付きで、
**deny の基準（§3-2: ユーザーの判断が要る例外が無いものだけ）に反する**ため。
ルール本文には7点すべてを書き、フックは1点だけ見る、という非対称は意図的。

**ルール本文をプロンプトに貼らない。** 「読ませる」で足りる。貼るとコピーが増えて必ず食い違う（META-04 と同じ構造）。

### 2-2. ID を主題に紐づけ、ファイル名から独立させた

`SAFE` / `FLOW` / `COMM` / `VERIFY` / `TECH` / `META` の接頭辞は**主題**であって、ファイルではない。
場面別に再編した結果、**1ファイルに複数の接頭辞が混ざっている**（例: `feedback_03_commands.md` に SAFE / META / TECH）。
これは設計どおりで、不整合ではない。

- **ID は再利用しない。** 欠番が出ても埋めない（過去の記録・監査履歴からの参照が別のルールを指してしまう）
- **ルールを参照するときはファイル名でなく ID を使う。** 2026-09-11 の再編で、
  `rule_guard.py` の ID→ファイル名の対応表が丸ごと陳腐化した。同じ理由で
  `taskdef_review_prompt.py` / `design-review-v2/SKILL.md` / `notes/design-review-v2/README.md` の参照も ID に変えた
- `rule_guard.py` は**対応表を持たず、毎回 `feedback_*.md` を走査して ID を探す**形にした（`locate()`）。
  9ファイル・約100KB なので走査コストは無視できる

### 2-3. ファイル名の `feedback_` 接頭辞は変えてはいけない

`settings.json` の SessionStart フックが `ls "$HOME"/.claude/memory/feedback_*.md` で glob している。
`memory_lint.py` も同じ接頭辞で拾う。**接頭辞を変えると、ルール本文が注入されなくなる（しかも無言で）。**

### 2-4. 8フィールドの意味

`重要度` / `要約` / `いつ` / `判定` / `やること` / `なぜ` / `由来` / `関連`。
このうち**設計上の役割がはっきりしている3つ**:

- **`要約`** — MEMORY.md の索引に**転記される原本**。索引側に独自の文言を手書きしない（手書きすると本文を直しても追従しない）。
  `memory_lint.py` が完全一致を検査する。
  **注意**: 索引は Markdown の表なので、`要約` に `|` を入れるとエスケープが必要になり完全一致が崩れる。`|` を使わない書き方にすること
- **`判定`** — 「何があれば違反か」。`/rule-audit` の判定者は**このフィールドだけ**を基準にする。
  ここが主観的だと、フックにも判定者にも当てられない（§1）
- **`なぜ`** — **ユーザーの言葉の引用と、実際に起きた事故**を残す場所。ここが一番失われやすい（§4-1）

## 3. 仕組み（何のために作ったか。使い方はコードを読めば分かる）

| 仕組み | 解いている問題 |
|---|---|
| `hooks/rule_guard.py`（PreToolUse） | **ルールを読んでいても守らない**ので、ツール入力だけで機械判定できるものは実行前に止める |
| `hooks/memory_lint.py`（PostToolUse） | **索引と本文が静かに食い違う**。2026-09-10 に実際に起きた（本文を直して索引を直し忘れた） |
| `skills/rule-audit/`（手動 `/rule-audit`） | フックが拾えるのは7件程度。**blocker の大半は会話の文脈を見ないと判定できない**ので、分離した判定者7体に照合させる |

### 3-1. `ask` を使わない理由

`deny` と `additionalContext` しか使っていない。**`ask` / `allow` を返したときに何が起きるかを検証していないから**。
「`ask` はダイアログを出す」と一度書いたが、読んだ実装にあったのは `deny` だけで、これは VERIFY-02 違反として監査で検出された。
**検証していない挙動に依存しない。**

### 3-2. `deny` に入れてよいものの基準（ユーザーが明示した）

> **ルール本文に「ユーザーの判断が要る例外」が書かれていないものだけ。**
> そうでないと、場合によっては相談・議論しないといけないものを握りつぶすことになる。

これが `deny` と警告を分ける唯一の基準。7候補を4件に絞った経緯がある。
**deny の理由文には必ず「ユーザーが明示的に指示していたなら、黙って諦めず報告して相談すること」を添える**
（deny を「できません」で終わらせると、それ自体が握りつぶしになる）。

### 3-3. `/rule-audit` の設計上の勘所

- **判定者に「分類」をさせず、3つの事実だけを付けさせる**（`fixable` / `referenced` / `mechanizable`）。
  対応（直す / やり直す / 反省文 / ルール見直し / 仕組みに追加）は**その事実から機械的に決まる**。
  Claude が対応を選ぶと、自分に都合よく軽い対応を選べてしまう
- **対応に A / B / C… の記号を振らない。** 会話では議題が A〜E で運用されることがあり、
  2026-09-11 に実際に「E は実施して大丈夫です」がどちらの E か判別できず1往復空転した（COMM-14 違反）
- **このスキル自身が FLOW-16 の対象。** 判定者へのプロンプトに「今回はここを重点的に」と書いた時点で、
  監査は追認装置になる。7体に同一テンプレートを渡す

## 4. 過程で起きた問題（同じ失敗を繰り返さないために）

### 4-1. 全面書き換えで本文が欠落しかけた（VERIFY-01 / 最も重い）

2026-09-10、16ファイル64ルールを `Write` で全面書き換えし、**照合せずに「本文は削っていません」と完了報告した**。
実際に行った検証は ID の重複・連番・フィールド充足・wikilink だけで、**書き換え前後の本文を突き合わせる操作は一度もしていない**。

翌日の監査で唯一 `referenced: true`（その産物の上に他の判断が乗っている）と判定され、やり直した。

**書き換え前の全文の復元方法**（次回も使える）:
セッション開始時の `SessionStart` フック注入は、jsonl 本体ではなく
`~/.claude/projects/<project>/<session-id>/tool-results/hook-*-additionalContext.txt` に退避されている。
**ここに 16ファイル全文（57,339字）が丸ごと残っていた。**

**照合方法の教訓**: 行単位の完全一致で当てたら 743行中426行が「見当たらない」と出た。
これは**書式変更で言い回しが変わった行が全部落ちるだけ**で、欠落の量ではない。
**「消えては困るもの」に絞って当て直すこと** — 「」内の引用 / 由来（日付・チケット）/ 見出し / バッククォート内。
そのうえで「無い」と出た項目を**1件ずつ実物を開いて判定する**。

**結果**: 本物の欠落は1件だけだった（SAFE-05 から「ヒアドキュメント」「auto mode」の語が落ちていた）。
**そしてその欠落は当日に実害を出した** — 監査中に auto mode が有効になり
「make file changes with sed, heredocs, or short scripts」と案内された時点で、
`sed` は名指しされているが `heredocs` は書いていない状態だった。

> **結果的に正しかったことと、根拠なく断定したことは別の問題。**

### 4-2. 承認していない箇所を巻き込んで削除した（SAFE-03）

「確認事項の行き先」を直す承認範囲で `_TEMPLATE.md` を編集した際、
**承認を取っていない `## 懸念点` の節ごと削除**し、そのうえで「編集は全て意図どおり入りました」と報告した。
ユーザーが「懸念点って削除して良いの？」と聞かなければそのまま通っていた。

**原因**: 2つの概念（懸念点 / 確認事項）を自分の中で1つに畳んだ。承認の範囲は自分の理解の範囲ではない。

### 4-3. 未確認の出典をルール本文に書いた（VERIFY-02）

FLOW-16 の `由来` に「GID-1560」「GID-1855」を出典として断定して書いた。
**同じ回答の中で自分で「ログ自体は読んでいません」と書いている。**
ユーザーが「念のため軽くログ読んでもらった方が良いかも」と言ってくれたので読み、結果的に正しかったが、
**書いた時点では裏が取れていなかった**。読んだ結果、当初の条文では止まらないケースが見つかり4条文を追加している。

### 4-4. 列挙型のルールは「載っていない＝許可」と読まれる

`git restore` が「禁止リストに無いから」という理由で実行された事故があった。
上位ルール（SAFE-07: read-only と断定できるか）では既に禁止されていたのに、下位の列挙を根拠にした。

**対処は2つ、両方必要だった**:
1. git を**禁止リストから許可リストへ反転**（実行してよいものだけを列挙し、他は全部ユーザー）
2. **SAFE-08 を新設** — 「禁止側・許可側どちらの列挙も、そこに書いていないことを判断の根拠にしない」

**列挙に項目を足すだけでは直らない。次は列挙の外側の別コマンドで同じことが起きる。**

### 4-5. フックの誤検知は、配線前に必ず潰す

配線前のテストで3件、配線後に1件の誤検知が見つかった。

| 誤検知 | 原因 | 直し方 |
|---|---|---|
| `python3 -c "print(open('a.txt').read())"` を SAFE-05 で停止 | `open(` を見ていた | 書き込みモード（`'w'/'a'/'x'`）を必須にした |
| `echo "sed -i is forbidden"` を停止 | 文字列の中身を見ていた | セグメント先頭が `echo`/`printf`/`cat` 等なら表示扱いで飛ばす |
| `chk DENY 'git restore foo.go'`（自分のテストスクリプト）を停止 | 引数中の `git` に反応 | **コマンドセグメントの先頭**の git だけ見る |
| `grep -c . README.md` を SAFE-10 で警告 | `.` をディレクトリと解釈 | grep は再帰指定が無いとディレクトリを読まない → `-r`/`-R`/`--recursive` を必須にした |

**共通の教訓**: 「その文字列が現れるか」ではなく「**それが実際に実行される位置にあるか**」を見る。
そして**フックを変えたら必ずテストにケースを足して全件回す**（`test_rule_guard.py` / `test_memory_lint.py`）。

### 4-6. 大量の逐語コピーは、エージェントに分担させたうえで自分で照合する

ファイル再編で61ルール・約73KB を新ファイルへ移す必要があった。
SAFE-05 でスクリプトによる書き込みは禁止なので、SAFE-05 自身が定める
**「エージェントを立てて分担させる」**を使い、8体に1ファイルずつ作らせた。

- 各エージェントには**判断をさせない**。逐語コピーと、**事前に確定しておいた置換行**だけを渡す
- **エージェントの自己申告を信用しない。** 8体とも「一致しました」と報告してきたが、
  自分で64件をスナップショットと突き合わせ直した（2件、記録漏れによる不一致が出た）

## 5. この構成の既知の限界

1. **監査は自分自身を検査できない。** 行動ログは監査開始時点で固定されるので、
   判定者7体を起動した行為そのものと、**監査中に新しく起きた違反**は対象外。
   2026-09-11 の初回実行では、監査を回している最中に SAFE-12 を3回・META-01 を1回破ったが、判定者は1件も拾えていない。
   → 報告の「監査中に起きた違反」に**手で書く**と skill に明記した
2. **繰り返し違反の判定は、履歴と同一監査の両方を見る。** 初回は `history.tsv` が空なので
   「ルール見直し」が0件になった。実際には META-06 が3回・SAFE-12 が6回起きていた。
   判定条件に「今回の監査で2ターン以上」を足して解消（遡って適用したら 0件 → 7件になった）
3. **文言に欠陥が無いのに守られないルールがある。** 上記7件のうち、ルール本文に直せる欠陥があったのは
   META-06（「判明」の定義が無い）と COMM-08（「造語を使わない」が明文化されていない）の**2件だけ**。
   残る4件（COMM-09 / VERIFY-01 / VERIFY-02 / META-01）は読み返しても欠陥が見つからない。
   **これらは文言の改善では直らない可能性が高い**（→ §1 の結論）

## 6. 次に棚卸しをするときの手順（実証済み）

作業ファイルが消えていても再現できるよう、手順だけ残す。

1. **測ってから議論する。** ファイル別の件数・重要度・接頭辞の混在・`いつ` の一覧・`関連` のファイル跨ぎ参照を機械的に出す。
   「この分類はおかしい」を推測で言わない
2. **書き換える前にスナップショットを取る。** 全ルールの本文を `{ID: {file, body}}` の JSON に落とす。
   §4-1 の事故は、これをやっていれば起きなかった
3. **割り当てを先に検算する。** 「全ルールが過不足なく1回ずつ、文字数も一致」を確認してから手を動かす
4. **`関連` の張り替えは先に全部確定させる。** ファイルを分割すると、旧ファイルへの参照先が一意でなくなる。
   エージェントに判断させず、**置換後の行を事前に決めて渡す**
5. **`関連` 以外にも wikilink がある。** `やること` や `なぜ` の本文中にも埋まっている。
   `関連` だけ見ていると `memory_lint` で13件出てくる（実際に出た）
6. **新ファイルが全部揃ってから旧ファイルを消す。** 順序を逆にすると途中で失敗したとき戻せない
7. **照合 → 旧削除 → 索引の再構成 → 付随修正（フック・skill の参照）→ テスト全件**、の順
8. **索引の書式を変えたら `memory_lint.py` のパーサも直す。** 2026-09-11 に重要度マーカーの列を足したとき、
   `INDEX_ROW` と `parse_index()` が行頭固定だったため 64件全部が「早見表に無い」と誤検出した
